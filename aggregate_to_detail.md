# NIMBUS Order Distribution — SAP Aggregate Work Center ↔ NIMBUS Detail Machine — Design

Status: **DRAFT for review** · Date: 2026-09-17, revision 3 (gap review and UI review folded in the same day — §16.10) · Author: Trevor Holton with Claude
Related: `ROUTING_RUNTIME_DESIGN.md` (amended by this design — the machine → work center link now lives here; sub-order run time is resolved by its resolver, §5.8), `docs/SAP_INTEGRATION_ROADMAP.md` §2.2 (order key, ALPHA conversion), `docs/changeover_matrix.md` §6 (time segmentation — a different "split"), `docs/multi_change_spec_08.20.26.md` OD-A4/OD-A5/OD-A6 (`material_plants.default_machine`, work-center cardinality, `wc_group` rename), `docs/architecture/optimizer-dispatch.md` (per-machine optimizer), `.claude/skills/promote-azure/SKILL.md` (how the migration is applied).

## 1. Context

SAP plans many work centers **in aggregate**: one SAP work center stands for several physical machines, for data-maintenance, complexity, and duplicated-sub-machine reasons. SAP tolerates this by treating the aggregate as extra complexity in its own scheduling. NIMBUS cannot: its base model is the discrete machine — one order runs on one machine — so an aggregate SAP order aimed at a work center has no single place to land.

This design bridges the two levels in both directions:

- **SAP aggregate → NIMBUS detail (inbound):** an aggregate order is *distributed* into sub-orders, one per machine of the work center, by weights held as master data and adjustable per order afterwards.
- **NIMBUS detail → SAP aggregate (outbound):** the sub-orders roll back up into one aggregate order (earliest start, latest finish, summed quantity) that the future SAP connector can present.

Three things do not change: uploads that already carry NIMBUS machine names keep working verbatim; the optimizer keeps deciding *when* an order runs, never *where*; and every table is per plant and paged, per the scale roadmap in the root `CLAUDE.md`.

### 1.1 Terminology

| Term | Meaning |
|---|---|
| Work center | SAP work center code (`ARBPL`), per plant. Master row in `sap_workcenter`. |
| Aggregate order | An SAP planned order (PLAF) or production order (AFKO) addressed to a work center. |
| Distribution | Apportioning an aggregate order across the work center's machines by weights. |
| Sub-order | The ordinary `orders` row created for one machine's share, numbered `A-1000`, `B-1000`, … |
| Parent | The SAP order key the sub-orders came from (`orders.parent_production_order`). |
| Header | The `order_distribution` row holding the parent's SAP facts, review state, and its shares. |
| Share | One `order_distribution_share` row: machine, letter, weight, materialized child id. |
| Default basis | Which rule produced a header's default shares: material default machine, tooled single, or work-center weights (§5.2). |
| Anchor | The start time carried onto newly created sub-orders from the schedule they replace. |
| Bucket | The calendar hour / day / ISO week a sub-order's start falls in; max separation compares buckets. |
| Derived status | A header state computed at read time from current master data and children (`wc_changed`, `membership_changed`, `incomplete`, …), never stored (§5.7). |

### 1.2 Two things this is not

- **Not "Split-order allocation."** NIMBUS already has a per-plant policy (`plants.split_order_policy ∈ never|overlong_only|partial_allowed`, UI "Split-order allocation" / "Allocation policy", `frontend/locales/en.js:586-594`) that cuts *one* order into productive *segments* across working windows on *one* machine (`order_schedule_segments`, `docs/changeover_matrix.md` §6). Distribution is quantity across machines. The two compose: a sub-order may itself be segmented by that policy. The words "split" and "allocation" are therefore not used for anything in this design.
- **Not `machine.wc_group`.** "Workcenter Group" on the machine row (`schema.sql:521-524`) is a labor-planning grouping (`labor_plan.wc_group`), a pure rename from `pl_group` (OD-A6). The new column is labelled **SAP Work Center** to keep them apart.

### 1.3 Relationship to the routing design

`ROUTING_RUNTIME_DESIGN.md` (DRAFT, 2026-09-16) resolves an order's SAP operations through the machine → work center link. That link was going to be the existing `workcenter_mapping` table; this design moves it to a column on `machine` (§3.2) and retires the table (§3.5). The routing doc is amended accordingly (D1, D13, §4.3, §4.5, §4.6, §5, §6.2 step 4, §7.4, §8.1, §8.3, §9.2, §9.5). Sub-orders are ordinary orders to the resolver: once routing ships they get their run time from their own quantity; until then they carry a proportional share of the parent's run time as a placeholder. The exact order of operations is §5.8.

## 2. Decisions (planning Q&A, 2026-09-17, two rounds)

| I | Parent rerouted in SAP (round 2) | **Header authority.** When a later upload moves a distributed parent to another work center or to a plain machine, the header keeps its shares and children; it lists as `wc_changed` with the old and new codes; shares outside the new work center read as stale; the planner re-weights or resets. | J | Distribution tab layout (UI round) | **List + detail panel.** A paged list on the left, the selected SAP order's shares and actions in a panel on the right — the Orders + Inspector and Machines-tab shape. The list never jumps, bulk selection stays visible, and the editor scales to a large work center. Inline expansion under the row was rejected (§16.10). |
| K | Weight entry (UI round) | **Relative weights with a live preview.** The planner types weights; effective % and each machine's quantity update beside them from a server dry run (§5.5 step 8); no other row changes under the cursor. Per-row **Only this machine**, **Even**, and a **By quantity** toggle. Self-rebalancing percent inputs were rejected. |
| L | Where the review queue is visible (UI round) | **A count on the menu entry, in the Dashboard situation line and in the Ctrl+K needs list**, all fed by one `GET /distribution/{plant}/summary` (§7, §10.3). |
| M | Sub-order marker (UI round) | **A small `letter·count` tag** (`B·3`) on lettered sub-order bars and in the grid's order column, in the Gantt's existing `split-order-part` style; the bare 100 % child carries the keyline class only (§8). |

Derived rules, fixed by the above:

- Sub-orders are ordinary `orders` rows. `production_order = '<Letter>-<parent>'`. `orders.id = make_id(production_order, material_number)` is **unchanged** (`db.py:103-106`); the dash lives in `production_order`, so `id` stays an opaque 32-hex MD5 and nothing that parses ids is affected. No code ever parses the letter out of `production_order`; `parent_production_order` and `distribution_letter` are the only source.
- A single 100 % share yields `production_order = '<parent>'` with **no letter** — the same id as a plain order — and the header row persists so the order can be re-distributed later. That bare child still carries `parent_production_order`, so it is machine-locked like any sub-order.
- A header exists only for orders whose work center is in `distribute` mode. Single-mode work centers rewrite the machine and create no header.
- **Default-share precedence** (F, G, and the NULL-weight rule of §3.2): (1) material default machine set and a member → 100 % on it, `default_basis = 'material_default'`; (2) else the material is tooled and `distribute_tooled = false` → 100 % on the work center's `default_machine` if set and a member, else the alphabetically first member, `default_basis = 'tooled_single'`; (3) else work-center weights, `default_basis = 'workcenter_weights'`.
- Header states other than `reviewed` and `source` are **derived at read time**, never stored (§5.7); the one stored lifecycle mark is `share.purged_at` (§5.7).
- The Distribution tab is a third Scheduling Board sub-tab beside Gantt Timeline and Orders, laid out as a paged list with a detail panel (decision J).

## 3. Data model

Migration `migrations/2026-09-17-order-distribution.sql`, mirrored verbatim in `schema.sql`. Additive and idempotent, zero `UPDATE`s of business data. **It does not auto-apply:** the deploy guard blocks any file matching `\b(ALTER|DROP|DELETE|UPDATE|TRUNCATE|RENAME|GRANT|REVOKE)\b` (`.claude/skills/promote-azure/scripts/apply-migrations.ps1:67`) and every `ADD COLUMN` / `ADD CONSTRAINT` here is an `ALTER`. The skill's documented path for a verified-additive file is the reviewed `-AllowDestructive` apply (`SKILL.md:43`); the operator reads the file first. `scripts/schema_bootstrap_smoke.py` fingerprints the `orders` column shape from `schema.sql` against a migration replay (`_orders_columns`, `:280`), so both files must add identical columns.

Conventions used below:
- Audit columns (`created_at`, `updated_at`, `reviewed_at`, `purged_at`) are `TIMESTAMPTZ DEFAULT now()`, the newer convention. Copies of SAP dates (`basic_start_date`, `basic_finish_date`) stay naive `TIMESTAMP` because they mirror `orders.basic_*` (`schema.sql:41-42`), which are stored as plant-local wall clock.
- Every business column of `sap_workcenter` and the two new `machine` columns get `column_metadata` seed rows, so they are editable in the Admin Cockpit grid (the INNER JOIN in `master_data._column_meta`, `master_data.py:198-232`, is the switch). The brief requires that. Validation the grid cannot express lives in a `sap_workcenter` post-write check (§4.1) and in the Work Centers tab's own route (§7). The transactional tables (§3.4) get no seeds and are never grid-editable.
- Boot: one hook, `ensure_order_distribution_tables()`, creates `sap_workcenter`, then `order_distribution`, then `order_distribution_share` (FK order) with the same DDL, registered in the lifespan sequence after the `ensure_machine_*` hooks (`brain.py:262-291`); the new `machine`/`orders` columns follow the repo's no-hook convention for column additions (`master_data.py:2109-2111`). The hook duplicates the migration's DDL on purpose (that is how every existing hook works, `db.py:2825-2845`); keep the three copies identical (as of 2026-09-18, none of the three carries the table-level `default_machine` CHECK dropped that day).
- `Config.SCHEMA_VERSION` (`frontend/platform/foundation.mts:136-137`) is **not** bumped: the two new task fields are optional (`types.mts:151-157`), and a bump discards planners' cached unsaved edits (`persistence.mts:1061-1066, 1115-1120`).

### 3.1 `sap_workcenter` (per plant)

```sql
CREATE TABLE IF NOT EXISTS sap_workcenter (
    plant              TEXT NOT NULL,
    sap_workcenter     TEXT NOT NULL,
    description        TEXT,
    distribution_mode  TEXT NOT NULL DEFAULT 'single'
                       CHECK (distribution_mode IN ('single','distribute')),
    default_machine    TEXT,   -- soft ref machine(plant, machine); required in single mode, recommended in distribute mode (tooled fallback, §5.2)
    max_separation     TEXT NOT NULL DEFAULT 'none'
                       CHECK (max_separation IN ('none','hour','day','week')),
    review_required    BOOLEAN NOT NULL DEFAULT TRUE,   -- FALSE: default headers are created already reviewed
    distribute_tooled  BOOLEAN NOT NULL DEFAULT FALSE,  -- TRUE: tooled materials follow the weights (machines hold their own tool copies)
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (plant, sap_workcenter),
    CHECK (distribution_mode = 'distribute' OR default_machine IS NOT NULL)
);
INSERT INTO column_metadata (table_name, column_name, display_label, is_locked, column_order) VALUES
    ('sap_workcenter', 'plant',             'Plant',               TRUE,  1),
    ('sap_workcenter', 'sap_workcenter',    'SAP Work Center',     TRUE,  2),
    ('sap_workcenter', 'description',       'Description',         FALSE, 3),
    ('sap_workcenter', 'distribution_mode', 'Distribution Mode',   FALSE, 4),
    ('sap_workcenter', 'default_machine',   'Default Machine',     FALSE, 5),
    ('sap_workcenter', 'max_separation',    'Max Separation',      FALSE, 6),
    ('sap_workcenter', 'review_required',   'Review Required',     FALSE, 7),
    ('sap_workcenter', 'distribute_tooled', 'Distribute Tooled',   FALSE, 8)
ON CONFLICT (table_name, column_name) DO NOTHING;
```

**§3.1a Implementation reversal note (2026-09-18):** The table-level `CHECK (distribution_mode = 'distribute' OR default_machine IS NOT NULL)` shown in the DDL block above was dropped in migrations/2026-09-18-sap-workcenter-allow-unconfigured.sql, effective 2026-09-18. A work center may now be created with only plant/code/description from SAP ingest or the Manage Data grid, deferring configuration to later. The reason: three-field creation was impossible when `distribution_mode` defaults to `'single'` and the CHECK forbade `'single' + NULL`. The enforcement did not disappear — it moved to the `save_workcenter` route's Python validation (400 `single_mode_without_default`) and the Work Centers tab's frontend gate, plus a non-blocking warning on the generic grid path. Ingest treats the unconfigured state by leaving orders as plain orders with a `default_machine_invalid` warning.

- `single` = every order for this code lands on `default_machine` — required by the save route's validation even when only one machine is assigned, since the code and the machine name differ or the row would not be needed (the DB CHECK that used to enforce this was dropped 2026-09-18, see §3.1a). `distribute` = orders are distributed across members by weight.
- `max_separation` applies only in `distribute` mode; `none` disables the check. `week` means ISO week (Monday start), the same key labor planning uses (`labor_plan.period`, `schema.sql:660-666`); the per-user `firstDayOfWeek` preference (default Sunday, `frontend/shell/application-shell.mts:184`) is display-only and cannot define a scheduling constraint.
- `review_required = FALSE` creates default headers with `reviewed = TRUE`, `reviewed_by = 'policy'`, so a high-volume work center does not put every order into "needs review". Manual re-weights still record who and when.
- **Display labels.** The stored codes never appear in planner-facing UI. Locale keys render `distribution_mode` as "One machine" / "Distribute across machines", `max_separation` as "No limit" / "Same hour" / "Same day" / "Same week (Mon–Sun)", `review_required` as "Planners review each order's shares", `distribute_tooled` as "Distribute tooled materials too (each machine has its own tool)"; the all-NULL weight state reads "Even — no weights set". Buckets are shown the way labor planning labels weeks — "week of 09/14/26" (`labor-planning.mts:131-157` labels a week by its Monday as `MM/DD/YY`; no "Wk 38" form exists in the app) — and as "Sep 17" / "Sep 17 · 14:00" for day and hour. The cockpit grid keeps the raw codes.
- **Write-path rules (not expressible as CHECK), enforced by the Work Centers route (400) and reported as warnings by the `sap_workcenter` post-write check when the generic grid is used (§4.1):** a machine named exactly like a work-center code must be explicitly linked to it (`machine.sap_workcenter` = the code), which makes a **1:1 work center** — `wc_code_shadowed_by_machine` fires only when that machine is unlinked or linked to another code; an aggregate may not be named after one of its own machines, i.e. a linked same-named machine alongside a second member or in distribute mode (`wc_code_is_member_of_aggregate`, 400 on the route, warning on the grid), since its orders would land on that machine and never distribute; `default_machine`, when set, must be a member of this work center (`default_machine_not_member`); single mode without a default machine (`single_mode_without_default`; implied, hence not raised, for a 1:1 work center; the DB CHECK used to refuse it — dropped 2026-09-18, see §3.1a); distribute mode with fewer than two members (`distribute_mode_thin`, warning only).

### 3.2 `machine` additions

```sql
ALTER TABLE machine ADD COLUMN IF NOT EXISTS sap_workcenter      TEXT;
ALTER TABLE machine ADD COLUMN IF NOT EXISTS distribution_weight NUMERIC
    CHECK (distribution_weight IS NULL OR distribution_weight >= 0);
DO $$ BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'fk_machine_sap_workcenter') THEN
        ALTER TABLE machine ADD CONSTRAINT fk_machine_sap_workcenter
            FOREIGN KEY (plant, sap_workcenter) REFERENCES sap_workcenter (plant, sap_workcenter)
            ON UPDATE CASCADE ON DELETE RESTRICT;
    END IF;
END $$;
CREATE INDEX IF NOT EXISTS idx_machine_sap_workcenter ON machine(plant, sap_workcenter);
INSERT INTO column_metadata (table_name, column_name, display_label, is_locked, column_order) VALUES
    ('machine', 'sap_workcenter',      'SAP Work Center',     FALSE, 10),
    ('machine', 'distribution_weight', 'Distribution Weight', FALSE, 11)
ON CONFLICT (table_name, column_name) DO NOTHING;
```

- One work center per machine is enforced by the column itself (OD-A5's `(plant, machine)` cardinality, now structural).
- **Weight semantics.** Weights are relative, not percentages. If **every** member's weight is NULL, the distribution is even. If **any** member has a weight, NULL members get **0** (their letter is reserved, no child is created). Rationale: "set the percentages you care about" is how planners think; the alternative (NULL = 1 next to 60/40) would silently create sliver sub-orders. The Work Centers tab shows the live percentage with "(not set → 0 %)".
- **No machine speed exists in NIMBUS.** The `machine` table has no rate, efficiency or UPH column (`schema.sql:294-303, 328, 521, 536-540, 1179-1180`); duration is a property of the order, and the routing design gives every machine of one work center the same standard value (its D1). "Even" therefore means even by quantity *and* by time. The requester confirmed on 2026-09-17 that member speeds can in fact differ and that a separate per-machine factor is intended future work; equal speeds are the working assumption for now. A `machine.rate_factor` would be a new concept for both designs — deferred (§13.16).
- The FK is deliberately hard, unlike the repo's soft-reference habit for plant-scoped tables: distribution keys off the code, the cockpit cell is free text, and a typo should be a readable 400 (`bulk_apply`'s `ForeignKeyViolation` catch, `master_data.py:829-831`) rather than an order that never distributes. `ON DELETE RESTRICT` refuses deleting a work center with members; the cascade preview (§3.6) reports members and headers.
- `column_order` 10/11: the seeded `machine` columns occupy 1–9 (`schema.sql:523, 543-547, 634-636`); wizard-added columns take `MAX + 1` (`master_data.py:1053-1061`), and ties only affect display order (`:217`).
- The generated `machine_key` stays out of `column_metadata` as before.

### 3.3 `orders` additions

Exactly two columns, NULL for plain orders. **No stored share**: it would drift the moment SAP changes the parent quantity; the client derives share % from sibling quantities and "machine locked" from `PARENT_ORDER != null`.

```sql
ALTER TABLE orders ADD COLUMN IF NOT EXISTS parent_production_order TEXT;
ALTER TABLE orders ADD COLUMN IF NOT EXISTS distribution_letter     TEXT;
CREATE INDEX IF NOT EXISTS idx_orders_parent
    ON orders(plant, parent_production_order, material_number)
    WHERE parent_production_order IS NOT NULL;
```

Wire: `PARENT_ORDER`, `DISTRIBUTION_LETTER` join the TaskDTO (`backend/scheduling/models.py` `TaskDTO`, `db._ORDERS_SELECT` `db.py:492-534`, `get_tasks` dict `backend/scheduling/routes.py:185-224`; alignment pinned by `tests/test_task_response_models.py`), `NimbusTask` (`frontend/platform/types.mts`), and `ORDER_FIELD_CATALOG` (hidden by default). They are **not planner-writable**: excluded from `Persistence._taskEditSnapshot` and `TaskDateUpdate`. Names deliberately avoid `date` (`Persistence._prepTask` coerces by name).

Run-time provenance rides on the routing design's `orders.run_time_source` (`ROUTING_RUNTIME_DESIGN.md` §4.5), which gains the value **`'distributed'`** = "proportional share of the parent's uploaded run time written by distribution; treated like `legacy` by the resolver" (§5.8). No further `orders` column.

### 3.4 `order_distribution` (header) and `order_distribution_share`

Transactional. **Not** in `ALLOWED_TABLES` (visible in the Table Browser, which is catalog-driven; never grid-editable). Written solely by `backend/distribution/`.

```sql
CREATE TABLE IF NOT EXISTS order_distribution (
    plant              TEXT NOT NULL,
    production_order   TEXT NOT NULL,    -- SAP parent key as uploaded (planned or production order)
    material_number    TEXT NOT NULL,
    sap_workcenter     TEXT NOT NULL,    -- current work center as last uploaded; the previous one lives in sap_facts.previous_workcenter after a reroute
    order_quantity     NUMERIC,          -- parent facts as last ingested
    run_time           NUMERIC,          -- parent hours as uploaded; informational once routing resolves children (§5.8)
    basic_start_date   TIMESTAMP,
    basic_finish_date  TIMESTAMP,
    firming_indicator  TEXT,
    sap_facts          JSONB,            -- remaining copied SAP columns (description, color, form size, categories, BOM keys, planned-order quantities, no_of_fte…) plus previous_workcenter, runtime_defaulted
    source             TEXT NOT NULL DEFAULT 'default' CHECK (source IN ('default','manual')),
    default_basis      TEXT NOT NULL DEFAULT 'workcenter_weights'
                       CHECK (default_basis IN ('material_default','tooled_single','workcenter_weights')),
    reviewed           BOOLEAN NOT NULL DEFAULT FALSE,
    reviewed_by        TEXT,
    reviewed_at        TIMESTAMPTZ,
    reviewed_quantity  NUMERIC,          -- parent qty at approval → "qty changed since review"
    updated_by         TEXT,
    last_batch_id      UUID,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (plant, production_order, material_number),
    FOREIGN KEY (plant, sap_workcenter)
        REFERENCES sap_workcenter (plant, sap_workcenter) ON UPDATE CASCADE ON DELETE RESTRICT
);
CREATE INDEX IF NOT EXISTS idx_order_distribution_wc
    ON order_distribution(plant, sap_workcenter, reviewed);

CREATE TABLE IF NOT EXISTS order_distribution_share (
    plant            TEXT NOT NULL,
    production_order TEXT NOT NULL,
    material_number  TEXT NOT NULL,
    machine          TEXT NOT NULL,
    letter           TEXT NOT NULL,
    weight           NUMERIC NOT NULL DEFAULT 0 CHECK (weight >= 0),
    child_id         TEXT,                             -- orders.id currently materialized; NULL when weight = 0 or purged; soft ref
    purged_at        TIMESTAMPTZ,                      -- set by purge; a fresh upload of the parent clears it (§5.7) (amended 2026-10-01: Reset and reapply-defaults also revive — §5.7)
    PRIMARY KEY (plant, production_order, material_number, machine),
    UNIQUE (plant, production_order, material_number, letter),
    FOREIGN KEY (plant, production_order, material_number)
        REFERENCES order_distribution (plant, production_order, material_number) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_ods_machine ON order_distribution_share(plant, machine);
```

- A child table rather than a JSONB array: row-level letter uniqueness and weight CHECKs, machine-filtered header listing through a btree, Table Browser readability, and `child_id` makes deletion and reconciliation id-based. Header + shares are replaced wholesale under a header lock inside one transaction — the re-weight transaction (§5.5) or the ingest post-hook transaction (§5.4).
- The header's `xmin` is its optimistic-concurrency token (`base_version` on the wire, 409 `stale` on mismatch), mirroring the setup domain's 409-for-stale behaviour. The ingest post-hook also compares it against the value it read during planning (§5.4).
- The header → `sap_workcenter` FK keeps `order_distribution.sap_workcenter` in step with a renamed code (the `machine` FK already cascades renames); `RESTRICT` means a work center with open headers cannot be deleted — the cascade preview says so (§3.6).
- **There is no stored `stale` flag.** Whether a share's machine still belongs to the header's work center, whether a member lacks a share, whether a child is missing — all of that is derived when the header is read (§5.7). Stored flags maintained by after-commit hooks would drift (the existing `machine` post-write hook runs after `bulk_apply` has committed, best-effort, non-fatal, `backend/master_data/routes.py:339-354`). The one stored lifecycle mark is `purged_at`, because "this child was purged" cannot be derived from anything else.
- `child_id` and `default_machine` stay soft references (the only hard FK into `orders` in the repo is segments); integrity is owned by `backend/distribution/`.

#### 4.3a — Implementation reversal note (2026-09-18)

Two design decisions were reversed during implementation of the Work Centers tab, recorded here so the original prose remains legible:

1. **Creation removed.** The design mandated a **"New work center"** action for admins. This was reversed: work centers are authoritative SAP source data, and a planner-invented code would never match an incoming order. Creation now lives exclusively with the SAP sync ingest path (`backend/integration/sap_sync.py`, via `md.bulk_apply`) and the Manage Plant Data grid (the generic Admin › Manage Data Tables UI). The tab became edit-only.

2. **Autosave adopted over staged Save.** The design stated edits "are staged behind an explicit **Save** with the `.md-dirty-badge` 'n unsaved' counter … **not** the Machines pane's autosave, because policy and weights are one validated transaction." This was reversed: **atomicity is a property of the PUT's single transaction, not of the UI's batching.** Autosave changes the *granularity* of writes (per-field vs. per-dialog), not their atomicity — each autosave still sends one whole create-or-replace payload (policy fields plus the full member weight map) through the same single-transaction route (`PUT /distribution/{plant}/workcenters/{wc}`), so "policy and weights are one validated transaction" remains true per write. The client-side pre-flight gate (`WorkCenters._wcBlockReason`) blocks all invalid payloads before the PUT fires, making autosave safe against the route's hard 400s.

The zero-member dead end (unsaveable by construction, not a bug) was accepted as designed.

## 5. Ingest and materialization

Lives in **`backend/distribution/service.py`** (pure functions over plain rows, unit-testable without a DB) and **`backend/distribution/data.py`** (DB wrapper). `db.py` never imports `backend.*` (every router imports `db`; a reverse import would be a cycle), so callers pass two callables into `db.upsert_orders` — a new optional pair of parameters — from `db.ingest_orders_from_excel` at its `upsert_orders` call (`db.py:2666-2673`) and from `sap_sync.sync_object` (`backend/integration/sap_sync.py:698`, after `map_records` at `:674`).

**Transaction structure — designed around what `upsert_orders` actually does.** The upsert has no connection open at the id/dedup loop (`db.py:2290-2318`); it opens one at `:2329` and **commits every 500-row chunk** (`:2321-2324, :2342`) and again after each backfill, precisely so a large upload never holds a table lock. Distribution therefore runs in two steps, neither of which holds a lock across the upload:

- **`plan(rows, batch_id) → (rows_out, plan, warnings)`** — called before the id/dedup loop. **Read-only**, on its own short pooled connection: headers and shares (with header `xmin`), work-center policy and members, `material_plants` attributes (`default_machine`, `prt_01`, `prt_02`, `min_lot_size`, `incremental_lot_size`). It returns the rows to upsert (children instead of distributed parents, rewritten machines for single-mode codes) and a **plan**: per parent, the header snapshot (`xmin` or none), the intended shares, the intended child ids, the previous child ids, and the anchor source.
- **`apply(plan, batch_id)`** — called after the last chunk and the backfills have committed (`:2381`), before the `upload_audit` insert (`:2427`) so its counters land in `warnings`. **One transaction of its own** (§5.4). Idempotent: running it twice with the same plan changes nothing the second time.

The children upsert itself goes through the normal chunks and `_UPSERT_SQL` unchanged. The **crash window** is honest and small: if the process dies after some children chunks committed but before `apply` ran, the new children exist (the normal upsert now writes `parent_production_order` and `distribution_letter`, 2026-10-05), the header is missing or outdated, and superseded children are not yet deleted. **Correction (2026-10-05):** `POST /distribution/{plant}/resolve` with `scope: 'repair'` (§5.6) recovers only parents whose header *exists* (`incomplete` status); it walks existing headers and does **not** sweep sub-orders whose parent has no header at all (a crash before the header was ever created, or a purged header). Those orphans are recovered by re-uploading the parent (a fresh upload plans and creates the header; the stable child ids overwrite the orphans), which is the recovery path the upsert already documents (`:2323-2324`). A header-less orphan sweep was deliberately not built: deleting header-less children would silently delete real production orders left behind by a master-data cascade.

### 5.1 Resolve and classify (inside `plan`)
1. **One row per (production_order, material_number).** A second row for the same parent with the *same* machine/work-center value is a duplicate and is dropped (`duplicate_parent_rows`) — otherwise the batch-local dedup (`db.py:2290-2309`) would `_1`-suffix a second set of children that nothing ever deletes. A second row with a *different* value is an error: the whole parent is skipped and listed under `conflicting_parent_rows` in the upload summary. The order extract is order-level today (21 recognised headers, no operation column, `db.py:2642-2664`) and stays so — confirmed 2026-09-17. The work-center code arrives in the same `MACHINE|PRODUCTION_LINE` column as machine names do today — also confirmed.
2. Resolve the plant: the row's `PLANT|WERKS` → else the `MACHINE` value's unique plant across `machine` → else across `sap_workcenter` → else leave the row untouched and warn `ambiguous_workcenter_plant` (today plant is derived post-upsert, `db.py:2348-2362`; distribution needs it earlier).
3. Classify X = the `MACHINE|PRODUCTION_LINE` value:
   - `machine(plant, X)` exists → **plain order, today's path**. Machine name wins.
   - else `sap_workcenter(plant, X)` exists → mode `single`: rewrite `machine := default_machine`, no header — unless the default machine is missing, deleted, or no longer a member, in which case the row stays plain with `machine = X` and warns `default_machine_invalid`; mode `distribute`: **zero members** → the row stays plain with `machine = X`, warns `workcenter_without_members`, and appears on `unresolved` (§7) — a header with no shares would make the order vanish from the schedule; otherwise §5.2.
   - else plain with today's unknown-line warning — **computed from the emitted rows, not the raw column** (fix `lines` at `db.py:2679-2680`; otherwise every resolved code trips "Unknown production line" in `backend/integration/routes.py:81-89`).
4. **Existing header whose parent now resolves elsewhere** (decision I): a distributed parent's row now carries a different work center, a single-mode code, or a real machine name. The header keeps authority: children are materialised from its existing shares as before; `sap_workcenter` is refreshed to the new code when it is a work center, and the previous code is written to `sap_facts.previous_workcenter` (a plain machine name or single-mode code is recorded there too, with the header's work center left as it was). The header lists as `wc_changed` (§5.7). Nothing moves on upload.

Machine-first precedence is the only order that survives the SAP path: there `machine` is mapped from `ARBPL` (once the §3.6 seeds exist), and a 1:1 work center's code *is* the machine name. Consequence: a 1:1 work center needs its same-named machine linked to it explicitly (`machine.sap_workcenter` = own code; routing resolves operations through that link too), while a placeholder machine named after an *aggregate* work center must be renamed or deleted (§3.1 rules). `resolve` scope `wc_codes` skips orders already sitting on a real machine, so 1:1 orders are never candidates.

### 5.2 Header (planned in `plan`, written in `apply`)
- **New:** one share per current member of the work center, ordered by machine name, letters `A, B, …, Z, AA, AB, …`, `source = 'default'`, `reviewed = NOT review_required` (`reviewed_by = 'policy'` when pre-reviewed). Weights follow the **default-share precedence** of §2: (1) `material_plants.default_machine` set and a member → that machine 100 %, every other member 0, `default_basis = 'material_default'`; (2) else the material is tooled (`prt_01` or `prt_02` is a non-placeholder value — the alert core's `TOOL_PLACEHOLDERS` = `'', '-', '0', 'N/A', 'NONE', 'NULL'`, `frontend/nimbus-compute-core.js:391`; the same list is mirrored in `service.py` and pinned by a parity test) and `distribute_tooled = FALSE` → 100 % on the work center's `default_machine` if it is a member, else the first member, `default_basis = 'tooled_single'`; (3) else the members' `distribution_weight`s (§3.2 NULL rule), `default_basis = 'workcenter_weights'`. If a plain row `make_id(parent, material)` already exists (the order arrived before the work center was configured, or via §5.6), capture its **anchor** (`COALESCE(first segment start, scheduled_start)`), `notes`, and `planning_status/planning_reason` for §5.4.
- **Existing:** refresh the SAP facts only (`order_quantity`, `run_time`, dates, `firming_indicator`, `sap_facts`, `last_batch_id`; `sap_workcenter` per §5.1 step 4). Shares, `reviewed`, `default_basis` are untouched; the list shows "quantity changed since review" when `order_quantity ≠ reviewed_quantity`. A share with `purged_at` set is revived (cleared) by this refresh because the parent is evidently still in SAP (§5.7).

### 5.3 Materialize (rows emitted by `plan`)
For every share with `weight > 0` and `purged_at IS NULL` build one child row:
- `production_order = f"{letter}-{_str_id(parent)}"`, or the bare parent when exactly one share is positive (`_str_id` first: `'A-1000.0'` would not be stripped, `db.py:98`).
- `machine = share.machine`, explicit `plant`, `parent_production_order`, `distribution_letter` (NULL for the bare case).
- **Quantity apportionment (proportional; fractional shares round up).** **Amended 2026-09-25 (owner): no lot-size rounding for now.** Each sub-order gets its proportional share of the parent quantity, and a share that comes out fractional always rounds **up** to a whole piece. For example, 1,031 split evenly becomes 516 + 516 = 1,032, and 1,030 split evenly becomes 515 + 515 whatever the lot size. `material_plants.incremental_lot_size` is not applied yet. A fractional SAP parent quantity (SAP `QUAN 13,3`) isn't covered by this rule yet. The round-up rule applies to quantity only: run time, labor hours and machine hours keep their exact-sum split. The difference from the SAP parent quantity must be visible to the planner. The current code still rounds to the lot size and rounds some fractional shares down; this is tracked as H6 in `Code_Review_09_25.md`. Children whose quantity is below `material_plants.min_lot_size` (> 0) are still created; the read path marks them `below_min_lot` for the pane.
- **Run time.** `orders.run_time` is **hours** (`_EFF_END_SQL` multiplies by `INTERVAL '1 hour'`, `db.py:192-197`; the mismatch check compares `ROUND(run_time*60)` with segment minutes, `:227-232`). Apportion in integral **minutes** — `ROUND(parent_run_time × 60)` by the *post-rounding* quantity ratio, Hamilton again — and store **`minutes / 60`** hours, so `ROUND(child.run_time × 60)` equals the apportioned minutes and the children's minutes sum to the parent's. NULL parent run time → NULL children. This value is the **placeholder**; §5.8 says when the routing resolver replaces it.
- `ADDITIVE_COLS = (order_quantity, run_time, labor_hours, machine_hours)`. **Everything else is copied**, including the planned-order facts `planned_order_initial_quantity` and `reduced_quantity` (the original planned quantity and the part already converted to production orders — confirmed 2026-09-17; facts about the parent, not shares), dates (they are the due-date baseline: `ORIGINAL_END_DATE` is an alias of `basic_finish_date`, `db.py:504-505`; NIMBUS never rescales them — whether SAP planned the parent as parallel work depends on whether operation splitting was invoked for that order, so when it was not, SAP's finish is later than parallel sub-orders need, which is harmless: the SAP date is a ceiling, not a target), `firming_indicator`, `material_description`, `color`, `form_size`, `order_category`, `order_type`, BOM keys, `no_of_fte` (crew per machine-run — confirmed 2026-09-17). Confirmed or delivered quantity does not reach NIMBUS: NIMBUS plans the full order quantity (confirmed 2026-09-17). `prt_01/prt_02/production_version` are not uploaded columns — `_stamp_order_attributes` stamps them per `(plant, material_number)` after the upsert, for children like any order.
- Child existence is driven by shares only, never by rounding: a parent quantity smaller than the number of positive shares yields 0-quantity children, allowed and counted as `zero_quantity_children`. A SAP quantity cut can therefore never delete a scheduled child.
- Emit the children **instead of** the parent row. If the parent row's `RUN_TIME` was absent or unparseable, the upload silently used 1.0 h (`db.py:2568-2571`); the transform records `sap_facts.runtime_defaulted = true` and counts `parent_runtime_defaulted` in the warnings entry, because a defaulted hour divided four ways is a fifteen-minute sub-order nobody asked for.

The children then go through `_UPSERT_SQL` (`db.py:2001-2074`) unchanged: existing children keep `scheduled_start/end`, `notes`, `planning_status/reason`; SAP-owned columns are overwritten; a run-time change under a scheduled child sets `runtime_schedule_mismatch` (`db.py:2041-2046`) exactly as for any order; the plant/`machine_key` backfills need no change.

### 5.4 `apply` — the post-hook transaction
Runs after the backfills, in one transaction:
1. **Setup observation seam.** Call `setup_data.capture_setup_states_before_schedule_mutation(...)` for the affected plants before any child is deleted — the same seam `/upload`, `/purge` and the SAP sync already use before destroying a prior schedule (`backend/integration/CLAUDE.md:24`, `sap_sync.py:694-697`, signature `backend/setup/data.py:501-502`).
2. **Lock** every affected header in one statement — `SELECT … FROM order_distribution WHERE (plant, production_order, material_number) IN (…) ORDER BY 1,2,3 FOR UPDATE` — key-ordered so a concurrent re-weight (§5.5), which locks in the same order, cannot deadlock it. New headers are inserted here.
3. **Re-check.** For each planned parent compare the locked header's `xmin` with the snapshot taken in `plan`. Equal → proceed. Different (a planner re-weighted between `plan` and `apply`) → re-plan that parent from the header's *current* shares and facts and correct the already-upserted children with guarded updates (`UPDATE … WHERE order_quantity IS DISTINCT FROM %s OR run_time IS DISTINCT FROM %s …`); children the current shares do not want are treated as superseded below. The planner's re-weight wins; the upload only refreshes facts.
4. **Write** header facts and shares (wholesale replace under the lock; letters and weights of untouched shares preserved).
5. **Carry** onto newly inserted children: `scheduled_start = anchor`, `scheduled_end = anchor + child run_time` (satisfies `chk_orders_sched_range`, `schema.sql:94-97`); `notes` copied; `needs_planning` inherited with its reason and null dates (the CHECK at `schema.sql:1334-1348` requires that; `planning_reason.code` is free text under it — no schema change for `distribution_separation`). Segments are not carried — they belonged to one machine and one run time. Notes are per child from then on; the header has no notes.
6. **Delete** `orders` rows whose id is in the previous child set (`share.child_id`, plus the plain id on a 1→N transition) and not in the new set. `order_schedule_segments` cascades. Set `setup_occurrence_override.status = 'replaced'` where a predecessor or successor id was deleted (`schema.sql:1256-1257` already permits the value).
7. Update `share.child_id`; append one `upload_audit.warnings` entry `{level: 'info' | 'warn', msg: '<n> aggregate orders distributed into <m> sub-orders (<k> deleted, <p> parents ambiguous)…', category: 'distribution', parents_distributed, children_upserted, children_deleted, headers_created, headers_refreshed, replanned_after_reweight, single_rewrites, duplicates_dropped, conflicting_parent_rows: […], zero_quantity_children, parent_runtime_defaulted, ambiguous_plant: […], workcenter_without_members: […], default_machine_invalid: […]}`. `level` and `msg` are required: the cockpit's warning list renders only those two fields (`frontend/admin-ops/admin-ui.mts:1064-1081`) and counts every entry as a warning (`:2467-2481`); `level` is `warn` whenever any list is non-empty, else `info`. This mirrors the `missing_master_data` entry (`db.py:2392-2402`). The Excel result page (`frontend/admin-ops/admin-ui.mts`, §6 "Upload pages") reads this entry from the upload response and, when `headers_created + headers_refreshed > 0`, renders **Review {{k}} distributions** as the deep link `#gantt/distribution?batch=<batch_id>` (§6).

On the SAP path `sync_object`'s result carries no `warnings` key (`sap_sync.py:644-653`); the entry lands in `upload_audit` under `filename = 'sap:sap'` (`db.py:2264-2265`) and the SAP Interface page reads it from there (§6 "Upload pages").

### 5.5 Re-weight (planner, `POST /distribution/{plant}/{order}/{material}/shares`)
1. Validate: Σ weights > 0; every machine is an existing share (or `allow_stale: true` for a derived-stale one); no positive weight on a share with `purged_at` set (400 `share_purged` — re-weight itself never revives it) (amended 2026-10-01: Reset and reapply-defaults also revive — §5.7); header `base_version` matches (else 409 `stale`).
2. Setup observation seam (as §5.4 step 1), then lock the header and its children `FOR UPDATE` (header lock in the same key order as §5.4); recompute §5.3 from the stored header facts; run the §5.8 resolution for the resulting children.
3. Kept children are updated only when a value differs (`UPDATE … WHERE order_quantity IS DISTINCT FROM %s OR run_time IS DISTINCT FROM %s …`) so untouched children keep their `xmin` and no planner's unsaved edit is discarded. A changed scheduled child gets `runtime_schedule_mismatch = TRUE`, same semantics as ingest.
4. New children: anchor = the earliest existing child's effective start, else `basic_start_date`.
5. Removed children: if any has `scheduled_start` or segments, respond **409 `children_scheduled`** listing them unless the body carries `confirm_remove_scheduled: true`; then delete as in §5.4 step 6.
6. **N→1 collapse:** if the surviving 100 % machine already has a child, copy its `scheduled_*`, `notes`, `planning_*` and its `order_schedule_segments` rows onto the new plain id before deleting the lettered children; otherwise use the anchor. All share rows keep their letters and weights so a later re-distribution restores them.
7. `source = 'manual'`, `updated_by`, `reviewed`/`reviewed_quantity` per the body; `admin_audit` row. Response carries the full child DTOs, removed ids, the **previous shares** (for the pane's one-level undo, §6) and the new `base_version`, so the pane can patch the Store without a plant reload.
8. **Dry run (decision K).** `dry_run: true` runs steps 1–3 and the §5.8 resolution against the stored header facts **without writing** — no lock held past the read, no `admin_audit`, no resolver persistence — and returns `{plan: [{machine, letter, weight, effective_pct, qty_before, qty_after, hours_before, hours_after, outcome: 'unchanged' | 'resized' | 'new' | 'removed', scheduled, frozen, below_min_lot}], removed_scheduled, base_version}`. It is the same code path as the real call, so the preview cannot disagree with the write (§12 pins that parity). The pane calls it, debounced, as the planner types (§6). `reset` accepts `dry_run` the same way, so "Reset to work-center defaults" previews too.

The pane refuses Save while any child id is in `Persistence._dirtyIds`. NIMBUS-firmed children (`Store.firmedIds`) keep `runtime_schedule_mismatch` until unfirmed because `reconcileRuntimeSchedules` skips firmed tasks (`frontend/scheduling/persistence.mts:799`) — the pane says so. A re-weight is not on the board's `UndoStack` (it covers drag, unschedule, optimize and auto-fix only, `frontend/platform/store.mts:881-908`); the pane's own "Undo last change" is the way back.

### 5.6 Resolve (`POST /distribution/{plant}/resolve`)
- scope `wc_codes` (default): plain orders in the plant whose `machine` equals a work-center code → §5.1–5.4 (single → guarded `UPDATE … WHERE machine IS DISTINCT FROM`). This is the backfill after master data is created.
- scope `machines` (opt-in, `workcenter` required, `dry_run` supported): plain orders already sitting on that work center's members get a header with 100 % on their current machine (`source = 'manual'`, `reviewed = false`), schedule preserved. Re-distributing is then a planner act — this is how a single-mode work center becomes distributed without touching schedules.
- scope `repair`: for headers whose children set does not match their positive, unpurged shares (`incomplete`), re-run §5.4 from the current shares and facts. This is the recovery for the crash window described in §5 **only when the header already exists**, and for any inconsistency the derived status surfaces; it does not recover sub-orders whose parent has no header (re-upload the parent). Never recreates a purged share's child.

### 5.7 Derived statuses, purge, membership, identity
- **Derived statuses** (computed by `GET /distribution/{plant}` and the detail route from current master data and children; never stored): `needs_review` (`reviewed = false`); `qty_changed` (`order_quantity ≠ reviewed_quantity`, reviewed headers only); `incomplete` (a positive, unpurged share has no living child, or a child exists that no share points at); `mode_mismatch` (work center now `single`); `wc_changed` (`sap_facts.previous_workcenter` set and not yet acknowledged — acknowledging is a re-weight, reset or approve); `membership_changed` (a positive share's machine no longer has `machine.sap_workcenter = header.sap_workcenter` — *derived-stale* — or a member of the work center has no share); `below_min_lot`; `zero_quantity_children`; `purged` (any share with `purged_at`); `runtime_mismatch` (any child with `runtime_schedule_mismatch`). Separation status is computed client-side (§6). A share is **stale** when its machine is not a current member or no longer exists; re-weight refuses `weight > 0` on it without `allow_stale`.
- **Purge.** `purge_orders_by_date` (`db.py:1511-1545`) deletes by effective end date with an optional machine filter, so siblings routinely straddle its boundary and partial child sets are normal. In the same transaction: set `purged_at = now()` and `child_id = NULL` on the shares whose child was deleted; delete headers whose every share is purged or zero-weight. A purged share's child is **never** recreated by re-weight, reset, `reapply-defaults` or `resolve`; only an upload that still carries the parent clears `purged_at` (§5.2) and re-materialises it. Re-upload never deletes (unchanged), so a parent that disappears from SAP lingers until purge, like every order. **Amended 2026-10-01 (owner):** the claim that only an upload revives a purged share is superseded. After purge removes a finished sub-order, any of an upload of the parent, an explicit **Reset**, or the admin **reapply-defaults** sweep recreates it at its normal share and clears `purged_at`; **Repair and re-weight still never do.** Example: order 1000 split A-1000 = 500 / B-1000 = 500; A-1000 finishes and is purged; Reset → A-1000 = 500 and B-1000 = 500 again.
- **Membership.** A machine leaving a work center changes nothing in the tables; its shares read as stale and its headers as `membership_changed`. Children are never auto-deleted. A machine joining gets the lowest unused letter in an existing header the first time a planner gives it weight; new headers are alphabetical. Letters are therefore stable per parent, and stable across parents as long as membership does not change. Machine renames and deletions leave `share.machine` and `orders.machine` as soft references, exactly as for every order today; the derived status shows them.
- **Identity.** `make_id` is plant-blind (`tests/test_make_id.py:26-41`); children inherit that; the header PK includes plant. No new hazard, documented.

### 5.8 Run-time resolution order for sub-orders
The routing design computes `run_time` from machine-role standard values ÷ base quantity × order quantity (`ROUTING_RUNTIME_DESIGN.md` §6.4), stores provenance in `run_time_source ∈ routing|manual|legacy` (§4.5), leaves an unresolvable order's existing `run_time` untouched (§6.5, its D5), runs at ingest "immediately after stamping" (§5) and re-runs on quantity, machine or production-version changes and on master-table changes (D6). Every machine of one work center shares one standard value (D1), so all siblings resolve through the same operation. Sub-orders fit this without special cases:

1. **Ingest.** `plan` writes the proportional placeholder (§5.3) with `run_time_source = 'distributed'` (new value; the routing CHECK and its §6.5 are amended). The children are upserted, stamped, and then the resolver runs over the batch like any order: where it resolves, `run_time` is replaced with the child's own quantity × rate and `source = 'routing'`; where it cannot (no production version, no operation at this work center, …), the placeholder stays with no flag — the resolver treats `distributed` exactly like `legacy` (its D5), because both are shares of an uploaded number and neither is worse than the other. Which design ships first does not matter: if distribution ships first there is no `run_time_source` column yet, the routing migration's one-time backfill later stamps existing children `legacy`, and they behave as above; if routing ships first, uploads no longer carry `RUN_TIME` at all (its §5 step 1), the parent's hours are NULL, the placeholder is NULL, and every child resolves or is flagged `runtime_unknown` like any new order.
2. **Re-weight, reset, reapply-defaults, resolve.** After writing the new quantities, `service` calls `resolver.resolve_orders(order_ids = <children>)` inside the same transaction; children the resolver leaves at `distributed` get the proportional placeholder from the header facts. Until the routing design ships, step 2 is just the placeholder.
3. **Setup.** Pre-routing, apportioning an uploaded `RUN_TIME` that includes setup undercounts total setup by N−1 setups (each child machine sets up once); post-routing the machine-only formula excludes setup and the changeover matrix charges one setup per child machine, which is coherent. Confirmed 2026-09-17: the uploaded `RUN_TIME` is production time only, so the placeholder divides fairly and the undercount does not arise.
4. **Header `run_time`** is the parent's uploaded hours, informational once children are routing-resolved; the pane shows Σ child hours next to it.
5. **Planner edits.** A planner may still key a child's `RUN_TIME` (it is in the save payload, `persistence.mts:1263-1279`); like any SAP-owned value it is overwritten by the next re-weight or upload, and the Inspector says so for sub-orders. Quantity and machine edits on sub-orders are rejected (§8); the routing draft's plan to accept `ORDER_QUANTITY`/`MACHINE` in the save payload (its §9.2/§9.5) gets a note excluding rows with `parent_production_order`.

## 9. Optimizer

The optimizer buckets orders by `MACHINE` and searches each machine independently, alphabetically, committing patches before the next machine is examined (`frontend/optimization/setup-scheduler.mts:5304, 5491, 5710, 5796`; `byLine` at `:5321, :5509`). There is no cross-machine state, and `docs/architecture/optimizer-dispatch.md:96` lists cross-machine solving as roadmap work. Max separation is therefore the first cross-machine constraint in NIMBUS, which is why decision E phases it.

Sub-orders need no evaluator change to stay machine-locked: the optimizer already preserves `MACHINE`. When the planner optimizes only some of a parent's machines, alignment is impossible by construction; P3a still detects and reports.

### 9.1 P3a — detect
- Pure `checkDistributionSeparation(patches, snapshot)` in `setup-scheduler.mts`, called by all four evaluators before they return. Groups tasks by `(plant, PARENT_ORDER, material)`, reads each work center's `max_separation` from `snapshot.masterData.workcenters[]` — the structured-cloneable per-plant array of §6 — through the task's machine → `sap_workcenter`.
- Bucket key from a shared `separationBucketKey(date, scope)` in `frontend/nimbus-compute-core.js`: `hour → YYYY-MM-DDTHH`, `day → YYYY-MM-DD`, `week → ISO YYYY-Www` (Monday start; the `labor_plan.period` key style, `labor-planning.mts:131`). Wall-clock, no timezone conversion.
- A violation is a `ValidationFinding {code: 'distribution_separation', severity: 'warning', parents: […]}` — rendered in the preview (`optimize-ui.mts:1968`), does not block Apply; the live path toasts `toast.optimize_distribution_separation` (the missing-setup summary precedent, `engine.mts:2165`). No score-vector change.

### 9.2 P3b — align (separate approval)
Anchor bucket = the bucket of the earliest sibling start after pass 1. Re-run only the offending machines with per-task `startNotBefore`/`startNotAfter` bounds, carried as cloneable snapshot fields rather than closures so the optimizer-worker path works (`notBefore`/`notAfter` at `engine.mts:2066-2067` are closures and live only on the synchronous path). Siblings that still cannot be placed go to `needs_planning` with `planning_reason.code = 'distribution_separation'`. Finding severity becomes `error` when a plant opts into hard mode. If a soft tier is ever needed, score index 8 is appended — never inserted (`setup-scheduler.mts:719-745`). Alignment must respect `tool-conflict`: siblings of a tooled material distributed under `distribute_tooled` still cannot share one physical tool.

## 13. Flagged for review before P2 go-live

1. **Pre-existing gap:** planner cross-machine moves of *any* order never persist (`Persistence._taskEditSnapshot` `persistence.mts:1263-1279` and `TaskDateUpdate` `models.py:196-218` carry no machine; only `_UPSERT_SQL` writes `orders.machine`). A grid or Gantt machine change lives in the Store and localStorage cache and reverts on reload. This design avoids depending on it; fixing it is separate work that also affects routing D7.
2. Machine-name-first precedence, and the rule that a work-center code may not equal a machine name in its plant.
3. NULL-weight rule (all NULL → even; any set → NULL is 0).
4. `reviewed` never auto-resets — not on quantity change, not on membership change; "quantity changed since review" and `membership_changed` are derived instead. `review_required = false` pre-reviews defaults.
5. Quantity and run-time apportionment: increments from `material_plants.incremental_lot_size`, `below_min_lot` flag, integral minutes stored as hours; no UoM conversion.
6. Header persistence when a parent disappears from SAP (purge only); partial headers `incomplete`; `purged_at` shares are never recreated without an upload (amended 2026-10-01: Reset and reapply-defaults also revive — §5.7).
7. `xmin`: re-upload already bumps every re-upserted row today; re-weight guards with `IS DISTINCT FROM`; the pane refuses Save over dirty children; the ingest post-hook re-plans a parent whose header moved between `plan` and `apply`.
8. Run-time resolution order (§5.8): placeholder `run_time_source = 'distributed'`, resolver overwrites, re-weight re-resolves; setup is not proportional pre-routing; `RUN_TIME` silently defaults to 1.0 h on upload (`db.py:2568-2571`) — pre-existing, now counted as `parent_runtime_defaulted`.
9. Letters beyond `Z`; machine renames (letters persist on children); letters are stable across parents only while membership is unchanged.
10. Buckets on naive wall-clock timestamps vs `plants.timezone` (DST-edge days); ISO week vs the per-user Sunday-start display preference.
11. The SAP write-back interface itself (Q2 excluded). `sap_field_map` maps only the parent; children are generated after `map_records` and must stay that way. The `ARBPL`/`WERKS` seeds (§3.6) are a hard prerequisite for SAP-path distribution.
12. Soft refs in `setup_occurrence_override` → `status = 'replaced'` on child deletion; `make_id` plant-blind.
13. Deferred, to be recorded in `docs/MIGRATION.md` at implementation time: `DROP TABLE workcenter_mapping`; P3b; `permissions.distribution_planner`; the CRHD sync object; fixed-option selects in the cockpit grid; per-machine capacity context in the pane; a change history view from `admin_audit`; parent-deduped dashboard KPIs; a material-level weights table (decision G defers it).
14. **Planned-order conversion re-keys the parent in SAP** (PLAF-PLNUM → AFKO-AUFNR). Under Q1 the header is keyed by the uploaded order number, so after conversion NIMBUS sees a *new* parent; the planner's distribution on the planned order does not carry over and the old header lingers until purge. Ask PP whether the extract can carry the originating planned-order number on converted production orders so the header can be re-keyed (design hook: `POST /distribution/{plant}/rekey`, not built in v1). Answer 2026-09-17: possibly, via a change request to PP — the hook stays deferred until the extract carries the number; conversion is rare at the pilot, which runs planned orders only.
15. **Planned-order number churn.** Unfirmed planned orders are deleted and recreated with new numbers by every MRP run — the frequent cousin of item 14, with no mitigation in the codebase (`id = MD5(production_order|material_number)`). At the pilot MRP regenerates **weekly** and the intake is planned orders only (2026-09-17). Decision G (material default machine) carries the 100 % case across renumbering; weights beyond that are re-defaulted each week unless SAP's own firming indicator holds the order (SAP-side behaviour, unrelated to NIMBUS's frozen horizon); old headers linger until the weekly purge (runbook §14.1).
16. **No machine speed** in NIMBUS (§3.2); a `machine.rate_factor` would touch both designs. The requester intends it as separate future work (2026-09-17).
17. **Deploy:** the migration trips the deploy guard's verb filter and needs the reviewed `-AllowDestructive` apply (§3).
18. **Two cross-domain prerequisites** the design depends on: `/tasks/refresh` `missing` ids + client removal (§7), and the cache overlay's `row_version` skip (§8). Both fix pre-existing hazards.
19. Tooling: decision F assumes one physical tool per PRT value (pilot-plant confirmation of 2026-09-11, re-confirmed by the requester 2026-09-17); plants where machines hold their own tool copies set `distribute_tooled`.
20. Two planned-order quantity columns are copied, not apportioned (meanings confirmed 2026-09-17); confirmed quantity does not exist in NIMBUS and will not — NIMBUS plans the full order quantity.
21. Dashboard KPIs count sub-orders individually (§10.3).
22. **SAP capacity semantics vary per order.** Whether SAP planned an aggregate order as parallel work depends on whether operation splitting was invoked for it ("depends on the data", 2026-09-17). NIMBUS copies SAP's dates as a ceiling and never rescales them; a parent SAP planned serially will look early in NIMBUS, which is acceptable.
23. **Order-type marker codes unknown.** The pilot is 100 % planned orders; v1 labels rows "planned" unless `order_category` says otherwise (§6). PP supplies the codes when production orders start arriving.
24. **Firming.** NIMBUS's movement lock is the frozen horizon (§8); `firming_indicator` is informational on sub-orders as on every order. Which SAP flag feeds the upload's `FIRMING_INDICATOR` column (the roadmap's open item) therefore no longer gates this design.

27. **Hardcoded English nearby** (pre-existing, not fixed here): the Gantt hover-card labels (`gantt.mts:3686-3720`), the Inspector split-summary card (`orders.mts:1931-1944`), the `#schedule-unsaved` text (`persistence.mts:177-181`) and the cascade-preview sentences (`master-data/admin-ui.mts:3457-3459`). ## 16. Appendix — Context and discussion record (for hand-off)

This appendix exists so that whoever implements the design later has the full picture without the planning session. It records the original request, every question asked and how it was answered, the code facts that shaped the answers, the alternatives that were rejected and why, two review passes, the related documents, and the questions still open with PP and SAP.

### 16.1 The original brief (2026-09-17)

The request, as given:

> In SAP, many workcenters are planned in aggregate. This is for various reasons including data maintenance, complexity, and duplication of sub-machines. In SAP, this can be handled by treating these as additional complexities — however, this does not come without its own issues.
>
> In Nimbus, this creates unique challenges as Nimbus' base data model is at the most discrete level — machine. This means that there is a detail-to-aggregate extrapolation needed at ingestion on both system ends (Nimbus Detail → SAP Aggregate or SAP Aggregate → Nimbus Details). To do this, Nimbus will maintain at least 2 staging tables to maintain these relationships.
>
> **Master Data:** On the master data side for SAP Workcenters we will need to define whether the SAP Workcenter = Nimbus Machine or if SAP Workcenter = Multiple Nimbus Machines.
>
> **Transactional Order Data:** On the transactional data side for SAP Planned Orders we will need to define whether the SAP Order = Nimbus Order or if SAP Planned Order = Multiple Nimbus Orders. The reason for this split is the logical flow of aggregate SAP workcenters. If there is an aggregate workcenter it is logical that there would also be aggregate planned orders … rather than discrete orders for specific machines being planned at an aggregate level.
>
> It may be worthwhile to have an aggregate master data level that bundles changes for the Nimbus Machines. For example, the SAP workcenter level can hold details on underlying machines, if orders need to be split and what is that default split (i.e. by default, orders to SAP Workcenter A come into nimbus and even split that order across all 4 machines. Perhaps even the ability to adjust underneath that.) or (if order split is allowed) what needs to be the max separation of orders across all lines (for ex: all orders need to be ran within the same hour/day/week) as a constraint to the optimizer.
>
> With this inclusion, where we will need a way to subdivide an order (on the mapping side), we will need to find a way to support the max separation with a "parent" order from SAP for the purposes of respecting max separation across different nimbus machines. Additionally, we will need a taxonomy for the sub-orders identification. In the present state, it would seem sufficient to have an Order, lets say 1000. sub-orders are classified as A-1000, B-1000, C-1000 and so on.
>
> We will need the SAP Workcenter table to be viewable in the table browser, as well as maintainable in the Manage Data tables (both in the admin cockpit). We will also need a new master data tab for the users to manage the: 1. Review of Nimbus Machine → SAP Workcenter; 2. Order Split Master Data (if yes, define weights (default is even). If no, identify a default Nimbus Machine); 3. Max Separation of Orders (applied to optimizer only if Order Split is allowed).
>
> Note: a Nimbus Machine can only be added to 1 SAP workcenter at a time. This Nimbus Machine assignment to SAP Workcenter should be maintained in the Machine's master data tab. This means a new field will be needed in the Machine tab for this assignment. This means that on the Workcenter tab, it is fetching the relationships but the SAP Workcenter table won't maintain them — the SAP workcenter table will maintain the Order Split changes.
>
> The Order Weighting will also need a new tab (I think) in the hamburger pane underneath the Scheduling board where users will "approve" the order specific weighting. Example: By default in the SAP workcenter table 4 lines get 25% each. However, an order is so small it doesn't need to be split. Here, users can adjust if a split is needed — an adjustment of Order Split weightings (for that specific order) so maybe they say 100% to only 1 line. This means, that if it is 100% it no longer needs a "A/B/C" prefix. This table would need an ongoing ability to be altered … this isn't simply an "at ingestion" staging area. Note, if an order is able to be split — even if altered to 100% it should remain in the table for later adjustment.

Every requirement in that text maps to a section above: the two staging tables are §3.1/§3.2 (master) and §3.4 (transactional); the work-center bundle with default weights, default machine and max separation is §3.1 + §3.2; the parent link is `parent_production_order` + the header; the taxonomy is decision D and §5.3; Table Browser and Manage Data are §4.1; the users' master-data tab is §4.3 with the machine assignment on the Machines tab per §4.2; the approval tab is §6; the ongoing editability and the "stays in the table at 100 %" rule are §5.5 and the derived rules in §2. The requester's "(I think)" about the hamburger pane was confirmed: the Scheduling Board group there already has two sub-views (Gantt Timeline, Orders), and Order Distribution becomes the third.

### 16.2 The question rounds

Three rounds of questions were asked in the first session, a fourth in the gap review, a fifth put the PP/SAP questions back to the requester (§16.7), and a sixth came with the UI review (§16.10) — all the same day. Each round offered a recommended option first. The chosen option is marked ✔.

**Round 1 — framing, asked before code was read.**

- *Which SAP order object is the aggregate order?* Options: planned orders only (PLAF-PLNUM; production orders 1:1); **both, same treatment** ✔ (the parent key is whatever the upload's order-number column carries); production orders only (the roadmap's current object). Reasoning offered: the `orders` table and `docs/SAP_INTEGRATION_ROADMAP.md` §2.2 map production orders today, and the choice sets which firming flag applies. Choosing "both" keeps ingest uniform; the conversion re-key hazard (§13.14) and the renumbering hazard (§13.15) were found later during review.
- *How far should the outbound side go?* Options: **rule + read-only aggregate view** ✔ (recommended; no SAP connector exists, only the `sap_sync` skeleton whose connectors return empty lists); full write-back (needs PP/Basis input on BAPI/IDoc/file drop); inbound only.
- *How is "run within the same hour/day/week" measured?* Options: **start times in the same calendar bucket** ✔ (recommended: literal to "same day", planner-natural, easy to check); rolling window on start times (latest − earliest ≤ 60 min / 24 h / 7 d; "same day" can straddle midnight); whole envelope inside the bucket (earliest start to latest end; strictest; conflicts with the existing time-segmentation policy when a sub-order spills across days). It was stated with the question that the constraint would be hard for the optimizer and an alert, not a block, for manual drags, matching the free-manual-placement rule.
- *What is the feature called?* Options: **Order Distribution** ✔ (recommended); Quantity Split (still shares the word "split"); Sub-orders. This question existed because exploration had found that "Split-order allocation" and "Allocation policy" already label the per-plant time-segmentation feature in the UI, so both "split" and "allocation" were taken.

**Round 2 — grounded in the code exploration.**

- *Where should the machine → work center assignment and the default weight live?* Context given: `workcenter_mapping (plant, machine → sap_workcenter)` exists with zero readers, zero writers and no UI, and the unimplemented routing design planned to give it its first UI. Options: **columns on `machine`, retire `workcenter_mapping`, amend the routing design** ✔ (recommended: one relation, no synchronization, auto-renders in the cockpit grid); keep `workcenter_mapping` as storage with a separate weight table (two tables to keep consistent with membership, two writes per Machines-tab save).
- *Should sub-orders be schedulable immediately or held until approved?* Options: **schedule immediately, review is a checkbox** ✔ (recommended: defaults are the plan of record, nothing piles up unscheduled after each upload); hold until approved (children in `needs_planning` with reason `distribution_unreviewed`, excluded from Gantt and optimizer).
- *What happens when a planner drags sub-order B-1000 to another machine?* Disclosed with the question: cross-machine drags of *any* order do not persist today, so any machine-move behaviour would be a new write path. Options: **block and point to the Distribution tab** ✔ (recommended: sub-orders machine-locked, time drags free, optimizer decides when not where, no new write path); allow and rewrite shares (merge B's share into the target machine's share; slick, but adds the machine write path plus merge/rename semantics in the drag handler).
- *How are letters assigned?* Options: **stable per machine within the work center** ✔ (recommended: "B-xxxx is always Line 2"; a 0 % machine leaves a gap; the letter is stored at creation and never renamed); sequential per parent (always contiguous, but the same machine can be A on one order and B on another).

**Round 3 — after the optimizer exploration.**

- *How far should the optimizer go to enforce max separation?* Disclosed: the search runs one machine at a time with no cross-line state (`setup-scheduler.mts:5509-5534`), and the architecture docs list cross-machine solving as roadmap work; per-task date bounds (`notBefore`/`notAfter`) are the cleanest hook for alignment. Options: **detect + alert first, align in a later phase** ✔ (recommended: P3a preview finding + persistent alert with the planner resolving by dragging; P3b re-runs only the offending machines with anchored start bounds, still-unplaceable siblings to `needs_planning`); alignment pass in P3 directly (hard from day one, roughly doubles P3, adds a new start-cap bound type); detection only, permanently (treat like tool conflicts and same-midnight siblings today).

**Round 4 — the gap review (same day; full record in §16.10).**

- *How do PRT tools relate to machines inside an aggregate work center?* Disclosed: the alert core treats an equal PRT value on two machines overlapping in time as one physical tool in two places, confirmed with the pilot plant on 2026-09-11; sub-orders copy the parent's PRTs, so siblings of any tooled material would always alert, and `max_separation = hour` forces exactly that overlap. Options: **tool is unique, default tooled materials to one machine** ✔ (recommended; per-work-center `distribute_tooled` opt-out); each machine holds its own tool copy (would need a sibling exemption that weakens the alert where tools really are unique); aggregate work centers never run tooled materials.
- *Should the existing material default machine drive distribution defaults?* Disclosed: `material_plants.default_machine` is planner-editable and has no consumer. Options: **yes, 100 % on it when set and a member** ✔ (recommended: zero new tables; survives planned-order renumbering); yes plus a material-level weights table (fuller answer to churn, adds a table, a route and UI); no, work-center weights only. The requester asked for the recommended option in plain language before confirming; the explanation now sits in decision G.
- *Should sub-order quantities respect the SAP lot-size data already loaded?* Options: **round to the increment, flag below minimum** ✔ (recommended); plain unit rounding with both as markers; enforce both by folding shares (changes which children exist).
- *What should the next upload do when SAP reroutes an already-distributed parent?* Options: **keep the header's shares and flag it** ✔ (recommended: nothing destructive on upload); follow SAP when nothing is scheduled or reviewed (two code paths); always follow SAP (destructive).

**Round 6 — the UI review (same day; record in §16.10).**

- *How should the Order Distribution tab be laid out?* Options, each with an ASCII mock-up: **list + detail panel on the right** ✔ (recommended: the Orders + Inspector and Machines-tab shape; the list never jumps, bulk selection stays visible, scales to large work centers); expand under the row (fewer panels, but a 30-machine editor pushes the list away and closes on paging).
- *How should a planner type new shares?* Options: **relative weights with a live preview and a per-row "Only this machine" button** ✔ (recommended: no row changes under the cursor); percent inputs that rebalance the other rows while typing (always sums to 100 %, jumpy with many machines).
- *Where should the "awaiting review" count appear?* Options: **menu count + Dashboard situation line + Ctrl+K need** ✔ (recommended: one server count feeds all three); menu count only; no count.
- *Should sub-order bars carry a marker beyond the label?* Options: **a small `letter·count` tag** ✔ (recommended: the Gantt's existing part-counter style; the 100 % piece gets the keyline only); label only.

### 16.3 Exploration findings that changed the design

Three read-only surveys (master data, ingest and identity, optimizer and shell) ran in parallel before the round-2 questions, and two more (data model and planner write path; routing draft, alerts, KPIs, Inspector, grid, shell) plus an independent review ran during the gap review. The facts that mattered, and what each did to the design:

- `orders.id` is `MD5(production_order|material_number)` (`db.py:103-106`) and nothing anywhere parses or numerically sorts ids. → Letters go into `production_order`; ids stay opaque; `make_id` is untouched. The two `ovl-…` id-parsing fallbacks in the insights code are therefore unaffected.
- "Split" already means time segmentation on one machine (`plants.split_order_policy`, `order_schedule_segments`, `ui.split_order_*`, `cmdp.toast_split_orders_whole`). → New vocabulary throughout.
- `workcenter_mapping` is registered but unused, and the `machine` table is keyed `(subnetwork, plant, machine)` while the mapping table is keyed `(plant, machine)`. → Retire it rather than give it a first UI; put the link on `machine`.
- The planner save path (`_taskEditSnapshot`, `TaskDateUpdate`, `db.update_task_dates_bulk`) carries no machine or quantity field, but does carry `RUN_TIME`, `PRT_01/02`, `PRODUCTION_VERSION` and dates; only `_UPSERT_SQL` writes `orders.machine`. → Sub-orders are machine-locked by design; the gap is flagged (§13.1) rather than papered over; a child's manual run-time edit is allowed and overwritten later (§5.8).
- Adding a column to `machine` is schema-driven for the cockpit grid (`column_metadata` INNER JOIN) but the planner-facing Machines pane (a master/detail view that autosaves on change) is hand-coded. → Explicit field there, automatic in the grid. The generic `_fkSelect` cannot express a plant-scoped dropdown → combobox pattern from the BOM component picker.
- Re-upload never deletes rows; only `/purge` does. → Explicit child deletion in the post-hook; purge marks shares `purged_at`.
- `order_schedule_segments` is the only hard FK into `orders` and cascades on delete. → Anchor and segment carry rules for 1→N and N→1 transitions.
- Any `UPDATE orders` bumps `xmin`, discarding planners' unsaved edits on that row. → `IS DISTINCT FROM` guards on re-weight, a dirty-guard in the pane, and the observation that re-upload already bumps every re-upserted row today.
- AG Grid is the community build (no grouping or tree data). → Catalog columns plus a sibling highlight, no parent/child grid; a comparator keeps siblings adjacent.
- The hamburger drawer is navigation only, with one nested group (Scheduling Board: Gantt Timeline, Orders); `gotoGanttSub`, the section label, the landing defs and the action cluster are hardcoded. → Third sub-tab and a registry refactor shaped like `_MASTER_SUBS` that carries label, landing eligibility and pane.
- Alerts are computed only in `nimbus-compute-core.js`, shared by the worker and the sync fallback; cross-line alerts force a full recompute. → Bucket key and alert live there with parity tests; sub-orders trigger full recompute like tooled orders.
- `plants.timezone` exists, but stored timestamps are naive plant-local wall clock; labor planning keys ISO weeks while the per-user week-start preference defaults to Sunday. → Buckets on wall clock, ISO weeks; the timezone steers only "now".
- Planner writes on `/tasks/update` use `require_authenticated` only; the setup writes add `require_api_key`. → The setup precedent for the planner writes here, because they delete rows.
- `brain._ADMIN_WRITE_OPERATIONS` names admin writes for the audit middleware, and `scripts/schema_bootstrap_smoke.py` fingerprints `orders` columns across `schema.sql` and a migration replay. → Registration step and identical DDL in both files (and in the boot hook).
- **`upsert_orders` opens its connection only at the chunked loop and commits every 500 rows** (`db.py:2321-2342`). → The first draft's "transform with a connection before the dedup loop, post-hook in the same transaction" was impossible; replaced by a read-only `plan` and an idempotent `apply` transaction with an honest crash window (§5).
- **The deploy guard blocks any `ALTER`** (`apply-migrations.ps1:67`). → The "auto-applies" claim was false; corrected (§3, §13.17).
- **`sap_field_map` maps five order fields and no work center or plant** (`schema.sql:925-929`). → SAP-path distribution needs two seed rows (§3.6).
- *(Stale as of 2026-10-07: the refresh/removeTask prerequisite now exists — `POST /tasks/refresh` returns `missing` ids, `backend/scheduling/routes.py:592-618`, and `persistence.mts` drops ghosts through `Store.removeTask`, `persistence.mts:1666-1679`; the same applies to the §7 "cross-domain change" paragraph. Verify against live code before acting on this bullet.)* **Deleted rows are never signalled to clients** (`/tasks/refresh` ignores missing ids; `saveAll` treats `not_found_ids` as accounted) and **the localStorage overlay overwrites server-side schedule writes** (`_overlayUserMoves`). → Two cross-domain prerequisites (§7, §8, §13.18).
- **`orders.run_time` is hours** while the first draft called minutes canonical. → Minutes for apportionment, hours stored (§5.3).
- **The `machine` post-write hook runs after commit, best-effort** and the generic write path validates nothing beyond Postgres constraints. → Derived statuses instead of stored flags; a `sap_workcenter` post-write check for the grid path; the `reviewed` auto-reset contradiction removed.
- **`material_plants` already holds `default_machine`, `min_lot_size`, `incremental_lot_size`** and `machine` holds no rate of any kind; PRT values identify one physical tool. → Decisions F, G, H and the "even = even by time" statement.
- **The routing draft resolves run time after stamping and leaves an existing run time untouched when it cannot resolve** (its §5, §6.5). → §5.8: placeholder with `run_time_source = 'distributed'`, resolver overwrites, re-weight re-resolves.
- **The cascade preview model is closed and its non-`material_plants` wording says "will delete N production lines"**; `list_rows` has no search; the upload-history list renders only `level`/`msg`; `UndoStack` never sees re-weights; the Inspector has a `MACHINE` select. → §3.6, §4.3, §5.4, §5.5, §8 amended accordingly.

### 16.4 Alternatives considered and rejected

| Alternative | Why rejected |
|---|---|
| Keep `workcenter_mapping` as storage | Two relations for one fact; every Machines-tab save becomes two writes; the table had no consumers to protect. |
| Fold a `split_seq` into `make_id` and render `A-1000` only in the UI | Display plumbing at every `Util.orderNumber` call site and a `make_id` change the whole scheduling domain relies on for id stability. |
| JSONB `shares` array on the header | No row-level constraints, GIN filtering for machine-scoped lists, no `child_id` for reconciliation, poor Table Browser readability. |
| Store `distribution_share` on `orders` | Drifts the moment SAP changes the parent quantity; derivable from siblings. |
| NULL weight = 1 | Next to explicit 60/40 weights it yields sliver sub-orders; "set the percentages you care about" matches planner intent. |
| Hold sub-orders in `needs_planning` until approved | Unplaced work after every upload; defaults are already the plan of record. |
| Allow cross-machine drags and rewrite shares | Requires the missing machine write path plus merge and rename semantics in the drag handler. |
| Sequential letters per parent | Same machine gets different letters on different orders; planners cannot learn the mapping. |
| Alignment pass in P3 directly, or detection only forever | The former doubles P3 and adds a new bound type before the value is proven; the latter never satisfies "constraint to the optimizer". |
| Rolling-window or whole-envelope separation | Rolling straddles midnight; envelope conflicts with time segmentation and confuses duration with misalignment. |
| SQL view for the roll-up | Would duplicate the effective-date SQL in `db.py:192-225` and drift. |
| Reuse `require_setup_scheduler` for approvals | That permission means "may record setup truth". |
| Auto-collapse headers when a work center flips to single mode | A destructive side effect of a master-data save; mode governs new arrivals instead. |
| Work-center-code-first precedence at ingest | Breaks the SAP path, where the machine column is mapped from `ARBPL` and a 1:1 code equals the machine name. |
| Names "Quantity Split" / "Sub-orders" | The former keeps the collision; the latter names the output, not the feature. |
| Per-work-center setting in the per-plant Scheduling Rules pane | The setting is per work center, not per plant; a JSONB sidecar on `plants` cannot hold a row set with per-machine weights. |
| `DROP TABLE workcenter_mapping` in the additive migration | Genuinely destructive; the deploy skill sequences such statements as their own decision. |
| One transaction around the whole upload for distributed batches (gap review) | Reintroduces the long table lock the 500-row chunking exists to avoid; the read-only plan + idempotent apply keeps the crash window small and recoverable instead. |
| Stored `stale` flag and `reviewed` auto-reset via the post-write hook (gap review) | The hook runs after commit, best-effort, non-fatal, so stored flags drift; and §13.4 already promised `reviewed` is never auto-reset. Derive on read. |
| Follow SAP automatically when a distributed parent is rerouted (gap review) | Destructive on upload — scheduled children would move or vanish; header authority plus a `wc_changed` status keeps uploads non-destructive. |
| Treat each machine as holding its own tool copy by default (gap review) | Requires exempting siblings from `tool-conflict`, weakening it where tools are unique — which the pilot plant confirmed they are. Opt-in flag instead. |
| Enforce `min_lot_size` by folding shares (gap review) | Changes which children exist, contradicting the rule that shares alone drive existence; flag instead. |
| Bump `Config.SCHEMA_VERSION` for the two task fields (gap review) | Discards planners' cached unsaved edits; optional fields never need it. |
| Re-materialise purged children from header facts (gap review) | Recreates orders without any SAP input; a purged share waits for an upload (amended 2026-10-01: Reset and reapply-defaults also revive — §5.7). |
| Hardcode the third sub-tab like the first two (gap review) | The section label, landing defs and action cluster would be wrong for it; a registry fixes all three once. |
| Inline expansion of the shares editor under each list row (UI review) | A 30-machine editor pushes the list away and closes on paging; the list + detail panel is the shape the Orders and Machines screens already use. |
| Percent inputs that rebalance the other rows while typing (UI review) | Rows change under the cursor; relative weights with a live dry-run preview are exact and calm. |
| Colouring sub-orders on the Gantt (UI review) | Bar colour already means standard/firmed and the line palette is a closed set (`DESIGN.md` §2); the `dist-part` pill and keyline carry the cue. |
| A family band or row grouping across machines on the Gantt (UI review) | vis-timeline groups are machines; a cross-row band fights the model and clutters at 70 machines. |
| Sibling connector lines through `DependencyOverlay` (UI review) | The selection highlight already links siblings; lines across 70 rows read as noise. |
| Drag-to-adjust weight bars; keyboard shortcuts for review (UI review) | Imprecise for lot-rounded quantities; bulk *Mark reviewed* covers throughput without more surface to document and test. |
| A dedicated notification centre for distribution events (UI review) | The review count in three existing places plus the alerts drawer suffice in v1. |
