# Workstream B — Optimizer & Scheduling Behavior — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let planners place orders anywhere without silent calendar correction (while finally alerting on the working-hours violations that free placement can create); stop the optimizer from auto-nudging siblings after a manual edit; make "Min Changeover" always route through the setup-aware evaluator (using a synthetic zero-cost matrix when a plant hasn't activated setup tracking) so the optimizer can never silently disagree with itself about whether setup costs time; and pin, with tests, that the configured priority lists — not the setup matrix — are what changeover minimization is actually optimizing for.

**Architecture:** Four independent-but-file-adjacent behavior changes inside the existing scheduling engine (`web/schedule-services.mts`, `web/setup-scheduler.mts`, `web/schedule-workbench.mts`, `web/nimbus-compute-core.js`). No new tables, no new endpoints — this is behavior surgery on an already-built optimizer, not new infrastructure. One exception: OD-B3b's recommended `plants.min_productive_segment_minutes` column, which follows the exact schema+boot-hook dual-provisioning pattern established by every prior workstream on this branch.

**Tech Stack:** TypeScript compiled in place (`web/*.mts`), a UMD compute core (`web/nimbus-compute-core.js`), PostgreSQL/FastAPI for the one new plant setting.

**Spec:** `docs/multi_change_spec_08.20.26.md` — Workstream B (§B, lines 266–410), plus the Locked Decisions table's five "Change #2" rows (lines 32–36), Reconciliation #1/#2/#5 (lines 74–107), and F2 (line 697, explicitly parked — do not implement a bounded/max-lateness optimizer in this workstream).

### Task 1: B1 (part 1) — One policy-independent, segment-shift-aware manual commit path

**Model:** Sonnet (touches the core placement contract three call sites depend on; a mistake here breaks grid edits, Inspector edits, and Timeline drags simultaneously).

**Context.** Today, `Engine.manualSchedulePatchFor` (`web/schedule-services.mts:2010-2031`) branches on `Engine.splitOrderPolicyFor(plant)`: under `'never'` it commits verbatim at `Util.snap` with `scheduleSegments: []` (a full collapse to one continuous block); under any other policy it calls `Engine.schedulePatchFor` → `Calendar.allocateRuntime`, a real calendar-aware regeneration. Separately, `web/schedule-workbench.mts`'s Timeline drag handler (`_onDataSetUpdate`, the branch starting at `:6594`) decides whether to regenerate at all via `Interaction._dragRequiresRegeneration` (`:6523-6526`: true whenever `split_order_policy !== 'never'` OR the task already has ≥2 `scheduleSegments`) — when true, it calls `_regenerateDragPatch` → `manualSchedulePatchFor` per-task, and for the specific task that was dragged, always passes the **new snapped start as the requested parent start** (`:6614-6616`), which is exactly OD-B1a's "dragging segment 3 of a 3-day split sets the whole order's first start to that instant." When regeneration isn't required, the plain verbatim branches (`:6640-6676` multi-select, `:6678-6691` single-item) apply the new start/end/line directly with no split-awareness at all.

**Resolved design (OD-B1a).** "Commits verbatim" does not mean "always collapses to one segment" — it means *no calendar-aware recomputation ever happens on a manual edit*. Reconciled with the Scope's "splitting becomes an optimizer-only outcome": a manual edit never *creates or resizes* a split via `Calendar.allocateRuntime`, but if the order already has ≥2 `scheduleSegments` (put there by a *previous optimizer run*), a manual edit must *translate* that existing shape by the requested delta rather than either destroying it or fully re-deriving it. Concretely:
- Task has `scheduleSegments.length < 2`: identical to today's `'never'` branch — `start_date`/`end_date` become `Util.snap(requestedStart)` and `Util.snap(requestedStart) + runtimeMinutes`, `scheduleSegments: []`. Regardless of the plant's `split_order_policy`.
- Task has `scheduleSegments.length >= 2`: compute `deltaMs = Util.snap(requestedStart).getTime() - task.start_date.getTime()`, then every existing segment's `startDate`/`endDate` shifts by `deltaMs`; the parent's `start_date`/`end_date` become the (shifted) first segment's start and last segment's end. No calendar lookup, no `Calendar.allocateRuntime` call, no re-derivation of segment boundaries.
