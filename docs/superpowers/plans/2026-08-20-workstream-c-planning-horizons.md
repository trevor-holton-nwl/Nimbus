# Workstream C — Plant Visibility & Frozen Horizons — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** C1 gives each plant a configurable visibility horizon — how far into the future a planner can see on the Gantt and Orders tab, enforced server-side so the horizon bounds the payload, not just the view. C2 gives each plant a frozen horizon — a window the optimizer may never schedule into, treating any order that starts inside it as implicitly pinned.

**Architecture:** C1 is a read-path filter (query + response shaping on `GET /tasks`, view clamping on the Gantt/Orders grid). C2 is a write-path floor (a shared helper consulted at every placement site, plus a new Gantt band). Both are plant-level settings living beside the existing `visibility_horizon_days`-shaped columns, surfaced in the same Scheduling Rules panel, and both render a background band on the Timeline using the same one-second-ticker pattern the existing `alert-horizon-zone` band already uses.

**Tech Stack:** Same as prior workstreams in this effort — PostgreSQL, FastAPI/Python, TS/JS frontend (vis-timeline for the Gantt bands).

**Spec:** `docs/multi_change_spec_08.20.26.md` §C (C1/C2, lines ~412–500), Locked Decisions (Change #6/#7 rows), PT-16 in the pressure-test log, and Consolidated Open Decisions OD-C1b–OD-C1e, OD-C2a, OD-C2c.

## Global Constraints

- **Model policy:** Sonnet or Haiku only — never Opus, never Fable.
- **C1 and C2 share files** (`schema.sql`, `brain.py`, the plant Scheduling Rules panel in `web/plant-and-administration.mts`, and `Timeline`'s band-rendering code in `web/schedule-workbench.mts`) — implement **sequentially**, not in parallel, to avoid concurrent-edit conflicts. C1 first (it's the simpler, more contained of the two).
- **C1 adopted defaults:** gate on the same three-way coalesce `GET /tasks` already reports (`COALESCE(seg.first_start, scheduled_start, basic_start_date)`), not a two-way approximation. Add the same bound to `db.count_orders`'s separate WHERE builder so `meta.total` never disagrees with the actual filtered set. Plant-local midnight with a UTC roll hour (default 19:00 UTC) is deliberate. An order starting inside the window but ending outside it is **included** (gate on start only). **Hide** rows beyond the horizon on both the Gantt and Orders tab — don't just block scrolling, or the two surfaces disagree about what exists.
- **C2 adopted defaults (locked: full placement floor, not a one-line seam):** an order whose **start** falls inside the frozen window is treated as implicitly pinned (same effect as `Store.isFixed`, distinct reason so the UI can explain why). Nothing may be scheduled into the window — enforced at every placement site (~8, per the spec's citation list), not just the couple of places `Engine.earliestAllowedStart`/`bounds.notBefore` happens to be read today (that seam does **not** generalize — verified in the spec's PT-2, don't rely on it). Frozen does **not** block manual drags (OD-C2c) — the planner can always move things by hand; it constrains the optimizer only.
- **Both horizons are per-plant, nullable/zero-means-off** columns on `plants` — never a global default, never assumed present.
- **The finish-to-start link chain built in `GET /tasks`** is truncated by any bound (same pre-existing incoherence already documented for `limit`/`offset`) — don't try to "fix" that generally, just don't make it worse, and don't let a horizon-truncated link silently look like a data-integrity bug (it's a known, already-accepted limitation).

## C1 — Plant visibility horizon

**Files:** `schema.sql`, `master_data.py` (or wherever plant-scoped scheduling settings like `split_order_policy`/`max_pull_forward_days` are read/written — follow that exact precedent), `db.py` (`query_orders`, `count_orders`), `brain.py` (`GET /tasks`), `web/schedule-workbench.mts` (Gantt `max` clamp), `web/schedule-data.mts`/wherever the Orders grid's date filter lives, `web/plant-and-administration.mts` (Scheduling Rules panel), `web/locales/*.js`.

- [ ] **Step 1.** Add `plants.visibility_horizon_days INTEGER` (NULL = unlimited) and `plants.horizon_roll_hour_utc INTEGER NOT NULL DEFAULT 19` to `schema.sql`, following this file's existing pattern for adding nullable/defaulted columns to `plants`. Add the matching `master_data.ensure_*` provisioning-hook column(s) so a normal boot (not just a fresh `schema.sql` apply) provisions them too — this repo's dual-provisioning hazard (documented in workstream A's completion notes) applies here exactly as it did there.
- [ ] **Step 2.** Compute the effective visibility-horizon **end instant** for a plant: plant-local midnight of `anchor_day + visibility_horizon_days`, where `anchor_day` is today's date in the plant's `timezone` (already a real column per `docs/multi_change_spec_08.20.26.md`'s reference to `plants.timezone`), advancing to tomorrow once the current UTC time passes `horizon_roll_hour_utc`. Write this as a single, testable function (Python for the server-side gate, and confirm whether the frontend needs its own copy for the Gantt clamp or can just read a value the backend already computed and sent down — prefer the latter to avoid a second implementation of the same clock math, matching this repo's general aversion to duplicated logic).
- [ ] **Step 3.** `GET /tasks`: add the horizon bound to the **same three-way coalesce** the endpoint already reports (`COALESCE(seg.first_start, scheduled_start, basic_start_date)` in `db.py`'s `query_orders`), gating on start only (OD-C1d). Add the identical bound to `db.count_orders`'s separate WHERE builder (it does not share a query with `query_orders` today — confirmed duplicated builder) so `meta.total` agrees with the actual returned/filtered set whenever paging is active. Add an index supporting the bounded, plant-scoped query if the existing `idx_orders_line_eff_start`(now likely renamed to a `machine`-based name per workstream A)-style index doesn't already cover a `(plant, effective_start)` shape — check `schema.sql`'s current indexes on `orders` first, only add what's missing.
- [ ] **Step 4.** Gantt: clamp `vis-timeline`'s `max` option to the plant's horizon end instant computed in Step 2/3 — do **not** clamp the past edge (only bounds the future). Read `Timeline.rebuild` (`web/schedule-workbench.mts`) for where zoom/range bounds are currently set (the design doc cites "its only temporal limits are zoom bounds") and add the horizon as an additional bound, not a replacement of the zoom bounds.
- [ ] **Step 5.** Orders grid: hide rows whose effective start is beyond the horizon — find the grid's current single-exact-day `dateKey` filter (the design doc cites it as matching one exact day, not a range) and extend it to also respect the horizon end, consistent with the server already excluding those rows from the payload (this is belt-and-suspenders — the row shouldn't reach the client at all per Step 3, but the grid's own filter logic should not silently assume an unbounded set either, in case a cached/stale payload briefly disagrees).
- [ ] **Step 6.** Surface `visibility_horizon_days`/`horizon_roll_hour_utc` as editable fields in the plant Scheduling Rules panel (`web/plant-and-administration.mts`) beside wherever `max_pull_forward_days`/`split_order_policy` are already edited — same permission gating, same save/validate pattern.
- [ ] **Step 7.** New i18n keys (field labels, help text) in all 5 locale files.
- [ ] **Step 8.** Add a test proving `count_orders` and `query_orders` agree on the filtered set under a horizon bound (this is the PT-16 hazard this workstream must close — a mismatch here silently lies about pagination totals).

## C2 — Plant frozen horizon

**Files:** `schema.sql`, `master_data.py`, `brain.py`, `web/schedule-services.mts` (the shared placement-floor helper + every one of its ~8 call sites), `web/schedule-workbench.mts` (`Timeline`'s new `.frozen-horizon-zone` band, `Timeline._frozenHorizonIds`), `web/styles.css` (new band color — "darker green... layered above the existing alert-horizon band"), `web/plant-and-administration.mts` (Scheduling Rules panel), `web/locales/*.js`.

- [ ] **Step 1.** Add `plants.frozen_horizon_days INTEGER` (NULL/0 = off) to `schema.sql` + the matching provisioning hook, same pattern as C1 Step 1.
- [ ] **Step 2.** Write **one shared floor helper** (do not scatter the check across call sites ad hoc) — given a task and a plant, return whether the task's current start falls inside the plant's frozen window (per OD-C2a: frozen iff **start** is inside), and if so, treat it as implicitly pinned for optimizer purposes. This must carry a **distinct reason** from `Store.isFixed` (e.g. a `frozenHorizon: true`/reason-coded flag) so the UI can explain *why* an order didn't move, without conflating it with a genuine manual pin.
- [ ] **Step 3.** Apply this helper at **every** placement site the spec enumerates (re-derive the current, possibly-shifted line numbers by reading the file — the design doc's citation list, paraphrased: the legacy walk's several `earliestAllowedStart` call sites, `autoReflow`, `Calendar.placeWithSetup`, `Calendar.allocateRuntime`, and any manual-path placement code that currently ignores `bounds.notBefore` entirely). This is the largest single piece of C2 — budget real time for it, it is explicitly **not** a one-line change (the spec calls this out as the biggest correction in its own draft history: the originally-proposed `bounds.notBefore` reuse does not generalize to a floor, per PT-2).
- [ ] **Step 4.** Timeline band: add `.frozen-horizon-zone` — one background item per visible line/machine, layered **above** the existing `.alert-horizon-zone` (darker green, per the spec's visual description — pick an actual color value and add it to `web/styles.css`, matching this file's existing token/variable conventions rather than a bare hex literal if the file uses CSS variables for its palette). Track ids in a new `Timeline._frozenHorizonIds` list, re-advanced on the **same one-second ticker** the alert-horizon band already uses (`Timeline.rebuild`'s existing interval — don't create a second, redundant ticker).
- [ ] **Step 5.** Confirm manual drags are **not** blocked by the frozen window (OD-C2c) — this constrains the optimizer only. Add a test dragging a task into/out of the frozen window and asserting the drag succeeds either way, while a subsequent optimizer run leaves that order untouched if its start is inside the window.
- [ ] **Step 6.** Surface `frozen_horizon_days` in the Scheduling Rules panel, same location/pattern as C1's new fields.
- [ ] **Step 7.** New i18n keys (field label, help text, and whatever surfaces the "didn't move — inside the frozen window" reason to a planner, e.g. an Inspector or alert-adjacent explanation) in all 5 locale files.
- [ ] **Step 8.** Add a test proving an order whose start is inside the frozen window survives every one of the ~8 placement sites without being rescheduled into or through the window, across at least the legacy walk and `autoReflow`.
