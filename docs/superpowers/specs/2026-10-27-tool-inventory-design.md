# Tool Inventory (Tool 1 / Tool 2 capacity): design

Status: design settled 2026-10-27; implementation not started (Wave 0 only). Branch `feature/tool-inventory`, worktree `.claude/worktrees/tool-inventory`. Progress is tracked in `2026-10-27-tool-inventory-progress.md` (orchestrator-owned). Symbol names are the anchors; line numbers are approximate and must be re-verified at HEAD before each wave.

## Owner decisions (settled, do not re-ask)

1. Tool ids are maintained **per plant** (no cross-plant tools). Inventory keyed `(plant, tool_id)`.
2. A tool id is a **type; the plant owns several interchangeable copies**. Same id in PRT-01 and PRT-02 of one order = 1 copy. Capacity = distinct machines at the same instant; half-open [start,end).
3. A **split order keeps its tool mounted across the weekend/blackout gap** (owner stated as an assumption; confirm with pilot plant). Tool occupancy of an order = first-segment start to last-segment end, NOT segments only. This CHANGES alert rule 1b (today `scheduleIntervals` counts segments only) and the optimizer; one shared helper `toolOccupancyInterval(task)` must serve both. Needs a release note + tests.
4. Missing inventory row = 1 copy. Available = max(0, total - out_of_service). Qty 0 allowed = unavailable.
5. **Optimizer architecture: "fix it afterwards"**: optimize as today, then one plant-wide tool-overflow pass finds overlaps and re-places the least urgent offender into a tool-free gap, or queues it to Needs Planning if nothing fits. Search-time tool awareness is a possible LATER upgrade only for contended tools (not in scope). This replaces the earlier "track during placement" decision because of finding O1 below.
6. Toggle "PRT's as Hard Constraint": per plant, default OFF, lives in **System Settings > Scheduling Rules > Order Rules**, shown as a **drop-down (Off / Hard)** (named-mode enum so a middle mode can be added later without migration), **planners can change it** (so the setter route is NOT `require_admin` like sibling rules; use planner-level auth + plant scoping like the inventory route). Right-click "More info" help (existing RULE_HELP mechanism). OFF = optimizer ignores tool counts; Gantt alert fires regardless.
7. Optimize safety net = **preview confirm only** (no per-run cap): preview shows "of which tool: N" newly queued and requires an extra confirm; the same guard on "Apply what still fits", "Apply without preview" (background result), and Alert "Fix overload".
8. Tool occupancy for the retry/placement semantic = **run time only** (setup/changeover may overlap another machine's tool use), consistent with the alert. (Under decision 5 this matters for the gap-fill re-placement.)
9. Alert: count-aware sweep; keep type `tool-conflict`; one alert per "pusher" order; keep `peerId` (representative peer) and add `peerIds[]`; alert text names tool, available, in use, holders; zero-available has its own wording; **keep legacy `toolc-prev|cur` id for exactly-2-order conflicts**, new id `toolc-<pusher>|<sanitized tool>` otherwise (sanitize `/ % #`; collision check when 2 tools conflict on the same pair).
10. Inventory editing: **planners and admins** edit via a new Master Data subtab (plant-scoped save route); Manage Data (admin) also lists the table. **Planners can create rows for tool ids no material/order uses (pre-register). No rename: Tool ID locked once saved; fix a typo by delete + re-add (do it in one save so the tool never reverts to 1 copy).** **Deleting a tool id used by orders shows a warning confirm** (count + first few orders, states "back to 1 copy; use quantity 0 to mark unavailable", default Cancel); count must be server-side (orders table, both PRT columns, same normalization), applied on every delete path incl. Manage Data.
11. Excel: prefilled template, current-data export, .xlsx upload by **planners with a "review changes" step before commit** ("N new, M changed old->new, K unchanged"); upsert-only (rows missing from file untouched; say so in How-to sheet and summary). Template also lists tools in use on orders that have no row (case-preserved, placeholder-filtered, new query).
12. My stated defaults (owner did not object; confirm in the plan): tool ids stored **trimmed + upper-cased** on every write path (because `/tasks` already upper-cases PRT; matching case-sensitively against upper-cased wire values would make a typed `t100` silently never match); blank Total rejects the row, blank Out of Service = 0; manual placements (drag, Slot, Override, autoReflow, reconcile) stay alert-only; Remove Backlog explicitly exempt; pre-existing violations grandfathered as warnings (protected-vs-protected always warning, still reserves copies); alert shows "no inventory row, treated as 1 copy" and the alert/Needs Planning reason deep-link to the Tool Inventory row (quick filter by tool id); "N tool alerts cleared" in the inventory-save toast; stale-preview banner when inventory/toggle changes; help text says "Tool 1 / Tool 2" not SAP field codes; wave order = Waves 1-3 first, alerts next, optimizer last behind the toggle; add `ensure_tool_inventory_table()` boot hook.

## G1. Context, goals, non-goals, anti-goals
**Why.** Rule 1b (`computeAlerts`, `frontend/nimbus-compute-core.js` ~:714-764) treats every PRT_01/PRT_02 value as one physical tool and fires red `tool-conflict` when two machines use it at once. Plants own several copies, so it false-fires; the optimizer has no tool logic (only sort terms).
**Outcome.** Per-plant Tool Inventory (planner + admin editing, Excel round trip with review step); count-aware alert (fires on the (N+1)th machine); behind a per-plant Order Rule "PRT's as Hard Constraint" (Off/Hard, default Off) an optimizer overflow pass that slides the least urgent offender into a tool-free gap on its own line or queues it to Needs Planning with a structured reason.
**Goals.** (1) inventory table + editing + Excel. (2) count-aware alert via ONE shared pure function set in the compute core. (3) optimizer "fix it afterwards" pass: toggle-gated, never-freeze, protected never moved, Off byte-identical. (4) explanations everywhere. (5) Waves 1-5 independently shippable with the toggle Off.
**Non-goals.** Per-copy serials; dated return-from-repair; search-time tool awareness; cross-plant tools; Sandbox snapshotting master data; per-bar Gantt tint; deriving `distribute_tooled` from inventory.
**Anti-goals.** No SAP field codes in planner text ("Tool 1 / Tool 2"); no second hand-mirrored tool rule; no per-run cap on queued orders; Manage Data stays admin-only; NO `ALTER|DROP|DELETE|UPDATE|TRUNCATE|RENAME|GRANT|REVOKE` word anywhere in the migration, comments included.

## G2. Architecture
**Data flow.** `tool_inventory(plant, tool_id, total_qty, out_of_service_qty, note)` -> `GET /master-data/tool_inventory?plant=` -> `Persistence` loads it in the same `Promise.all` as plants/lines/workcenters -> `Store.setMasterData({..., tool_inventory})` where `tool_inventory` is `rows[] | undefined` (undefined = fetch failed, NEVER "empty") -> (a) `_buildSnapshotBase` posts masterData (compact projection) to the alert worker/sync path where rule 1b calls the shared core functions; (b) `snapshotSchedule` clones it into `ScheduleSnapshot.masterData`, where `toolingRuleForSnapshot` + `buildToolIndex` feed `resolveToolOverflow`; (c) UI (subtab, Order Rules pane, Inspector row, Optimize preview). Writes: `POST /tool-inventory/{plant}/bulk|upload` (planner-level, plant-scoped) or admin generic `/master-data/tool_inventory/bulk`, all through `bulk_apply` with one normaliser/validator, then `refreshStoreMasterData(source,'tool_inventory')` -> `master-data-changed` -> `Alerts.scheduleRecompute()` + preview stale banner. Toggle: `plants.setup_policy_config.toolingRule` = `'off'|'hard'` (JSONB merge, `version:2`), read only from `snapshot.masterData` in the optimizer (never `bounds`/`runContext`).
**Shared pure API in `nimbus-compute-core.js` (+ `.d.ts`):** `TOOL_PLACEHOLDERS` (`'' - 0 N/A NONE NULL NAN TBD`, one set; `services.mts taskCarriesTool` and `backend/distribution/service.py` match, parity-tested); `normalizeToolId` (trim, upper, placeholder->null); `taskToolIds(task)` (deduped PRT_01/PRT_02); `taskToolPlant(task, plantOf)` = `task.PLANT || plantOf(MACHINE)`; `toolOccupancyInterval(task)` (envelope first-segment start -> last-segment end; finish-only row -> `[end-run_time, end]` U29 bar; else null); `buildToolCapacity(masterData)`; `availableCopies(cap, plant, tool)` (missing -> `{1,false}`); `findToolOverages({items, capacityFor, now?})` (per (plant,tool) sweep sorted `(t, end-before-start, line, id)`, distinct machines, one cluster per pusher `{plant, tool, at, available, hasRow, inUse, pusher, holders[]}`, deterministic under shuffle, prunes tools with `available >= distinct machines`); `toolConflictAlertId(cluster)`; `toolHeadroom(index, plant, tools, from, to, excludeLine)` (tool-free windows for the optimizer).
**Invariants.** Never-freeze (queue with structured `planning_reason`); detached/pure scheduler; protected (manual firm under Respect firmed, running, frozen, `placement_exception`, window-end held, explicit boundaries) never moved; patches never change MACHINE; Off byte-identical to today; determinism (sorted iteration; only nondeterminism = existing budget guard).

## Appendix A: Context

**What prompted the feature.** The Gantt alert rule 1b (`computeAlerts` in `frontend/nimbus-compute-core.js`) treats every Tool 1 / Tool 2 value (`PRT_01` / `PRT_02` columns) as a single physical tool and raises a red `tool-conflict` alert whenever two machines use the same tool id at once. Plants actually own several interchangeable copies of a tool, so the rule false-fires, and the optimizer has no tool logic at all (only priority-list sort terms). The owner asked for a per-plant inventory, a count-aware alert, and an optional hard constraint in the optimizer.

**Non-obvious facts a successor must know** (full detail in G7 below):

optimizer places FORWARD (earliest fit); rule 1b has no worker mirror, is plant-blind, counts protected orders and split SEGMENTS only, and `scheduleIntervals` excludes setup; `/tasks` upper-cases PRT; the migration runner regex is `\b`-anchored, scans comments, and lives at `.claude/skills/promote-azure/scripts/apply-migrations.ps1:78`; image-before-migration returns 200 with no metadata (reads as loaded-empty) and bulk writes 500; 3 pair alerts become 2; `finalizeCandidate` repairs BOTH incumbent and result before comparing; `fillPlanningGaps` rebuilds `runContext: undefined` and validates without repairing; `retainCompatiblePlacements`/gap-fill validate against a single-line `{...snapshot, tasks: peers}`; `repairCandidate` rejects every failing task per pass; `_pruneAgainstLive` key includes the finding message; `staticPlanningDefect` memo keys on `masterData` identity; `PREVIEW_TASK_CHANGE_EVENTS` is tasks-only; `refreshStoreMasterData` rebuilds `{plants, lines, workcenters}` wholesale; `_ADMIN_WRITE_OPERATIONS` keyed by route template; `.d.ts` `NimbusMasterData` declares only `lines?` while `types.mts` has required `plants/lines/workcenters`; `Alerts.applyFix` is synchronous; "planner" is not a server role (`require_authenticated` accepts any known user).

Additional facts established by the reviewers:

- The optimizer places FORWARD (earliest fit); finish-anchoring and backward derivation live only in engine paths (reconcile, manual, finishAnchoredPatchFor, push cap). A tool conflict slides an order later, like a blackout; never earlier by search (the overflow pass may pick an earlier tool-free gap on its own line, default F1).
- Rule 1b has no worker mirror: the worker, the sync path and the optimizer worker all load `nimbus-compute-core.js`. Today it keys on the raw tool string and is plant-blind (safe only because the payload is single-plant); `scheduleIntervals` counts split segments only and drops rows with no start.
- Tool ids are not ingested per order: they are stamped from `material_plants.prt_01/prt_02`; the Orders grid and Inspector inputs are free text and are overwritten by the next stamp/resync. `/tasks` trims and upper-cases PRT, so inventory ids must be stored trimmed + upper-cased or a typed lower-case id would silently never match.
- `taskCarriesTool` placeholder set (`'' - 0 N/A NONE NULL`) is hand-duplicated in the compute core, `services.mts` and `backend/distribution/service.py`; `NAN`/`TBD` are missing everywhere. The shared set fixes this and gets a parity test.
- The migration runner (`.claude/skills/promote-azure/scripts/apply-migrations.ps1`) scans the whole file, comments included, with a `\b`-anchored case-insensitive destructive-word regex; the migration must contain none of those words.
- If the image rolls before the migration, `GET /master-data/tool_inventory` returns 200 with empty rows and no column metadata (reads as loaded-empty, i.e. every tool = 1 copy) and bulk deletes return 500. Hence the boot hook `ensure_tool_inventory_table()` and the migration-first deploy order.
- `finalizeCandidate` repairs BOTH the incumbent and the result before comparing them, so the overflow pass must run on both inside it. `fillPlanningGaps` rebuilds context with `runContext: undefined` and validates without repairing; `retainCompatiblePlacements` and gap-fill validate against a single-line peer snapshot (cross-line blind).
- `repairCandidate` rejects every failing task per pass, and `_pruneAgainstLive`'s key includes the finding message: a tool finding must name exactly one task per cluster with a fixed message.
- Every apply path funnels through `_commitPatches` / `validateCandidateForApply`, so a single pre-commit confirm seam is feasible. `Alerts.applyFix` ("Fix overload") is synchronous and live; on an error finding it applies nothing but today still pushes Undo and dismisses the alert (pre-existing silent no-op).
- Three overlapping pair alerts become two (one per pushing order); existing tests only cover 2-order conflicts. A third holder flips the alert id and loses its acknowledgement; old acks orphan when capacity rises.
- "Planner" is not a server role: `require_authenticated` accepts any known user, so plant scoping (`get_allowed_plants_for_request` + `md._assert_plant_allowed`) is the real guard. The tooling-rule setter therefore differs from its `require_admin` siblings by design.
- The CI workflow (`.github/workflows/ci.yml`) is a real gate (typecheck, lint, tests, legacy-surface, static-assets, api-types drift, ruff, pytest); the promote-azure skill's "no GitHub CI gate" sentence is stale (fixed in Wave 7).
- Local tests: pytest requires local Postgres with `NIMBUS_TEST_DB=1` / `NIMBUS_REQUIRE_TEST_DB=1`; never retarget `.env` at Azure.

## Appendix C: Things learned along the way (2026-10-28)

- **Wave 3 freshness fingerprint.** The first freshness check compared against a version read after the rows, so a save landing between the two reads was reported as fresh. The baseline is now the server's own version string read BEFORE the rows (f023c10), with an own-save race guard.
- **Wave 6 validation findings.** M2-M4 and M-A are described here (M1 is in the validator report). M2: retain, gap-fill and the repair cascade did not label tool-caused queues, so Needs Planning showed an ordinary reason (fixed: `tool_contention` + `toolBlocked`, cascade entries carry `cause: 'cascade'`). M3: the pass re-swept every cluster after each move and was far too slow at 3,360 orders (fixed: per-tool cluster cache, one greedy sweep per tool after budget expiry). M4: never-committed SAP baseline bars reserved copies for mutable work (fixed: warning only, owner decision F3). M-A: the relaxed (second) gap walk accepted a slot that gave a protected successor a new setup warning, because the validator only warns for protected orders (fixed in d519a6c and 48efba2: a relaxed trial is compared with the same line without the placement; new protected setup warnings 84 -> 13 on seeds 1-3000, and the 13 occur identically with the rule Off).
- **Flaky worker-clock test.** The worker localizes its deadline on the injected clock, but the engine judges `performance.now()`; a fake clock of 5000 put the worker deadline in the past once the process was a few seconds old, so worker and main-thread runs diverged under CPU load. Tests now use the real clock with a 600 s duration (47817b0).
- **F3 consequences.** Because never-committed bars only warn, after a Hard Apply the Gantt tool alert can fire on them. This is by design.
- **Split-order nesting.** A split order reserves its segments, not its envelope, so other orders may nest into its gaps; nested placement is more frequent under Hard.
- **Prune-cap change on Off.** `_pruneAgainstLive` now caps its passes at `min(8, kept patches)` on every plant, so Apply without preview and Apply what still fits resolve drop chains of 3-7 instead of refusing them. This is an intentional Off-path change.
- **Zero-copy search perturbation.** Zero-copy tools (qty 0 or all copies out of service) perturb the earlier search slightly, so a Hard run can place a few fewer orders than a pure queue would.
- **Wave 6 validation history.** fed8872 gate on, 5cf2f00 gate off, e18cf6c fixes, 47817b0 clock-pinning tests, 48efba2 M-A fix, Opus verdict SHIP behind a pilot-only Hard toggle, then 44d160a gate on.
