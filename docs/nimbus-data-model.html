How to read these diagrams

NIMBUS's schema has two very different kinds of relationship, and conflating them is the fastest way to misjudge what a migration or a delete is safe to do. Every diagram below is a canvas — scroll/pinch to zoom, drag to pan, double-click to reset, or use the toolbar buttons.

hard foreign key — Postgres enforces it, a bad write is rejected soft reference — same plant/machine/order text, no constraint, no cascade
Why so many soft references

Order data, calendars, blackout blocks, priority lists and setup state are all allowed to reference a plant or machine that master data hasn't caught up to yet — an order can arrive on a machine code before that machine is registered in machine. Hard-FK'ing those tables to master data would mean a scheduler-blocking rejection every time SAP is ahead of the admin tab. The tradeoff: nothing stops a typo'd plant code from silently creating an orphaned calendar or priority list that never joins to anything.

Read this as

A double arrow (==>) is a real FK from plants, cascading on delete. A dashed arrow is a column that holds a plant or machine string with nothing in the database stopping it from pointing at nothing. column_metadata, admin_audit, and schema_migrations aren't drawn here — they describe the system rather than participate in it; see Admin plumbing.

Deliberately not wired in

schema_migrations carries no relationships at all — it's a migration ledger, not business data. column_metadata and admin_audit reference table/column names as free text for any table the admin CRUD registry recognizes, not a fixed set, so a drawn edge would misrepresent them as scoped to one table. Notable

machine.machine_key is a generated column (subnetwork || '_' || plant || '_' || machine) — it exists so downstream tables can carry one stable identity string instead of three, but it's never written to directly and never registered for the Add-Column admin UI, because Postgres rejects writes into a generated column.

material_plants.plant has no FK to plants at all, unlike its FK to materials — a plant can appear here before it's onboarded in the master-data tab.

workcenter_mapping maps a NIMBUS machine to its SAP workcenter code, per plant — like material_plants.default_machine, it has no FK to machine or plants, so a mapping can exist for an order-derived machine that lags master data.

Load-bearing hazard

There is no in-memory order cache anywhere in the backend, so orders.xmin doubles as the optimistic-concurrency base_version the frontend saves against. Any UPDATE orders — even on a column the UI never touches — bumps xmin for every row it touches and makes those rows come back stale on the planner's next save, discarding the in-flight edit (last-writer-loses). This is why the priority-list attribute stamp only ever runs batch-scoped at ingest or on an explicit admin resync call, never as a background sweep.

Notable

Task IDs are stable across reschedules because make_id() hashes only production_order|material_number — no timestamp — which is what lets drag/edit operations key off an id that never changes underneath them.

Sharp edge

setup_occurrence_override references two orders.id values with no foreign key at all. Deleting or re-uploading an order that has an active override silently orphans it rather than cascading or rejecting — the override just stops matching anything at optimizer time.

Notable

color_wheel is superseded by priority_list (Stage 1, 2026-08-11) via a one-time, ledger-guarded backfill — it's kept in place only so the legacy /color-wheel/* endpoints have something to read/write behind their old response shape. There is deliberately no global fallback tier: a plant with nothing uploaded to priority_list just has no entry, full stop.

Domain 8

Admin plumbing 3 tables

Tables that describe the system rather than participate in its business data — none of them FK to anything, by design.

TableKey columnsPurpose
column_metadata(table_name, column_name) PKDisplay label + locked flag for any column the Manage Data Tables UI shows — for any table in ALLOWED_TABLES, not just these 32.
admin_auditid PK (bigserial)One row per DDL change or bulk data operation — table_name/column_name/user_email are plain text, nothing FK'd.

Read before touching orders

schema_migrations exists because a data-mutating statement in schema.sql is otherwise re-run on every apply. The current live example of the pattern it now guards against is the opposite failure mode: the one-time orders_mp_attrs_backfill stamps orders from material_plants and records itself applied even when it matches zero rows — if it runs before a plant's material_plants rows exist, it will never run again for that plant. POST /master-data/resync-order-attributes is the real, repeatable mechanism; this migration is convenience only.
