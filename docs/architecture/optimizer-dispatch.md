# Optimizer Dispatch — `Engine.runAndApply` internals

Full mechanics behind the summary in `CLAUDE.md` → Key Patterns → Optimization. Read this before touching `Engine._sortTerms`, `Engine.evaluateSetupAware`, or anything that reads `Store.priorityRankMaps`.

## Modes

`Engine.runAndApply(mode)` where `mode ∈ {'spt', 'changeover', 'backlog'}`. These are **dispatching heuristics, not true optimization** — there is no finite-capacity constraint, and finish-to-start precedence is not consulted.

- `'spt'` sorts by run-hours ascending across the whole horizon (via `Engine._sortTerms` + a greedy back-to-back placement walk, jumping fixed orders and calendar/blackout-closed windows, with a 200-iteration guard that logs via `ErrorLog.warn` if it fails to converge) — the legacy single-sort walk, still `'spt'`'s only path. `'spt'` only takes the setup-aware evaluator (below) when the plant's real `Store.setupSnapshot` is active-and-matching; otherwise it stays on this walk exactly as before Workstream B.
- `'changeover'` **always** routes through `Engine.evaluateSetupAware('min-changeover', ...)` — see "Setup-aware dispatch" below. As of Workstream B Task 5 (2026-08-21, commit range `1678865..b1b1c01`), this is unconditional: an active-and-matching real `setupSnapshot` is used when one exists, otherwise `Engine._syntheticZeroCostSetupSnapshot(plant)` fabricates a zero-cost stand-in (empty matrix/overrides, `plant_active: true`, a `synthetic: true` marker) purely to satisfy `evaluateSetupAware`'s activation gate. `'changeover'` can no longer take a legacy per-line walk at all — **`Engine._dispatchDayIntegrity` and its inner `seqCompare` were deleted** as dead code once this made them unreachable. The day-integrity tiering they implemented (native/carry/pull-in/floater, the 90-consecutive-zero-admission-day force-place escape hatch) no longer exists in any form; `'changeover'`'s placement decisions are now made entirely by the setup-aware evaluator described below, synthetic-snapshot or not.

**Diagnostic suppression for synthetic runs.** A synthetic run must produce zero visible sign that setup tracking exists — no `toast.optimize_missing_setup_summary` / `toast.optimize_orders_left_in_place` / `toast.optimize_lines_guarded`, all three gated on `!effectiveSetupSnapshot.synthetic` inside `runAndApply`. The synthetic snapshot is a **local variable only**, never assigned to `Store.setupSnapshot` — so `deriveSetupObservation`'s Timeline-bar-rendering path (which always reads `Store.setupSnapshot` directly, never `runAndApply`'s local `effectiveSetupSnapshot`) continues to see the plant's real, inactive snapshot and draws no setup bars, unaffected by the synthetic mechanism.

**Known, accepted side effect — the anchor rule is now universal, not a corner case.** `setup-scheduler.mts`'s pre-existing `initialScheduledAnchor` (an already-dated task starting earliest on a line becomes an immovable anchor whenever that line has no persisted `machine_setup_state` row — protecting a physical predecessor of unknown state from being silently resequenced) now fires on **every** `'changeover'` run for **every** plant that has never configured setup tracking, because the synthetic snapshot's `machine_states` is always `[]`. Before Task 5 this was reachable only by active-setup plants with an uncovered line; it is now the default-Optimize-button experience for the majority of NIMBUS plants. This was ruled *not* a Task 5 defect — Task 5's own parity guarantee (synthetic and real-but-empty-matrix must sequence identically) requires it, and unwinding it is a `setup-scheduler.mts` design decision outside that task's scope, not a mechanical fix. **A candidate narrower fix, not yet built:** gate `initialScheduledAnchor` on the plant's *matrix* being empty (`plant_rows.length === 0 && machine_rows.length === 0`) rather than the *line's* `machine_state` being unrecorded — every transition already resolves to zero cost when the matrix itself is empty, so the anchor's safety rationale (protecting against a wrongly-assumed cost saving around an unknown predecessor) provably cannot apply in that case, whether the empty matrix is synthetic or a genuinely active-but-unconfigured plant. This preserves Task 5's parity guarantee (both sides of the parity still skip the freeze together) while confining the freeze to plants that actually have partial real matrix coverage, where the safety rationale still holds. Whoever next revisits this evaluator's anchor logic should consider it.

## `_sortTerms` — the single source of truth for ordering

Which sort terms exist at all is `Engine._sortTerms(mode, { plant })`'s decision, and every consumer (the `'spt'` legacy walk's comparator, `'changeover'`'s setup-aware evaluator via its own `activePriorityKeys` mirror in `setup-scheduler.mts`) reuses its output verbatim — it is the single source of truth for optimizer ordering.

Since Stage 3 of `docs/scheduling_priority.md`, `_sortTerms` is a **generic term factory**, not a hardcoded color branch: it walks `Engine.activeConstraintKeys(plant)` → `Engine.flattenConstraints(plant)`, a pre-order DFS of the plant's `plants.constraints` JSONB **tree** (a disabled node skips its entire subtree; a duplicate key collapses to its first occurrence and the UI marks it "(no effect)"; a plant with no stored tree falls back to `CONSTRAINT_CATALOG`'s enabled defaults), and pushes one `{get, cmp}` term per key, in tree order, ahead of the intrinsic tail.

Each term's `get()` reads the order's own value for that field — `Engine._taskFieldFor(key)` maps `colorWheel`→`COLOR`, `prt01`→`PRT_01`, `prt02`→`PRT_02`, `productionVersion`→`PRODUCTION_VERSION`, hardcoded as offline defaults that `GET /priority-fields` **merges** over rather than replaces (a `key.toUpperCase()` guess is wrong for 3 of the 4 and would silently rank every order 999999) — and resolves that value's rank **per task, at compare time**, out of `Store.priorityRankMaps`: shape `{line|'': {field_key: {VALUE: RANK}}}`, loaded by `Persistence.loadPriorityRankMaps` from `GET /priority-rank-maps?plant=` (served straight from the in-process `brain.PLANT_LISTS`, zero DB hit).

A line-scoped map wins over the plant-wide `''` map **for the order's current `PRODUCTION_LINE`** — which is exactly why a cross-line drag or an Orders-grid line edit picks up the destination line's ranks with no refetch: **no rank is ever stamped on the order row or the task DTO.**

The sort key is `pad(rank,7) + '|' + normalizedValue` (rank rounded and clamped to `[0, 9999999]` so a fractional or oversized rank can't defeat the fixed width; a non-finite one falls back to unranked), so unranked values — rank `999999` — **group by value after all ranked ones** instead of scattering under later terms. No term is created for a disabled or unconfigured field, so the cost is opt-in: 1 configured field is 4 terms, all 4 fields is 7, measured at ~1.5x end-to-end `runAndApply` time.

## Rank-cache freshness (load-bearing)

`OptimizeDialog.run()` awaits `Persistence.loadPriorityRankMaps(plant)` whenever `Persistence._rankMapsPlant` doesn't match (that marker is set only on a true 2xx) and confirms with the user if it still isn't fresh; `Alerts.applyFix`'s overload branch **cannot** await it (`schedule-services.mts` must not import `schedule-data.mts` — layer direction), so it uses whatever is cached. That is safe only because `Persistence.load()` (plus `_loadCache`/`_loadDemo`) **clears the cache and the marker the moment a plant change is detected** — before `/tasks`, before the master-data fetches, and so before the first `schedule:hydrated` emit renders any Fix button.

**Do not remove that clear**: without it the auto-fix path sequences the newly-loaded plant's orders against the *previous* plant's ranks, which is far harder to spot than the unranked fallback.

`GET /priority-rank-maps` is plant-gated server-side, so `loadPriorityRankMaps` must keep using `Util.fetchTraced` (bare `fetch` sends no identity header and 403s for plant-restricted users).

`Engine._comparator('changeover', …)` no longer reflects the mode's actual placement order (kept only for hypothetical external callers) — see "Setup-aware dispatch" below for the real logic, which now governs `'changeover'` unconditionally.

## Constraint registry

`CONSTRAINT_CATALOG`, populated at boot from `GET /priority-fields` with a hardcoded `colorWheel` offline fallback, plus `constraintsFor` / `constraintEnabled` / `flattenConstraints` / `activeConstraintKeys` / `hasPriorityRanks`, is surfaced as an indented, reorderable tree with a live effective-sequence panel in the per-plant System Settings pane (`Plant._renderSettingsPane`).

All four registered fields are wired into the optimizer; adding a fifth means registering it in `master_data.RANKABLE_FIELDS` on the backend — the frontend picks it up from the registry with no code change, and `Engine._fieldTaskFields`/`_fieldDescriptions` want a matching entry so it survives a failed registry fetch.

## Setup-aware dispatch (`web/setup-scheduler.mts`)

`'changeover'` **always** routes through `Engine.evaluateSetupAware('min-changeover', ...)` as of Workstream B Task 5 — unconditionally, not gated on activation (see "Modes" above for the synthetic-snapshot mechanism that makes this possible for an inactive/unconfigured plant). `'spt'` still only takes this path when a plant's `setup_definition.active` is set via the "Include setup times in optimizer" checkbox (`docs/Setup_matrix_redesign.md` §15) and the real `Store.setupSnapshot` is active-and-matching; otherwise `'spt'` stays on its legacy walk. Full setup-matrix design and semantics live in `docs/changeover_matrix.md`; this section covers the dispatch/control-flow mechanics.

**Never-freeze rule.** The setup-aware evaluator never returns an empty patch set for a line because setup data is incomplete. `searchFragment` partitions each fragment's orders into `known` (a resolvable setup state) and `SearchRun.unknownTail` (blank or unresolvable signatures); the min-changeover permutation search runs over `known` only, so unknown orders are never charged a fake zero-minute setup. Orders with known signatures but uncovered transitions (missing matrix pairs) are admitted *in sequence* within the `known` set, charged zero setup minutes, and de-preferred by a coverage-tier score comparison that counts uncovered edges — fewer is better. This tier is compared immediately after policy key and outside the mode-permuted terms list, ensuring fully-covered sequences still win whenever one exists and that same-signature orders tend to cluster together. Once search completes, `placeUnknownTail(...)` appends the truly unknown orders (blank signatures) *after* the core, ordered by the same `orderedByPolicyThenDue` (SPT: `orderedByProductiveRuntime`) tail ordering used elsewhere, never interleaved — placing each via the real `freeIntervalsFor` capacity and split policy but charging zero minutes to setup/score, and tagging each with the dedicated `'scheduled-without-setup'` missingEdge reason the live-run toast and OptimizerPreview tally consume. A completed `searchFragment` produces a winner in every case except an active-override conflict (`adjacency.issue`) — fail closed by design, not frozen by omission. The line itself is never frozen in the ordinary case; the missing-setup case surfaces as a derived alert instead (see below), not as an unchanged line.

**Coverage-tier score comparison.** The candidate score vector carries a coverage tier (index 6, `SCORE_UNCOVERED`) that counts uncovered edges in a candidate sequence; fewer is better. It is compared immediately after policy key and *outside* the mode-permuted terms list, so a fully-covered candidate always beats an otherwise-identical uncovered one. Because identical complete states resolve to implicit-zero (and thus a covered edge), minimizing uncovered edges is equivalent to minimizing state changes — orders with the same signature tend to cluster together, providing both better behavior (fewer edge gaps) and a principled tie-break when multiple local routes exist. This tier is load-bearing for fixed boundaries — see below.

**Coverage tier and fixed boundaries.** When a fixed boundary exists, `evaluateLineWithFixedBoundaries` enumerates the locally-feasible routes — candidates whose incoming transition and required-last placement both satisfy the boundary's constraints. The coverage tier (counting uncovered edges) breaks ties among multiple feasible routes, preferring the sequence with fewer uncovered edges. A secondary hardening (`candidateEntersBoundaryUncovered`) also excludes a fallback option whose *incoming* transition into the fixed boundary is only "feasible" because of the boundary-leniency in `candidateForSequence` (below) from counting as a genuine covered route, so a single order that can never really enter the boundary doesn't manufacture a false tie-break. This tier is load-bearing: it provides the principled ranking among local routes that a per-line evaluator needs without requiring a full branching planner.

**Ambiguous fixed-boundary routes now tail-place.** When a fixed boundary has multiple locally-feasible routes, the coverage tier (above) provides a principled tie-break: the sequence with fewer uncovered edges wins. If all routes have identical coverage (e.g., all fully covered or all equally uncovered), the coverage tier defers to the next sort term (policy key, then the configured priority fields). If even that produces no winner, `evaluateLineWithFixedBoundaries` tail-places the fragment instead of freezing it — the orders place via the normal tail ordering and real capacity constraints, with zero setup minutes and alerts. This supersedes the earlier scope cut that left such fragments frozen: the coverage tier + tail-place mechanism now provides a principled resolution that respects capacity and prioritization without requiring a full branching planner.

**Unknown initial line state.** `FragmentContext.predecessorState` is nullable. Both evaluators try the scheduled-anchor fallback first; if no anchor exists, the fragment proceeds with `predecessorState = null` instead of skipping the line — the first order places via the zero-minute tail mechanism with an `initial-state-unknown` edge, and chaining continues normally from that order's own (known) state onward. `signature-incompatible` lines route the same way (kept as a diagnostic, not a skip). This does *not* weaken the fixed-boundary/override guards protecting pinned orders — those stay fail-closed: `override-inactive`, `fixed-boundary-invalid`, and protected-fixed-boundary-outside-horizon still preserve the affected run rather than moving it.

**Per-line iteration budget.** `SETUP_AWARE_ITERATION_CAP` (20,000) is constructed **per line**, inside `evaluateDueDateFirst`'s and `evaluateSptWithSetup`'s per-line loop — not once for the whole plant-wide run. A line that exhausts its cap or deadline with no winner falls back to whole-fragment tail placement rather than freezing every line behind it in iteration order.

**Min-changeover per-pass deadlines and starvation guard.** `evaluateMinChangeover` no longer runs its due-safe baseline pass and its candidate pass against one shared wall-clock deadline. The baseline pass gets half the remaining time; the candidate pass runs against the caller's own unmodified `bounds.deadline` — i.e. whatever remains in the original budget, not a fresh half-split of it. If the candidate pass is starved (hits its deadline/iteration limit) and produces no patches — or strictly fewer patched lines — while the baseline has patches, **or the candidate pass completes with zero patches** (no starvation signal, but still nothing gained), the evaluator returns the baseline with reason `min-changeover-starved`: a starved or empty candidate can never beat a non-empty baseline.

**Live-run diagnostics.** `Engine.runAndApply` nulls `Engine.lastSetupAwareResult` at the top of every non-candidate run, then stores the setup-aware result there on a setup-aware apply (mirroring `lastBacklogResult`'s clear-then-set lifecycle), and warns via `Toast` with a summary of distinct orders scheduled without setup data and the affected lines (i18n key `toast.optimize_missing_setup_summary`), counted from the dedicated `'scheduled-without-setup'` missingEdge reason. No new alert wiring is needed — alerts are derived, not evaluator-produced: `deriveSetupObservation` re-derives intervals/diagnostics from the *applied* schedule, and `Alerts.scheduleRecompute()` picks up the resulting `successor-state-unknown` / `setup-uncovered` / `initial-state-unknown` diagnostics as user-facing alerts over the newly applied schedule.

## Search controls (convergence, deadlines, termination)

The setup-aware evaluators (`web/setup-scheduler.mts`) run a bounded search per line, gated by a small set of time/iteration controls and a severity-ordered way to combine each line's outcome into one plant-wide verdict.

- **`SETUP_AWARE_CONVERGENCE_WINDOW` (2000, exported constant).** `exactSearch`/`greedySearch` stop early — before exhausting the deadline or iteration cap — once this many consecutive candidates have been evaluated with no winner improvement *and* a feasible winner already exists, reporting `termination: 'converged'` instead of continuing to burn a plateaued search. Overridable per-run via `bounds.convergenceWindow` (the live engine wiring always passes this constant explicitly; tests shrink it to make a plateau cheap to construct).
  - **Deliberate tradeoff:** `'converged'` counts as **conclusive** (`isSearchConclusive`) and, critically, does **not** set `limitReached` — `limitReached: termination === 'deadline' || termination === 'iteration-cap'` omits it on purpose. A converged run found a real, trustworthy winner (unlike a deadline/iteration-cap cutoff, which may have missed a better candidate), so the preview's "may not be optimal" badge stays hidden. The accepted cost: a plateaued-but-technically-improvable search shows no such badge either, since NIMBUS has no way to distinguish "truly optimal" from "stopped improving for 2000 candidates" from the outside.
- **`SETUP_AWARE_TAIL_OVERRUN_MS` (1000, exported constant).** A **time-based, not iteration-based**, valve on the tail-placement passes (`placeUnknownTail`/`placeWholeLineAsTail`): once wall-clock time exceeds `bounds.deadline` by more than this many milliseconds, the pass stops *attempting* placement and routes every remaining order through the existing `'unknown-setup-tail-unplaced'` diagnostic instead. This preserves the never-freeze invariant (an order is retained at its current dates and surfaced, never silently dropped) while capping how long an already-overrun run can keep trying.
- **Per-line deadline share.** `evaluateDueDateFirst`/`evaluateSptWithSetup` divide whatever wall-clock budget remains **evenly and dynamically** across the lines not yet visited: `lineDeadline = min(bounds.deadline, now + remainingMs / linesRemaining)`, recomputed fresh from the clock on every iteration (not decremented by a fixed slice up front). A line that finishes early lets its unused share roll forward to the lines after it, so one large line can no longer consume the entire run budget and starve everything behind it in iteration order. The iteration cap (`SETUP_AWARE_ITERATION_CAP`, 20,000) is a separate, fresh-per-line budget on top of this — see "Per-line iteration budget" above.
- **Severity-ordered termination aggregation.** Combining N lines' outcomes into one plant-wide `SearchDiagnostics.termination` is not "last write wins" — `worseTermination(current, next)` compares `TERMINATION_SEVERITY`: `deadline (3) > iteration-cap (2) > converged (1) > completed (0)`. A later line's clean `'completed'` can never silently overwrite an earlier line's genuine `'deadline'`/`'iteration-cap'`, which would otherwise falsify `limitReached` for the whole run and defeat `evaluateMinChangeover`'s starvation guard. `'converged'` deliberately outranks `'completed'` (worth surfacing distinctly) but must never be conflated with, or ranked above, a genuine budget cutoff. Every aggregation site that folds a per-line/per-fragment `SearchRun`/`LineSearchResult` termination into a running plant-wide value must route through `worseTermination` rather than assigning directly — a whole-branch review found two direct `termination = fallbackCursor.termination` assignments (the terminal-fixed-boundary fallback paths in `evaluateLineWithFixedBoundaries`) that bypassed this helper and were corrected to route through it.
- **`deadlineAt` option (`EvaluationRequest.deadlineAt`).** An optional absolute `performance.now()` timestamp a caller can supply to override the evaluator's default fresh `SETUP_AWARE_DEADLINE_MS` (5000, `schedule-services.mts`) window. `runAndApply`'s live setup-aware path computes this once (`performance.now() + SETUP_AWARE_DEADLINE_MS`) up front so it is an explicit, inspectable number rather than an implicit "however long is left when the evaluator starts." A past `deadlineAt` is not special-cased — the search simply terminates immediately into tail placement, the existing safe deadline-exceeded path.
- **The deferred Plan B run.** `OptimizerPreview.runWithPreview` evaluates the primary (Plan A) candidate synchronously, paints the preview, and only then — via `requestAnimationFrame` + a `setTimeout(0)` yield to guarantee a paint happens first — evaluates the alternate-mode comparison ("Plan B") off the click path. **Ruling (whole-branch review):** Plan B gets the **same full `SETUP_AWARE_DEADLINE_MS` window** as Plan A, not a reduced budget — an earlier `ALT_PLAN_BUDGET_MS = min(SETUP_AWARE_DEADLINE_MS, 2500)` silently handicapped the comparison with no UI label, and has been removed. Because background time off the click path is acceptable, there is no reason to shortchange Plan B's search quality relative to Plan A's. The deferred callback bails (updates neither `_finalists` nor `_finalistsPending`, issues no render) if the preview is no longer the active one (`OptimizerPreview.active`), a newer run has superseded it (`OptimizerPreview._runSeq !== runSeq`), or the preview has gone stale (`OptimizerPreview.stale`, e.g. a Store setup write landing between paint and this callback) — the last of these guards against Plan B evaluating against setup data Plan A never saw.

## Deliberately out of scope (see `docs/MIGRATION.md`)

A release-date floor on pull-forward, and auto-pinning (in-progress orders, SAP-firmed/FIXKZ orders) — manual pinning (`Store.isFixed`) is the only such protection. Sequence-dependent setup-time minutes are **implemented**, not out of scope — see "Setup-aware dispatch" above and `docs/changeover_matrix.md` for the full setup-aware design.

**Correction — a frozen near-term fence shipped 2026-08-20, it is not out of scope.** `plants.frozen_horizon_days` → `Store.frozenHorizonEnd` is enforced via `Engine.isFrozenHorizon`/`Engine.applyFrozenFloor` at the legacy walk's fixed/free split, the setup-aware evaluator's `fixedIds`, and `autoReflow` — treating a frozen-window order like an implicitly pinned one, same as `Store.isFixed`, at every placement site except one: as of 2026-08-22, `Engine.removeBacklog` ('backlog' mode / "Remove Backlog") is exempt from both the obstacle-skip and the placement floor, by planner decision (SAP002 parity) — its overdue-order compression is meant to reach into the frozen window, shifting frozen orders later (never earlier) as the cursor reaches them, counted in `diagnostics.frozenMoved`.
