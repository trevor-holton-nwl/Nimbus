# Optimizer Dispatch — `Engine.runAndApply` internals

Full mechanics behind the summary in `web/optimization/CLAUDE.md`. Read this before touching `Engine._sortTerms`, `Engine.evaluateSetupAware`, or anything that reads `Store.priorityRankMaps`.

## Modes

`Engine.runAndApply(mode)` where `mode ∈ {'spt', 'changeover', 'duedate', 'backlog'}`. These are **dispatching heuristics, not true optimization** — there is no finite-capacity constraint, and finish-to-start precedence is not consulted.

- `'spt'` uses the setup-aware evaluator's runtime-first search across the plant horizon. Inactive or mismatched setup data is represented by the synthetic zero-cost snapshot, so SPT keeps one mode-specific search and hard-bound contract regardless of setup activation. The legacy single-sort walk remains only as an internal compatibility path.
- `'changeover'` **always** routes through `Engine.evaluateSetupAware('min-changeover', ...)` — see "Setup-aware dispatch" below. As of Workstream B Task 5 (2026-08-21, commit range `1678865..b1b1c01`), this is unconditional: an active-and-matching real `setupSnapshot` is used when one exists, otherwise `Engine._syntheticZeroCostSetupSnapshot(plant)` fabricates a zero-cost stand-in (empty matrix/overrides, `plant_active: true`, a `synthetic: true` marker) purely to satisfy `evaluateSetupAware`'s activation gate. `'changeover'` can no longer take a legacy per-line walk at all — **`Engine._dispatchDayIntegrity` and its inner `seqCompare` were deleted** as dead code once this made them unreachable. The day-integrity tiering they implemented (native/carry/pull-in/floater, the 90-consecutive-zero-admission-day force-place escape hatch) no longer exists in any form; `'changeover'`'s placement decisions are now made entirely by the setup-aware evaluator described below, synthetic-snapshot or not.

**Diagnostic suppression for synthetic runs.** A synthetic run must suppress only `toast.optimize_missing_setup_summary` (gated on `!effectiveSetupSnapshot.synthetic` inside `runAndApply`); the other diagnostics `toast.optimize_orders_left_in_place` and `toast.optimize_lines_guarded` fire regardless of `synthetic` because they report genuine unplaced orders and untouched lines unrelated to setup data, and suppressing them would violate the never-freeze "drops can't happen silently" guarantee. The synthetic snapshot is a **local variable only**, never assigned to `Store.setupSnapshot` — so `deriveSetupObservation`'s Timeline-bar-rendering path (which always reads `Store.setupSnapshot` directly, never `runAndApply`'s local `effectiveSetupSnapshot`) continues to see the plant's real, inactive snapshot and draws no setup bars, unaffected by the synthetic mechanism.

**Known, accepted side effect — the anchor rule is now universal, not a corner case.** `setup-scheduler.mts`'s pre-existing `initialScheduledAnchor` (an already-dated task starting earliest on a line becomes an immovable anchor whenever that line has no persisted `machine_setup_state` row — protecting a physical predecessor of unknown state from being silently resequenced) now fires on **every** `'changeover'` run for **every** plant that has never configured setup tracking, because the synthetic snapshot's `machine_states` is always `[]`. Before Task 5 this was reachable only by active-setup plants with an uncovered line; it is now the default-Optimize-button experience for the majority of NIMBUS plants. This was ruled *not* a Task 5 defect — Task 5's own parity guarantee (synthetic and real-but-empty-matrix must sequence identically) requires it, and unwinding it is a `setup-scheduler.mts` design decision outside that task's scope, not a mechanical fix. **A candidate narrower fix, not yet built:** gate `initialScheduledAnchor` on the plant's *matrix* being empty (`plant_rows.length === 0 && machine_rows.length === 0`) rather than the *line's* `machine_state` being unrecorded — every transition already resolves to zero cost when the matrix itself is empty, so the anchor's safety rationale (protecting against a wrongly-assumed cost saving around an unknown predecessor) provably cannot apply in that case, whether the empty matrix is synthetic or a genuinely active-but-unconfigured plant. This preserves Task 5's parity guarantee (both sides of the parity still skip the freeze together) while confining the freeze to plants that actually have partial real matrix coverage, where the safety rationale still holds. Whoever next revisits this evaluator's anchor logic should consider it.

## `_sortTerms` — the single source of truth for ordering

Which sort terms exist at all is `Engine._sortTerms(mode, { plant })`'s decision, and internal compatibility consumers plus the setup-aware evaluators' priority-key mirror in `web/optimization/setup-scheduler.mts` reuse its ordering rules — it is the single source of truth for optimizer ordering.

Since Stage 3 of `docs/scheduling_priority.md`, `_sortTerms` is a **generic term factory**, not a hardcoded color branch: it walks `Engine.activeConstraintKeys(plant)` → `Engine.flattenConstraints(plant)`, a pre-order DFS of the plant's `plants.constraints` JSONB **tree** (a disabled node skips its entire subtree; a duplicate key collapses to its first occurrence and the UI marks it "(no effect)"; a plant with no stored tree falls back to `CONSTRAINT_CATALOG`'s enabled defaults), and pushes one `{get, cmp}` term per key, in tree order, ahead of the intrinsic tail.

Each term's `get()` reads the order's own value for that field — `Engine._taskFieldFor(key)` maps `colorWheel`→`COLOR`, `prt01`→`PRT_01`, `prt02`→`PRT_02`, `productionVersion`→`PRODUCTION_VERSION`, hardcoded as offline defaults that `GET /priority-fields` **merges** over rather than replaces (a `key.toUpperCase()` guess is wrong for 3 of the 4 and would silently rank every order 999999) — and resolves that value's rank **per task, at compare time**, out of `Store.priorityRankMaps`: shape `{line|'': {field_key: {VALUE: RANK}}}`, loaded by `Persistence.loadPriorityRankMaps` from `GET /priority-rank-maps?plant=` (served straight from the in-process `brain.PLANT_LISTS`, zero DB hit).

A line-scoped map wins over the plant-wide `''` map **for the order's current `PRODUCTION_LINE`** — which is exactly why a cross-line drag or an Orders-grid line edit picks up the destination line's ranks with no refetch: **no rank is ever stamped on the order row or the task DTO.**

The sort key is `pad(rank,7) + '|' + normalizedValue` (rank rounded and clamped to `[0, 9999999]` so a fractional or oversized rank can't defeat the fixed width; a non-finite one falls back to unranked), so unranked values — rank `999999` — **group by value after all ranked ones** instead of scattering under later terms. No term is created for a disabled or unconfigured field, so the cost is opt-in: 1 configured field is 4 terms, all 4 fields is 7, measured at ~1.5x end-to-end `runAndApply` time.

## Rank-cache freshness (load-bearing)

`OptimizeDialog.run()` awaits `Persistence.loadPriorityRankMaps(plant)` whenever `Persistence._rankMapsPlant` doesn't match (that marker is set only on a true 2xx) and confirms with the user if it still isn't fresh; `Alerts.applyFix`'s overload branch **cannot** await it (`web/insights/services.mts` must not import `web/scheduling/persistence.mts` — layer direction), so it uses whatever is cached. That is safe only because `Persistence.load()` (plus `_loadCache`/`_loadDemo`) **clears the cache and the marker the moment a plant change is detected** — before `/tasks`, before the master-data fetches, and so before the first `schedule:hydrated` emit renders any Fix button.

**Do not remove that clear**: without it the auto-fix path sequences the newly-loaded plant's orders against the *previous* plant's ranks, which is far harder to spot than the unranked fallback.

`GET /priority-rank-maps` is plant-gated server-side, so `loadPriorityRankMaps` must keep using `Util.fetchTraced` (bare `fetch` sends no identity header and 403s for plant-restricted users).

`Engine._comparator('changeover', …)` no longer reflects the mode's actual placement order (kept only for hypothetical external callers) — see "Setup-aware dispatch" below for the real logic, which now governs `'changeover'` unconditionally.

## Constraint registry

`CONSTRAINT_CATALOG`, populated at boot from `GET /priority-fields` with a hardcoded `colorWheel` offline fallback, plus `constraintsFor` / `constraintEnabled` / `flattenConstraints` / `activeConstraintKeys` / `hasPriorityRanks`, is surfaced as an indented, reorderable tree with a live effective-sequence panel in the per-plant System Settings pane (`Plant._renderSettingsPane`).

All four registered fields are wired into the optimizer; adding a fifth means registering it in `master_data.RANKABLE_FIELDS` on the backend — the frontend picks it up from the registry with no code change, and `Engine._fieldTaskFields`/`_fieldDescriptions` want a matching entry so it survives a failed registry fetch.

## Setup-aware dispatch (`web/optimization/setup-scheduler.mts`)

`'changeover'` **always** routes through `Engine.evaluateSetupAware('min-changeover', ...)` as of Workstream B Task 5 — unconditionally, not gated on activation (see "Modes" above for the synthetic-snapshot mechanism that makes this possible for an inactive/unconfigured plant). `'duedate'` uses the same seam with its delivery-first comparator, and `'spt'` uses it with its runtime-first comparator. An inactive or mismatched `Store.setupSnapshot` is replaced by the synthetic zero-cost snapshot for all three modes, so setup activation cannot change which optimizer algorithm runs. Full setup-matrix design and semantics live in `docs/changeover_matrix.md`; this section covers the dispatch/control-flow mechanics.

**Never-freeze rule.** The setup-aware evaluator never returns an empty patch set for a line because setup data is incomplete. `searchFragment` partitions each fragment's orders into `known` (a resolvable setup state) and `SearchRun.unknownTail` (blank or unresolvable signatures); the min-changeover permutation search runs over `known` only, so unknown orders are never charged a fake zero-minute setup. Orders with known signatures but uncovered transitions (missing matrix pairs) are admitted *in sequence* within the `known` set, charged zero setup minutes, and de-preferred by a coverage-tier score comparison that counts uncovered edges — fewer is better. This tier is compared immediately after policy key and outside the mode-permuted terms list, ensuring fully-covered sequences still win whenever one exists and that same-signature orders tend to cluster together. Once search completes, `placeUnknownTail(...)` appends the truly unknown orders (blank signatures) *after* the core, ordered by the same `orderedByPolicyThenDue` (SPT: `orderedByProductiveRuntime`) tail ordering used elsewhere, never interleaved — placing each via the real `freeIntervalsFor` capacity and split policy but charging zero minutes to setup/score, and tagging each with the dedicated `'scheduled-without-setup'` missingEdge reason the live-run toast and OptimizerPreview tally consume. A completed `searchFragment` produces a winner in every case except an active-override conflict (`adjacency.issue`) — fail closed by design, not frozen by omission. The line itself is never frozen in the ordinary case; the missing-setup case surfaces as a derived alert instead (see below), not as an unchanged line.

**Bounded quality search.** Exact fragments enumerate their declared occurrence space. Larger fragments use deterministic mode-specific seeds and bounded insertion/swap neighborhoods through the same `candidateForSequence` path: setup-nearest/grouped/policy/runtime for Min Changeover, due/slack/runtime/policy/source for Due Date, and runtime/due/policy/current-order for SPT. `SearchDiagnostics.seedCount` and `localMoveCount` expose the attempted work. SPT keeps the runtime-first result for equal admission and permits an alternate seed to win only when it admits more urgent work; fixed machine assignment, hard bounds, active overrides and coverage diagnostics remain unchanged.

**Coverage-tier score comparison.** The candidate score vector carries a coverage tier (index 6, `SCORE_UNCOVERED`) that counts uncovered edges in a candidate sequence; fewer is better. It is compared immediately after policy key and *outside* the mode-permuted terms list, so a fully-covered candidate always beats an otherwise-identical uncovered one. Because identical complete states resolve to implicit-zero (and thus a covered edge), minimizing uncovered edges is equivalent to minimizing state changes — orders with the same signature tend to cluster together, providing both better behavior (fewer edge gaps) and a principled tie-break when multiple local routes exist. This tier is load-bearing for fixed boundaries — see below.

**Coverage tier and fixed boundaries.** When a fixed boundary exists, `evaluateLineWithFixedBoundaries` enumerates the locally-feasible routes — candidates whose incoming transition and required-last placement both satisfy the boundary's constraints. The coverage tier (counting uncovered edges) breaks ties among multiple feasible routes, preferring the sequence with fewer uncovered edges. A secondary hardening (`candidateEntersBoundaryUncovered`) also excludes a fallback option whose *incoming* transition into the fixed boundary is only "feasible" because of the boundary-leniency in `candidateForSequence` (below) from counting as a genuine covered route, so a single order that can never really enter the boundary doesn't manufacture a false tie-break. This tier is load-bearing: it provides the principled ranking among local routes that a per-line evaluator needs without requiring a full branching planner.

**Ambiguous fixed-boundary routes now tail-place.** When a fixed boundary has multiple locally-feasible routes, the coverage tier (above) provides a principled tie-break: the sequence with fewer uncovered edges wins. If all routes have identical coverage (e.g., all fully covered or all equally uncovered), the coverage tier defers to the next sort term (policy key, then the configured priority fields). If even that produces no winner, `evaluateLineWithFixedBoundaries` tail-places the fragment instead of freezing it — the orders place via the normal tail ordering and real capacity constraints, with zero setup minutes and alerts. This supersedes the earlier scope cut that left such fragments frozen: the coverage tier + tail-place mechanism now provides a principled resolution that respects capacity and prioritization without requiring a full branching planner.

**Unknown initial line state.** `FragmentContext.predecessorState` is nullable. Both evaluators try the scheduled-anchor fallback first; if no anchor exists, the fragment proceeds with `predecessorState = null` instead of skipping the line — the first order places via the zero-minute tail mechanism with an `initial-state-unknown` edge, and chaining continues normally from that order's own (known) state onward. `signature-incompatible` lines route the same way (kept as a diagnostic, not a skip). This does *not* weaken the fixed-boundary/override guards protecting pinned orders — those stay fail-closed: `override-inactive`, `fixed-boundary-invalid`, and protected-fixed-boundary-outside-horizon still preserve the affected run rather than moving it.

**Calendar and run clocks.** `respectCalendar` defaults to `true` and is applied consistently to production, setup reservation, validation and gap fill. `false` uses continuous capacity while retaining protected occupancy, hard dates and horizon bounds. `planningStart` defines eligibility; `runNow` is the captured wall-clock instant used for frozen/protected decisions; `placementStart = max(planningStart, runNow)` is the floor for new work. A scheduled interval wholly outside `[planningStart, horizonEnd)` remains unchanged and out of dispositions. Queued demand with no committed interval remains eligible for repair; one-sided, reversed or otherwise malformed scheduled intervals stay outside the mutable scope until explicit data repair. Reversed or empty horizons return `status: 'invalid_horizon'` with no patches.

**Snapshot/apply boundary.** `snapshotSchedule` captures cloned tasks, calendars, blocks, master data, priority ranks, setup truth, frozen-horizon metadata and `readModelVersion`. The worker receives only this clone-safe read model. `validateCandidate` compares the captured revision with the live snapshot at Apply and returns `stale_candidate` before any mutation when the model changed; validation also retains the full captured state for deterministic structural checks.

**Global primary search budget.** One `SearchBudget` is constructed per evaluator invocation and passed through every selected line, fragment, and boundary fallback. The absolute deadline and iteration cap are monotonic and diagnostics aggregate the worst termination (`deadline` > `iteration-cap` > `converged` > `completed`). A timeout preserves any valid incumbent and tail-places remaining demand with an explicit incomplete-search reason rather than freezing later lines. Exact search runs only when a fragment has at most 500 distinct orderings (F1: the multiset leaf count, in addition to the `exactSearchThreshold` state limit); every other fragment takes the bounded heuristic path. Calendar windows are served from a per-run, per-line free-interval index (F2), and the iteration cap is 20,000 × the lines in scope (F4; the plant's own lines when `opts.lines` is absent).

**Min Changeover search.** `evaluateMinChangeover` runs a single `evaluateDueDateFirst(..., 'min-changeover')` pass; there is no due-date-first baseline and no baseline/candidate arbitration. Candidates compare admitted order count first (more is better), then hard errors, over-cap (the push-forward limit), uncovered edges, setup minutes, policy key, then lateness (count, minutes, worst case), scheduled count, instability and sequence key — so due dates only break ties and the pull-forward floor stays a hard placement clamp. `finalizeCandidate` keeps the current schedule only when the new plan schedules fewer orders (by count). The result carries explanation code `min-changeover-selected`.

**Live-run diagnostics.** `Engine.runAndApply` nulls `Engine.lastSetupAwareResult` at the top of every non-candidate run, then stores the setup-aware result there on a setup-aware apply (mirroring `lastBacklogResult`'s clear-then-set lifecycle), and warns via `Toast` with a summary of distinct orders scheduled without setup data and the affected lines (i18n key `toast.optimize_missing_setup_summary`), counted from the dedicated `'scheduled-without-setup'` missingEdge reason. No new alert wiring is needed — alerts are derived, not evaluator-produced: `deriveSetupObservation` re-derives intervals/diagnostics from the *applied* schedule, and `Alerts.scheduleRecompute()` picks up the resulting `successor-state-unknown` / `setup-uncovered` / `initial-state-unknown` diagnostics as user-facing alerts over the newly applied schedule.

### Due-date push-forward limit (max lateness cap)

**Per-plant cap on order lateness.** `plants.max_push_forward_days` (nullable INTEGER ≥ 0; NULL = no limit, default) constrains how far an order's scheduled end can drift past its SAP due date — "over cap" when scheduled `end_date` > (original due date local midnight) + (N+1) calendar days. `Engine.latestAllowedEnd(task, plant)` computes the per-order ceiling. The setup-aware evaluator appends an 8th score tier `score[7]` (`SCORE_OVER_CAP`), populated by `candidateForSequence` via a simulation cursor that counts over-cap orders in the sequence; compared immediately after `policyKey` and **before** the coverage tier `score[6]`, a deliberate decision so the cap can beat pure changeover grouping or the feature is moot. Min Changeover ranks over-cap ahead of setup (no baseline gate; the single search simply prefers fewer over-cap orders). The internal compatibility SPT walk uses pure helper `capAwareSequence` (scheduler-contract.mts) to re-order the SPT list, pulling a still-savable capped order ahead only when the SPT head would push it past its latest allowed start. The setup-aware SPT evaluator applies the same cap facts through its candidate comparator. Default-off (NULL) is a no-op: all score[7]=0, ranking unchanged. Since 2026-10-20 the ceiling is HARD: an order that cannot finish within it is queued as Needs Planning (`push_limit_unmet`), never placed past it, so `score[7]` is zero for every unprotected order and only counts a protected/firmed order already past its ceiling (kept for score-vector arity). The post-run toast and preview banner that used to tally violations were removed. Remove Backlog (which also ignores the pull-forward floor), manual drag, Alerts auto-fix and autoReflow ignore the cap.

### Due Date mode

**Dispatch and ranking heuristics.** `'duedate'` mode is dispatched like `'changeover'` — always through the setup-aware evaluator (`Engine.evaluateSetupAware('due-date', …)`), with a synthetic zero-cost snapshot when the plant has no active-and-matching setup definition. Its ranking order is hard → over-cap → late count → late hours → priority-list order → coverage → −patches → setup minutes, implemented via `compareDueDateCandidate`, where lateness tiers outrank both the configured priority fields and same-signature grouping. Large fragments compare deterministic due, slack, runtime, policy and source-order seeds, plus bounded insertion/swap neighbors. `compareBoundaryFallback` receives `mode` to adapt fixed-boundary tie-breaking. Coverage-rejection diagnostics (`appendRejectedCoverageDiagnostics`) are suppressed for this mode because its winner is not guaranteed minimal-coverage — a due-date-optimal sequence may leave some transitions uncovered if the covered alternative would increase lateness. Pull-forward hard floor, anchor freeze, split-never day skip, and firmed-gap partition all still apply identically to every mode.

## Search controls (convergence, deadlines, termination)

The setup-aware evaluators (`web/optimization/setup-scheduler.mts`) run a bounded search per line, gated by a small set of time/iteration controls and a severity-ordered way to combine each line's outcome into one plant-wide verdict.

- **`SETUP_AWARE_CONVERGENCE_WINDOW` (2000, exported constant).** `exactSearch`/`greedySearch` stop early — before exhausting the deadline or iteration cap — once this many consecutive candidates have been evaluated with no winner improvement *and* a feasible winner already exists, reporting `termination: 'converged'` instead of continuing to burn a plateaued search. Overridable per-run via `bounds.convergenceWindow` (the live engine wiring always passes this constant explicitly; tests shrink it to make a plateau cheap to construct).
  - **Deliberate tradeoff:** `'converged'` counts as **conclusive** (`isSearchConclusive`) and, critically, does **not** set `limitReached` — `limitReached: termination === 'deadline' || termination === 'iteration-cap'` omits it on purpose. A converged run found a real, trustworthy winner (unlike a deadline/iteration-cap cutoff, which may have missed a better candidate), so the preview's "may not be optimal" badge stays hidden. The accepted cost: a plateaued-but-technically-improvable search shows no such badge either, since NIMBUS has no way to distinguish "truly optimal" from "stopped improving for 2000 candidates" from the outside.
- **`SETUP_AWARE_TAIL_OVERRUN_MS` (1000, exported constant).** A **time-based, not iteration-based**, valve on the tail-placement passes (`placeUnknownTail`/`placeWholeLineAsTail`): once wall-clock time exceeds `bounds.deadline` by more than this many milliseconds, the pass stops *attempting* placement and routes every remaining order through the existing `'unknown-setup-tail-unplaced'` diagnostic instead. This preserves the never-freeze invariant (an order is retained at its current dates and surfaced, never silently dropped) while capping how long an already-overrun run can keep trying.
- **Global primary budget.** evaluateDueDateFirst and evaluateSptWithSetup reuse one absolute wall-clock deadline and iteration cap across every selected line and fragment. Min Changeover uses the same SearchBudget for its search, and all boundary fallbacks consume it too. A line that finishes early leaves work for later lines; a cutoff is aggregated by severity and reported as incomplete. Exact search runs only for fragments with ≤500 distinct orderings (F1), the per-run free-interval index serves placement windows (F2), and the iteration cap is 20,000 × lines in scope (F4).
- **Severity-ordered termination aggregation.** Combining N lines' outcomes into one plant-wide `SearchDiagnostics.termination` is not "last write wins" — `worseTermination(current, next)` compares `TERMINATION_SEVERITY`: `deadline (3) > iteration-cap (2) > converged (1) > completed (0)`. A later line's clean `'completed'` can never silently overwrite an earlier line's genuine `'deadline'`/`'iteration-cap'`, which would otherwise falsify `limitReached` for the whole run and defeat `evaluateMinChangeover`'s starvation guard. `'converged'` deliberately outranks `'completed'` (worth surfacing distinctly) but must never be conflated with, or ranked above, a genuine budget cutoff. Every aggregation site that folds a per-line/per-fragment `SearchRun`/`LineSearchResult` termination into a running plant-wide value must route through `worseTermination` rather than assigning directly — a whole-branch review found two direct `termination = fallbackCursor.termination` assignments (the terminal-fixed-boundary fallback paths in `evaluateLineWithFixedBoundaries`) that bypassed this helper and were corrected to route through it.
- **`deadlineAt` option (`EvaluationRequest.deadlineAt`).** An optional absolute `performance.now()` timestamp a caller can supply to override the evaluator's default fresh `SETUP_AWARE_DEADLINE_MS` (5000, `web/optimization/engine.mts`) window. `runAndApply`'s live setup-aware path computes this once (`performance.now() + SETUP_AWARE_DEADLINE_MS`) up front so it is an explicit, inspectable number rather than an implicit "however long is left when the evaluator starts." A past `deadlineAt` is not special-cased — the search simply terminates immediately into tail placement, the existing safe deadline-exceeded path.
- **Cancellable worker previews.** `OptimizerPreview.runWithPreview` routes setup-aware primary and alternate candidates through `optimizer-worker-client.mts`, using `optimizer-worker.mts` for module-worker execution and run IDs/`AbortSignal` to terminate stale work. The client falls back to the synchronous detached evaluator when Workers are unavailable or disabled, preserving tests and non-UI callers. Each candidate keeps its own absolute five-second diagnostics; stale responses update neither the active preview nor its finalist state.
- **Search controls (Run in background): `EvaluationRequest.searchBudgetMs` / `exhaustive`.** `searchBudgetMs` sets the primary deadline and scales the iteration cap (20 000 × lines in scope × scale, scale = max(1, budget / 5 000)); `exhaustive: true` also enables the Exhaustive knobs. The Optimize dialog's Run in background checkbox picks Normal (unticked, 8 s, foreground) or Exhaustive (ticked, up to 3 min, background; the dialog shows no durations); alternate (comparison) plans always use Normal with `exhaustive: false`. The bounds builder in `engine.mts` derives these values:

  | Derived value | Absent | Normal (`SETUP_AWARE_NORMAL_BUDGET_MS`, 8 000 ms) | Exhaustive (`SETUP_AWARE_EXHAUSTIVE_BUDGET_MS`, 180 000 ms) |
  |---|---|---|---|
  | `exhaustive` | false | false | true |
  | Primary deadline | 5 000 ms (`SETUP_AWARE_DEADLINE_MS`) | 8 000 ms | 180 000 ms |
  | Iteration-cap scale | 1 | 1.6 | 36 |
  | Iteration cap per line in scope | 20 000 | 32 000 | 720 000 |
  | `gapFillBudgetMs` | 1 000 | 2 000 | 36 000 |
  | `exactSearchThreshold` | 8 | 8 | 10 |
  | `exactSearchLeafCap` | 500 | 500 | 5 000 |
  | `convergenceWindow` | 2 000 | 2 000 | 10 000 |

## Deliberately out of scope (see `docs/MIGRATION.md`)

A release-date floor on pull-forward, and auto-pinning (in-progress orders, SAP-firmed/FIXKZ orders) — manual pinning (`Store.isFixed`) is the only such protection. Sequence-dependent setup-time minutes are **implemented**, not out of scope — see "Setup-aware dispatch" above and `docs/changeover_matrix.md` for the full setup-aware design. Maximum push-forward lateness is also **implemented** — see "Due-date push-forward limit" above.

**Correction — a frozen near-term fence shipped 2026-08-20, it is not out of scope.** `plants.frozen_horizon_days` → `Store.frozenHorizonEnd` is enforced via `Engine.isFrozenHorizon` (FINISH-based since 2026-10-27: planned finish in `[now, frozenHorizonEnd)`; a straddler that starts inside and finishes after the edge is not frozen) at the setup-aware evaluator's `fixedIds`, `autoReflow`, and the validator's protection checks — treating a frozen-window order like an implicitly pinned one, same as `Store.isFixed`. The placement floor is a separate FINISH floor (`Engine.frozenFinishFloor(runNow, snapshot.frozenHorizonEnd)` → `DueDateFirstBounds.finishFloor`, serialized through the worker contract): no unprotected order may finish before it, applied at `candidateForSequence`, the unknown tail, `fillPlanningGaps` and `autoReflow` through `placeWithFinishFloor` (closed form for `never`, a bounded bisect for split-capable policies, free intervals rebuilt on every attempt because `freeIntervalsForPlacement` stops at the first fitting interval). `earliestAllowedStart` is now the pull-forward start floor only (`applyFrozenFloor` is gone). As of 2026-08-22, `Engine.removeBacklog` ('backlog' mode / "Remove Backlog") is exempt from both the obstacle-skip and the finish floor (`backlogBounds` sets no `finishFloor`), by planner decision (SAP002 parity) — its overdue-order compression is meant to reach into the frozen window, shifting frozen (and running) orders later as the cursor reaches them, counted in `diagnostics.frozenMoved`.

**Future capability boundary.** The current optimizer preserves each order's assigned machine and does not solve cross-machine reassignment, labor availability, material availability, or finish-to-start precedence. Those require a separate constraint model, admission policy and validation contract; they remain documented roadmap work rather than implicit fallback behavior in the setup-aware search.
