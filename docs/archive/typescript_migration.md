# TypeScript Migration

> **Archive note (P6, 2026-09-01):** this doc's Phases 0-7 were executed and are historically accurate for the 7 CQ-1 mega-modules named below, but those files no longer exist — the domain-refactor split (see `docs/architecture/domain-refactor-plan.md`) broke each of them into per-domain files under `web/<domain>/`. **Current module ownership lives in the per-domain `CLAUDE.md` network** (root `CLAUDE.md`'s directory table is the index); treat every `web/schedule-*.mts`/`web/plant-and-administration.mts`/`web/application-shell.mts` path below as historical, not live.

Tracks NIMBUS's frontend migration from untyped vanilla JS to real, compiled TypeScript. This is a multi-session effort — update the phase table below as work lands, the same way `docs/MIGRATION.md` tracks other long-running follow-up work.

> **This document is deliberately front-loaded.** The [Codebase migration map](#codebase-migration-map-read-before-any-phase) section below captures a full read of the ~25k-line frontend done up front (bridge topology, every domain data shape, the string-enum inventory, the API/persistence contract surface, and the `.d.ts`-vs-reality drift list). It exists so each future phase reads *findings here* instead of re-deriving them from the source every time — the analysis was the expensive part; spend it once. When a phase lands, correct anything here that turned out wrong rather than letting it rot.

## Why

NIMBUS's frontend (~25k lines across `app.js`, `nimbus-intelligence.js`, `nimbus-compute-core.js`, and 7 CQ-1 ES modules under `web/`) is entirely untyped, with no build step — files load directly via CDN `<script>` tags. That's fine for a prototype; it's the clearest gap between "prototype that grew" and "engineered enterprise system" for a live production scheduling tool with a stated roadmap to scale further (see `CLAUDE.md` → Production Scale Roadmap).

The chosen approach is real `.ts` files compiled by a real build step — not JSDoc-only advisory typing — on the reasoning that a type error should be load-bearing (it blocks a build) rather than merely advisory (a lint warning someone can ignore). That's a bigger lift than JSDoc, accepted deliberately in exchange for a stronger guarantee.

## Design decisions (Phase 0, validated against the real repo)

- **Compiler: `tsc` alone.** No esbuild/webpack. The scope of any given phase is a handful of files; `tsc` handles both type-checking and per-file emission, keeping new tooling to one devDependency — matching `eslint.config.js`'s own stated philosophy of minimal, purposeful tooling rather than a broad framework.
- **Compiled output lives in place.** `web/schedule-state.mts` compiles to `web/schedule-state.mjs` right next to it (gitignored, regenerated by `npm run build`). This required zero changes to `app-entry.mjs`'s import specifiers, `index.html`, `brain.py`'s `STATIC_DIR`, or any test import path. The alternative — a separate `web/dist/` — would have forced rewriting all of those and re-architecting the static-serving boundary for no real benefit at this scale.
- **Two separate tsconfigs, not one** — a real finding from actually running the build, not anticipated in the original design: `tsconfig.json` (browser ESM modules, `module`/`moduleResolution: "nodenext"`, `lib: ["es2022", "dom"]`) covers future `.mts` modules, while `tsconfig.worker.json` (`module: "none"`, `lib: ["es2022", "webworker"]`) covers `nimbus-worker.ts` alone. Reason: under `"nodenext"`, TypeScript mirrors Node's real loader semantics, where *every* plain `.ts` file is treated as a module (and gets a CommonJS `__esModule` marker) regardless of whether it has import/export syntax — correct for Node/bundler-consumed files, but wrong for a classic worker script loaded via `importScripts()`, which must have zero module wrapper (a Web Worker has no `exports`/`module` global; the marker throws at runtime). `"module": "none"` is tsc's genuine classic-script emit mode. Splitting by execution context this way also sidesteps any `dom`/`webworker` lib clash entirely (each config only declares the lib it needs) — cleaner than trying to share one lib array across both. `strict: true` from day one in both, not a ratchet — `include` only ever lists files actively, deliberately being converted, so there's no legacy-strict-debt to manage. `npm run typecheck`/`npm run build` run both configs in sequence.
- **`nimbus-compute-core.js` (the UMD file) is never compiled by tsc.** It's left byte-for-byte as-is. A hand-written ambient `web/nimbus-compute-core.d.ts` gives other converted files real type-checking against its shape (`computeAlerts`, `computeUtilization`, the calendar helpers, the constants) without risking its three-way Node/worker/browser export branch, which `tsc --module umd` cannot reproduce faithfully (it doesn't special-case `self` vs `window` the way this file's own `(typeof self !== 'undefined' ? self : this)` does, and it would add an AMD `define()` branch that has never existed here). `tests/js/compute-core.test.js` pins this file's behavior byte-for-byte across all three consumers — not the file to take an unforced tooling risk on.
- **`nimbus-worker.js` → `nimbus-worker.ts`** is the Phase 0 pilot conversion: it has no top-level `import`/`export`, so TypeScript treats it as a global script and emits plain unwrapped `.js` — identical runtime shape, now type-checked. **Trap:** never add a top-level import/export to this file — the moment one appears, TS reclassifies it as a module and the emitted shape changes (adds `Object.defineProperty(exports, ...)`), silently breaking the classic-worker-script contract `nimbus-worker.js` depends on. Ambient globals (from a `.d.ts`) don't require an import statement, so referencing `NimbusComputeCore`'s ambient type doesn't trip this.
- **CDN libraries (AG Grid / vis-timeline / Flatpickr): hand-written minimal ambient `.d.ts`** (`web/types/vendor.d.ts`), not `@types/...` packages. Installing real type packages creates a second version to keep in lockstep with the CDN-pinned versions actually loaded in `index.html` (`ag-grid-community@31.3.2`, `vis-timeline@7.7.3`, `flatpickr@4.6.13`) — a mismatch there is a silent "types describe a runtime you didn't install" trap. This mirrors what `eslint.config.js`'s `CDN_GLOBALS` already does for lint purposes, and the actually-used surface is already enumerated by `tests/modules/helpers/load-legacy-app.mjs`'s CDN stubs.
- **ESLint gap closed via `typescript-eslint`.** `.mts`/`.ts` files contain syntax ESLint's default `espree` parser can't parse, and no existing flat-config block or npm-script glob matched `.mts` — meaning newly-converted files would have silently stopped being linted at all. Fixed by adding a new flat-config block using `typescript-eslint`'s parser, reusing the same `SHARED_RULES` philosophy with TS-aware equivalents (e.g. `@typescript-eslint/no-unused-vars`), and adding the glob to `lint`/`lint:ci`/`lint:errors`. Note the TS-eslint blocks run **without** `parserOptions.project`, so they are syntactic-only — the real type gate is `npm run typecheck`, by design.
- **CI/Docker wiring:** `npm run build` is wired as `pretest` (so `npm test` always sees fresh compiled output with zero new CI-specific plumbing); a new explicit `npm run typecheck` step runs right after `npm ci` in `.github/workflows/ci.yml` for a clean, fast-failing, clearly-labeled signal distinct from the ESLint/test steps. `Dockerfile` gains a `node:20-slim` builder stage that runs `npm ci && npm run build` before the existing Python runtime stage's `COPY --from=webbuild`. Ordering `COPY web ./web` before `RUN npm run build` in that stage means Docker's layer cache invalidates correctly whenever any file under `web/` changes — no stale-compiled-output risk from caching. **Docker gotcha fixed 2026-07-28:** the builder stage must `COPY` *both* tsconfigs (`npm run build` runs `tsc -p tsconfig.worker.json` first), and `.dockerignore` must **not** strip `package.json`/`package-lock.json` (the builder needs them for `npm ci`) — both were wrong when Phase 0 first landed and would have failed the image build. See [Traps](#common-migration-mistakes-nimbus-specific) T-10/T-11.
- **`scripts/check-static-assets.mjs`**: `.mts`/`.ts` added to `ALLOWED_EXTENSIONS` — `.ts` source ships alongside its own compiled output inside the image, which is a non-issue for an internal single-container tool (not a public artifact). No changes needed to the import-closure walker: new `.mts` files keep writing full `.mjs`-suffixed import specifiers (e.g. `from './foo.mjs'`), which is both the codebase's existing style and the required convention under `nodenext` resolution — TypeScript is designed for source to reference the specifier the *compiled* file will have, not the `.mts` source extension.
- **Known, accepted regression:** editing a `.mts`/`.ts` file requires `npm run build` before `uvicorn brain:api` serves fresh output — `CLAUDE.md`'s "single command" dev flow no longer holds for converted files. Mitigated with a `tsc --watch` script to run in a second terminal alongside `uvicorn --reload`; documented plainly in `CLAUDE.md` rather than papered over.

## Codebase migration map (read before any phase)

*Full read of the frontend, 2026-07-28. File:line references are to the state at that date — verify before relying on an exact line, but the shapes and topology are the durable part.*

### A. Module topology — where types flow, and the three seams where they die

The 7 CQ-1 modules already form a **real, acyclic static-`import` DAG** among themselves. `app-entry.mjs` imports all seven as namespaces and assigns them onto `window.__NIMBUS_*` globals purely to hand them across the ESM→classic-script boundary into `app.js`, then **deletes those globals after boot** (`app-entry.mjs:20-51`) — the bridge is a transient hand-off, not a stable API.

```
application-foundation  (leaf: zero imports; only reads window.* env globals)
        ↑
   schedule-state
        ↑
   ┌────┴────┐
schedule-services  schedule-data
   └────┬────┘
 schedule-workbench
        ↑
plant-and-administration
        ↑
 application-shell
```

Verbatim intra-module imports (top of each file): `schedule-state.mjs:6` ← foundation; `schedule-services.mjs:33-34` ← foundation, state; `schedule-data.mjs:36-37` ← foundation, state; `schedule-workbench.mjs:143-146` ← foundation, state, services, data; `plant-and-administration.mjs:40-44` ← foundation, state, services, data, workbench; `application-shell.mjs:32-37` ← foundation, state, services, data, workbench, plant-admin.

**Implication for the migration: types flow cleanly *within* this DAG.** Once two modules are `.mts`, the `import` edge between them is fully type-checked. That is the entire payoff engine of Phases 1–7. But three boundaries defeat the type system and **must be bridged with hand-authored `.d.ts`/`declare` shims — never "fixed" into imports** (doing so re-introduces the cycles these seams exist to break):

1. **The `window.__NIMBUS_*` bridge → `app.js`.** `app.js:271` does `const { Store, … } = window.__NIMBUS_STATE;`. `app.js` is a classic, untyped script, so every module's type dies here. `app.js` then re-collects all ~40 module objects into a `const NIMBUS = {…}` namespace (`app.js:719-730`) — the widest type sink in the codebase.
2. **The ambient bare-identifier `NIMBUS` global.** The upper three modules (`workbench`, `plant-admin`, `shell`) *and* all of `nimbus-intelligence.js` reach `NIMBUS.Foo.bar()` **at call time** through realm-shared classic-script lexical scope (e.g. `schedule-workbench.mjs:713` `NIMBUS.Inspector.show`, `application-shell.mjs:239-252` `NIMBUS.Timeline/.Table/…`, `nimbus-intelligence.js:28` `const { Store, … } = NIMBUS`). `NIMBUS` is neither an import nor a `window` property — it is `app.js`'s top-level `const`. `nimbus-intelligence.js`'s `window.NIMBUS && …` fallback branches (`:22-23,354,470`) are **dead code** — `window.NIMBUS` is never assigned. Typing any of this requires a hand-authored `declare const NIMBUS: {…}` global.
3. **The imperative DI resolver seams** wired in `app.js:281-306` (table below). A type checker verifies each setter's *signature* but cannot verify the seam was actually wired — forgetting the call compiles clean and fails only at runtime.

These seams are also **deliberate cycle-breakers.** The bare-`NIMBUS` reaches point *upward* in the DAG (e.g. `workbench` reaching `NIMBUS.App.*`, where `App` lives in `shell`, which already imports `workbench`) or *sideways into the non-module* `nimbus-intelligence.js` (`NIMBUS.Confidence`, `NIMBUS.DarkMode`, `NIMBUS.LangSwitcher`). Promoting any of them to a static `import` creates a real circular import. **Rule: keep intra-DAG edges as real imports (already correct); leave every upward/intelligence-layer reach as an ambient `NIMBUS.*` call, typed only by a `declare`.**

**Block / blackout** (`Store.blocks`, `schedule-state.mjs:31`): `{ id: string, line: string|null, plant: string|null, start, end, reason: string }`. `id` auto-assigned `Util.uid('blk')`. `line:null` = all lines in plant; `plant:null` = legacy global. `start`/`end` are stored as-received and **re-parsed via `Util.parseDate` on every read** — so they are `Date | string`, NOT guaranteed `Date` (unlike tasks). ### E. `.d.ts`-vs-reality drift (fix while writing `types.ts`)

`web/nimbus-compute-core.d.ts` is a deliberately minimal subset of what the compute core reads. A full `web/types.ts` must go beyond it, and a few entries are outright stale:

1. **`NimbusTask`** declares 6 fields; reality is ~25 (section C is the superset).
2. **`NimbusBlock`/`NimbusPlantBlock`** omit `id: string` (auto-assigned) and type `start/end` as `unknown` — should be `Date | string`.
3. **`NimbusLineSetting`** omits `bottleneck`, `excludeFromOpt`, `plGroup`.
4. **`NimbusUtilizationRow.tasks: string[]`** is true for the worker/core contract, but `Utilization.computeMatrix` **rewrites `tasks` to a task-object array** on the main thread (`schedule-services.mjs:706-711`). And `Utilization.dayByLine` returns a *different* row shape entirely — `{ capacity, effectiveCapacity, scheduled, pct }`, no `date`/`tasks`. These are **two distinct utilization row types**; don't force them into one.
5. **`NimbusAlert`** types `line`/`time` as required; `Store` treats `line`/`time`/`taskId` as optional — align optionality.
6. **`NimbusMasterData`** only declares `lines?`; reality also has `plants` (with `subnetwork`/`constraints`).

Only alert `type`/`sev` and `WorkHours` match reality verbatim — safe to lift.

### F. Client↔server contract surface (the neglected boundary)

**There is no shared schema, no codegen, no OpenAPI→TS pipeline.** Python builds every response dict by hand in `brain.py`; JS reads fields off `.json()` by string name. FastAPI *does* auto-generate OpenAPI from the Pydantic **request** models (`TaskDateUpdate`, `TasksUpdatePayload`, `TaskRefreshPayload`, `DueDateCorrection`), but the load-bearing **read** responses (`/tasks`, `/plant-calendar`, `/color-wheel`, `/labor-plan`, `/health`) set no `response_model` — so even a generator would emit `any` for exactly the shapes that matter most. See [Open decisions](#open-decisions--needs-your-call) for the strategy question.

- **`GET /tasks`** (`brain.py:1057-1103`): `{ data: TaskDTO[], links: LinkDTO[], meta: {...} }`. Dates are **bare naive strings** `"%Y-%m-%dT%H:%M:%S"` — **no `Z`, no offset** (parsed as local by `new Date`). `row_version` = `xmin` int, nullable. One key literally contains parens: `"ORDER_QUANTITY_(GMEIN)"`. `links`: `{ id, source, target, type: "0" }`. `meta.total` = full filtered count only when paging, else `len(data)`; the empty-result path returns a smaller `meta` subset → most `meta` fields must be optional in the type.
- **Optimistic concurrency** (the update endpoints): request `{ id, start_date?, end_date?, base_version?: int, force: bool }`; response (bulk) `{ status, updated, persisted, failed, invalid, not_found, stale: id[], versions: {id:newXmin}, error_code?, cause? }`. `/task/update` (singular) returns a **narrower** shape and *does* raise 404/400; the bulk paths **never 4xx** — a version conflict is always HTTP 200 with the id in `stale`.
  - ✅ **Fixed 2026-07-28 (was a latent contract bug a type would have caught):** frontend reads `result.invalid_ids`/`result.not_found_ids` (`schedule-data.mjs:919-920`) to clear terminally-rejected ids from its dirty set. `db.update_task_dates_bulk` produced those arrays, but the `/tasks/update` + `/tasks/bulk_update` endpoints forwarded only the `invalid`/`not_found` **int counts** and dropped the arrays — so those reads were always `[]`, rejected ids never cleared, and every save re-posted them + re-warned "Partial DB save". Endpoints now forward the arrays (shape stabilized on all `_apply_task_date_updates` return paths); regression test in `tests/modules/schedule-data.test.mjs`. Still a good example of *why* a shared response type is worth having.
- **`Util.fetchTraced(input, init?)`** (`application-foundation.mjs:298-337`) returns the **raw `Response`**, not parsed JSON — every caller does its own `.then(r => r.json())`. Correct type: `(input: RequestInfo, init?: RequestInit) => Promise<Response>`, never a `Promise<T>`. It injects `x-request-id` + `x-user-email`, and on `!r.ok` logs but **still resolves** (does not throw); only network/non-abort failures reject. Companion `Util.parseBackendError(resp) => Promise<{message,errorCode,status}>`. **Caller inconsistency:** the main `/tasks` load uses bare `fetch` (`schedule-data.mjs:114`), not `fetchTraced` — a TS pass should funnel all calls through the one typed wrapper.
- **Other destructured responses** (all read by-name, all drift points): plant-calendar `{ plant_work_hours, line_work_hours:{line:{0..6:[h,h]|null}}, line_blackouts:[{id,line,start,end,reason}], plant_blackouts:[…] }`; master-data `{ rows:[…] }`; color-wheel `{ entries:[{color, order_y}], meta:{…} }`; labor-plan `{ rows:[{pl_group,period,avail_hours}] }`; session/me `{ username, role, is_admin, allowed_plants, first_name, last_name, settings, role_settings }`; health `{ db, pool, memory, color_wheel }`.
- ⚠️ **Date-encoding split** (a subtle contract detail any typedef comment must capture): the task-save path serializes with `Util.toLocalSeconds` (naive local, **no Z**) to match the naive read path, but blackout writes serialize with `.toISOString()` (**UTC with Z**) (`schedule-data.mjs:1462`). Same conceptual "timestamp", two wire encodings. Model as documented aliases (`type NaiveLocalTs = string`, `type IsoUtcTs = string`) at minimum.

### G. localStorage — `StoredState` ≠ `LiveState` (the classic serialization trap)

Key `nimbus.state.v3` (`Config.LS_KEY`), gated by `Config.SCHEMA_VERSION = 4` (**bump the version, never the key suffix**). Serialized snapshot (`_saveCache`, `schedule-data.mjs:1023-1038`): `{ _schemaVersion, _buildId, _savedAt, tasks, blocks, calendars, fixedIds:[...Set], plants, plantBlocks, lineSettings, selectedPlant, userSettings }`.

- **`JSON.stringify` turns every `Date` into an ISO string** and the `Set` fixedIds into an array. So the on-disk shape has strings where Dates live and `string[]` where a `Set` lives.
- **Rehydration re-parses:** `_prepTask` re-coerces `*date*` keys, `_restoreNonTaskState` re-wraps block `start/end`, the fixedIds array becomes a `Set` again.
- **A quota-guard writes progressively smaller tiers** on `QuotaExceededError` (tasks sliced to last 2000/500, or a metadata-only tier) — so `StoredState.tasks` may be **partial**.

**Write an explicit `serializeState()`/`hydrateState()` pair with distinct `LiveState` (Dates, `Set<string>`) and `StoredState` (ISO strings, `string[]`, possibly-truncated `tasks`) types.** Do **not** let the `key.includes('date')` runtime-magic coercion survive into TS untyped — TS cannot know which string fields become Dates without an explicit field list.

## Common migration mistakes (NIMBUS-specific)

Not generic TS advice — these are the traps this codebase specifically sets:

- **T-1 — Adding a top-level `import`/`export` to `nimbus-worker.ts`.** Reclassifies it from script to module; tsc adds `Object.defineProperty(exports,…)`, which throws in a real Worker. Use ambient `.d.ts` globals, never imports, in that file.
- **T-2 — "Cleaning up" an ambient `NIMBUS.*` reach into a static import.** Re-creates a circular import (the reach points upward in the DAG or into the non-module `nimbus-intelligence.js`). Type these with `declare const NIMBUS`, never with `import`. (§A)
- **T-3 — Refactoring a DI resolver seam into a direct import.** Same cycle problem; also silently un-wires a runtime seam tsc can't see is missing. (§B)
- **T-4 — Expecting types to flow into `app.js`/`nimbus-intelligence.js`.** They won't — those stay classic, untyped scripts. A converted module's payoff is capped at the DAG boundary until a hand-authored `declare` shim for `NIMBUS`/`window.__NIMBUS_*` exists. Decide early whether to write that shim (see Open decisions).
- **T-5 — Trusting the compute-core `.d.ts` as the full domain model.** It's a 6-field subset with known drift (§E). `types.ts` is the superset; keep the two consistent by hand (no automated check ties them).
- **T-6 — One `Task` type for wire + runtime + stored.** Three distinct shapes: server DTO (naive-string dates, `row_version`), live (`Date` objects, snapped), stored (ISO strings, partial). Collapsing them hides the `row_version`↔`base_version` rename and the Date-fidelity gap. (§F, §G)
- **T-7 — Assuming block `start`/`end` are `Date`.** They're `Date | string` (re-parsed on read), unlike task dates. (§C)
- **T-8 — Modeling the two utilization row shapes as one.** `computeMatrix` rows carry `date`+task-objects; `dayByLine` rows don't. (§E4)
- **T-9 — Running `test:modules`/`test:legacy` directly after editing a `.mts`.** Only `npm test` has the `pretest`→build hook; the sub-scripts run against **stale** compiled output. Always `npm test`, or add `pretest:modules`/`pretest:legacy`.
- **T-10 — Docker builder stage missing a tsconfig.** `npm run build` runs *both* tsconfigs; the `COPY` must include `tsconfig.worker.json`. *(Fixed 2026-07-28.)*
- **T-11 — `.dockerignore` stripping build inputs.** `package.json`/`package-lock.json` are needed by the builder stage's `npm ci`; they must not be ignored. *(Fixed 2026-07-28.)*
- **T-12 — `check:static-assets` on an unbuilt tree.** Its import-closure walker `existsSync`-checks resolved `.mjs` specifiers, which only exist post-build for `.mts`-source modules. CI survives only because it runs after `npm test` (which builds). Run standalone on a clean tree and it fails — build first.
- **T-13 — A stray non-worker `.ts` file.** ESLint blocks/globs cover `.mts`, `.d.ts`, and the exact path `nimbus-worker.ts`, but there is **no `web/**/*.ts` glob** — a `.ts` module escapes linting silently. Standardize on `.mts` for all future modules; forbid new plain `.ts`.

## Per-module conversion ritual (Phase 1+ playbook)

Every converted module is a *tracked hand-written `.mjs` today* that becomes *generated output*. Both git steps are mandatory and have **no glob safety net** — miss them and a generated artifact gets version-controlled and silently drifts from source.

1. Rename `web/<module>.mjs` → `web/<module>.mts`.
2. `git rm --cached web/<module>.mjs` (stop tracking the now-generated output) **and** add `web/<module>.mjs` to `.gitignore` by specific filename (not a blanket glob — must not swallow hand-written fixtures like `web/_static-delivery-check.mjs`).
3. Add/extend domain typedefs in `web/types.ts` (§C/§D/§E); don't duplicate an existing type.
4. It's picked up automatically by `tsconfig.json`'s `web/**/*.mts` glob. Keep import specifiers pointing at the `.mjs` output name (`from './foo.mjs'`) per `nodenext`.
5. Confirm `eslint.config.js`'s `web/**/*.mts` block + the `lint`/`lint:ci`/`lint:errors` globs cover it (they use `**/*.mts`, so a new file under `web/` is covered — verify if it lives elsewhere).
6. `npm run typecheck` and `npm run build`; fix type errors until clean.
7. `npm test` (uses `pretest`→build) and confirm no regression. If the module has a suite in `tests/modules/`, it imports the compiled `.mjs` by path — the build must have run (it has, via `pretest`).
8. Update the phase table's Status column below.
