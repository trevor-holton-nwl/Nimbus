# Order Distribution — Stress-Test Audit, 2026-10-01

**Scope:** all code shipped for `aggregate_to_detail.md`:
- `backend/distribution/*` and `frontend/distribution/*`;
- the ingest hook in `db.py`;
- the Work Centers tab;
- the Gantt and Orders-grid sub-order wiring;
- separation alerts;
- the summary, badge, Dashboard and Ctrl+K counts;
- translations, upload-result screens and the migrations.

**Code reviewed:** `main` at **`c00ea70`**. Ten commits landed during the audit, including `09a8e40` and `5294380`, which fixed several distribution items. Every finding below was re-checked against `c00ea70`. **No application code was changed.**

## Verdict: yes, changes are needed

The design is sound. The single shared write engine, structured error codes and plant scoping are all real strengths. The weak spots are where this feature meets everything else: purge, routing, the Orders grid, What-If, the version tokens other screens rely on, and growth past pilot size. Most of them share one cause: **the tests that would catch them only run against a database, and they skip on this machine.** Locally, every database-backed test (33 of 33) skipped. Of the passing tests, only the pure-math and route-shape tests touch distribution logic.

**Five findings can lose, duplicate or wrongly commit planner data. Fix these before rolling distribution out to more work centers:**

| # | What happens | Example |
|---|---|---|
| D01 | On a plant with routing turned on, an upload fails every time once a work center switches from single-machine to distributed. | The plain order 1000 and its new A-1000/B-1000 both stay on the board, so the quantity counts twice. Every retry fails the same way. |
| D02 | A purged, finished sub-order comes back as new demand. | The weekly purge deletes the finished A-1000. The next Repair, re-weight or reset recreates it unscheduled. |
| D03 | Setting a work center's machine weights to all zero deletes the order and creates nothing. | An admin "pauses" WC1 with 0/0 weights. The next upload removes the scheduled order and nothing flags it. |
| D04 | A plain order listed on two machines in one upload is silently dropped, on **every** plant, distributed or not. | Order 2000 is split by hand across M1 and M2 in the Excel file, and neither row reaches the board. |
| D05 | "Save schedule" in the Distribution pane, while in What-If, commits the whole what-if experiment to the live schedule. | A planner exploring What-If clicks the red "runtime mismatch" badge, and their experiment is saved for real. |

### Status as of 2026-10-01 (branch `fix/distribution-audit-low-risk`)

Of the 61 findings below, **35 are fixed, 9 are partly fixed** (residual noted per row), **and 17 are deferred.** All five of the critical/high findings above that can lose, duplicate or wrongly commit planner data are addressed: D02-D05 are fully fixed, and D01 is partly fixed (uploads no longer fail; the per-parent SAVEPOINT is deferred). Status is marked per row in the Wave 1, Wave 2 and Wave 3 tables below, and in "Status of earlier distribution findings" further down.

## How to read this

- **Severity** means data-integrity or user impact at the pilot's size. Scale-only problems are marked *(scale)*.
- **Evidence:**
  - **Probe** means a throwaway test reproduced the bug against the real code, with no database.
  - **Trace** means an exact code path was read end to end.
  - **Plausible** means the logic is sound but the bug wasn't reproduced.
- **Seen by** shows how many of the five independent reviewers found it. Agreement between reviewers raises confidence.
- **Earlier IDs** (H6, H10, P9, N04 and so on) refer to `Code_Review_09_25.md` and `Code_Review_09_30.md`.

## Root causes behind most findings

1. **The real behaviour is only tested against a database that isn't running here.** Every test of plan/apply, re-weight, collapse, preview parity and repair is pg-marked. Locally only the pure math and route shapes run. Two pg tests pass *despite* the bug they target: the concurrent re-weight test doesn't delete children, and the run-time guard test bypasses `upsert_orders`. **Recommendation:** run the pg suite in CI on every PR. `docs/AUDIT_REPAIRS_2026-09-30.md` shows a disposable PostgreSQL 18 at `127.0.0.1:55439` already works for this. Fail the job on skips (already proposed as 09-25 C2).
2. **Boundaries with other domains are assumed, not tested.** This covers purge (D02), the routing hold (D01, D11, D23), the unsaved-changes tracker (D08), the Orders grid (D12), What-If (D05) and the undo stack (D31). Each needs one producer→consumer test, not a mock.
3. **"Changed?" tests compare too much.** The batch id makes every write look like a change (D15), which spends version tokens other screens depend on.
4. **Python does what SQL should.** Classifying, paging and counting thousands of headers in Python (D13, D14), plus per-row statements in `apply()` (D39). The cap hides the cost and then causes wrong answers.
5. **Async UI without request identity.** D09, D26, D32 and D44 are all "the last response wins, even when it's for the wrong thing". One shared request-token helper fixes the whole class.

## Appendix: method

- **Brief:** "run an audit against all of the code written in aggregate_to_detail as if you are a stress-testing code architect who reviews junior code and looks for immature inefficiencies or missed gaps. Feel free to create and run additional tests. Report back with an audit report… if anything needs to be changed, the risk, and why."
- **Split:** five independent reviewers, each with its own slice:
  1. the ingest seam (`service.py`, `plan`/`apply`, the `upsert_orders` hook, migrations);
  2. the planner/admin write engine and routes;
  3. read paths, SQL and master data;
  4. the Distribution pane and shares editor;
  5. everything outside the distribution folders.
- **Rules:** repo read-only, no database connections (`.env` points at the live Azure pilot), probes in the scratchpad only, file:line evidence required for every claim.
- **Orchestrator checks:** independently re-checked D01, D02, D05, D08, D10, D12, D27 and D34 in the code, and re-ran every probe set. Findings raised by more than one reviewer are marked in **Seen by**; they were merged, not counted twice.
- **Dropped or downgraded:** items the domain `CLAUDE.md` files explicitly accept were not re-reported: deep links, editor virtualization, a member with no share row, the zero-member work-center dead end, and `reconcileRuntimeSchedules` not skipping firmed. XSS was checked: every server string goes through `Util.escapeHtml`. Worker/main drift was checked: both run the same `nimbus-compute-core.js`.
