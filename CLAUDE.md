# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**NIMBUS** (Newell Integrated Batch & Unified Scheduling) — a production scheduling and order optimization tool for Newell Brands manufacturing. It renders a Gantt chart timeline, an AG Grid orders table, a dashboard with KPIs/charts, and a calendar manager for working hours and blackout blocks.

## Git Branch Conventions

**`main` is the active trunk again** (as of 2026-08-03). It had gone stale for a stretch — an actively-developed branch (`feature/user-first-last-name`) quietly became the de facto trunk while `main` stopped being updated — but `main` has since been fast-forwarded to that branch's tip and is back to being kept current. Feature branches fork from `main`'s tip and merge back into it. `feature/user-first-last-name` is retired as a trunk (left in place for now, not deleted) — don't fork new work from it or treat it as the merge-base going forward.

## Production Scale Roadmap

NIMBUS is designed to grow to enterprise scale. **All UI and data design decisions must anticipate this:**

| Dimension | Current (prototype) | Target scale |
|-----------|--------------------|--------------:|
| Plants | 1–3 | **50+** |
| Production lines per plant | ~5 | **70+** |
| Total lines across system | ~15 | **3,500+** |

**Design implications:**
- **Never use bubble/chip selectors for plants or lines** — these break at any scale beyond ~10 entries. Use searchable dropdowns (comboboxes) instead.
- **Plant and line lists must always be filterable** — at 50+ plants and 70+ lines, scrolling is not enough.
- **Hierarchy navigation** (plant → line) must be scoped to reduce cognitive load; showing all lines for all plants simultaneously will not scale.
- **API endpoints that return plant or line lists** must support pagination or filtering at the server level — full list queries become untenable.
- **Color wheels, blackout blocks, and calendar configs are per-plant** — storage and retrieval must be keyed by plant ID, not assumed to be global.
- **Utilization and dashboard charts** must be filterable and aggregatable by plant, not rendered for all plants at once.

This is the primary long-term scalability constraint for every feature in NIMBUS.

## Running the App

The backend serves **both** the JSON API and the static frontend (a `StaticFiles` mount at `/`), so local dev is a single process.

```bash
pip install -r requirements.txt
uvicorn brain:api --port 8000      # add --reload for auto-reload during dev
# Then open http://localhost:8000/
```

> `brain.py` has **no `if __name__ == "__main__"` block** — `python brain.py` does nothing. The entrypoint is always `uvicorn brain:api` (this is also the container `CMD`).

No build step for most of the frontend — JavaScript and CSS are loaded directly; most libraries come from CDN. **Exception:** a small, growing set of modules is real TypeScript compiled in place by `tsc` (see `docs/typescript_migration.md`) — currently `web/nimbus-worker.ts` → `web/nimbus-worker.js`, `web/application-foundation.mts` → `web/application-foundation.mjs`, `web/schedule-state.mts` → `web/schedule-state.mjs`, `web/schedule-services.mts` → `web/schedule-services.mjs` (`Calendar`/`Compute`/`Alerts`/`Utilization` fully typed; `Engine` deliberately typed loose — it's the live optimizer with 4 known unfixed bugs, and precisely modeling its internals is deferred to a future phase), `web/schedule-data.mts` → `web/schedule-data.mjs` (`Persistence`/`CalendarSync`/`Session`, all fully typed — no loose-typing exception), `web/schedule-workbench.mts` → `web/schedule-workbench.mjs` (`Timeline`/`Table`/`Inspector`/`Hierarchy`/`Dashboard`/`Interaction`/etc., all fully typed), `web/plant-and-administration.mts` → `web/plant-and-administration.mjs` (`CalendarUI`/`Plant`/`ProdLines`/`LaborPlanning`/`MasterData`/`AdminCockpit`/`Interface`/`Security`, all fully typed), and `web/application-shell.mts` → `web/application-shell.mjs` (`Settings`/`SessionUIAdapter`/`showLoginScreen`/`EmptyState`/`PlantSelector`/`App`, all fully typed), plus the domain-typedef module `web/types.mts` (no runtime output — it's type-only, all its exports erase on compile) and the generated (not hand-written; see `docs/typescript_migration.md` §"Resolved decisions") declaration-only module `web/types/api-generated.d.mts` (OpenAPI→TS codegen of `brain.py`'s Pydantic `response_model=`s for the task-date-update endpoint family). If you edit a `.ts`/`.mts` file, run `npm run build` (or `npm run build:watch` in a second terminal, alongside `uvicorn --reload`) before `uvicorn` will serve the updated output — this is a deliberate, scoped-to-those-files regression from the single-command flow above, not a bug.

**Legacy two-process split** (serving the UI separately on another port) still works but now needs a shim, because `app.js` `API_BASE` defaults to same-origin (relative). Set `window.NIMBUS_API_BASE = 'http://localhost:8000'` before `app.js` loads, then serve the `web/` directory: `cd web && python -m http.server 9000`. Prefer the single-process command above.

## Database Setup

Postgres must be running locally. Bootstrap the schema — now **safe to re-apply**: one-time data-mutating migrations are guarded by a `schema_migrations` ledger (the former `plants` horizon ×1440 landmine, which re-multiplied any value `<= 365` on every run, is now recorded as applied and no longer re-mutates — see the note in `schema.sql` and `docs/MIGRATION.md`):
```bash
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres -c "CREATE DATABASE nimbus;"
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres -d nimbus -f schema.sql
```

Connection credentials are read from environment variables (via `.env` file in the project root, loaded by `python-dotenv`):
```
PG_HOST=localhost
PG_PORT=5432
PG_DB=nimbus
PG_USER=postgres
PG_PASS=your_password
```

Pool tuning knobs (all optional): `NIMBUS_PG_POOL_MIN`, `NIMBUS_PG_POOL_MAX`, `NIMBUS_PG_POOL_TIMEOUT`, `NIMBUS_PG_STATEMENT_TIMEOUT_MS`.

> **pytest is guarded against the live Azure DB:** `tests/conftest.py` + `tests/support/db_safety.py` validate `PG_HOST`/`PG_DB` at collection time and raise `pytest.UsageError` — not a per-test skip — if the host isn't `localhost`/`127.0.0.1`/`::1`/`postgres`, or if the local DB tests aren't explicitly opted into via `NIMBUS_TEST_DB=1`. This means **the entire pytest run fails to even collect** (not just the `@pytest.mark.pg` tests) whenever `.env`'s `PG_HOST` points at a non-local host — which it may, since `.env` on this machine has pointed at the live Azure pilot DB before. This is deliberate: it's the guard against local test runs mutating the live pilot DB, not a bug to work around by pointing `.env` at Azure.

> **Color-wheel paths are env-driven:** `COLOR_FILE` and `COLOR_WHEEL_DIR` in `brain.py` read from env vars (`os.getenv`), defaulting to a local Windows path for dev — override them via `.env` on a new machine. The container image sets them to `/data/color_wheel.xlsx` and `/data/color_wheels`. **Per-plant uploaded wheels are now durable in the Postgres `color_wheel` table** (2026-07-07), so `COLOR_WHEEL_DIR` on `/data` only holds the shared `_audit_log.json`. Still ephemeral: the **global** `COLOR_FILE` wheel (lost on restart until it's baked into the image) — see `docs/MIGRATION.md` WS5.

## Data Sources

**Orders live in Postgres**, not Excel. `db.py` owns all connection management and queries; `brain.py` is **stateless** — it holds no in-memory order cache. Every `GET /tasks` request queries the DB directly via `db.query_orders()`. This allows multiple uvicorn workers or replicas without shared state.

- **Order ingest** — `POST /upload` accepts a `sequence_testing`-shaped `.xlsx` and upserts rows into the `orders` table (`db.ingest_orders_from_excel`). The actual orders-upsert is now factored into `db.upsert_orders`, the **shared** upsert used by both the `/upload` path and the SAP sync path (`sap_sync.py`). Each order's **plant is materialized on the row** (`orders.plant`) at ingest — from a `WERKS`/`PLANT` upload column when present, else derived from the line→plant mapping — so the `/tasks` read path selects `o.plant` directly instead of `LEFT JOIN`ing `production_lines` on the line code alone (which fanned out / mis-attributed orders when a line code is reused across plants). `orders.plant` is added by a `schema.sql` migration: **re-run `schema.sql`** after pulling this change or `GET /tasks` errors on the missing column. A real authoritative plant source (Excel column or upload picker) and a plant-aware `make_id` are still needed before line codes are reused across plants — see `docs/MIGRATION.md`.
- **Color wheels** — **per-plant wheels persist in the Postgres `color_wheel` table** (one row per plant: a JSONB `{COLOR: ORDER_Y}` map + upload metadata; `db.upsert_color_wheel` / `get_color_wheel_row` / `load_all_color_wheels`, migration `migrations/2026-07-07-color-wheel-table.sql`, self-bootstrapped by `db.ensure_color_wheel_table()`). The **global** wheel is still a file (`color_wheel.xlsx`, `COLOR_FILE`). Uploaded via the Plant tab. Both are cached in `GLOBAL_CW` / `PLANT_CWS` (global from file, per-plant from the DB) at startup, on `POST /reload`, and **inline after every color-wheel upload/delete** (`_reload_one_plant_wheel`, so a new wheel takes effect without an explicit `/reload`). The `apply_color_merge` read path and the frontend `ColorWheelViewer`/optimizer are unchanged — same in-memory cache and `{entries:[{color,order_y}]}` response shape. The upload/delete **audit trail** still appends to `COLOR_WHEEL_DIR/_audit_log.json` (shared with `optimization_run` events; ephemeral — a separate durability follow-up).
- **Master data** — `master_data.py` backs the `/master-data/*` and `/labor-plan*` endpoints against Postgres. `ALLOWED_TABLES` covers eight tables — `subnetworks`, `plants`, `production_lines`, `materials`, `material_plants`, `bom_items`, `roles`, `role_plants` — keyed by composite keys (plants by `(subnetwork, plant)`, not plant alone). Beyond list/bulk CRUD it owns runtime DDL (add/drop/rename-label column), the cascade-delete preview, an `admin_audit` log, per-plant JSONB constraint config (`set_plant_constraints`), the **Labor Planning** subsystem (`labor_plan` + `labor_plan_line` tables, aggregate + line-level load/upsert), and `known_plant_line_codes()` (used by `/upload` validation). The Add/Drop Column DDL wizard mutates whichever DB is live (local or Azure) directly with no git record — deliberately left unrestricted since admins are expected to use it against the pilot too. `export_schema_sql()` (`GET /master-data/_schema-export`, "Export Schema" button in Manage Data Tables) is the recovery path: it dumps every column currently registered as idempotent `ADD COLUMN IF NOT EXISTS`/`INSERT ... ON CONFLICT DO NOTHING` SQL, safe to paste into `schema.sql` wholesale to catch up on drift (see `docs/DEPLOYMENT.md` → "Syncing live schema changes back into files"). This is how `production_lines.bottleneck`/`excl_optimizer`/`buffer_*` were reconstructed and fixed after going missing from both `schema.sql` and Azure (2026-07-03). Most dynamic SQL goes through `psycopg.sql.Identifier` / parameterized placeholders; `add_column`'s `NUMERIC(length)` is validated as `precision[,scale]` and rebuilt via `sql.Literal` before composing (previously a raw DDL-injection sink). Maintenance DDL in `db.py` (`VACUUM ANALYZE`/`ANALYZE`) uses an allowlist check against `pg_stat_user_tables` rather than `Identifier`.
- **SAP sync (skeleton)** — `sap_sync.py` is a **transport-agnostic** SAP→NIMBUS sync engine; its connectors are **stubs today** (no live SAP calls). It is backed by three Postgres tables: `sap_sync_config` (per-object sync settings), `sap_sync_run` (run history/status), and `sap_field_map` (SAP field → NIMBUS column mapping). The synced orders are written through `db.upsert_orders` (the same upsert as `/upload`). Surfaced in the Admin **Interface** sub-tab.

## Deployment Notes

- **Hosted on Azure (single-container pilot, live since 2026-06-30).** Deployed as one container to **Azure Container Apps** — FastAPI serves the API and the static UI from the same origin, against Azure Database for PostgreSQL. Live URL: `https://ca-nimbus-dev.delightfulwater-7252cdf0.eastus2.azurecontainerapps.io/`. Resources (RG `rg-nimbus-dev`, region `eastus2`): ACR `acrnimbusdev` (image `nimbus:vN`), Container App `ca-nimbus-dev`, env `cae-nimbus-dev`, Postgres `pgdb-nimbus-dev`/`nimbus`. **Redeploy:** `az acr build -r acrnimbusdev -t nimbus:vN <repo>` then `az containerapp update -g rg-nimbus-dev -n ca-nimbus-dev --image acrnimbusdev.azurecr.io/nimbus:vN`. Full runbook + gotchas in **`docs/DEPLOYMENT.md`**; remaining hardening (Entra SSO, Key Vault, color-wheel durability) in **`docs/MIGRATION.md`**. The pilot runs **single-replica** (in-process color-wheel cache + log buffer), and CORS is effectively vestigial since the UI is same-origin.
- **`POST /reload`** refreshes the in-process color-wheel cache only (global wheel from `COLOR_FILE`, per-plant wheels from the `color_wheel` table). It does **not** reload orders (they are never cached — every `/tasks` request hits Postgres).
- **`NIMBUS_BUILD_ID`** in `index.html` must be bumped on every deploy to bust static asset caches — it single-source-drives the `?v=` on every script/locale/stylesheet URL, `Config.BUILD_ID`, and (CQ-1) `app-entry.mjs`'s `runCacheBustGuard()` version-mismatch redirect. There is no longer a separate `APP_VERSION` constant to keep in sync in `app.js` — that guard (and its own hardcoded version string) moved to `app-entry.mjs` and now reads `NIMBUS_BUILD_ID` directly.
- **CORS / optional auth env:** `NIMBUS_ALLOWED_ORIGINS` (comma-separated; default `*`, with `allow_credentials=False`) pins allowed origins for hosting. `NIMBUS_API_KEY` (unset by default ⇒ no-op) gates the destructive/DDL/maintenance routes behind an `X-API-Key` header — a deployment-config stopgap, **not** user-level auth (actor identity is still read from spoofable `X-User`/`x-user-email`; the real fix is Entra SSO — see `docs/MIGRATION.md`).
- Structured JSON logs are emitted to stdout (`nimbus.*` logger tree, one JSON object per line). `x-request-id` is threaded through every request (only requests slower than 1500 ms are logged). A 2000-entry in-memory ring buffer (`_BACKEND_LOG`) is surfaced via `GET /logs/backend` — it is **per-process** (lost on restart, not shared across replicas). Frontend `ErrorLog` entries **do** store the `x-request-id` (as `reqId`, set by `Util.fetchTraced` and carried through the log payload), so backend correlation is by `reqId` when present (falling back to timestamp/scope otherwise).
- **Admin-route actions are automatically audit-logged**: `request_id_mw` calls `_log_admin_action(operation, outcome, ...)` for any request `_admin_route_details()` recognizes, recording `actor` (from `x-user-email`/`x-user`), `route`, `method`, `duration_ms`, and `outcome` (`success`/`rejected`/`failure`) into the same `_BACKEND_LOG` ring buffer with `event`/`outcome` fields — filterable via `GET /logs/backend?event=...&outcome=...&rid=...`.

See that same document's §1 for the full module ownership map, §6 for the 2 still-open `Store._state`/`_rev` consumer exceptions (`Plant`, `LaborPlanning` — both have a known one-line fix available, tracked as follow-up, not blocking completion), and §8 for the honest final-criteria report against the design doc's own completion bar, including the three criteria CQ-1 does **not** fully satisfy (global task-ID uniqueness — deferred to a separate `docs/MIGRATION.md → task-id` effort; a distinct `hydrate` mode — `Store.mode()` only ever returns `'live'`/`'draft'`; and full inline-handler elimination) and the Docker/browser boot smoke test, which has never been run in any of CQ-1's four phases.

All modules are plain vanilla JS IIFEs that execute top-to-bottom and attach to a single `window.NIMBUS` namespace. The module load order matters — each module can only reference modules declared above it.

A second frontend file, **`nimbus-intelligence.js`** (~2,300 lines, loaded after `app.js` in `index.html`), extends `window.NIMBUS` with the intelligence layer: `CommandPalette` (Cmd+K), `NeedsEngine`, `TimeMachine`, `Confidence`, `RipplePreview`, `Diff`, `Patterns`, `DarkMode`, and `LangSwitcher`, plus an `IntelDB` IndexedDB helper. (There are **no** `Voice` or `Haptic` modules.) Depth varies by module — `CommandPalette`, `NeedsEngine`, and `Confidence` are the most mature.

**Localization:** `locales/` holds i18n string maps (en, de, es, fr, pt). Loaded **before** `app.js` (first in the script chain) — `app.js` reads these maps when it defines `window.t`, so they must exist on `window` first.

**Web Worker + compute core:** `nimbus-worker.js` runs Alerts and Utilization compute off the main thread. (`nimbus-worker.js` is now **compiled from `nimbus-worker.ts`** by `tsc` — the hand-written source is the `.ts` file; the `.js` is a gitignored build artifact. See `docs/typescript_migration.md`.) The actual compute logic now lives in **`nimbus-compute-core.js`** — the **single source of truth** for the `Config` constants + `Util` helpers (`OVERLOAD_THRESHOLD`, `WARN_THRESHOLD`, `SHOW_NEAR_CAPACITY_ALERTS`, `DEFAULT_SHIFT`, `WEEKEND_OFF`, `parseDate`, `dayKey`, `startOfDay`, `runHours`, `mergedOverlapHours`, `fmtDTReadable`, plus `toLocalSeconds`/`toLocalInput`), the **`Calendar` capacity engine** (`getPlantForLine`, `ensureCalendar`, `ensurePlant`, `_dayWindow`, `workWindow`, `dailyCapacityHours`, `effectiveFromCapacity`), and the **entire alert rule set** (overlap / overload / closed / blackout / fixed-closed / fixed-out-of-hours). It is a **UMD module**: the worker loads it via `importScripts` (inheriting the worker URL's `?v=<BUILD_ID>` cache-bust), the browser main thread loads it via a `<script>` injected just before `app.js` (`window.NimbusComputeCore`), and the Node test-suite (`tests/js/*.test.js`) `require`s it directly. `nimbus-worker.js` is just the `postMessage` protocol shim (dispatch to `Core.computeAlerts`/`computeUtilization`). Zero DOM access, no `window.NIMBUS` dependency; the core must never import/reference `app.js`. `app.js` fails fast at boot if the core global is missing.

**What delegates today:** `Alerts._recomputeSync` → `Core.computeAlerts`; `Utilization.computeMatrix` → `Core.computeUtilization` (passing an explicit plant-scoped `lines` set; the core returns `row.tasks` as IDs and `computeMatrix` resolves them back to task objects; memoization wrapper preserved); `Calendar._dayWindow` and `Calendar.effectiveFromCapacity` → the core. So the alert rules and the utilization matrix are now a **single implementation** shared by the worker and the main thread. The core was reconciled UP to app.js first (it now plant-scopes *line* blocks and carries the O(1) line→plant memo — behaviors the drifted worker had lost).

> **Remaining reconciled-but-not-delegated (follow-up):** `Calendar.workWindow` / `dailyCapacityHours` / `effectiveCapacityHours` stay in `app.js` because they are coupled to the Engine's per-run cache (`_runCache`) and `Store`'s O(1) plant index, and are called directly by the Engine/Interaction/Hierarchy on the main thread. They call the SAME math as the core's copies and are parity-pinned by `tests/js/compute-core.test.js`, but until they too delegate, a change to that capacity math must be mirrored in `nimbus-compute-core.js`. The separate unmemoized `Utilization.dayByLine`/`todayByLine` path also still uses `Calendar` directly.

The `Compute` module (in `schedule-services.mjs`; a singleton `new Worker('nimbus-worker.js?v=' + Config.BUILD_ID)` wrapper) posts plant-scoped Store snapshots over `postMessage` and falls back to synchronous main-thread compute if the worker fails to load or errors — **and this fallback is permanent for the session** (a single worker `onerror` sets `_dead=true` with no auto-restart, routing all later compute to the main thread until reload). The snapshot is deliberately scoped to the selected plant's lines — the structured-clone on each `postMessage` is the dominant main-thread cost, so `calendars`/`lineSettings` are pruned to on-screen lines.

> `Util` is **not** purely "pure helpers": it also owns `fetchTraced` (the standard fetch wrapper — attaches `x-request-id`, logs slow/failed requests), the i18n resolver `Util.t` / global `window.t`, the `fpDatetime` Flatpickr factory, and the SAP-variance/optimizer-KPI helpers (`sapDueDate`/`scheduledEnd`/`latenessHours`/`countChangeovers`/`scheduleKpis` — the last calls `Utilization.computeMatrix`, so it is not stateless).

> `Interaction` also owns a Ctrl/Cmd+drag marquee multi-select (edge-scroll), a 500 ms hover-preview card, double-click-label line isolation, 60 fps multi-order ghost-drag, and two-way AG Grid ↔ `Selection` sync.

> `AdminCockpit` is far more than upload/data management: it embeds a Postgres ops console (pool utilization, server info, table bloat + VACUUM/ANALYZE triggers, active-connection stacks, blocking-lock chains, index usage/unused detection, slow-query bars via `pg_stat_statements`, sequence exhaustion), a `PerfMonitor` thread profiler, and a diagnostics-bundle exporter. `App` manages top tabs (home/gantt/masterdata/admin/labor) plus three independent sub-tab dimensions (`_ganttSub` timeline|orders, `_laborSub`, `_currentMasterSub`). The admin area carries an **Interface** sub-tab (Overview → Manage Data Tables → Interface), backed by a dedicated `Interface` frontend module that manages the SAP sync config, field mapping, and run history (see Backend → `sap_sync.py`); the SAP connectors are **stub skeletons** today.

**State flow:** User action → `Interaction` → mutate `Store` → `Store.publish()` → subscribed UI modules re-render.

**Undo:** `UndoStack` (10 levels) wraps any destructive Store mutation. Always snapshot before calling Engine optimization or bulk drag operations.

**Known plants:** `Config.KNOWN_PLANTS` (`['5512', '1006']`) is only a **fallback** seed. `Store.knownPlants()` prefers master-data plants and returns them alone when present, ignoring `KNOWN_PLANTS` entirely; the seed (merged with order-derived discovery) is used only when master data has no plants. The authoritative onboarding path is the Master Data `plants` table, not editing `KNOWN_PLANTS`.

### Backend (`brain.py` — FastAPI; data layer in `db.py`, `master_data.py`)

`brain.py` exposes ~65 endpoints (tasks, task notes, concurrency refresh, diagnostics + DB deep-dive/maintenance, upload/purge/audit, color wheels, master data + column DDL + constraints, labor planning, backend log buffer, health). A separate `sap_sync.py` module owns the SAP→NIMBUS sync engine and an **in-process APScheduler started in the lifespan hook — disabled by default**, gated by `NIMBUS_SAP_SYNC_ENABLED` (unset ⇒ scheduler never starts). The pilot runs single-replica, so this in-process scheduler is safe today; multi-replica needs an advisory-lock guard (see `docs/MIGRATION.md`). `GET /tasks` and the whole task-date-update path (`POST /task/update`, `POST /tasks/update`, `POST /tasks/bulk_update`, `POST /tasks/refresh`, `POST /tasks/baseline-correct`) now carry `response_model=`-backed Pydantic response contracts (`TasksResponse`, `TaskDTO`, `LinkDTO`, `TaskUpdateResult`, `BulkUpdateResult`, `TaskVersionRow`, `TasksRefreshResponse`, `BaselineCorrectResult`), so FastAPI validates its own responses at runtime; the frontend consumes the OpenAPI-codegen'd TS types for these same endpoints in `web/schedule-data.mts` (see `docs/typescript_migration.md` Phase 4). No other endpoint family has `response_model=` yet. The most load-bearing endpoints:
- `GET /tasks` — task list with finish-to-start links and metadata; supports `?plant=`/`?line=` server-side scoping plus optional `?limit=`/`?offset=` pagination (`meta.total` carries the full filtered row count when paging). Calls `db.query_orders()` on every request — no cache.
- `GET /diagnostics` / `GET /diagnostics/deep` — load statistics and DB stats. `GET /diagnostics/db` exposes a deep DB-observability layer (pool stats, server info, table health, connection activity, blocking-lock chains, index usage, slow queries via `pg_stat_statements`, sequence health); `POST /maintenance/vacuum-analyze` and `/maintenance/analyze` trigger maintenance behind a table allowlist. Driven by the AdminCockpit console.
- `POST /task/note`, `POST /tasks/refresh` (concurrency reconciliation), `GET/POST /logs/backend`(+`/clear`), `GET /upload/audit`, `GET/POST /audit/log`(+`/clear`), `GET /health`, `/labor-plan` + `/labor-plan/line`, `POST /master-data/plants/{plant}/constraints`, `/master-data/{table}/cascade-preview`, `/master-data/{table}/columns` (ADD/DROP/rename label DDL), `/master-data/_audit`
- `POST /reload` — refreshes color-wheel file cache (`GLOBAL_CW` / `PLANT_CWS`); does **not** affect orders
- `POST /task/update` — update one task's start/end
- `POST /tasks/update` — bulk update (the frontend autosave path; payload `{ tasks, blocks?, calendars? }`)
- `POST /tasks/bulk_update` — flat-list alias for external tooling
- `POST /upload` — ingest a `sequence_testing`-shaped `.xlsx` into the `orders` table

All three `/update` endpoints call `db.update_task_dates_bulk()`, which validates payloads, **persists each edit to Postgres** (`scheduled_start` / `scheduled_end`), and rejects inverted ranges (end ≤ start). A DB-write failure leaves Postgres unchanged (single transaction). `POST /reload` does not touch orders.

**Optimistic concurrency:** each update carries `base_version` (the row's Postgres `xmin`, surfaced as `ROW_VERSION` on the read path) and a `force` flag. Under `SELECT … FOR UPDATE`, a `base_version` mismatch is **not** a 4xx — the id is returned in a `stale` list (HTTP 200) along with new `versions`, and the frontend reconciles via `POST /tasks/refresh` with **last-writer-loses** semantics (the local edit is discarded and server truth refetched). `force` (set for optimizer-dirtied ids, or when `Config.CONCURRENCY_CHECK` is false) bypasses the check. `db.py` also has single-row `update_task_dates()` and `update_task_note()` paths.

Task IDs are MD5 hashes of `f"{PRODUCTION_ORDER}|{MATERIAL_NUMBER}"` computed by `make_id()` in `db.py`. Because the hash excludes time, IDs are stable across reloads and reschedules — the frontend relies on this for keying drag/edit operations.

### Key Patterns

- **Optimization** runs through `Engine.runAndApply(mode)` where `mode ∈ {'spt', 'changeover', 'combined'}`. These are **dispatching heuristics, not true optimization** — there is no changeover-cost matrix, no finite-capacity constraint, and finish-to-start precedence is not consulted. `'spt'` sorts by run-hours ascending across the whole horizon (via `Engine._sortTerms` + a greedy back-to-back placement walk, jumping fixed orders and calendar/blackout-closed windows, with a 200-iteration guard that logs via `ErrorLog.warn` if it fails to converge) — this is the only mode still on that legacy single-sort walk. `'changeover'` and `'combined'` ("Smart" in the UI) both route through **`Engine._dispatchDayIntegrity`**, a day-integrity dispatch: a calendar day's own orders (its "native" set — orders whose `Util.sapDueDate` falls on that day) get first refusal on every fragment of their day before any other order is considered, so a native order can never be pushed to a *later* day while its own day still has room for it (it can only be pulled *earlier* by an emptier prior day, or bumped by a genuinely overdue arrival from a prior day that needs the room). The dispatch walks calendar days forward; per day it ranks the remaining queue into 4 tiers — 0 native (due today), 1 carry (overdue from a prior day, due-date-ascending), 2 pull-in (due later — `'combined'` ranks these due-ascending-then-color, `'changeover'` ranks them color-first-then-due, the only behavioral difference between the two modes), 3 floater (no due date) — then runs the same admit-then-resequence two-phase placement as the old bucket mechanism, but bounded to that day's window so nothing bleeds past midnight (or shift close, under `respectCalendar`) into a day it doesn't belong to: phase 1 admits ranked candidates by concrete `fitsAt` simulation (fixed order / blackout / shift close are hard obstacles — a day can fragment into multiple sub-bucket admission passes), phase 2 resequences each admitted fragment by `COLOR` → `FORM_SIZE` and places it. An unplaced native simply stays in the queue — on the next day's ranking pass its due day is now in the past, so it becomes tier-1 carry automatically; no separate bookkeeping. A day-integrity guarantee is **per-fragment best-effort**: a mid-day fixed order or blackout can still fragment a day so a native fits no single fragment even though the day's total hours would have covered it — that native spills to the next day. If an order's `RUN_TIME` can never fit any day's capacity at all (a data problem), the dispatch would otherwise spin forever advancing one calendar day per outer iteration with zero admissions; after 90 consecutive zero-admission days it force-places the top-ranked remaining order at the cursor (bypassing `fitsAt`) and warns via `ErrorLog.warn`, one order at a time, so the loop always terminates. The color term drops out automatically when a plant's `colorWheel` constraint is disabled (both phases reuse `_sortTerms(mode, …)`'s own output, the single source of truth for which constraint terms are active). `Engine._comparator('combined'|'changeover', …)` no longer reflects either mode's actual placement order (kept only for hypothetical external callers) — see `_dispatchDayIntegrity` for the real logic. `Engine` carries a per-plant switchable-constraint registry (`CONSTRAINT_CATALOG` / `constraintsFor` / `activeConstraintKeys`) backed by the `plants.constraints` JSONB column and surfaced in the per-plant System Settings pane (`App._renderSettingsPane`). Today only `colorWheel` is wired into the optimizer; the registry is the extension point for future constraints. Deliberately out of scope for now (see `docs/MIGRATION.md`): sequence-dependent setup-time minutes, a release-date floor on pull-forward, and auto-pinning (in-progress orders, SAP-firmed/FIXKZ orders, a frozen near-term fence) — manual pinning (`Store.isFixed`) is the only protection an order has from being moved.
- **Auto-reflow** after manual edits: `Engine.autoReflow()` re-flows subsequent unfixed orders on the affected line to eliminate overlap created by a drag. It only shifts dates within one line, so it triggers an incremental, line-scoped alert recompute. Anything in the Interaction → Engine path needs to be aware of this.
- **Alerts** (overlap, overload, blackout, fixed-closed, fixed-out-of-hours) are computed by `Alerts.recompute(opts)`. A bare call scans all lines; `recompute({ lines })` does an **incremental pass** scoped to specific lines and merges the result into the existing alert list. The debounced dispatcher (`scheduleRecompute` / `scheduleRecomputeLines`) is **adaptive** — its delay scales with the last recompute's measured cost (replacing the old fixed 80 ms window). The actual compute is offloaded to `nimbus-worker.js` via the `Compute` wrapper (sync fallback if the worker is down — see Web Worker above). **Note:** `Confidence.init` (in `nimbus-intelligence.js`) monkey-patches `Alerts.recompute` to also trigger a debounced confidence recompute, but it **forwards all arguments** (`Alerts.recompute = (...args) => { const r = origRecompute(...args); … }`), so the `{ lines }` incremental scope is **preserved** (a previous version of this note wrongly claimed an arity-0 wrapper dropped the scope). Blackouts are also visually enforced by `Calendar` — dragging onto a blackout block snaps to the next valid slot.
- **Utilization** is computed per-line per-day in `Utilization.computeMatrix()` (surfaced in `Hierarchy`, `UtilStrip`, and `Dashboard`). There is a second utilization path — `Utilization.dayByLine` / `todayByLine` (backing today/day summaries) — that is **unmemoized and not worker-offloaded**: it re-parses every blackout block on each call. The Store-backed path (`srcTasks === null`) is **memoized** on `(startMs, days, Store._rev)`; `Store._rev` bumps on every mutation, so a cache hit reflects current data **only for that path**. Two scope caveats: (1) `Dashboard` always passes a **non-null filtered** task subset (`srcTasks !== null`), which bypasses the memo entirely — the matrix is rebuilt several times per dashboard render. (2) The off-thread prewarm writes a **plant-scoped** matrix under the same `(startMs, days, rev)` key the synchronous path expects to be **global** (all lines), so for a given key whichever producer runs first wins — the key carries no plant discriminator. Heavy matrix builds are pre-warmed off-thread through the same `nimbus-worker.js` worker.
- **Auto-save** is debounced 1,200 ms in `Persistence` and writes the **localStorage cache only** (`_saveCache`) — it does **not** post to the backend. Backend persistence (`saveAll` → `POST /tasks/update`) is **explicit**: Cmd/Ctrl+S or the Save button. Note `saveAll` always POSTs full `blocks`/`calendars` even with an empty dirty-task set, and on a partial save it clears all dirty ids before checking `persisted < total`, so un-persisted rows are not auto-retried.

### Date / Time Inputs — Flatpickr Standard

**All date and time inputs in NIMBUS use [Flatpickr](https://flatpickr.js.org/) — never native `<input type="date">`, `<input type="datetime-local">`, or `<input type="time">`.**

Flatpickr is loaded via CDN in `index.html` (before `styles.css`). The NIMBUS amber theme lives mid-file (~line 2226) under `/* Flatpickr calendar — NIMBUS amber theme */`, with dark-mode counterparts at ~line 4158. **Exception:** the AG Grid inline `start_date` cell editor (`Table._DateTimeEditor`) is a native `<input type="datetime-local">`, not Flatpickr.

**Configs by input type:**

| Type | `enableTime` | `noCalendar` | `dateFormat` | `altInput` | `altFormat` |
|------|:---:|:---:|---|:---:|---|
| Date-only | — | — | `"Y-m-d"` | `true` | `"M j, Y"` |
| Datetime | `true` | — | `"Y-m-d\\TH:i"` | `true` | `"M j, Y · h:i K"` |
| Time-only (hours table) | `true` | `true` | `"H:i"` | — | — |

**Pattern for modal inputs (lazy init + setDate):**
```js
if (!Module._fpMyInput) {
  Module._fpMyInput = flatpickr('#my-input', {
    enableTime: true, dateFormat: 'Y-m-d\\TH:i',
    altInput: true, altFormat: 'M j, Y · h:i K', minuteIncrement: 30,
  });
}
Module._fpMyInput.setDate(someDate, false); // false = suppress onChange
```

**Pattern for dynamic/table time inputs (wiring loops):**
```js
flatpickr(inS, { enableTime: true, noCalendar: true, time_24hr: true, dateFormat: 'H:i', onChange: upd });
flatpickr(inE, { enableTime: true, noCalendar: true, time_24hr: true, dateFormat: 'H:i', onChange: upd });
```

With `altInput: true`, existing `.value` reads in save functions keep working — the hidden original input holds the machine-readable `dateFormat` value; the visible alt input shows `altFormat`.

**Registered Flatpickr instances** (module-level, lazy init):
- `OptimizeDialog._fpStart` / `._fpEnd` — optimization modal time window
- `Plant._pillFps` — 7 per-day {start,end} working-hours pickers; `EditCalendar._fp` — 14 working-hours time pickers; `LaborPlanning._fpHorizon` — horizon date-jump
- `Calendar._fpBlkStart` / `._fpBlkEnd` — blackout block modal (line-level)
- `Plant._fpBlkStart` / `._fpBlkEnd` — plant blackout modal
- `ProdLines._fpBlkStart` / `._fpBlkEnd` — production lines blackout modal
- `Table._fpOvrStart` — order override modal
- `Printer._fpStart` / `._fpEnd` — export/print modal
- `AdminCockpit._fpPurgeStart` / `._fpPurgeEnd` — admin purge date range
- Inspector `start_date` — initialized fresh on each `Inspector._render()` call (no stored instance; old one is discarded with innerHTML reset)
