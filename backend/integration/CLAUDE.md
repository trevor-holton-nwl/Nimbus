Importing it never opens a connection; the distribution/routing/setup domains are imported lazily inside functions (they import `db`). Design of record: `docs/SAP_STAGING_DESIGN.md` (D1-D35); the Mulesoft-facing contract: `docs/NIMBUS_INTERFACE_ARCHITECTURE.md` section 7.

**Necessary internal adjustment from the pure-move otherwise promised elsewhere in this refactor:** `sap_objects()` in `routes.py` used to read the scheduler off `api.state` (brain.py's module-level FastAPI instance). ## Key invariants & hazards

- **Uploads never block on missing `material_plants` rows.** The id-scoped attribute stamp runs automatically right after every `/upload` upsert; unmatched `(plant, material_number)` pairs become a per-batch exception report at `GET /upload/{batch_id}/missing-master-data` (`?format=csv` for a downloadable CSV) rather than failing the ingest. On a routing-enabled plant the LIVE per-plant report (`db.missing_master_data_for_plant`) also lists PV - Machine rows, one per (material, production version) with `production_version` and `order_count` (orders on that plant+material currently carrying that PV), counted into `unmatched_pairs`/`unmatched_orders`: `pv_workcenter_missing` (the PV header's `sap_workcenter` is blank, so the PV offers no machine) and `pv_workcenter_no_operation` (the header work center has no non-deleted `routing_operation` in the PV's own routing). Both CSV writers (batch and live) carry a `production_version` column (empty for the older reasons); the admin panel shows `material / PV` and `ui.mmd_reason_<reason>`.
- **The ingest-time stamp is convenience only.** `POST /master-data/resync-order-attributes` is the *real* mechanism for re-stamping a plant's orders on demand (e.g. after fixing `material_plants` rows) — call it rather than waiting for a re-upload. **It bumps `orders.xmin` for every matched row**, which *is* the optimistic-concurrency `base_version` — any planner's unsaved edit to an affected order is discarded on their next save (last-writer-loses reconciliation). It is both admin-gated and `role_plants`-scoped for exactly that reason; run it at a quiet moment, not mid-shift.
- **Manual Excel run-time precedence (owner decision 2026-10-13):** `ingest_orders_from_excel` takes the file's `MACHINE_HOURS_(MEINH)` as the run time when present and > 0 (0 counts as blank), else `RUN_TIME`, else 1 h, before date hygiene, with one `info` warning giving the row count. Routing-on plants are unaffected (`upsert_orders` nulls `run_time`); SAP staging rows carry neither column and never pass through this function.
- **The finish is stored as received (owner rule, 2026-10-14).** `db._date_hygiene_df` (shared by Excel and SAP staging through `apply_order_date_hygiene_rows`) never fills, rewrites or re-derives `basic_finish_date`: a date-only (exact midnight) finish and a same-date finish earlier than the start are kept as sent. A blank or unparseable finish, or a finish on an earlier calendar date than the start, drops the row with an `error` warning naming the order and bumps `DIAGNOSTICS['dropped_no_finish_date']` (the staging validator rejects a missing finish as `invalid_date`). **The start is optional (backward scheduling Task 2.7, OQ24/OQ25):** the Excel required columns are `PRODUCTION_ORDER`, `MATERIAL_NUMBER`, `BASIC_FINISH_DATE` (a file missing the finish column is rejected before any row is written); a blank or missing start leaves the row with a NULL start (never placed, so it reads its finish as the SAP finish and the browser derives its start), an unreadable start does too with one `warn` warning and `DIAGNOSTICS['unreadable_start_date']`, and nothing is dropped for it. The staging validator treats a missing start as valid and a missing finish as `invalid_date` (a malformed start is still `invalid_date`). `_UPSERT_SQL` writes `basic_start_date` as `COALESCE(EXCLUDED, stored)`: a start SAP did not send never erases one.
- **Run-time cap (OQ28).** After the Machine Hours rule, `db.upsert_orders` runs `_apply_run_time_cap` over the rows it wrote: a run time over `db.cap_hours()` (a flat 336 h; no horizon term) is queued exactly like a routing hold (`needs_planning`, reason `run_time_over_cap`, dates NULL, firm cleared, segments deleted, via the resolver's `_write_holds`); a queued `run_time_over_cap` order re-uploaded within the cap is released; a PLACED over-cap order whose run time is unchanged keeps its slot and firm (only a never-placed order or a changed run time is re-queued; the resolver path follows the same rule); another subsystem's hold and a running order are never touched. A row outside the DB representation bound (negative, >= 8760 h, not finite) is dropped by Excel row number with an `error` warning instead of failing the chunk.
- **`orders.runtime_schedule_mismatch`** flags an ingest-side `RUN_TIME` change that would otherwise make prior NIMBUS timing look valid without actually reflecting the new runtime.
- **The Stage 0 observation seam:** both `/upload` and `/purge` (and SAP's order sync) call `setup_data.capture_setup_states_before_schedule_mutation(...)` immediately before the operation that would otherwise destroy the prior schedule's setup-state observability. This never changes orders, dates, capacity, alerts, or optimizer behavior — it's read-only capture.
- **SAP sync (the pull connectors) is a non-live skeleton.** All three connectors return `[]` from `extract()` and report "not configured" from `test_connection()`. No pull from SAP is ever made from this code. `NIMBUS_SAP_SYNC_ENABLED` (default off) gates the per-object cron jobs on the in-process APScheduler started in `brain.py`'s lifespan hook. SAP *staging* (below) is the live path: Mulesoft pushes into Postgres, NIMBUS never calls out.
- **The APScheduler is safe single-replica only** for the per-object cron jobs. A multi-replica deployment needs a `pg_try_advisory_lock` guard so only one replica runs a given object's sync at a time (documented, not solved here — see `docs/MIGRATION.md`, "Workstream — SAP Interface"). The staging poll already takes `pg_try_advisory_lock(hashtext('sap:staging-poll'))` (acquire-or-skip), which covers the poll itself but not the rest of a multi-replica rollout.
- **Secrets discipline in `sap_sync.py`/`routes.py`:** `_SAP_SECRET_KEYS` names the `source_params` keys that must never be returned by `GET /sap/interface/config/{object}` (only `has_secret: bool` is exposed) or passed to `_log_event`. `POST .../config/{object}` merges `source_params` into the stored value rather than replacing it wholesale, so omitted keys (including secrets) survive.
- **`POST /master-data/material-plants/attributes` is deliberately NOT admin-gated** — planners, not just admins, are its users. Its write surface is a hard server-side allowlist (`md.EDITABLE_MATERIAL_PLANT_ATTRS`); it can never insert new rows, only update existing ones.

## Gotchas

- If you're tracing "who else can write to `orders`," don't stop at this domain's `/upload` — `sap_sync.sync_object` reaches the exact same `db.upsert_orders` function for the `orders` SAP object, and both routes through the identical `_stamp_order_attributes` seam afterward.
- The SAP sync engine having zero live connectors today means `POST /sap/interface/sync/{object}` and the scheduled jobs are functionally no-ops in production — don't assume "SAP sync ran" means real SAP data arrived; check `rows_read` in the run record (it will be 0 for every stub transport).
- `docs/SAP_INTEGRATION_ROADMAP.md` describes the intended live-connector future state — don't confuse it with what's actually implemented (the stub skeleton described here).

Optimizer queue state (`orders.planning_status`/`planning_reason`) is planner-owned and excluded from `_UPSERT_SQL` conflict updates, just like scheduled dates. SAP/Excel refresh updates baselines without restoring a queued schedule. The one exception is the locked reset for an order SAP actually changed (see "SAP-is-truth re-upload rules" below): it clears the slot and puts a Needs Planning order back to `scheduled`.

## SAP-is-truth re-upload rules (`db.upsert_orders`, shared by Excel and SAP sync)

SAP is the source of truth; a re-upload only disturbs an order SAP actually changed. Baselines for "what SAP sent last time" live on `orders`: `sap_workcenter` (the RAW work-center/machine value, captured in `distribution.data._plan_core` before any default-machine rewrite), `sap_production_version` (after the routing zero-pad; blank stored as `''`), `sap_basic_start_date`, `sap_basic_finish_date` (the finish SAP actually SENT, stored as received: ingest rejects a row with no usable finish, so a surviving row always has one, and NIMBUS never derives a finish from the start + run time, so a run-time change is never read as SAP moving the dates; `NULL` only on rows written before this rule). They are written ONLY by ingest (`_UPSERT_SQL` and distribution's `_CHILD_UPSERT_SQL`), as `COALESCE(EXCLUDED.x, orders.x)` so an incoming NULL ("column not sent") never erases one. NULL baseline = unknown = never a change (the first upload after the columns shipped records them and resets nothing). The comparison uses `sap_basic_*` and not `basic_*`, because `basic_*` is the planning copy NIMBUS reads for scheduling and as the due-date fallback.

- **Skip unchanged.** `_UPSERT_SQL` ends in `WHERE <sap differs> OR <baseline fill>`; a skipped row returns nothing, so its xmin, slot, firm and manual run time are untouched. Compared: order/material/description, SAP dates vs baselines, quantity, form size, firming indicator, the 9 detail columns, parent link + letter, work center and PV baselines, plant (only when sent), run time (only on non-routing plants). NOT compared (re-stamped from master data or just tags): color, prt_01/02, production_version, upload_batch_id, updated_at, machine. Counts: `inserted`, `updated` (= changed), `unchanged` in the result, the `upload_counts` warning in `upload_audit` and the admin-ui upload line/history column.
- **Machine.** The machine follows SAP only when what SAP sent in the work center / machine field CHANGED vs its previous upload (`_RESOLVED_MACHINE_SQL` first arm: stored baseline equals the incoming value keeps the planner's machine, name feeds included, so a description-only change never reverts a move). Otherwise an ordinary order still keeps its current machine while that machine's `machine.sap_workcenter` equals the work center SAP sent; the plant/machine_key CASEs compare against the same resolved expression. Children always take the incoming machine. SAP sending back the machine NAME NIMBUS already holds is an echo, not a work center change. The kept machine must still exist in the order's (possibly new) plant, otherwise the incoming machine wins (self-heal). **The `dates` change is judged on the FINISH alone (OQ25 c, Task 2.7):** it fires only when the SAP finish differs from its baseline and is neither an echo of the finish NIMBUS sent (`_row_finish_echo`) nor equal to the planner's placed `scheduled_end`. A start-only SAP change keeps the placement (slot, firm, segments) and refreshes `original_start_received` only when the finish is not an echo (a never-sent order, or alongside a genuine finish change); on an echo both locked columns keep their stored values. The quantity rule is unchanged (OQ25 a).
- **Production version.** Planner edits survive. SAP's value wins only when SAP's own PV changed vs its previous upload (children exempt); a blank SAP cell becomes the material default via `_stamp_order_attributes`; a column absent from the file is "not sent" (Excel passes `sap_production_version=None`, a blank cell `''`).
- **Locked reset (per chunk, one transaction).** (a) one statement locks `ORDER BY id FOR UPDATE` every row the chunk may write plus all siblings of any distribution child in it (`_CHUNK_READ_SQL`: the chunk's ids UNIONed with a self-join on the `(plant, parent_production_order, material_number)` index, so it never walks the whole table) and reads the before-image; (b) upsert; (c) `sap_changed_fields` (db.py) per written existing row; (d) a changed child pulls in every locked sibling (same plant + parent order + material); (e) a RUNNING order (stored start <= now < stored end, plant-local: first/last segment else `scheduled_start`/`scheduled_end`; a never-placed order is never running) is not reset (`sap_changed_running` warning with ids, counted only for orders that actually hold a slot; the ids are also handed to the resolver as `protect_ids` so it cannot hold them either); frozen-horizon orders ARE reset; (f) delete the segments, then `manual_firmed = FALSE`, slot cleared, `planning_status = 'scheduled'`. Duplicate `ORDER|MATERIAL` rows are sorted by (start, quantity, raw machine) before the `_n` suffix so file order never permutes ids; suffixed ids are never judged. Warnings: `sap_changed`, `unfirmed`, `sap_changed_running`.
- **Source-scoped upsert for SAP (A1).** `upsert_orders(source="sap")` runs `db._UPSERT_SQL_SAP`, derived from `_UPSERT_SQL`: the Excel-only columns (`db._EXCEL_ONLY_COLS`: description, form size, order category/type, labor/machine hours, FTE) use `COALESCE(EXCLUDED.c, orders.c)` in the SET and `EXCLUDED.c IS NOT NULL AND ... DISTINCT` in the differs check, so SAP rows (which never carry them) neither blank them nor force a rewrite. The Excel statement is unchanged.
- **Quantity change is judged on total (A3).** `sap_changed_fields` compares the incoming `planned_order_initial_quantity` to the stored one when present, else `order_quantity`; a partial conversion does not unschedule.
- **Distribution children are judged on the PARENT's quantity.** A child's own quantity is its share, which a planner re-weight changes (a stale plan can put the old one back), so `upsert_orders` ignores it and compares SAP's new parent quantity against the one the distribution header stored at SAP's previous upload (`distribution_plan[...]["existing_header"]`); a planner re-weight racing an upload no longer resets the slot/firm.
- **An unchanged re-upload still fills master-data attributes that are NULL.** Rows skipped as unchanged whose color / PRT / production version is still NULL while `material_plants` now has a value are added to the stamp set in `_backfill_and_stamp` (found by an unlocked read before the id-ordered lock); rows with nothing to fill are untouched (xmin kept). The stamp's `IS DISTINCT FROM` guard (`_stamp_run`) means an order whose color / PRT / production version already match master data is no longer rewritten, so `xmin` and `updated_at` stop moving on every ingest or resync stamp (previously every stamped row was bumped). During ingest the stamp records no schedule-event rows; `db._record_ingest_attr_net` writes one net PRT / production-version row per order afterwards (see `backend/schedule_events/CLAUDE.md`). Unparseable incoming dates count as not sent and raise an `unparseable_dates` warning; a protected running order raises `routing_running_kept`. Dates arriving as ISO strings (SAP-sync path) are normalised to naive datetimes before any comparison.
- **Post-upload steps take id lists, not the batch tag** (unchanged rows keep their old `upload_batch_id`): plant/machine_key backfill, `_stamp_order_attributes(ids=...)`, the ambiguous-plant and routing-hold queries, distribution's `_stamp_batch_children(conn, ids)` and the resolver (`resolve_orders(..., ids=...)`). The missing-master-data report still covers EVERY incoming id. The reset finishes before the resolver runs.
- **Tests:** `tests/test_ingest_data_layer.py::TestSapTruthReupload`, `tests/test_distribution.py::TestSapTruthDistributionReupload`, `tests/test_audit_routing_db.py` (manual run time), `tests/test_orders_routing_ingest.py::Test_sap_changed_fields`.

## SAP staging (2026-10-07; design of record `docs/SAP_STAGING_DESIGN.md`, Mulesoft contract `docs/NIMBUS_INTERFACE_ARCHITECTURE.md` section 7)

**Flow.** Mulesoft writes a full per-plant snapshot into the `sap_stage_*` tables (header -> rows -> mark `ready`); NIMBUS polls, validates, and — only under admin control — applies the batch to the live tables. Seven tables (`migrations/2026-10-08-sap-staging-tables.sql`): `sap_stage_batch` (header), four inbound row tables (`sap_stage_material_plant`, `sap_stage_planned_order`, `sap_stage_production_version`, `sap_stage_routing_operation`), `sap_stage_planned_order_out` (outbound queue) and `sap_stage_vanished_order` (30-day archive). Column additions are a separate file (`2026-10-08-sap-staging-columns.sql`: `sap_sync_config.apply_mode`, `material_plants.sap_missing_since`, `production_version.sap_missing_since`); the remembered-send side table `order_sap_sent` is the eighth table of the tables migration. Object keys: `stage_material_plants`, `stage_production_version`, `stage_routing_operation`, `stage_planned_orders`.

**Route inventory (`routes.py`, all admin-only; every write also needs `require_api_key`; reads and writes are plant-scoped through `_assert_stage_plant_allowed`, the purge guard — an unknown batch id is 404, an out-of-scope plant 403; apply/discard/validate map `BatchSuperseded`/`BatchNotApplicable` to 409 `{error: "superseded" | <code> | "not_applicable", ...}`).**

| Method + path | Guard | Purpose |
|---|---|---|
| `GET /sap/staging/batches` | admin | Batch headers, newest first (`object`, `plant`, `status`, `limit` filters), scoped to the caller's plants |
| `GET /sap/staging/batches/{batch_id}` | admin | One batch: header + `row_counts` by row status + `actual_rows` + warnings |
| `GET /sap/staging/batches/{batch_id}/rejected` | admin | Rejected rows with `reject_reason`; `?format=csv` for a formula-guarded CSV (raw code kept, plus a plain-English `reject_reason_text` column) |
| `GET /sap/staging/batches/{batch_id}/deletions` | admin | The exact orders a planned-order batch would delete on apply, each with a `running` flag (D21: running orders are deleted too; the UI says so) |
| `POST /sap/staging/batches/{batch_id}/validate` | api key + admin | Re-run validation on a ready/validated/held batch |
| `POST /sap/staging/batches/{batch_id}/apply` | api key + admin | Apply a validated batch; `{confirm_held: true}` for a held one; resumes an `error`/crashed `applying` batch |
| `POST /sap/staging/batches/{batch_id}/discard` | api key + admin | Discard an un-applied batch (not allowed while applying or after applied) |
| `POST /sap/staging/poll` | api key + admin | Run one poll pass now (the Interface tab's Refresh); blocks until it finishes |
| `POST /sap/staging/upload/{object}` | api key + admin | Excel/CSV with SAP headers -> a `source='upload'` batch, validated, never applied; multipart `file` + `plant` |
| `GET /sap/staging/archive/{plant}` | admin | Orders deleted by a snapshot apply in the last 30 days |
| `POST /sap/staging/archive/{archive_id}/restore` | api key + admin | Restore one archived order with its schedule segments |
| `POST /sap/staging/send/{plant}` | api key + admin | Send to SAP: queue the plant's firmed orders into the outbound table |
| `GET /sap/staging/send/{plant}/status` | admin | Outbound tiles: ready/sent/error counts, last queued/sent time |
| `GET /sap/staging/send/{plant}/rows` | admin | Outbound rows (`status` = ready/sent/error); `?format=csv` |

The seven audited writes are named in `brain._ADMIN_WRITE_OPERATIONS` for the audit middleware (`sap.staging_validate|apply|discard|poll|upload|restore`, `sap.send_to_sap`).

### Invariants

- **The status machine is `loading -> ready -> validated | held | rejected -> applying -> applied | error | superseded | discarded`.** Mulesoft only ever sets `loading`, `ready` (with `ready_at` and `row_count_expected`) or `rejected`; NIMBUS owns every other transition.
- **The poll (`poll_once`) processes only `ready` batches whose actual row count equals `row_count_expected`.** A `ready` batch whose count does not match is skipped until `NIMBUS_SAP_STAGING_LOADING_TIMEOUT_MIN` has passed, then rejected as `incomplete_rows`; a `loading` batch past the timeout is rejected as `stale_loading`. Per object + plant only the newest candidate is taken; older un-applied ones become `superseded`. The body is guarded by `pg_try_advisory_lock(hashtext('sap:staging-poll'))` (acquire-or-skip) and never raises.
- **Completeness gate (validate AND apply).** A `source='mulesoft'` batch is refused (`BatchNotApplicable`, code `incomplete_rows`, 409) unless `row_count_expected` is set and equals the live count of stage rows; apply re-checks it. Upload batches keep today's behaviour (NIMBUS set the count). **The poll never auto-applies a `source='upload'` batch** (D18); it only validates it and reports it under `skipped`.
- **Master-object deletions have the planned-order safeguards.** At validation, material-plant / production-version / routing batches count live rows of the plant absent from the snapshot; more than 25 % -> `held` (`vanish_threshold`, same `counts.vanish_*`, confirm flow; `GET .../deletions` lists the keys). The protection set is every row SAP sent except `plant_mismatch` / `unknown_plant` / `key_too_long` (and `deleted_flag`) rejections, so rows rejected as `duplicate_key` etc. are never swept; a `missing_key` row still protects what resolved from it (a material whose `material_id` resolved; a routing GROUP -- material, task list type, group, counter -- whose operation key is incomplete). Material-plant and production-version sweeps write an `admin_audit` row (`sap_snapshot_vanish`, keys capped at 200). The reviewed candidate count is frozen in `counts.vanish_candidates` (+ `vanish_keys` / `vanish_keys_complete`, up to 5000 keys, not returned by the API): a confirmed apply aborts with `revalidate_required` if the live set grew by more than max(5 rows, 5 %), and **every deletion step (planned-order vanish, material / production-version / routing absent sweeps) deletes only keys in the frozen list** (when complete) and re-runs the 25 % gate on that set right before the delete (unconfirmed trip -> batch `error`, `vanish_threshold`); orders that became candidates after review are kept (`vanish_not_reviewed` warning). A batch validated while the plant's horizon was unlimited (`counts.horizon_end_present = false`) is refused with `revalidate_required` if a horizon was set before apply. The gates (routing_required, vanish) also run when resuming an `error` / crashed `applying` batch; a vanish hold then needs `counts.confirmed_held`.
- **Env parsing never stops boot.** `sap_staging.env_int(name, default, minimum)`: a non-integer value logs a warning and uses the default; a too-small value is floored (poll seconds minimum 0, loading timeout minimum 1).
- **Object apply order within one poll is fixed:** material plants -> production versions -> routing operations -> planned orders (`APPLY_ORDER`), regardless of the order Mulesoft delivered them. A batch is auto-applied only when its object's `sap_sync_config.apply_mode` is `auto` and validation ended `validated` (never `held`); the Excel/CSV upload never auto-applies.
- **Only ACTIVE `sap_field_map` rows flow into live columns** (`active_map`). Fields with no map row stay staging-only.
- **Composite rules live in code, not in the field map** (`build_order_rows`): start = SAP start date + time, finish = SAP finish date + time, both converted from `NIMBUS_SAP_SYSTEM_TZ` to the plant zone (a missing or `000000` time is a date-only value and is not converted); `order_quantity` = total - reduced (never below 0); `planned_order_initial_quantity` = total; `reduced_quantity` = reduced; a blank version means the material default (the SAP version baseline stores `''`); an open quantity <= 0 still upserts the order but sets `planning_status='needs_planning'`, reason `zero_open_quantity`, clearing its slot and segments; `matnr` loses leading zeros when all digits (`alpha_strip`) and the order number loses them via `strip_zeros` (an all-zero number is `missing_key`); subnetwork is truncated to 3 characters; material-plant lot sizes are int-cast (a fraction rounds, `lot_size_rounded` warning); the production line (`mdv01`) is the machine value and distribution resolves it.
- **Planned-order apply calls the same `db.upsert_orders(rows, source="sap", plan_fn, apply_fn, resolve_fn)` Excel uses**, after the shared date hygiene (`db.apply_order_date_hygiene_rows`, `db.py:4369`) and a setup-state capture. Do not fork this path: `upload_audit(source='sap')` filters on `filename = 'sap:sap'`, and the skip-unchanged / locked-reset rules above apply identically.
- **Apply is a resumable step ladder, NOT one transaction** (`upsert_orders` commits every 500 rows by design). The batch goes `applying`, the current step is kept in `counts.step`, each step is idempotent, and any failure sets `error` with `<step>: <message>`; running Apply again resumes. Ladders: material plants `create_materials -> upsert -> clear_missing -> absent`; production versions `write -> absent -> recompute`; routing operations `write -> delete_absent -> recompute`; planned orders `setup_capture -> upsert -> zero_open -> vanish`. **Deletions run only after every upsert step succeeded.** A resumed planned-order apply uses a fresh `upload_audit` batch id because that column is a primary key.
- **Vanish rules (planned orders).** An order whose parent order number is absent from the batch and whose SAP start (fallback basic start) is on or before the plant's visibility end + 1 day is deleted on apply, whatever its origin (SAP or Excel), as a whole distribution family, through `db.purge_orders_by_ids` (`db.py:2033`, shared purge core: segments cascade, shares retired, headers cleaned, `admin_audit`), **archived first**. Order numbers SAP sent in rows that were rejected are still protected. Gates, evaluated at validation and re-checked at apply: **more than 25 % of the in-horizon live orders vanishing -> `held` (`vanish_threshold`, needs `confirm_held`)**; **routing runtime off for the plant or no routings loaded -> `held` (`routing_required`, cannot be confirmed away — enable routing first)**; **an empty snapshot** (planned orders: trips the 25 % hold whenever any in-horizon order exists; other objects: `held` `empty_snapshot`); an unlimited visibility horizon never deletes (warning `horizon_unlimited_no_deletes`). A converted or cancelled planned order vanishes even if it is running (D21).
- **Vanished master rows.** Material plants absent from the snapshot are deleted when no order, BOM item, production version or routing operation references them, otherwise stamped `sap_missing_since` (cleared when SAP sends them again); a bare `materials` row is created for an unknown material. Production versions: deleted when unreferenced by orders/routings, else flagged. Routing operations: routings absent from the snapshot are deleted (dependent orders go on hold at recompute). Rows flagged deleted by SAP are rejected `deleted_flag`.
- **Archive.** `sap_stage_vanished_order` holds the order row, its schedule segments and its distribution shares for 30 days (`ARCHIVE_RETENTION_DAYS`), swept by the poll. Restore (`db.restore_vanished_order`, `db.py:2116`) brings back the order and segments; shares are NOT restored (a re-upload of the parent revives them); an id that already exists raises `ValueError("order_exists")` (route: 409 `{error: "order_exists"}`), nothing is written and the archive row stays restorable.
- **Echo rule (D20).** `POST /sap/staging/send/{plant}` records on each sent order, in the side table `order_sap_sent` (`sent_finish`/`sent_version`/`sent_firm`/`sent_at`; never on `orders`, so a Send writes no orders row), what it sent. `db._CHUNK_READ_SQL` LEFT JOINs it. In `db.sap_changed_fields` (`db.py:2732`) an incoming finish that echoes the sent finish is not an SAP date change even when SAP back-scheduled the start. The echo is judged by `db.finish_echoes` (`db.py:2675`) in the SAP frame: a date-only SAP finish (no time sent) echoes when its calendar date equals the SAP-frame calendar date of the sent finish; a timed SAP finish echoes when both values, converted to the SAP zone, are equal to the minute. An incoming version equal to the sent one (or none sent / none incoming) is not a version change; the new SAP baselines are still written. A finish, version or work center that differs from what was sent re-plans the order as today. **The remembered values are NOT cleared by a planner edit** (D20 refinement: clearing let SAP's echo of the old send wipe the planner's newer edit); they are overwritten only by the next Send, which upserts a side-table row only when its finish/version/firm actually differ (members skipped for having no end are not written; no `orders` row is ever written, so no xmin churn). Example: a send of Thu 22 Oct 19:00 Chicago goes out as 00:00 UTC on Fri 23 Oct, so SAP's date-only echo of Fri 23 Oct is an echo, while a genuine change to Sat 24 Oct is not.
- **Outbound firm rule is add-only** (`firm_flag(manual, indicator, placed_start, placed_end, frozen_end, now)`, universal firm 2026-10-27, D6/D7): `X` for every NIMBUS-firmed order (planner firm; frozen by FINISH, the PLACED finish in `[now, frozen_end)` via `db.finish_in_frozen_window`; running, `placed_start <= now < placed_end`, independent of the frozen horizon) and for an SAP `X` (strip/upper, add-only, never cleared; SAP's flag drives no NIMBUS locking). `placed_*` come from `_outbound_candidate_rows` (`COALESCE(seg.first_start, o.scheduled_start)` / `COALESCE(seg.last_end, o.scheduled_end)`, NULL when needs_planning); the SENT end stays `db._EFF_END_SQL`. `queue_send_to_sap` reads one `(now_local, frozen_end)` pair from `db.frozen_window_for_plant`, which is `(None, None)` for a plant with no timezone (nothing frozen or running, matching the browser). **Strict (D7): an overdue order (finish before now) and a never-placed order are NOT firmed, so they are not sent** and `skipped_unfirmed` jumps on the first Send after this change. `build_outbound_groups(rows, frozen_end, now=None)`: with `now=None` running is off. A running or frozen child can carry a far-later sibling's end out with the group X (any member firmed => group X, group end = MAX over all candidate members). Distribution children roll up to one parent row with the latest child end; **only firmed orders are sent (OQ61, 2026-10-14): `build_outbound_groups` drops a planned order whose firm flag would be blank and counts it in `skipped_unfirmed` (per planned order; an aggregate stays when any member is firmed and keeps the latest end over all members)**; firmed orders with no effective end or in Needs Planning are skipped (`skipped_no_end`). End date/time are converted plant-local -> `NIMBUS_SAP_SYSTEM_TZ` (`plant_local_to_sap`). Still-`ready` rows of an earlier click are retired (`row_status='error'`, `error_text='requeued'`); retire + insert + remember + `admin_audit` are one transaction. NIMBUS sends its stored (unpadded) material and order numbers; SAP-side padding is Mulesoft's job.
- **SAP system time zone.** All SAP dates/times are in `NIMBUS_SAP_SYSTEM_TZ` (IANA name, default `UTC` until SAP Development confirms the value), converted per plant via `plants.timezone`. An unknown plant zone means no conversion (L10). **An invalid or blank `NIMBUS_SAP_SYSTEM_TZ` is loud, not silent** (Track 5 / F7): `sap_staging.sap_system_tz_invalid()` is true, the module logs a warning at import (boot), every validated batch carries the warning `sap_system_tz_invalid` (the batch still validates), and a planned-order apply (409, code `sap_system_tz_invalid`) and Send to SAP (400) are refused until the value is fixed; material, production-version and routing batches are not time-dependent and still apply.
- **Retention.** Latest applied batch per object + plant only (the previous `applied` batch is deleted on apply); `rejected`/`discarded`/`superseded` batches 7 days; vanished-order archive 30 days; outbound `sent` and `error` rows (incl. `requeued`) 30 days. Mulesoft never deletes anything. **Ordering and locks:** "newest" is the total order `(received_at, ready_at, batch_id)` (poll order, `supersede_older`, the apply-time newer check); `apply_batch` takes `pg_try_advisory_lock(hashtext('sap:apply:<object>:<plant>'))` so two applies for one object + plant never overlap (`apply_in_progress`, 409); an Excel upload supersedes only older uploads and never blocks a Mulesoft batch; a failed unlock closes the connection instead of returning it to the pool. The module raises `statement_timeout` for its own connections (`NIMBUS_SAP_STAGING_STATEMENT_TIMEOUT_MS`, default 600000; `db.upsert_orders` / `md.bulk_apply` keep the pool's 30 s). Master sweeps write their `admin_audit` row (`phase: planned`, then `done`) around the deletes, not after.
- **Rejection codes** (row level, `reject_reason`): `missing_key`, `plant_mismatch`, `unknown_plant`, `duplicate_key` (every row of a duplicated key), `invalid_date` (a missing or malformed finish, or a malformed start; a missing start is valid), `invalid_time`, `invalid_number`, `invalid_int` (non-finite / fractional integer fields; material-plant lot sizes only when non-finite or non-numeric, a fraction still rounds), `key_too_long` (material or plant longer than 18 / 10 characters, material-plant and planned-order rows; the production-version and routing staging columns are VARCHAR(18), so Mulesoft's own insert fails there), `value_too_long:<column>` (material plants: `mmsta` longer than 2), `deleted_flag`, `rejected_by_validator` plus the routing validators' own messages. A row that was `valid` at validation but cannot be built / is rejected by the live parser at apply goes back to `rejected` (never stamped `applied`). **Batch-level rejection codes (header `error`):** `unknown_plant` (the header plant is not a NIMBUS plant; the header plant is compared trimmed), `unknown_object_key` (a `ready` batch naming an object NIMBUS does not stage), `incomplete_rows`, `stale_loading`. **Apply refusal codes (409):** `apply_in_progress`, `revalidate_required`, `vanish_threshold`, `routing_required`, `incomplete_rows`. **Batch warning codes:** `sap_system_tz_invalid`, `vanish_not_reviewed`, `routing_required`, `vanish_threshold`, `horizon_unlimited_no_deletes`, `empty_snapshot`, `stale_loading`, `incomplete_rows`, `lot_size_rounded`, `unknown_columns`, `rows_not_staged`, `discarded`. A batch with rows but none valid is `rejected` (`no valid rows in batch`).
- **Env knobs.** `NIMBUS_SAP_STAGING_POLL_SECONDS` (`brain.py`, default 0 = no poll job; the lifespan creates the scheduler when this OR `NIMBUS_SAP_SYNC_ENABLED` is on, the per-object cron jobs stay under the sync flag); `NIMBUS_SAP_STAGING_LOADING_TIMEOUT_MIN` (default 120), `NIMBUS_SAP_STAGING_STATEMENT_TIMEOUT_MS` (default 600000) and `NIMBUS_SAP_SYSTEM_TZ` (default `UTC`) are read in `sap_staging.py`.
- **Known limits** (documented, not fixed):
  - L2: `POST /sap/staging/poll` is global, not plant-scoped: a plant-restricted admin triggers validation/auto-apply for every plant (it would have run on the timer anyway).
  - L8: the upload route's size check (413) runs after the file body is read, matching the existing `/upload` and `/bom/upload` routes.
  - L10: a plant with no `timezone` gets no SAP-zone conversion in either direction (both sides stay consistent, no warning).
  - L11: requeueing outbound rows can race a Mulesoft read, so Mulesoft may send both queues; SAP last-write-wins makes it benign.
  - L1 (fixed 2026-10-14, Task 1.2): the date-only echo is now judged in the SAP frame by `db.finish_echoes` (re-exported from `sap_staging`), so a sent finish that crosses midnight when converted into the SAP zone (19:00 Chicago = 00:00 UTC next day) IS recognised. `upsert_orders(sap_tz=...)` carries the SAP zone (the staging apply passes `SAP_SYSTEM_TZ`; Excel passes none, so the plant's zone is the frame). The same rule decides the locked `orders.original_start_received` / `original_finish_received`: the upsert tuple carries the stored values on an echo and the incoming SAP dates otherwise (`_patch_locked_originals`, per chunk after the before-image read); the SET is `COALESCE(EXCLUDED.original_*, orders.original_*)`. `_finish_date_only` is a transient staging-row attribute (never an INSERT column); rows without it (Excel, children) treat exact midnight as date only.
- **Operational rules** (not enforced by code): SAP's planning horizon and the plant's visibility horizon must be kept equal; a plant on SAP snapshots must not also get Excel order uploads (Excel-only orders vanish at the next apply); routing runtime must be on with routings loaded before planned orders apply; the first SAP apply on a plant resets most scheduled slots; open planner sessions learn of an apply only on save/reload (D35, banner deferred).
