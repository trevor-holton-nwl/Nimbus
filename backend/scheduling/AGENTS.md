# backend/scheduling — the `/tasks` route family and optimistic-concurrency contract

## What lives here

- **`routes.py`** (646 lines) — every `GET/POST /task(s)*` route:
  - `GET /tasks` (`get_tasks`) — the task-list read path with finish-to-start links and diagnostics metadata; plant/machine scoping, `?limit=`/`?offset=` paging, per-user `role_plants` enforcement.
  - `GET /tasks/horizons` (`get_task_horizons`) — meta-only horizon probe: resolved visibility/frozen horizon instants and alert-flag horizon minutes without the task list.
  - `POST /task/update` (`update_task`) — single-task schedule/attribute edit.
  - `POST /task/note` (`update_task_note`) — free-text note persistence (max 500 chars).
  - `POST /tasks/update` (`tasks_update`) — the frontend's bulk explicit-save path, payload `{ tasks, blocks?, calendars? }` (only `tasks` is consumed).
  - `POST /tasks/bulk_update` (`bulk_update`) — flat-list alias of the same logic for external tooling.
  - `POST /tasks/refresh` (`tasks_refresh`) — refetch complete writable task aggregates, runtime provenance and matching `row_version` for concurrency reconciliation.
  - Private helpers used only within this domain: `_clean_id` (strips Excel float suffix from SAP ids), `_to_pydt` (pandas/ISO/None → naive datetime), `_schedule_segments_to_wire` (normalizes the split-order JSONB aggregate to the API's naive-local contract), `_apply_task_date_updates` (the single shared validate/persist/rollback path behind all three `/update`-family endpoints).
- **`models.py`** (309 lines) — the Pydantic DTOs backing `GET /tasks`'s `response_model=` runtime validation and every update endpoint's request/response shapes: `LinkDTO`, `ScheduleSegmentDTO`, `PlanningReason`, `TaskDTO` (mirrors `get_tasks`'s `data.append({...})` dict literal field-for-field), `TasksResponse`, `HorizonsResponse`, `ScheduleConflict`, `TaskUpdateResult`, `BulkUpdateResult`, `TaskVersionRow`, `TasksRefreshResponse`, `ScheduleSegmentInput`, `TaskDateUpdate` (carries `base_version`/`force` for the xmin contract), `TasksUpdatePayload`, `TaskRefreshPayload`.

Both files carry a header docstring confirming this was a **pure move from `brain.py`** (routes.py: lines 1493-1982 of the pre-split file; models.py: verbatim) per `docs/architecture/domain-refactor-plan.md` §4 — route paths, payload shapes, and response models are byte-identical to before.

## Key invariants & hazards

- **Refresh runtime contract (2026-10-01):** `get_task_versions` reads quantity, material, raw SAP start, runtime and xmin together. The route filters by authorized plant before exposing `PLANT`; quantity uses the existing `ORDER_QUANTITY_(GMEIN)` wire name. Nullable PV/machine attributes normalize before edit detection, so null and empty snapshots do not manufacture routing edits; an explicit clear of an existing PV still requires eligibility validation.

- **`orders.xmin` is `base_version`.** Any `UPDATE orders` — even on a column no UI reads yet — bumps xmin for every row touched, so those ids come back in the next save's `stale` list and the frontend discards its unsaved edit via last-writer-loses reconciliation (`POST /tasks/refresh`). Before adding any new `UPDATE orders` statement anywhere in the codebase, ask what it does to in-flight planner edits.
- **A version conflict is never a 4xx.** Under `SELECT … FOR UPDATE`, a `base_version` mismatch reports the id in a `stale` list inside a 200 response (see `TaskUpdateResult`/`BulkUpdateResult`), never an HTTP error. `force=True` bypasses the check only on `/tasks/update` in non-atomic mode (the client sends it when `Config.CONCURRENCY_CHECK` is false) and is logged as a warn `forced_write` event. The optimizer never uses `force` — it uses `atomic_optimizer`, under which `force` is ignored. `/tasks/bulk_update` strips `force` from every item.
- **Split-order segments:** `order_schedule_segments` (`(order_id, segment_no)`) is a durable multi-segment schedule aggregate handled by `_schedule_segments_to_wire`/`TaskDateUpdate.schedule_segments`. **Parent `orders.xmin` is the sole concurrency token** — segment rows are never independently exposed or updated by this API. Gated per plant by `plants.split_order_policy` (`never` | `overlong_only` | `partial_allowed`); an absent/malformed value keeps the continuous-order scheduler unchanged.
- **`orders.runtime_schedule_mismatch`** flags an ingest-side `RUN_TIME` change that would otherwise make prior NIMBUS timing look valid; surfaced on `TaskDTO`/`TaskVersionRow` as `runtime_schedule_mismatch`.
- **An explicit aggregate replacement is required, not implied.** `_apply_task_date_updates` treats a JSON `null` for `schedule_segments` as invalid (increments `invalid`, does not silently erase durable productive pieces) — a client must send `[]` explicitly to clear segments.
- **Never a whole-batch 4xx for `/tasks/update`/`/tasks/bulk_update`.** Both are best-effort and report per-row counts in the body (`persisted`/`failed`/`invalid`/`not_found`/`stale`/`versions`, plus `invalid_ids`/`not_found_ids` so the frontend can distinguish terminal rejections from transient loss). A whole-transaction rollback (a raised `psycopg.Error`) is reported as `{"status": "error", "error_code": ..., "cause": ...}` inside a 200, not as an HTTP 5xx.
- **`GET /tasks` refuses an unscoped, unbounded pull** — no `?plant=`, no `?machine=`, no `?limit=` raises 400. Plant is the scaling unit; this is deliberate given the production-scale roadmap (50+ plants).
- **Save path reports `conflicts` (N3).** The bulk-save path returns a `conflicts` list — plant+machine-scoped strict overlaps found among the orders just written, scanned under `SAVEPOINT conflict_scan` inside the same save transaction. Advisory by default (rows are already persisted); becomes hard rejection only when the save is also `strict_conflicts` with `atomic_optimizer` (`status:'error'`, `error_code:'schedule.conflicts'`, still inside a 200).

## `GET /tasks` read path (workload relief, 2026-10-22)

- **Shape.** `get_tasks` (sync `def`, so it runs in the threadpool) = `build_tasks_payload(plant, machine, limit, offset, allowed_plants)` (returns the dict; callable without FastAPI) -> `encode_tasks_response(payload, accept_encoding)` (explicit `TypeAdapter(TasksResponse).validate_python`, `dump_json(by_alias=True)`, gzip level 6 when the caller accepts gzip and the body is >= 1000 bytes, `Vary: Accept-Encoding` set exactly once: by us when we gzip or the body is under 1000 bytes, left to the middleware's IdentityResponder otherwise, so it is never duplicated). A pydantic `ValidationError` is re-raised as FastAPI's `ResponseValidationError` (500, input values stripped), never left as a `ValueError`, which `brain._value_error_handler` would turn into a 400 echoing row values. The decorator keeps `response_model=TasksResponse` only for OpenAPI; because a `Response` is returned FastAPI skips its own validation, which is why validation is explicit. Setting `Content-Encoding` here makes the app-wide `GZipMiddleware` (level 6) pass the body through (starlette's responder skips an already-encoded response). Never switch to `ORJSONResponse`, never paginate, never add workers.
- **No pandas on the hot path.** The reader is `db.query_orders_rows` (same SQL/scope/horizon filter/ORDER BY as `query_orders` via the shared `_fetch_orders`; rows are dicts keyed by the `_ORDERS_SELECT` aliases). `query_orders` (DataFrame) and `plcache.apply_priority_merge` are kept for their other callers/tests. `routes._build_task_rows(rows, plant)` does the merge + sort + row/link build in plain Python (`_stamp_order_y` mirrors `apply_priority_merge`: plant-wide `colorWheel` first, a machine-specific list REPLACES it for that machine, a colour absent from the applicable list -> `ORDER_Y` 999999 and counted in `color_merge_misses`; `missed_colors` excludes null colours).
- **Order is now defined:** machines ascending (`''` first, NULL machine last), then `BASIC_START_DATE` ascending with nulls last, then `ORDER_Y`, then original SQL row order (stable). The old per-machine quicksort left start-time ties unspecified, so only ties can differ from older responses. Links chain consecutive rows of a machine, skipping `needs_planning` rows and rows with no machine.
- **Pinned legacy quirks** (golden test): a null `MATERIAL_DESCRIPTION` becomes the text `"None"`; COLOR/PRT_01/PRT_02/PRODUCTION_VERSION are upper+strip normalised and a null stays null; if every row lacks dates the response is the normal envelope with `rendered: 0` and full DIAGNOSTICS meta (not `empty_meta`); NaN cells are null.
- **Contract kept:** `row_version = int(xmin)`; `schedule_segments` naive-local strings (`_schedule_segments_to_wire` now parses with `datetime.fromisoformat` via `_fast_pydt`, falling back to `_to_pydt`; shared with `/tasks/refresh`); `meta.server_now` fresh on every response; the read path never writes `orders`.
- **Timing.** One `tasks.timing` event per request, to the `nimbus.perf` JSON logger only; it enters the 2000-entry `/logs/backend` ring (as a `warn`) only when the request exceeded 1500 ms, so routine timings never evict real warnings. Fields: `sql_ms`, `build_ms`, `validate_ms`, `encode_ms`, `gzip_ms`, `total_ms`. Deliberately not a `DIAGNOSTICS` key: `meta` is `dict(DIAGNOSTICS, **cm_stats)` and would leak it.
- **Tests:** `tests/test_tasks_builder_golden.py` (frozen legacy pandas copy vs the live builder, DB-free), `tests/test_tasks_route_encoding.py` (gzip/identity parity, headers, NaN, aliases, scoping), plus a pg-marked round-trip in `tests/test_task_concurrency.py`. Patch `db.query_orders_rows`, not `db.query_orders`, to fake the `/tasks` reader.

## Optimizer planning exceptions (2026-09-09)

`orders.planning_status` is `scheduled` or `needs_planning`; `planning_reason` is a nullable `{code,message}` JSON object. Queued rows retain SAP baselines but expose null effective dates, have no child segments, and remain in scoped horizon-filtered query/count results. Date edits restore scheduled status. `/tasks/update` accepts opt-in `atomic_optimizer: true`: every row must have a current `base_version`, force is ignored, and any invalid/not-found/stale row prevents the entire batch from writing. Default and flat-list callers retain best-effort semantics. Apply migration `2026-09-09_optimizer_planning_exceptions.sql` before deploying dependent code.

## Save-path contracts added in the 2026-10 review/audit rounds

- **`machine_unknown` rejection + canonicalisation.** A `MACHINE` edit must name a machine the item's plant knows (registered in `machine`, or already holding orders there; `db._known_machine_keys`). Anything else is rejected per item inside the normal 200 envelope: the id lands in `invalid_ids` and `rejection_reasons[id] == "machine_unknown"`. The match is case/whitespace-insensitive (`db._machine_match_key`) and the stored value is the **canonical spelling**, never the typed one (`'m1 '` -> `'M1'`); a numeric Excel cell arrives as clean text via `_str_id` (`101.0` -> `'101'`). A distribution child still cannot take a direct `MACHINE` edit (decision C) -- that rejection comes first.
- **Strict-save advisory locks.** `atomic_optimizer + strict_conflicts` saves take `pg_advisory_xact_lock` per (plant, machine) in sorted order **before** the row `FOR UPDATE`s (`db._lock_machines_for_strict_save`). The lock text is `db._strict_lock_key(plant, _machine_match_key(machine))` -- the canonical key, so `'M1'`/`'m1'` share one lock; keying on the raw spelling let a differently-cased MACHINE edit slip past. **Scope: strict saves serialise only against other strict saves.** A non-strict (manual) save takes no advisory lock, so it can still interleave with a strict save's overlap scan; that is accepted, not a bug.
- **Routing eligibility cache (P7).** `update_task_dates_bulk` builds one eligibility cache per call and threads it through every `_check_eligibility_on_conn` of the batch, so N edited rows of a plant load the production-version/operation reference data once, not N times. Never hoist the cache above a call (it is not safe across transactions).
- **Batched UPDATE leaves unset columns untouched.** Date saves go through a batched `UPDATE ... FROM (VALUES ...)`; columns a payload row does not carry keep their stored value (including a non-NULL `run_time`/`scheduled_end`) -- tests seed those to prove it.
- **`RUN_TIME` is validated at the DTO and capped per plant.** `TaskDateUpdate.RUN_TIME` rejects NaN/Infinity/negative/>=8760 hours (models.py `field_validator`, H8; the DB CHECK `chk_orders_run_time_bounds` is the same representation bound) so a crafted value cannot reach the schedule math. The scheduling LIMIT is `db.cap_hours()` = a flat 336 h: `update_task_dates_bulk` rejects a changed `RUN_TIME` over it per id (`rejection_reasons[id] == 'run_time_over_cap'`, 200 envelope, nothing written); an unchanged over-cap value never blocks a save. Ingest and the routing resolver queue over-cap orders in Needs Planning instead (reason code `run_time_over_cap`).
- **Locked SAP dates are served, not written, here (backward-scheduling Phase 1, 2026-10-14).** `GET /tasks` (`original_start_date`, `original_end_date`) and `POST /tasks/refresh` serve `COALESCE(orders.original_*_received, orders.basic_*)`, so the due date is the SAP finish as received. The save and bulk routes do not write `original_*_received`; ingest does (`db.upsert_orders`, `backend/integration/CLAUDE.md`). The browser's date-only reading of that due date is in `frontend/scheduling/CLAUDE.md`.
- **The stored finish is the order's finish (backward-scheduling Task 2.2, 2026-10-14).** The server never computes a finish from `start + run_time`, with one sanctioned exception: the distribution N->1 collapse carry (`_collapse_to_survivor`, G-0.28 / OQ37 R2) writes the kept start plus the survivor's full run time as plain elapsed hours (end = start + 1 minute when there is no positive run time, so `chk_orders_sched_range` holds) and flags the row stale for the browser to re-derive. One set of SQL fragments in `db.py` is read everywhere: `_EFF_END_SQL` (last segment end, else `scheduled_end`, else the locked `original_finish_received`, else `basic_finish_date`), `_EFF_START_SQL` (NULL when queued, else first segment start, else `scheduled_start`, else `basic_start_date`), `_SAP_START_RECEIVED_SQL` (the visibility-horizon and vanish key: the locked SAP start, never a planner's placement), `_PLACED_SQL`; the wire, refresh and distribution readers use `_EFF_END_UNLESS_QUEUED_SQL`, which is NULL for a queued row. They are `o.`/`seg.`-qualified, so **every caller must alias `orders` as `o` and join `_SCHEDULE_SEGMENTS_LATERAL_SQL`**; `backend/distribution/data.py` imports them instead of regex-rewriting. `_order_is_running(row, now)` needs BOTH stored edges (segments, else `scheduled_*`), so a never-placed order is never running. The conflict scan's lookback is the fixed 30-day cap and its end is the stored finish; the purge selector reads `COALESCE(scheduled_end, original_finish_received, basic_finish_date)`. Production-version validity is judged on the locked SAP start (`original_start_received`), here (`update_task_dates_bulk` prefetch -> `check_eligibility`), in the resolver and in `Runtime.resolve`. `_EFF_END_WITH_RUNTIME_MISMATCH_SQL` is deleted (the stored finish already wins); the computed `_SCHEDULE_RUNTIME_MISMATCH_SQL` arm is unchanged. The conflict scan's neighbour set is placed, non-queued rows only (`_PLACED_SQL`): a never-placed order cannot conflict server-side.
- **Save contract: both edges or segments, always; the width check gates the stale flag; `placement_exception` (backward-scheduling Task 2.3, 2026-10-14).** A non-segment, non-queued save through `update_task_dates_bulk` must carry BOTH `start` and `end`; a single edge is rejected (`rejection_reasons[id] == 'single_edge'`, nothing written), because the server never completes one edge from the stored other. A status-only save to `scheduled` (no edges, no `schedule_segments` key) is accepted only for a row that already holds a stored placement (raw `scheduled_*` edges or two or more segments); a queued or never-placed row is rejected the same way (`single_edge`), because the SAP window the read path falls back to is never stamped as a placement. A continuous bar (no segments, or an empty/one-piece `schedule_segments`, which is what the browser always sends) is judged by `_validate_continuous_width(start, end, run_time, placement_exception, plant_tz)`: its ELAPSED plant-zone width (`zoneinfo`, so a 24/7 bar across a daylight-saving gap measures what elapsed; the naive wall-clock difference only when the plant has no zone or its zone name does not resolve) must equal the run time within `WIDTH_TOLERANCE_SECONDS` (60), else `rejection_reasons[id] == 'width_mismatch'`. The gate is skipped for an UNMOVED bar (both sent edges equal the stored RAW `scheduled_start`/`scheduled_end`, both non-NULL, run time unchanged: an attribute-only edit resends the full snapshot), and then the flag is left untouched; a never-placed order has NULL raw edges, so it is always judged. The check stands down (returns None) for a bar carrying a `placement_exception` (the item's value if it sent one, else the stored one) or with no (or a zero) run time. `runtime_schedule_mismatch` clears only on a validated segment aggregate, a queued row, or a continuous bar whose width check ran and held; a marked bar leaves the flag alone. `orders.placement_exception` is `'overtime'` | `'overlong'` | NULL (CHECK `chk_orders_placement_exception`; migration `2026-10-16-1-orders-placement-exception.sql`, destructive by text) and the ONE new `TaskDTO` wire field (also `TaskVersionRow`, `_ORDERS_SELECT` alias `PLACEMENT_EXCEPTION`, `get_task_versions`). `TaskDateUpdate.placement_exception` is read through `model_fields_set`: omitted leaves it, an explicit `null` clears it. Every queue writer nulls it with the dates (`_order_update_shape`'s queued literal, the routing holds, the zero-open sweep, the SAP-change reset in `upsert_orders`, the distribution carry). The Excel re-upload flag CASE in `_UPSERT_SQL` flags EVERY placed order whose run time moves (was distribution children only), and the routing resolver does the same (`_build_write_row`; the one-time cutover branch is gone). An item that must not trust its sent start carries `trust_start: False` (Task 2.7, OQ59; request field `TaskDateUpdate.trust_start`, default True, forwarded in the item dict only when False, so every existing item shape is unchanged): `update_task_dates_bulk` skips the width gate for it, stores the sent `end` as the placed finish, FORCES `runtime_schedule_mismatch = TRUE` (it beats the validator's clearing; `_order_update_shape`'s `force_mismatch`), still requires both edges and rejects an inverted range, and returns `start_derived: {id: True}` (a sparse map on `BulkUpdateResult`, never a `TaskDTO` field) for the ids it stored that way, so the browser re-derives the start on its next load. The caller list for `/tasks/bulk_update` (Phase 0 item g) is still unanswered, so the default stays trusted (the browser's own saves send starts it computed): external or integration callers send `trust_start: false`. `GET /tasks` serves a never-placed order with no start (`BASIC_START_DATE` NULL, its SAP finish as `end_date`); only a row with neither edge and no queue state is dropped.
- **`server_now` rides in `/tasks` `meta` (backward-scheduling Task 2.4, 2026-10-14).** ISO-8601 UTC with a `Z` (`routes._server_now_iso`), on both the normal and the empty-result envelope; never a `TaskDTO` field. The browser turns it into an offset (`Store.serverOffsetMs`) and derives every plant's "now" from it (OQ52). `/tasks/refresh` and `/tasks/horizons` do not carry it.
- **Body caps on the free-form sinks** (`brain.py` `_BODY_CAPS`, enforced on `Content-Length`; a missing/non-numeric length is 411, over the cap 413): `/logs/frontend` 1 MB, `/audit/log` 64 KB, `/logs/csp-report` 16 KB.

## What was last sent to SAP: side table `order_sap_sent` (2026-10-07, SAP staging)

- **`order_sap_sent` (`order_id`, `plant`, `sent_finish`, `sent_version`, `sent_firm`, `sent_at`)** is written only by Send to SAP (`sap_staging.queue_send_to_sap`, `backend/integration/CLAUDE.md`), and only when the remembered values actually change. It is a side table, not `orders` columns, so a Send never writes an `orders` row and never bumps xmin (the `base_version`). `db._CHUNK_READ_SQL` LEFT JOINs it and exposes `sent_finish`/`sent_version` to `sap_changed_fields` as `sap_sent_finish`/`sap_sent_version`. **A planner's save does NOT clear them** (`db.update_task_dates_bulk` never touches it; D20 refinement): they are overwritten only by the next Send. Reason: clearing let SAP's echo of the old send wipe the planner's newer edit. They are never part of the `/tasks` DTO.
- **Effect on re-ingest (echo rule, D20).** `db.sap_changed_fields` (`db.py:2732`; the finish is judged by `db.finish_echoes`, `db.py:2675`, in the SAP frame, see `backend/integration/CLAUDE.md`) treats an incoming SAP finish that echoes the remembered sent finish as NOT an SAP date change even when SAP back-scheduled the start (and a version equal to the remembered sent version as not a version change), so a re-import of what NIMBUS just sent does not reset the planner's slot; the new SAP baselines are still written. A different finish, version or work center still re-plans the order as before.
- **Quantity rule (A3).** `sap_changed_fields` judges a quantity change on the TOTAL: when the incoming row carries `planned_order_initial_quantity` (SAP planned orders: gsmng) it is compared with the stored `planned_order_initial_quantity`; only a row without a total (Excel) falls back to `order_quantity`. A partial conversion shrinks only the open `order_quantity` and does not unschedule the order; open quantity is still written for display/planning.
- **Excel-only columns on SAP applies (A1).** `upsert_orders(source="sap")` runs `_UPSERT_SQL_SAP`, which keeps stored description, form size, order category/type, labor/machine hours and FTE when SAP's row does not carry them (COALESCE; only a non-NULL differing value counts as a change), so Excel-loaded values survive and an identical SAP re-apply writes nothing.

## Manual firm and Delete (SAP-is-truth firming)

- **A planner's firm is `orders.manual_firmed`, shared server-side.** `GET /tasks` returns it as `firmed: bool` (`_ORDERS_SELECT` alias `FIRMED`), the refresh read (`get_task_versions` -> `TaskVersionRow.firmed`) returns it too, and `POST /tasks/update` accepts `FIRMED: bool` **only for rows whose firm the planner toggled** (omitted or null means untouched). SAP's own firming indicator stays in `ecc_firmed` and locks nothing: `routes.py` sends `ecc_firmed` as `str(FIRMING_INDICATOR or '').strip().upper() == 'X'` (universal firm B4; ingest stores the indicator raw or only stripped), so the grid "SAP Firmed" X, the Inspector tag and Send's X agree. The frozen state is FINISH-based (finish in `[now, frozen_end)`); the server helpers are `db.frozen_window_for_plant` / `db.finish_in_frozen_window`.
- **A FIRMED-only item is a valid edit.** Both empty-item checks (`routes.py` `_apply_task_date_updates` and `db.update_task_dates_bulk`) count it, it bumps xmin, it is still subject to the `base_version` stale check, and it is allowed on distribution children (the only `orders` rows of a distributed order). It does not count as a move for the conflict scan.
- **Delete** is the existing queued-write path: `planning_status='needs_planning'`, `planning_reason={"code":"planner_unscheduled","message":"Unscheduled by planner"}` (JSONB), null dates. No CHECK change; the routing resolver ignores unknown reason codes, so the order stays queued.
