# backend/routing — routing operations + production version master data, run-time calculation

## What lives here

**Shipped: P1 (data foundation) + P2 (resolver + ingest cutover) + P3 (client-side rate-map mirror, both the backend read/eligibility surface and the frontend consumer + the six edit-hook call sites)** -- `ROUTING_RUNTIME_DESIGN.md` §12. Orders on a plant with `routing_runtime_enabled = TRUE` now actually get `run_time` computed from routings, a drag/edit to an ineligible machine or production version is blocked client-side before it ever reaches the server, and the server independently re-validates and re-resolves on save (§8.5) rather than trusting the client.

- `routes.py` -- `POST /routing/upload/production-versions` (upsert-by-key `production_version`), `POST /routing/upload/operations` (scoped-replace `routing_operation`), and `POST /routing/{plant}/recompute` (runs the resolver over the whole plant on demand), all `require_api_key + require_admin`. The two upload routes are modeled on `backend/integration/routes.py`'s `/upload`/`/bom/upload`: `async def`, `UploadFile = File(...)`, a `NIMBUS_MAX_UPLOAD_BYTES` size cap, the blocking parse+write offloaded to a worker thread via `run_in_threadpool`, returning `{inserted, updated, rejected, warnings}` (`backend/routing/models.py`'s `RoutingUploadResult`). Both upload routes also call `resolver.resolve_orders(plant)` (deferred import) for each affected plant after their commit. Both upload results also carry `plants` (sorted distinct plants the file touched) so the UI can sync its plant filter. `POST /routing/validate/{table}` (`production_version`|`routing_operation`, same admin guards, >20,000 rows -> 413, read-only) runs pasted rows through `ingest.map_row_keys` + the shared `parse_*_rows` (`first_row=1`) and returns `{rows, rejected, warnings}` -- the Paste Rows pre-check. `GET /routing/{plant}/rate-map` (§8.1) is `require_authenticated` + plant scope only (no admin gate, read-only) and sets `Cache-Control: no-store`; it returns `resolver.build_rate_map(plant)` unchanged.
- `ingest.py` -- `parse_production_versions_upload`/`parse_routing_operations_upload`: Excel header-mapping, per-row validation/rejection, and (for operations) grouping by the routing key `(plant, material_id, task_list_type, routing_group, group_counter)` for the scoped-replace transaction `routes.py` performs. Headers are normalized via `db.clean()`; material IDs via `db._str_id`; a LOCAL `_zero_pad` helper (deliberately not shared with `db.py` — see its docstring) re-pads production version (4), group counter (2), operation/activity number (4), and sequence (6) so a spreadsheet's numeric coercion never creates a mismatched key. A row missing a PK value or carrying an unparseable numeric field is rejected per-row (`reason: missing_key`/`invalid_numeric_value`); a row whose plant, material, or SAP work center isn't already known to NIMBUS is rejected too (`unknown_plant`/`unknown_material`/`unknown_workcenter`, one DB round trip per parse call, not per row); a duplicate key within the same file is rejected (`duplicate_key`). A `routing_operation` row with its `DELETED` flag set is skipped entirely (never stored, never counted as rejected) — D10: it could never count toward run time anyway.
- `models.py` -- `RoutingUploadResult` (`{inserted, updated, rejected, warnings}`) and `UploadWarning`. Minimal — resolver.py owns its own return shapes (a plain dict recompute report per §5.6) rather than a Pydantic response model.
- `resolver.py` -- the real §5 run-time resolution logic: pure functions (`_to_hours`, `_pick_operation_hours`, `_select_operations`, `resolve_one`) over plain rows, plus the DB wrapper `resolve_orders(plant: str, *, conn=None, batch_id=None, full=False, ids=None, protect_ids=None) -> dict` (loads plant reference data once, resolves each affected order, writes back with set-based, change-only UPDATEs per outcome bucket, detects and handles first-time plant cutover by reusing `orders.runtime_schedule_mismatch` + the existing `Engine.reconcileRuntimeSchedules` client-side reconciliation path rather than inventing new date arithmetic). Called from: both upload routes and `/recompute` (this domain), `backend/master_data/routes.py`'s `md_bulk`/`delete_filtered` post-write hooks, `db.upsert_orders`'s new `resolve_fn` seam (after Order Distribution's `apply_fn`), and `backend/distribution/data.py`'s `reweight_shares`/`reset_one_header`/`_resolve_repair` (all via deferred `import backend.routing.resolver as routing_resolver`, never module-level, to avoid import cycles). `build_rate_map(plant: str, *, conn=None) -> dict` (§8.1) is the read-only counterpart: it reuses the SAME loaders (`_load_pv_lookup`/`_load_op_lookup`/`_load_machine_workcenter`/`_load_rules`) and the SAME pure functions (`_select_operations`, `_pick_operation_hours` at `order_quantity=1`) `resolve_one` uses, so the pre-aggregated `ops[...].minutes_per_unit` it publishes can never silently drift from what `resolve_one` would compute for a real order — a literal parity port, never a second derivation. Never writes. `resolve_one`'s own step 1-8 state machine (§5.2) was extracted into a shared `_resolve_steps(order, *, pv_lookup, op_lookup, machine_workcenter, rules)` helper so it and the newer `check_eligibility(plant, material_id, production_version, machine, order_quantity, sap_basic_start_date, *, conn=None) -> dict` (§8.5) can never drift apart either — `check_eligibility` runs the same steps for one hypothetical (material, PV, machine) combination without writing, called from `db.py`'s `update_task_dates_bulk` before it accepts a client's `MACHINE`/`PRODUCTION_VERSION` edit on a routing-sourced or unresolved order, reusing that same open transaction's `conn`.

## Gotchas

- Schedule candidate edits now persist authoritative runtime/basis inside `db.update_task_dates_bulk`'s original transaction. There is no post-save plant-wide resolve to invalidate returned versions. Explicit PV edits opt back into routing; machine-only edits rederive routing/unknown runtimes. Submitted preview duration mismatches reject the item as stale with `runtime_preview_changed` so the browser cannot acknowledge a different duration.
- Rate-map keys include material identity (`material|type|group|counter|workcenter`); production versions carry the matching prefix. A routing group alone is not unique across materials.

- `ingest.py`'s parse functions never open a write transaction themselves (except a read-only reference-lookup connection) — the actual DELETE+INSERT (operations) / upsert (production versions) happens in `routes.py`, so the scoped-replace's per-plant `pg_advisory_xact_lock` and the parse/validation step share no transaction; a lock is only ever held for the write.
- `resolve_orders(plant, *, conn=None, batch_id=None, full=False, ids=None, protect_ids=None)`: when called with no `conn`, it opens and commits its own short pooled connection — safe to call after another function's own transaction has already committed (every current call site does exactly this). Don't pass an open, uncommitted `conn` into it unless you actually want it to write inside that same transaction.
- `resolve_orders`/`_resolve_orders_on_conn` gate on `plants.routing_runtime_enabled` THEMSELVES, as the very first thing they do (a missing plants row reads as disabled) — a no-op report for a disabled plant, no reads/writes past that point. Deliberate defense in depth: `db.upsert_orders` also pre-filters by the switch (`routing_enabled_plants`) as an optimization, but the resolver must never trust a caller to have done that — a disabled plant is `is_cutover=True` by construction (no order has `run_time_source='routing'` yet), and `is_cutover` sweeps every currently-scheduled order into the batch via `_load_orders`' cutover clause. Applies to every caller, including the explicit `/recompute` admin route.

## Run-time contracts added in the 2026-10 review/audit rounds

- **A manual run time lasts until SAP next updates that order (routing-enabled plants).** `db._UPSERT_SQL` skips a row SAP sent nothing different for, so an unchanged re-upload leaves a manual run time untouched. When a row IS written because SAP sent something different, `run_time_source = 'manual'` drops back to `NULL` (the resolver re-derives every non-`'manual'` row: `NULL`, `'routing'`, `'sap_order'`, `'legacy'`), `run_time` keeps the stored value until the post-upload resolve overwrites it (`COALESCE(EXCLUDED.run_time, stored)`; the file's value is nulled on these plants), and the resolver recalculates it from the incoming production version. A row written only to record the SAP baselines (first upload after the baseline columns shipped) keeps its manual run time. A plant that is not routing-enabled takes the file's value as before (SAP wins, even over a leftover `'manual'` row). End state is routing-only. At routing switch-on a hand-keyed (`'manual'`) run time is KEPT (the resolver never loads manual rows); every other order is re-derived from routing.
- **Post-upload re-derive is scoped by id list.** `db.upsert_orders` calls `resolve_orders(plant, conn=..., batch_id=..., ids=touched_ids)` after the upsert and after the SAP-change reset; `_load_orders` ORs `id = ANY(ids)` onto its other arms (the batch tag is only stamped on rows the upload actually wrote, since unchanged rows are skipped), because a kept `'sap_order'`/`'legacy'`/NULL-source run time would otherwise go stale when the quantity changed. `_write_outcomes`/`_write_holds` sort their VALUES rows by id (id-ordered locking, like every other multi-row `orders` writer). A resolve failure is a per-plant SAVEPOINT -> upload warning `{category: 'routing_resolve', status: 'failed'}`, never a failed upload.
- **`POST /routing/{plant}/recompute` re-derives EVERY non-manual order of the plant** (`resolve_orders(plant, full=True)`), so an upload whose post-upload resolve failed (stale kept duration) is always repaired by a recompute. Routine callers (master-data hooks, uploads) keep the narrower selection.
- **`_fallback` no longer keeps a stale stored run time.** When routing cannot resolve: the order file's `machine_hours` -> `fallback_sap_order`; a **manual** order's own `run_time` -> `fallback_legacy` (retained, never rewritten); anything else is **held** (`runtime_unknown`, with the failing step as `detail_step`). A non-manual stored value is never relabelled `'legacy'` and kept.
- **Routing switch-on keeps no SLOT in place, but keeps a hand-keyed run time.** At a plant's first resolve (no routing-sourced order yet) every non-manual order gets its routing run time, and every already-placed order is flagged `runtime_schedule_mismatch` for re-placement, whatever its SAP firming indicator, manual firm or frozen-horizon position. A manual firm or a running order protects a slot, not a run time; a planner-keyed run time (`run_time_source = 'manual'`) is the one thing switch-on does not re-derive. The former `orders_kept_in_place` report key and the frozen-horizon lookup are gone.
- **A running order is never held; a hold clears the firm and segments.** `_resolve_orders_on_conn` collects held outcomes first, then drops any order that is running right now (`db._order_is_running`, plant-local; one batched read via `_running_ids`) or listed in `protect_ids` (`db.upsert_orders` passes the SAP-changed running ids it just kept in place, so its "slot and firm were kept" warning stays true). The protected order is reported as `running_kept` in the resolve report (only when non-zero). A re-derived run time may still move a running order's END, never its start or slot. When an order IS held, `_write_holds_chunk` also sets `manual_firmed = FALSE` and deletes its `order_schedule_segments` (rows locked `ORDER BY id` first, then the segment delete), so releasing the hold later leaves no stale bar.
