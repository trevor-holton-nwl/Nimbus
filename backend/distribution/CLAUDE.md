# backend/distribution — SAP aggregate work center <-> NIMBUS per-machine sub-orders

## What lives here

Order Distribution bridges SAP's aggregate work centers (one SAP work center standing in for several physical machines) with NIMBUS's discrete-machine scheduling model. `routes.py` holds this domain's FastAPI router; `data.py` holds the plain psycopg write logic over the shared pool (`db._pool`), mirroring `backend/setup/data.py`'s convention; `models.py` holds the route's typed response DTO.

**Shipped: P1 (write) + P2-2/P2-3 (ingest seam) + P2-6/P2-7 (read routes) + P2-8/P2-9 (planner writes `shares`/`review`/`reset` + admin writes `reapply-defaults`/`resolve`) + P2-15/P2-16 (full frontend Distribution pane with shares editor, dry-run, save/reset/undo, reconcile).**

- `PUT /distribution/{plant}/workcenters/{wc}` (`save_workcenter`) — a validated create-or-replace of one plant's `sap_workcenter` policy row and its member machines' `machine.distribution_weight`, in one transaction with an `admin_audit` row. Enforces the §3.1 write-path rules (`wc_code_shadowed_by_machine`, `wc_code_is_member_of_aggregate`, `default_machine_not_member`, `single_mode_without_default`, `distribute_mode_thin`) as 400s with a structured `{"code": ...}` detail, plus an additional `weight_machine_not_member` guard. A same-named machine (code == machine name) must be linked to the code (`machine.sap_workcenter` = code) — that is a valid 1:1 work center, and single mode without a default is allowed for it (default implied). **Since 2026-10-19 an EMPTY link is auto-filled on creation only** (reverses the 2026-10-12 explicit-link decision; an explicit link still wins, and editing an EXISTING work center never re-links, so a planner's deliberate clear sticks -- the shadow 400 below then applies to that work center's later saves until the machine or code is renamed or relinked): `save_workcenter` upserts the policy row first (`RETURNING (xmax = 0)` detects creation), then, only when it was created, calls `master_data._autolink_same_named_machines` scoped to only `(plant, code)` (it never links any other machine) in the same transaction (a refused save rolls both back), reports `auto_linked: true` (audit detail `auto_linked: [{plant, machine}]`, the same shape as `bulk_apply`'s) and the route recomputes routing for the plant. Shadow therefore fires only when that machine is linked to another code, the work center is an aggregate (distribute mode or other members), or the name exists in several subnetworks (the 400 message names which: other members / distribute / several subnetworks, and tells the planner to rename instead of advising a link); the cleared-link single-mode no-members case says "Machine {code} exists with no work center link. Link it in the Machines pane, or rename the machine or the work center." (server text, not localized), and `wc_code_is_member_of_aggregate` refuses a linked same-named machine alongside a second member or in distribute mode. `resolve` scope `wc_codes` excludes orders already on a real machine. The frontend pre-flight-gates all of the rule codes client-side, so the PUT normally fires only on a payload expected to pass — but the 400s remain the authority and a concurrent membership change still produces `weight_machine_not_member`. `distribute_mode_thin` and `single_mode_without_default` together make a zero-member work center unsaveable through this route by construction: a known, accepted dead end, not a bug to patch by relaxing the rule. No `base_version`/optimistic-concurrency token on this route — that belongs to the `order_distribution` header table. As of 2026-09-18, the table-level CHECK backing `single_mode_without_default` was dropped (migrations/2026-09-18-sap-workcenter-allow-unconfigured.sql), allowing a work center to be created from SAP or the Manage Data grid with only plant/code/description, entering an "unconfigured" state with `distribution_mode='single'` and NULL `default_machine`. This route's own 400 is unaffected—its rule checks run in Python after the policy row is written inside the same transaction, and any refusal rolls that write back (so a refused save leaves nothing behind). Ingest handles the state by leaving orders as plain orders with a `default_machine_invalid` warning (service.classify_row).
- `plan()`/`apply()` (`data.py`) — the ingest transaction seam (§5), wired into `db.upsert_orders` via its optional `plan_fn`/`apply_fn` parameters.
- Five read-only routes, all `require_authenticated` + plant scope, `Cache-Control: no-store` (§7): `GET /distribution/{plant}` (paged list, `list_headers_for_plant`), `GET /distribution/{plant}/{order}/{material}` (`get_header_detail`, carries `base_version`), `GET /distribution/{plant}/summary` (`get_summary`), `GET /distribution/{plant}/aggregate` (`get_aggregate`, the §10.2 roll-up built from `db._EFF_END_SQL`/`db._SCHEDULE_SEGMENTS_LATERAL_SQL`, `?format=csv` export), `GET /distribution/{plant}/unresolved` (`get_unresolved`, the `missing_master_data_for_plant` analogue). The list route's `bucket` filter and the summary route's counts share one classification helper, `data.classify_bucket_membership`/`status_matches_filter`, so the two bucket definitions (§6 "Data") can never drift apart.
- **Three planner-write routes** (§5.5-§5.7, §7), all `require_api_key + require_authenticated` + plant scope — deliberately NOT `require_admin` (§7: "All three planner writes use the identical guard set"):
  - `POST /distribution/{plant}/{order}/{material}/shares` (`save_distribution_shares` → `data.reweight_shares`) — the re-weight editor's save. Body `{shares:[{machine, weight}], base_version, reviewed?, allow_stale?, confirm_remove_scheduled?, dry_run?}`.
  - `POST /distribution/{plant}/review` (`review_distribution_orders` → `data.review_orders`) — bulk `{orders:[{production_order, material_number, base_version}], reviewed}`, per-item results; does NOT clear `sap_facts.previous_workcenter` (only a materializing re-weight/reset does).
  - `POST /distribution/{plant}/reset` (`reset_distribution_orders` → `data.reset_orders`/`reset_one_header`) — bulk revert-to-work-center-defaults, `source = 'default'`, same guards as `shares`.

**Route-guard 400s (audit fixes, this session).** Every body-driven write now rejects malformed input before it ever reaches `data.py`, each with a structured `{"code": ...}` detail so the UI can key off it instead of parsing text:
  - `base_version_required` — `shares`/`review`/`reset` all require `base_version` to be present and an actual integer (a `bool` is rejected too, since Python's `bool` is an `int` subclass). `reapply-defaults` is exempt on purpose: it's an admin sweep, not an edit against one planner's held header version.
  - `too_many_orders` — the bulk body array on `review`/`reset`/`reapply-defaults` is capped at 500 items.
  - `reviewed_required` — bulk `review` requires an explicit boolean `reviewed`; a missing/non-boolean value used to silently un-review everything (`bool(None) == False`), so it's now refused instead.
  - A malformed bulk-order item (missing/non-string `production_order`/`material_number`, or a non-dict entry) is a plain 400 rather than reaching `data.py` and surfacing as a 500.
  - A date-only `to=YYYY-MM-DD` filter (list/aggregate routes) now means the END of that day, not midnight at its start — so orders starting later the same day are no longer silently excluded.
  - `weight_invalid` — a share weight must be finite (no `NaN`/`Infinity`) and at or below the 1e9 ceiling.
  - `unknown_machine` — a share naming a machine that is neither an existing share on this header nor a current work-center member is refused outright; `allow_stale` only waives the *membership* check for a machine that already has an existing share (it never waives `weight_invalid` or admits a brand-new machine).
  - `weights_empty` — `shares` rejects an empty list outright, and `reset` raises it when a work center's own default shares are all zero (see "all-zero-weight work centers" below).
  - `already_reviewed` — `reapply-defaults`' explicit `orders` list used to only honor the "not reviewed" filter on its DB-query candidate path; a header named explicitly that was reviewed in the meantime (checked under the same `FOR UPDATE` lock) is now skipped with this error instead of silently re-defaulting it.
- **Two admin-write routes**, `require_api_key + require_authenticated + require_admin` + plant scope (the `save_workcenter`/`backend/setup/routes.py` precedent):
  - `POST /distribution/{plant}/reapply-defaults` (`reapply_distribution_defaults` → `data.reapply_defaults`) — bulk sweep over every matching `NOT reviewed` header (or an explicit `orders` list), via the same `reset_one_header` core, no `base_version` gate (an explicit admin sweep, not a single planner's edit).
  - `POST /distribution/{plant}/resolve` (`resolve_distribution_orders` → `data.resolve`) — `{scope: 'wc_codes'|'machines'|'repair', workcenter?, dry_run?}`. `wc_codes` (default) feeds synthetic ingest rows built from each candidate plain order straight through the EXISTING `plan()`/`apply()` machinery (no re-implementation); `machines` (opt-in, `workcenter` required) relabels an already-correctly-placed plain order as a schedule-preserving 100% bare child in a brand-new header; `repair` re-materializes every `incomplete` header from its CURRENT non-purged shares.

**The one shared internal engine.** `data._materialize_reweight(cur, ..., dry_run: bool, ...)` is the SINGLE function behind `shares`, `reset`, and `resolve`'s `repair` scope — every line of diff/materialize logic (recompute child rows via `_build_child_rows`, diff against the CURRENT children, N→1 collapse detection, the `children_scheduled` guard, the dry-run `plan` preview shape) runs identically whether `dry_run` is `True` or `False`; the boolean only decides whether the function returns before or after the write section. This is what makes a dry run's preview provably identical to what the following real call then writes (§5.5 step 8's parity requirement) — there is no second, independently-maintained preview code path to drift out of sync. `reweight_shares`/`reset_one_header` each open their OWN `_pool.connection()` and lock the header via `_lock_one_header` (reused verbatim from `apply()`). **Not** "a dry run rolls back, releasing the lock" — `db._pool.connection()` is `with conn: yield conn`, and psycopg's `Connection.__exit__` COMMITS on a clean exit (it only rolls back when an exception propagates), so a dry run that took `FOR UPDATE` would hold the lock for the connection's full lifetime same as a real write. The actual fix (D56): `_lock_one_header` takes `for_update: bool = True`, and `reweight_shares`/`reset_one_header` pass `for_update=not dry_run` — a dry run reads the header WITHOUT locking it at all, since nothing above `_materialize_reweight`'s `if dry_run: return ...` ever writes.

**The N→1 collapse** (`data._collapse_to_survivor`) runs only inside a real (non-dry-run) `shares`/`reset` write, only when the surviving 100%-weight machine already carried a positive, living share before the call. It carries `notes`, `planning_status/reason`, the manual firm and the kept `scheduled_start` onto the NEW bare id via one `UPDATE orders AS new_o ... FROM orders AS old_o` self-join, and the carried FINISH is OQ37 rule R2 (backward scheduling Task 3.5): `scheduled_end = scheduled_start + run_time * INTERVAL '1 hour'` (plain arithmetic, the survivor's full run time; a survivor with no run time carries `scheduled_end = scheduled_start + 1 minute` (the strict range check), not equal edges; a finish-only survivor keeps its stored finish), with `runtime_schedule_mismatch = TRUE` so the browser re-derives the start backward from it. The old partial-share `scheduled_end` is never copied and the partial-share segments are deleted, not re-pointed. An UNFIRMED survivor is excluded from the `children_scheduled` 409 check and the dry-run `removed_scheduled` list (its placement carries); a FIRMED one (manual firm or SAP firming indicator) is listed and needs the confirm, because its start may move. Repair (`_repair_one_header`) always passes `confirm_remove_scheduled=True`. The aggregate roll-up and its CSV carry `due_date` (the header's `original_finish_received`, empty when SAP sent none); the CSV column is appended last, the window key is unchanged.

**A schema gap `_parent_facts_from_header` works around, deliberately:** `order_distribution` has no `labor_hours`/`machine_hours` column (only `order_quantity`/`run_time`/dates/`firming_indicator` do — §3's `_ADDITIVE_COLS` are apportioned into children at ingest time and never summed back onto the header). Re-weight/reset/repair reconstruct the parent's labor/machine-hours total as the SUM of the header's CURRENT living children's own values, so a re-weight preserves the total instead of losing it. This is a scoped, documented choice, not an oversight — don't "fix" it by adding a header column without checking whether the apportionment math still needs to change too.

**Purge retires shares instead of leaving them dangling (D02/B6).** `order_distribution_share.child_id` is a soft reference (no FK) to `orders.id`. `db.purge_orders_by_date` (`db.py` ~1854) now retires, in the SAME transaction as the delete, every share whose `child_id` just got deleted: `purged_at` is stamped and `child_id` is cleared, but the share's `letter`/`weight` are left alone. A header left with no remaining live share (every share now weight-0 or purged) is deleted outright once purge runs (shares cascade). This means a later upload of the same parent order creates a fresh header rather than resurrecting a dead one. The purge audit's `admin_audit` JSON always carries `shares_purged`/`headers_deleted` (0 when purge touched no distribution rows at all), not just when nonzero. **Revival:** an upload of the parent, an explicit Reset, and admin `reapply-defaults` all revive a purged share — each clears `purged_at` the moment the share receives a positive weight again, through the same `_write_reweight_shares` core that `reset`/`reapply-defaults` and ingest's ordinary refresh path share. Repair (`resolve` scope `repair`) and a plain re-weight (`shares`) never revive a purged share; `_repair_one_header` excludes purged shares from its desired weights by design, and `_validate_share_payload` refuses a positive weight on an already-purged share (`share_purged` 400) before `shares`' own write path runs.

**All-zero-weight work centers (B3).** A work center whose current members are all weight-0 keeps an incoming order as a plain, undistributed order carrying a `workcenter_without_members` warning (`reason: zero_weights`) rather than failing ingest. The symmetric case on the write side: `reset`/`reapply-defaults` against such a work center raises `weights_empty` instead of materializing an all-zero split.

**List/summary classification in SQL (#24, supersedes the D13 candidate cap; D42 ordering kept).** `data._STATUS_SQL`/`_STATUS_FROM` express every derived status as SQL (one probe of the header's shares, one of its children, its work-center row and member machines, then array/boolean tests), so `get_summary` is one `count(*) FILTER` per bucket and `list_headers_for_plant` filters, counts (`total`, `scheduled_children`) and pages (OFFSET/LIMIT) in the database over EVERY header -- no cap; only the visible page is hydrated and run through `service.compute_derived_statuses`, which stays the oracle for the wire `statuses` and for `_resolve_repair`. `tests/test_distribution.py::TestSqlStatusClassificationParityAndScale` asserts SQL == Python for every status and that >5,000 headers are all counted; any change to `compute_derived_statuses` must be mirrored in `_STATUS_SQL`. `meta.truncated`/summary `truncated` are kept for wire compatibility and are always False (the frontend notice never shows). Ordering `basic_start_date ASC NULLS LAST, reviewed ASC, production_order ASC, material_number ASC` (D42 tiebreaker) is served by `idx_order_distribution_plant_start`; no new index was needed (existing `idx_orders_parent` and the share PK serve the probes). Search escapes `%`/`_`/backslash before an `ILIKE`.

**A real, previously-unnoticed bug fixed alongside this work:** `brain.py`'s global `_http_exception_handler` used to collapse ANY `HTTPException(detail=<dict>)` — including `_distribution_error`'s and this session's own `_distribution_conflict`'s structured `{"code": ..., "message": ...}` bodies — into the bare literal string `"error"`, silently discarding the whole object before it ever reached the client. Fixed to pass a dict `detail` through unchanged (synthesizing `message` from its `message`/`code`); a plain string `detail` (the overwhelming majority of routes) is completely unaffected. This means `save_workcenter`'s four §3.1 rule-code 400s ALSO now actually reach callers structured, not just this session's new 409s — check before assuming any pre-existing structured-detail test coverage exists elsewhere in the app, since none did before this fix.

## Lock-order and summary contracts added in the 2026-10 audit round

- **Child rows are locked in id order before they are written.** `/tasks` saves lock `orders` rows in id order but `_apply_children` upserts in letter order, which could deadlock a concurrent save. `_apply_children` now first runs `SELECT id FROM orders WHERE id = ANY(new + previous ids) ORDER BY id FOR UPDATE`; `_delete_superseded_children` and `_fetch_children_by_machine(lock=True)` already lock in id order. Any new multi-row writer of `orders` must do the same.
- **`resolve` scope `repair` runs one transaction per header** (`conn.commit()` after each `_repair_one_header`), instead of holding every header lock across the loop in `basic_start_date` order -- that order could invert against `apply()`'s key-ordered header locks (`plant, production_order, material_number`) and against saves' id-ordered child locks. Repair is idempotent, so a partial run is safe.
- **Upload summary counts planned sub-orders** (`counters["children_total"]`), not rows written; `children_upserted` stays the written-row count.
- **Ingest is the third id-ordered writer.** `db.upsert_orders` locks each chunk's rows plus every sibling of a distribution child (same plant + parent order + material) `ORDER BY id FOR UPDATE` in ONE statement before it writes, so an upload, a `/tasks` save and `apply()` can never hold a pair of rows in opposite order; chunk transactions are committed before `apply()` runs (no lock is held across them). A SAP change on one child resets ALL siblings (slot, firm, segments), only rows already locked, never a second material of the same order. A child counts as SAP-changed on quantity only when the PARENT's SAP quantity changed vs the header's stored one (children carry planner-editable shares), so a re-weight racing an upload does not reset. The slot-carrying transitions carry the manual firm too: the N->1 collapse (`_collapse_to_survivor`) and the 1->N conversion (`_load_anchor_sources` -> `_carry_anchor_onto_new_child`). **What a new child carries is the placed FINISH, never a start (backward scheduling Task 2.7, OQ58):** the plain order's stored finish (1->N) or the latest stored finish among the header's existing children (`_compute_reweight_anchor`, re-weight) is copied onto the new child as `scheduled_end`, `scheduled_start` stays NULL, and `runtime_schedule_mismatch` is set so the browser derives the start; with no stored finish to copy the child stays unplaced. "Scheduled" for the removal guard, the dry-run `scheduled` flag, the orphan sweep, the list's `scheduled_children` count and the ingest stale-flag CASE is the `_PLACED_SQL` shape (a stored start, a stored finish, or segments), so a finish-only child counts. See `backend/integration/CLAUDE.md` for the full re-upload rules.
- **Children carry the parent's RAW SAP work center and production version** (`sap_workcenter`/`sap_production_version` set in `_plan_one_parent`) plus `sap_basic_*` dates, written by `_CHILD_UPSERT_SQL` as `COALESCE(EXCLUDED, stored)`. **Only ingest writes dates and locked originals (OQ29):** `_CHILD_UPSERT_SQL` (apply) SETs `basic_*`, `sap_basic_*` and `original_*_received` (the latter decided per child by `db._locked_originals`, the one echo rule); every planner write (re-weight / reset / repair, `_CHILD_UPSERT_SQL_PLANNER`) never SETs any of them on a conflict, and a child it creates inherits the header's originals with NO SAP baseline (the next upload fills it). The header's `original_finish_received` is written by `_insert_new_header` / `_write_header_facts` only, kept on an echo of the roll-up finish (`_header_finish_echo`: the sent finish of ANY member child, since `order_sap_sent` is per child; no sent row = not an echo; the sent row cascading away on collapse is the accepted one-cycle gap). `apply(..., sap_tz=)` carries the SAP frame in from `db.upsert_orders`. That statement no longer rewrites `upload_batch_id` and no longer treats `color` (re-stamped from master data) or a routing/manual run time as a difference, so an unchanged re-upload leaves a child's xmin alone. `apply()` returns `touched_ids` (the children it actually wrote) and `_stamp_batch_children(conn, ids)` re-stamps exactly those.
- **Regression tests:** `tests/test_distribution.py::TestApplyAndRepairLockOrderNeverDeadlocks` (apply vs save, repair vs apply/save, with stepped hooks and `pg_stat_activity` lock-wait polling, no sleeps), `TestUploadMessageCountsPlannedChildren`, `TestSapTruthDistributionReupload` (unchanged re-upload keeps child xmin; sibling reset; ingest vs save vs apply lock order).

## Schedule event history (2026-10-23)

`apply(..., ev=None)` mints `EventCtx('distribution', actor, as_action_id(batch_id))` and records once per parent chunk inside `_run_savepointed` before `RELEASE` (a rolled-back chunk drops its rows). `_apply_children(events_out)` widens its id-ordered `FOR UPDATE OF o` read to the tracked columns plus segment count and reads back after the loop (covers `_carry_anchor_onto_new_child`); it emits `create` (+`carried_from`) and `modify` (diff) rows, and `_delete_superseded_children` now `DELETE ... RETURNING` a bounded snapshot and emits `remove` (+`superseded_by` when exactly one new id). `_materialize_reweight(..., ev_actor=)` (re-weight, reset, repair) reads before/after with a dedicated tracked-column helper (`_ev_read`; NOT `_fetch_children_by_machine`, whose `basic_finish_date` is the COALESCEd locked original and would give phantom diffs) and records one batch after the `admin_audit` INSERT, `action_id` = the write's upload batch uuid; `_resolve_repair` plumbs `ev_actor` to `_repair_one_header`. Dry runs record nothing. Details: `backend/schedule_events/CLAUDE.md`.
