## What lives here

- `triggers.py` — **pure** (stdlib + APScheduler). `validate_schedule(row)` normalises a payload (presets compile to cron, times become naive plant-local); `build_trigger(row)` is the ONE place a row becomes a trigger; `next_fire_times` / `preview` use that same trigger, so the UI preview cannot disagree with what fires. `PlantCronTrigger` fixes stock APScheduler DST behaviour on zoneinfo (gap time 02:30 -> 03:30 EDT, ambiguous 01:30 fires once). Numeric cron day-of-week is translated from standard cron (0/7 = Sunday) to names because APScheduler numbers Monday as 0.
- `context.py` — **pure** `JobContext`: `ctx.log(level, msg, step=, **data)`, `with ctx.step(name)`, `ctx.cancelled/check_cancel()/sleep()`. Caps: msg 2 KB, data 8 KB (replaced by a `_truncated` preview), 2000 lines per run (line 2000 is a warn marker, `truncated` flag -> `job_run.log_truncated`). Rows flush to an injected sink (DB in production) every 0.5 s; warn/error also go to `_BACKEND_LOG` via the mirror.
- `registry.py` — `JobType(key, label, params_model, run, plant_scoped, default_timeout_s, timeout_fn, lock_key, stub, needs_plant_timezone, defer_clock, kind, mutates)`, `JobOutcome(status, summary, error, artifact)`, `describe_params(jt)` (per-param metadata for the generic form). Stub types are hidden from `GET /jobs/types` and refused by `POST /jobs` unless `NIMBUS_JOBS_STUBS=1`.
- `windows.py` (W2) — **pure** `DateWindow` + `resolve_window(window, tz, now, last_success_at, first_run_lookback_days)`. `window_service.py` reads the plant timezone and the job's watermark and calls it; the run (`types/reports.py`) and the dialog preview (`POST /jobs/windows/preview`) both go through `window_service.resolve_for_plant`, so the preview cannot disagree with the run. `artifacts.py` — **pure** artifact cap / page / CSV. `types/reports.py` — the five report types.
- `types/noop.py` (stub, logs steps, cancellable) and `types/optimizer.py` (`optimizer.plant`, params `mode` due_date|min_changeover|spt, `search` normal|exhaustive default exhaustive, `respect_firmed`, `apply_mode` propose|apply). **The runner plugs into the seam `optimizer.set_runner(fn)`**, `fn(ctx, plant, params) -> dict` (optional keys late, changeovers, moved, applied, dropped, action_id, warnings, steps, proposal, status='failed'); `scheduler.install` wires `optimizer_runner.run_optimizer`. Unwired (tests, tools), a run fails with a clear message. `apply_mode` defaults to `apply` (owner ruling 2026-10-28 W1, reversing the earlier Propose default); `propose` is a dry run. The optimizer type sets `needs_plant_timezone` (a schedule for a plant with no timezone is a 400, a job without a schedule is fine) and `defer_clock`.
- `data.py` — `JOB_DDL`, `ensure_job_tables()` (lifespan boot hook), queries, `boot_sweep()`, `sweep_job_runs()`, session advisory-lock helpers.
- `runner.py` — `run_job`, `start_manual_run`, `fire_schedule`, `record_skipped`, `cancel_run`, `cancel_all`.
- `scheduler.py` — `install(scheduler)` (called in the `brain.py` lifespan before `scheduler.start()`), `reconcile`, the 60 s tick.

## Lifecycle and invariants

- `scheduled -> running -> succeeded | warning | failed | cancelled`, plus `skipped` (overlap, misfire). `finish_run` only moves a row still `scheduled|running`.
- **Scheduling**: DB is the source of truth, no `SQLAlchemyJobStore`. One APScheduler job per active schedule `job:<schedule_id>` (`max_instances=1`, `coalesce=True`, `misfire_grace_time=misfire_grace_s`). `reconcile` adds/replaces (by a row signature)/removes every 60 s; an exhausted trigger is never added (it would be added paused). A missed fire (EVENT_JOB_MISSED) records a `skipped` run.
- A `once` schedule is retired when it fires or misfires; reconcile never re-arms one that has a run.
- **Overlap**: per (job type, plant) SESSION advisory lock (`jobs:<type>:<plant>`, pattern from `sap_staging.poll_once`) held on a pooled connection for the whole run. Taken by someone else -> a recorded `skipped` run ("previous run still running"); `skip_if_running=false` queues behind it instead.
- **Concurrency** 2 (`runner.MAX_CONCURRENCY`, a semaphore). **Hard timeout**: job `timeout_s` or the type's (`optimizer`: Normal 120 s, Exhaustive 600 s = search budget + 60 s, remeasure at W6); the body runs in an inner thread, on expiry the cancel event is set, a body that ignores it for 10 s is abandoned and the run is `failed: timed out after Ns`.
- **Cancel**: `POST /jobs/runs/{id}/cancel` sets the in-process event and `cancel_requested`; the supervisor also polls the DB flag every 2 s. A `scheduled` run cancelled before start becomes `cancelled`.
- **Boot sweep** marks leftover `scheduled|running` rows `failed: interrupted by restart` (single-replica assumption). Fires that happen while the process is down are NOT recorded (APScheduler memory store); only misfires inside a live process are.
- **Retry**: fixed policy only: after a `failed` attempt with `attempt <= retry_max`, wait 30 s and run again as a new `retry` row. Backoff is deferred.
- **Retention**: `system_settings.job_run_retention_days` (`md.get_job_run_retention_days`, clamped 1-60, default 14; `POST /system-settings` rejects anything else with 400). `sweep_job_runs` removes log lines by `run_id` then the run rows, in chunks of 500 runs under an advisory xact lock, never touching `scheduled|running`; daily job `nimbus:job-run-sweep` plus a +90 s boot one-shot. Result in `DIAGNOSTICS["job_run_last_sweep"]`.

## W1 run status (2026-10-28)

- **SAP-style semantics (owner 2026-10-28)**: no approval inbox; jobs are admin-only; **`apply_mode` now defaults to `apply`** (API and dialog). `propose` is kept as a **dry run**: its proposal is viewable (`GET /jobs/runs/{id}/proposal`) and there is no approve or discard route. The stored proposal now carries `snapshot_version` so the route can say whether the board still matches.
- **Failure classification**: a failed run's `summary` carries `error_kind` (`config` = fix the job or its inputs: bad params, plant without a timezone, blocked or refused apply, inputs changed; `system` = timeout, interrupted by restart, crash, DB) and `failed_step` and `steps`. `optimizer_runner._fail(kind=, step=)` sets them for the optimizer; `runner._describe_failure` fills the rest (default `system`; `failed_step` from `ctx.failed_step` / `ctx.last_error_step`; `steps` from `ctx.step_timings`); the boot sweep writes `system`.
- **Heartbeat**: `scheduler.record_tick()` runs after the install reconcile and each 60 s tick; `scheduler.heartbeat()` is `ok` while the last tick is under 180 s old (in-process, cleared by a restart). **Missed** = a `skipped` run whose error starts `missed:`; a fire expected but never recorded (process down) is still not detectable. **Longer than usual** = a running run past max(2x median of the job's last 10 succeeded/warning runs, 5 min), only with >= 3 such runs (`data.longer_than_usual`).
- The proposal rows join `db.get_task_versions` (machine, live finish, status, `row_version` vs the patch's `base_version` -> `changed_since`); "finish before" is the LIVE finish now, rows sorted by |delta| and capped at 200 with the full `total`. Restart is audited as `jobs.run_restart`.

## Fix-wave behaviour (2026-10-29)

- `scheduler.install` and `boot_sweep` never raise into `brain.py`'s scheduler `try` (a failure is a logged event; the SAP and sweep jobs still start). Scheduled fires run on their own bounded pool (`scheduler._FIRE_POOL`, 6 workers), not the shared anyio threadpool the UI API uses; surplus fires queue there. A fire for a plant that no longer exists records a `skipped` run and disables the job.
- **Timeout clock**: a job type with `defer_clock` (the optimizer) starts the hard-timeout clock at `ctx.begin_work()`, called once the optimizer slot is held, so queueing behind another plant never eats the run's time (cancel still works while waiting). Other types start it at once.
- A retry re-reads the job: archived, disabled or removed stops the chain; edited params are used. `POST /jobs/{id}/run` is a 409 while a `scheduled|running` run of that job exists. `cancel_all` (shutdown) also kills live child processes (`optimizer_runner.kill_children`).
- **Child limits**: stdout over 64 MB and a stderr line over 64 KB are cut (the child is killed on the first); child log keys that collide with `ctx.log` parameters are dropped; the stored proposal is measured as a whole object against 256 KB.
- **Apply phase clock**: the live board is read at the LIVE bundle's `server_now` (`params.liveServerNow`), the run snapshot at the run's. A started-since order is dropped as `running`. `tz_mismatch` (the child's resolved zone is not the plant's) fails the run and the apply; apply also answers `plant_no_timezone` and `inputs_changed:<part>`.
- **What guards what at apply**: `calendar_version` (from `db.plant_calendar_version`) covers ONLY the calendar tables (plant hours, periods, machine calendars, plant and machine blackouts) plus the plant's default week and timezone. The apply phase additionally compares, between the run's and the live snapshot, this plant's `plants` row, machine / work-center / tool-inventory master rows, own-hours line calendars and both blackout lists (`plantInputsDiff`, refusal `inputs_changed:master_data|plant_calendar|line_calendars|blackouts|plant_blackouts`); priority lists, setup truth and tool inventory are in `snapshot_version`. Per-order changes are the `row_version` drop; a distribution family is every order sharing PARENT_ORDER + MATERIAL_NUMBER in either bundle, and one changed, missing or running member drops every patched member.
- The snapshot token is read before the wire is built and again after (one retry); the token read before the final build is kept.
- Tests: `tests/test_jobs_runner_unit.py` (no DB), `tests/test_jobs_optimizer_runner.py`, `tests/test_jobs_contract.py`; JS `tests/modules/optimization/headless-guards.test.mjs` (live clock, tz_mismatch, a child process in America/Chicago across the 2035-11-04 fall-back, input drift, families, helper drift check).

## W2 report jobs and date windows (2026-10-30, branch `w2-reports`)

- **`DateWindow`** (`windows.py`): `{mode: fixed|rolling, fixed: {from, to}, rolling: {anchor now|start_of_day|start_of_week|start_of_month|last_success, from_offset, to_offset, unit day|week|month}}` (negative offset = past, `serialize_by_alias` keeps `from`). Resolved in the PLANT's timezone by CALENDAR date (a wall time in a spring-forward gap becomes the real instant; month offsets clamp to month end; weeks start Monday; the span of "last 3 days" is 71 h or 73 h across a transition, never 72 h by arithmetic). The window is `[start, end)`; the label shows the last INCLUDED date (`2026-09-28 to 2026-10-28`; an open start prints `before 2026-09-28`, `from_offset <= -3650` days). `last_success` anchors only the START (the job's last succeeded or warning run's `started_at`; none -> `first_run_lookback_days` calendar days before now, param default 1) and the END is the run's own now, so "since last successful run" is offsets 0/0. A missing or unknown plant timezone is a `WindowConfigError` (`kind 'config'`): the run fails with `error_kind config`, `failed_step window`. Presets: `older_than_days`, `last_days`, `next_days`, `since_last_success`, `this_week`, `this_month`.
- **Param metadata** (`describe_params`): `{key, type string|enum|boolean|integer|number|multi_enum|date_window, label_key, title, default, required, widget, enum, enum_label_keys, min, max, pattern}`; a DateWindow param carries `x-widget: 'date-window'` (`Field(json_schema_extra=...)`). Label keys are `jobs.p.<type>.<param>[.<value>]` (frontend falls back to the schema title / raw value; the optimizer's keep their pre-W2 strings through `LABEL_ALIASES`). `tests/fixtures/jobs_types.json` is the live registry dump (`scripts/dump_job_types.py`), asserted equal by `tests/test_jobs_contract.py`, and read by the frontend form tests.
- **Report outcome**: a report body returns `JobOutcome(status, summary, artifact={sections:[{key,title,columns,rows}], summary})`. The runner stores it BEFORE `finish_run` (`runner._store_artifact`), so a viewer that sees the run finished always finds it; a save failure never fails the run (`summary.artifact_error` + an error line). `summary` carries `row_counts` per section (before the cap), `rows`, `window` (the resolved window, also logged) and `artifact: {row_counts, size_bytes, truncated}`. Cap: 5 MB of stored JSON text (`NIMBUS_JOBS_ARTIFACT_MAX_BYTES`), rows are cut from the largest section until it fits and the section gets `truncated: true` (`row_count` stays the real total). The retention sweep removes `job_run_artifact` rows by run id in code before the run rows (`deleted_artifacts` in its result). Reports are read-only (`mutates=False`), one run at a time per (type, plant) like every type, `default_timeout_s` 120, and have no outbound delivery (no email/Teams channel): the run viewer and per-section CSV are the result.
- **The five types** (`types/reports.py`; see the W2 fix wave below for the status rule): `report.what_changed`, `report.late_orders`, `report.missing_master_data`, `report.coverage` (selectable `tools` / `priority_lists` / `setup`), `report.distribution`. KPI snapshot is deferred (needs the headless-core phase and a kpi table).

## W2 fix wave (2026-10-29, branch `w2-fixes`, on top of `w2-reports`)

- **Report status (owner ruling): report CONTENT NEVER CHANGES RUN STATUS.** A report that ran to the end is `succeeded` with its counts in `summary` (`findings` and the per-report keys) and the tiles; `failed` only when the run did not complete. `late_orders`, `missing_master_data`, `coverage`, `distribution` take an optional integer `warn_if_over` (default null = never); the run becomes `warning` only when the report's finding count EXCEEDS it (late: late placed orders + queued past due; missing master data: unmatched pairs; coverage: unranked values + missing OBSERVED setup pairs + tools with no usable copy; distribution: unresolved orders). `what_changed` has none and never warns. The generic form renders it as an optional number box (blank clears to null).
- **Resolver** (`windows.py`): every bound is rebuilt from its OWN calendar date at the first valid instant of that date (a day with no local midnight, e.g. Sao_Paulo 2018-11-04, starts 01:00 for that bound only); only `now` and `last_success` keep a wall time. The label comes from the requested dates (a fixed range labels `from to to` exactly; a rolling end that is the first valid instant of its date prints the day before). Fixed dates are bounded 1990-01-01..2100-12-31 (422/400 beyond), a year overflow is a `WindowConfigError` (preview route 400, run `failed/config`), a zero-width window is a config error for non-`last_success` anchors, and a `last_success` watermark in the future falls back to the lookback.
- **`last_success` watermark** (`data.last_success_watermark`): the previous SCHEDULED (`trigger='schedule'`) succeeded or warning run's `summary.window.end` (fallback `started_at`), so manual runs never move it and consecutive windows are contiguous. The END is `now - LAST_SUCCESS_MARGIN_S` (120 s) so a commit in flight at the run's start is picked up by the next run (`summary.safety_margin_s` says so). The old `last_success_started_at` stays for compatibility.
- **`report.what_changed`**: one scan (`WITH ev AS MATERIALIZED` + `GROUPING SETS` for source / actor / op / total, plus the top-N orders) under `idx_schedule_event_plant_at (plant, at DESC)`; sources are grouped into planner categories (`planner`, `optimizer`, `ingest`, `routing`, `purge`, `distribution`, `other`; `SOURCE_CATEGORY`) with the raw source kept as a detail row; the artifact has no `order_id` column (production order first) and `last_change` is plant-local; a window starting before `now - schedule_event_retention_days` adds `summary.window_truncated` + `retention_days` and a `notes` section row (status unchanged).
- **`report.late_orders` uses the APP's due rule** (`backend/jobs/due.py`, twin of `dueDateInstant`, pinned by `tests/fixtures/due_rule_vectors.json` run by both `tests/test_jobs_due.py` and `tests/js/compute-core.test.js`): a date-only due (exact midnight) is the close of that day's working window (line hours ∩ plant hours incl. effective-dated periods, 30-day look-back, capped at the next midnight, else 23:59:59; blackouts are not considered, as in the app); late = finish strictly after it; a queued (`needs_planning`) order counts late against the plant clock. The window applies to the DUE instant: due before the window start is the **Already overdue** bucket, due inside the window is included even when the order finishes after it; placed orders that finished before today are history (same as the alert scan). Sections `by_machine`, `orders`, `queued` (state `past_due` / `due_soon`). The roll-up and the true total are computed over the UNCAPPED set (in Python after one superset query, because the due rule needs the calendar); only the detail rows are capped (`late_orders` total vs `late_orders_shown`, `capped`).
- **`report.coverage`**: setup section skipped with a `setup_off` note when `plants.setup_active` is false; a priority field with zero ranked values is a `no_list` note, not noise; `reachable` is never a finding; tools gain `usable_qty` and `no_usable_copy`; sentinels `__plant_total__` / `__plant_wide__` and reason codes are translated by the client. `report.distribution` passes `end - 1 µs` as `date_to` (`get_aggregate` compares `<=`), sorts headers with queued children first and caps rows (`headers_truncated`); `missing_master_data` and unresolved lists sort by `order_count` desc.
- **Artifacts**: column objects are `{key, label, type}` with `type` text | number | date | datetime | bool (`artifacts.col`); bool cells are real booleans, date / datetime cells ISO strings (naive plant-local); `cap_artifact` drops remaining rows then sets `summary.artifact_error = 'too_large'` if the skeleton alone exceeds the cap (the runner copies it to `summary.artifact_error`); NaN / inf become null. Reports are read-only: our own transactions are `SET TRANSACTION READ ONLY` and a test scans `types/reports.py` for write SQL words.
- **Deferred (recorded, not built):** per-order changed-field summaries in `what_changed`; KPI snapshot; outbound delivery (email / Teams).

## W3a multi-plant jobs (2026-10-31, branch `w3a-multiplant`, not merged)

One job definition can target many plants, fan out into per-plant runs under a batch, and read its schedule in each plant's zone, one fixed zone, or UTC. **A job with no target rows is exactly the old single-plant job** (same ids, same runs, no batch row).

- **Schema** (new TABLES only in `migrations/2026-10-31-1-job-targets.sql`, `JOB_TARGET_DDL`, pinned verbatim in migration + `schema.sql` like the other DDL; CREATE-only, no destructive words or cascade, so the deploy gate passes): `job_target(id, job_id FK, kind explicit|subnetwork|all, value, excluded, params_override JSONB)` and `job_batch(id, job_id FK, schedule_id FK, scheduled_for, trigger schedule|manual|restart, triggered_by, status running|succeeded|warning|failed, counts JSONB, started_at, ended_at, summary JSONB)`. **Columns on existing tables come from the startup hook only** (`JOB_COLUMN_DDL`, run by `ensure_job_tables`, mirrored in `schema.sql`, never a migration ALTER): `job_run.batch_id` (FK, partial index), `job_schedule.tz_mode` ('plant' default | 'fixed' | 'utc') and `fixed_timezone`, `job_definition.fan_out` JSONB `{stagger_s 0-3600, max_parallel 1-50|null, fail_fast}`.
- **Subnetwork exists**: `plants.subnetwork` (PK `(subnetwork, plant)`), so kinds `explicit`, `subnetwork` and `all` are all implemented. Named regions / tags are not (deferred). `job_definition.plant` stays the HOME plant (RBAC, history, the Jobs list filter's primary key).
- **`targets.py`** (pure, plant rows injected): `expand_targets(job, now, plants=)` -> `{plants:[{plant, timezone, skip, params_override}], warnings, single}`. Order = row order, then plant code inside a subnetwork / all; excluded rows (explicit or subnetwork) subtract from the union; a plant with no or an invalid IANA timezone, or one removed, stays listed with `skip` (a skipped child run, `error_kind config`; never armed). `all` stores `*` for an unrestricted admin or the admin's own plant list (a scoped admin's "all" never grows into plants they cannot reach). `params_override` is deep-merged (`deep_merge`) over the job params for the plants its row contributes. `rollup`: failed if any child failed, warning if any warning / skipped / cancelled, else succeeded; `counts_of` adds `total`. Expansion happens at FIRE time (new plants join a subnetwork / all automatically); `data.load_plant_rows()` is read fresh by every reconcile and request.
- **Scheduler arms** (`scheduler.plan_arms`, pure): `plant` mode with targets = one APScheduler job per runnable plant `job:<sid>:<plant>` in THAT plant's zone; `plant` mode without targets keeps `job:<sid>` but in the plant's CURRENT zone (the stored zone only when the plant has none); `fixed` / `utc` = one `job:<sid>` that fans out inside `fire_schedule`. `_sig` carries the effective zone and `arm_plant`, so a zone edit, a plant joining / leaving the set or a target edit re-arms at the next reconcile; stale ids (including the old `job:<sid>` once a job gains targets) are removed by the existing `have - want` pass. A skipped plant is logged once per schedule (`_WARNED`), not recorded as a run, in `plant` mode (nothing fires for it). A `once` schedule armed per plant is spent only when every runnable plant has a run (`data.schedule_fired_plants`), so the first plant's fire does not remove the others. `_on_missed` parses both id forms and records the skipped run for that plant.
- **Fan-out** (`runner.prepare_batch` / `execute_batch`): fire inserts a `job_batch`, then ALL child `job_run` rows up front (`batch_id`, `plant` per child; skipped / config-failed children already terminal), then runs the pending ones: `stagger_s` between child STARTS, `max_parallel` live children (on top of the global `MAX_CONCURRENCY` 2 and the per-(type, plant) lock), `fail_fast` stops launching after a failure and records the rest `skipped` ("stopped: an earlier plant failed"). Each child's merged params are validated through the type's model BEFORE it starts; a failure fails only that child (`config`, `failed_step validate`). `run_job(plant=, override=, batch_id=)` re-applies the override on every retry. The batch rolls up from the newest run of each plant (a retry replaces its failed attempt) in `data.finish_batch`, which sets `ended_at` only when every child is terminal. The scheduled path blocks one of the 6 fire-pool workers for the batch's whole duration (a long stagger holds it); manual run / restart dispatch on their own thread. Plant mode: each plant's fire is its own batch of one.
- **Boot sweep** fails running batches too (`error_kind system`, "interrupted by restart") after the child runs. **Retention** removes batches (older than the window, no runs left) after the runs in the same chunk transaction (`deleted_batches`).
- **Routes**: `POST/PATCH /jobs` take `targets` (`[{kind, value, excluded, params_override}]`, `[]` clears) and `fan_out`; schedules take `tz_mode` / `fixed_timezone`. SAVE-time scope: every plant the targets expand to must be in the admin's allowed plants (403), an unknown plant or subnetwork, an empty expansion and an invalid merged override are 400. `POST /jobs/targets/preview {targets | kind,value,excluded[], offset, limit<=500}` -> `{plants:[{plant,timezone,warning}], count, skipped, warnings}` (authenticated, same scope check). `GET /jobs/batches?plant&job_id&status&limit&before_id` and `GET /jobs/batches/{id}` -> `{batch, runs}`: a scoped caller only sees batches with a run in their plants and counts / status over those plants. `POST /jobs/{id}/run` and `/runs/{id}/restart` answer `{run, batch}` (`run` = first child, `batch` null for a single-plant job; 400 when the targets expand to nothing); both go through the same fan-out (`trigger` manual / restart). `POST /jobs/schedules/preview` accepts `tz_mode`, `fixed_timezone`, `targets`, `plant_offset`, `plant_limit<=50` and answers `{timezone, cron_expr, entries, plants:[{plant, timezone, entries}], total_plants, warnings}` (`plants` only for per-plant mode with targets). `GET /jobs/{id}/upcoming` and `/jobs/upcoming` list fires per plant arm (`plant`, `timezone`, `at_local` in that plant's zone). The job wire adds `fan_out`, `targets`, `target_kind` (single|selected|all|subnetwork|mixed), `target_count`, `target_skipped`; a run adds `batch_id`; a schedule adds `tz_mode`, `fixed_timezone`. The Jobs list `plant` filter matches the home plant OR any targeted plant. No new write route needs an audit entry (`run`/`restart` already are listed).
- Tests: `tests/test_jobs_multiplant.py` (expansion, arms, rollup, fan-out with a fake runner and in-memory data, pg: scope 403, batches, reconcile re-arming, fixed / utc, boot / retention sweep), `tests/test_jobs_contract.py` + `tests/fixtures/jobs_contract.json` (new shapes).
- **Deferred to W3b / later (not built):** DST policy choices, day filters / closed-day action, catch-up of fires lost to downtime, maintenance mode, run windows, a runs timeline, named regions / tags, a skipped child run recorded for a no-timezone plant in `plant` mode (it is only warned about), cancelling a whole batch, per-plant `params_override` editing in the UI (the API and storage work).

## Known limitations (accepted for the pilot)

- **Periodicity filter** uses the schedule's CURRENT kind (a schedule edited from daily to weekly moves its old runs to Weekly).
- **Missed** counts recorded misfires only; fires lost to downtime need W3's persisted `last_fire_at` / catch-up.
- **Heartbeat** reflects the reconcile tick, not each job's own firing.
- **Pre/post KPIs** (late count before and after) are deferred.

- **Boot sweep ownership during a rolling revision**: `boot_sweep` marks every `scheduled|running` row `failed: interrupted by restart`. While the old and new revision overlap, the new one can fail the old one's live runs (the old body keeps running and its `finish_run` is then a no-op). Safe only because the pilot is single-replica; a lease/heartbeat column is the fix.
- **Hourly preset on the fall-back day**: the DST-aware trigger fires an `hourly` job once per wall-clock hour, so the repeated 01:xx hour fires once and that day has one slot fewer than 24. Daily and weekly presets are unaffected.
- A body that ignores cancel past the 10 s grace is abandoned: the run is `failed`, the advisory lock and run slot are released, and the abandoned thread may still finish (the optimizer's write phase checks `ctx.cancelled` right before the write, so a timed-out run cannot write after the timeout; a write already started is not interrupted).

## Optimizer runner (`types/optimizer_runner.py`)

- **Bundle**: `gather_bundle(plant)` builds the `HeadlessWire` in-process (`build_tasks_payload` validated through `_TASKS_ADAPTER` as the wire `/tasks`, `md.load_plant_calendar` + `calendar_version`, `setup_data.get_setup_snapshot` + `plant_active`, `plcache.PLANT_LISTS`, `md.list_rows` plants / machine / sap_workcenter / tool_inventory, `db.plant_horizons` version tokens) plus `server_now` and `sched.optimizer_snapshot_version(plant)` (also served as `GET /optimizer/snapshot-version?plant=`: sha1 over priority lists, setup, calendar and tool inventory versions).
- **Child**: `node [--max-old-space-size=NIMBUS_OPTIMIZER_NODE_MB, 1536] headless-cli.mjs --phase run|apply --input -`, env `TZ=<plant timezone>` plus PATH/SYSTEMROOT/TEMP only (never the DB credentials), JSON on stdin/stdout, stderr JSON lines mirrored into `ctx.log` (a line with `ms` also feeds `summary.steps`). Hard timeout = search budget (Normal 8 s, Exhaustive 180 s) + 60 s; killed on timeout and on `ctx.cancelled`. Env knobs: `NIMBUS_NODE_BIN`, `NIMBUS_HEADLESS_CLI`, `NIMBUS_OPTIMIZER_CONCURRENCY` (1-2, default 1, a process semaphore on top of `runner.MAX_CONCURRENCY`).
- **Propose**: patches, `base_versions` and up to 50 findings go on `summary.proposal` (over 256 KB: counts only, `proposal_truncated`); blockers make it a `warning`.
- **Apply**: blockers or error findings fail the run; fresh bundle; a changed snapshot token fails it; `--phase apply` drops changed-`row_version` families (`warning` and a `dropped` list in the log), refuses on calendar / tool inventory change; the token is checked again right before the write; the write is `sched._apply_task_date_updates(..., atomic_optimizer, strict_conflicts, actor 'job:<id>', client_id 'job:<id>', ev=EventCtx(source 'optimizer'))`, never forced, so a stale or conflicting row rolls the whole batch back and the run fails. `summary.action_id` links to the Inspector history.
- Summary keys: late, moved (patches proposed), applied, dropped, setup_minutes, search_complete, termination, tool_blocked, steps, warnings, action_id (`changeovers` is not reported). Tests: `tests/test_jobs_optimizer_runner.py` (fake node script; one real-node smoke).
