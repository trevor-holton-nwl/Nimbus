# Master Data — pointer

Substantive docs for this domain live at `backend/master_data/CLAUDE.md`.

`MaterialGrids.setQuickFilter(which, text)` (`material-grids.mts`) sets a grid's quick-filter text from code: applied at once when the grid is ready, else kept and applied in `onGridReady` (the Alert Monitor's routing-gap cards call it right after `App.gotoMasterSub('routing-pv')`).

Master Data > Plant has a fourth inner tab, **Calendar** (`data-plant-tab="calendar"`; both `gotoTab` literals in `admin-ui.mts` carry it), owned by `frontend/calendar/calendar-periods-ui.mts` (see `frontend/calendar/CLAUDE.md`). The Working Hours panel moved there (now "Default week"), and so did Plant Blackouts (2026-10-19: editable, planner-writable, marked on the period timeline); General keeps the Production Lines roster.

**Machines pane hours (2026-10-23).** The detail pills and the Plant roster pills read `Store.activeLineHoursOn(line)` (the pattern in force today), not the default week. An inherited machine's note names its source: `ui.follows_plant_period` (period name + dates, `ui.no_end_date` when open-ended) or `ui.follows_plant_default`. An override whose hours are narrowed by the active period reads `ui.capped_by_plant_period`; otherwise the existing `ui.limited_by_plant_hours` check (union of all periods) stands. Edit Calendar still opens on the default week.

**Tool Inventory sub-tab (2026-10-27, `tool-inventory.mts`).** Master Data > Tool Inventory (`data-md-master="tool-inventory"`, pane `md-master-tool-inventory-pane`, registered last in `_MASTER_SUBS`) edits ONE plant's tool copies; the plant follows the top-bar plant. `ToolInventory = { init, render, refresh, setQuickFilter, openForTool }` (plus `_addRow/_save/_discard/...` hooks used by tests). `init()` is called from the shell (`App.init`, idempotent) and subscribes to `plant:selected`, `master-data-changed`, `sandbox:*` and `tasks:bulk`. The pane DOM is built by the module, not index.html.
- **Rows come from the Store**, not a grid fetch: `Store.masterData.tool_inventory` (`undefined` = not loaded/failed -> inline error + Retry via `Persistence.refreshToolInventory`; `[]` = loaded and empty -> EmptyState with Add row). A row tagged for another plant is treated as "still loading". Rows carry a client id `_cid` (`getRowId`), never the typed Tool ID.
- **State/draft model.** Live state = `rows` (new + saved, each with `_isNew` and `_orig`, the saved values it was loaded from) + `deletes` (STAGED removals of saved ids). A plant switch retains `{rows, deletes}` in a per-plant draft; returning restores it (rebased on the Store rows) with `toast.tool_inventory_draft_restored`. A remote change (`master-data-changed` for `tool_inventory`, i.e. the freshness probe or our own refetch) REBASES: a field the user did not touch follows the server, an edited field keeps the user's value, a saved row another session removed is DROPPED when the user left it untouched (never resurrected as a dirty row) and is kept as a new row, with `toast.tool_inventory_remote_deleted_kept`, only when the user had edited it; a staged delete of a vanished row is dropped. Last write wins at the server (no version check).
- **Validation** (every edit, cached until the next edit): Tool ID trimmed + UPPER-cased on commit, placeholders (`-`, `0`, `N/A`, `NONE`, `NULL`, `NAN`, `TBD`, blank) and > 100 chars rejected, case-insensitive duplicates across saved + new rows (a staged delete is not a row, so a re-added id never collides with its own old row), Total/Out of Service whole numbers 0..1,000,000, Out of Service <= Total (blank = 0), Note <= 500. `normalizeToolId`/`TOOL_PLACEHOLDERS` are a local copy pinned to `NimbusComputeCore` by a test. Invalid cells: `md-cell-invalid` + warning glyph + `aria-invalid` + the message as `title` (never colour-only); Save is disabled while any row is invalid, while writing, and while `Sandbox.active` (What-If), and edits are disabled in those states and after a 403 (`readOnly`, optimistic like MaterialGrids).
- **Locked id.** Saved Tool IDs are not editable (`ti-cell-locked`, tooltip `ui.tool_id_locked_hint`): no rename. A typo fix = delete the old id and add the new id; both go in ONE `/bulk` call.
- **Delete + save flow.** Delete selected stages saved rows (a never-saved row just disappears). Save builds ONE `POST /tool-inventory/{plant}/bulk` `{upserts: new + changed (normalised), deletes: staged, source: {kind: 'grid'}}`. A staged delete whose id is back as a row in the same save is an edit (upsert only: no delete, no usage call, no confirm). For the remaining deletes it first calls `POST /tool-inventory/{plant}/usage`; any count > 0 opens a `Modal.confirm` (tone warn, id + count + first 5 order numbers + "removing a row treats it as 1 copy; set Out of Service = Total instead"); an unreadable usage (network/403) opens the "could not check, remove anyway?" confirm; Cancel aborts the WHOLE save and keeps every staged edit (every `Modal.confirm` is a confirm-modal and `_modalOpened` in `frontend/platform/foundation.mts` focuses `#confirm-cancel-btn`, so Cancel is the default; Escape and a backdrop click cancel too). On success: toast, local commit (rows locked, deletes cleared, draft dropped), `await refreshStoreMasterData('tool-inventory-save','tool_inventory')` (moves the freshness baseline so the probe does not announce our own save), then the existing `master-data-changed` -> Alerts recompute does the rest. `tool-conflict` alerts are counted before the save; the watch subscribes before the refetch but its 3 s guard starts only after the refetch resolves, and it counts only an `alerts:change` that arrives AFTER the tool_inventory `master-data-changed` (an earlier or unrelated one is ignored; no such event inside the guard = silent): fewer for the same plant -> `toast.tool_alerts_cleared`. 400 `detail` ("Cannot save tool inventory: a; b ...") is split into an inline `role=alert` list + `toast.tool_inventory_save_failed`; edits stay.
- **Used by** = orders of the plant in the loaded Store tasks carrying the id in either PRT column (one count per order, built once per render/`tasks:bulk`); the header tooltip says "loaded window". **Status line** (`role=status`) always says inventory feeds alerts; the "Tooling rule: Off/Hard (optimizer)" text shows only when `TOOLING_RULE_CONTROL_READY` (exported from `admin-ui.mts`, `false` until Wave 6 flips it) is true.
- **Layout measurements** (node estimate from the five locale files, 7.2 px/char for 12.5 px semibold headers, 52 px cell chrome; NOT browser-verified): numeric headers wrap to two lines (`wrapHeaderText` + `autoHeaderHeight`), widths Total/Out of Service 150 (usable 98 px; longest word "Gesamtbestand" 94 px), Available/Used by 130 (usable 78 px; longest word "Disponible" 72 px), Tool ID min 170 / Note min 200; longest header strings: "Inventario total" 115 px, "Fuera de servicio" 122 px (2 lines). Toolbar: the original six buttons (Add row, Add tools in use, Delete selected, Export CSV, Discard, Save) total 487 px (en) to 669 px (fr); the three Excel buttons (Template, Export Excel, Upload Excel) add 308 px (en) to 357 px (de), longest single button 147 px ("Excel exportieren"), so all nine come to 967 px (en) to 1,268 px (de) beside a 260 px quick filter + 240 px filter select: `.table-toolbar` has `flex-wrap`, so the five locales never overflow (they wrap to a second and third row). Filter select longest option 232 px (de/fr; select is `flex: 0 1 240px`, min 190). Status line wraps (<= 518 px). Fallback everywhere: wrap, never truncate or scroll horizontally.
- **Review-fix wave (2026-10-27).** ONE AG Grid for the module lifetime (`_gridApi`, like MaterialGrids): `_blank(prev)` resets per-plant state but the grid, the filter select and the quick filter carry over, and `render()` always pushes the current rows (an empty list when not ready), so a plant switch can never stack a second grid. `_loadFromStore` shows `loading` (never `failed`) while `Persistence.isLoading()` or a tool-inventory refresh for the plant is in flight, and re-checks every 400 ms (bounded) because a load that ends without rows emits nothing. Typed ids also drop zero-width characters/nbsp and a numeric `.0` suffix (same as `master_data.normalize_tool_id`); the compute-core mirror `normalizeToolId` used for Used by is unchanged. A staged delete re-added with identical values is 0 changes. Only a 400 lists the server's problems inline. The post-save alert watch subscribes before the refetch but acts only on an `alerts:change` after the tool_inventory `master-data-changed`, and compares tool-conflict counts for the same plant. `render()` never runs while the Master Data top tab (`#masterdata-tab`) is not `.active`.
- **Add tools in use** (`btn.add_tools_in_use`): draft NEW rows (1 copy, none out of service) for every normalised tool id on plant orders in the loaded Store tasks (either PRT column, placeholders excluded) that has no row, draft or staged delete; sorted, de-duplicated, capped at 500 (a second toast says so); the tooltip says "orders in the loaded window". Filters: **In use now** = saved rows whose tool is carried by an order whose tool-occupancy interval covers the current time (`NimbusComputeCore.toolOccupancyInterval` when reachable, else start/end dates); **Used but no row** is select-and-add by design (no read-only ghost rows): it shows the draft new rows of used tools plus an inline line with the count of used tools still without a row and an Add tools in use button. There is NO "Updated" column: `GET /master-data/tool_inventory` does not return `updated_at`.
- **Excel flow (Wave 4b).** Toolbar buttons Template (`btn.download_template`), Export Excel (`btn.download_data`; distinct from the grid's Export CSV) and Upload Excel (`btn.upload_tool_inventory`). Template/Export are `GET /tool-inventory/{plant}/template.xlsx|export.xlsx` through `Util.fetchTraced`, blob + anchor (`_seams.saveBlob`), filename from Content-Disposition (`filenameFromDisposition`, sanitised) else `tool-inventory[-template]-<plant>.xlsx`, `toast.export_failed` on error. The template also lists tools in use that have no row (server side). Upload: the hidden `<input type=file accept=.xlsx>` opens first (the click keeps its user gesture; a cancelled picker fires no change event and changes nothing), and only once a file is chosen do unsaved grid edits open the existing discard confirm (declined -> `toast.tool_inventory_upload_dirty`, nothing sent); the chosen File is POSTed as multipart `?dry_run=1` (nothing written), the REVIEW MODAL opens, and Apply re-POSTs the SAME File (a fresh FormData) with `?dry_run=0`. There is no review token: the server re-parses and re-diffs at apply time, so the applied counts can differ from the review if someone saved in between (the summary toast shows the applied counts). The response type is decided by what was sent, never by sniffing fields. After a successful apply: `toast.tool_inventory_upload_done` (warn tone when rows were rejected), a `role=status` `aria-live` result block (`#ti-upload-result`) with the returned warnings (also `ErrorLog.warn`, capped 10), `await refreshStoreMasterData('tool-inventory-save','tool_inventory')`, a re-render of the grid (skipped when the grid shows another plant or holds unsaved edits, e.g. made while the review was open: those are never clobbered, the next Refresh/save rebases), and the same 'N tool alerts cleared' watch as the save flow. Failures: 413 -> `toast.tool_inventory_upload_too_large`, 403 -> read-only + `toast.no_write_permission`, 400/other -> `toast.tool_inventory_upload_failed` with the server's detail; a failed or cancelled review writes nothing. All three buttons are disabled while a request is in flight (module `_busy`), Upload also while saving, read-only, What-If or with no plant.
- **Review modal contract** (`#modal-tool-inventory-review`, static shell in `index.html` with `data-no-backdrop-close`; body rendered by `reviewHtml()`). What the UI relies on from the dry-run response: `counts{new,changed,unchanged,rejected}` (exact; drive the summary and `N = new + changed`), `new[]` (`tool_id,total_qty,out_of_service_qty`), `changed[]` (`tool_id,before{total_qty,out_of_service_qty,note},after{...}`), `rejected[]` (`row` = Excel row number, `tool_id`, `error`), `warnings[]` (strings or `{msg}`); the lists are capped at 200 by the server and the UI computes `and N more` from the counts. Shows the file name, `N new, M changed, K unchanged, R rejected`, the Changes table (Tool | Total | Out of Service | Note, `3 -> 4` only where a value changed), New tools, Rejected rows, Warnings (cap 10), the permanent sentence 'Rows missing from the file are left unchanged.' and, when R > 0, a `role=alert` 'Rejected rows will be skipped; the valid rows will still be saved.'. The primary button 'Apply changes (N)' (no plural form needed) is disabled at N = 0; Cancel carries `data-autofocus` (default focus), Escape (a document keydown listener while the review is pending) and the close button cancel; the backdrop never closes it. Focus trap, `aria-labelledby` and focus return come from `Modal.open/close`.
- **Manage Data registration.** `tool_inventory` is a `MasterDataTable` in the admin grid engine (`data-md-tab="tool_inventory"`, admin-only like the rest of Manage Data): `TABLE_LABELS`, `KEY_COLS ['plant','tool_id']`, `NEW_ROW_DEFAULTS {total_qty:1, out_of_service_qty:0}`, `FK_SOURCE {plant:'plants'}`, `SCOPED_TABLES` (plant, appended after the machine/material_plants lines the regex pin matches), `AUTO_SCOPE_FROM_SELECTED_PLANT`, `UPLOAD_ENDPOINT '/tool-inventory/{plant}/upload'` + `UPLOAD_TOAST_STEM`. `resolveUploadEndpoint(endpoint, plant)` (exported pure helper) substitutes the grid's scope-filter plant; with no plant `_uploadFile` toasts `hint.scope_pick_plant` and aborts. Manage Data has no review step of its own, so for this table `_uploadFile` calls `ToolInventory.uploadFile(plant, file)` (lazy import: tool-inventory imports admin-ui, so a static import would cycle) and then reloads the grid. The grid's `_save` runs `ToolInventory.confirmRemovals(plant, ids)` (the same in-use / could-not-check confirm as the planner grid, per plant, skipping ids that are also upserted in the same save) before the bulk write; its post-save `refreshStoreMasterData('master-data-save', 'tool_inventory')` refetches the selected plant's rows so the Store never goes stale.
- **Alert deep link.** A `tool-conflict` alert that carries its tool (`a.tool` or `msgVars.tool`) offers 'Open tool inventory' (`ui.alert_open_tool_inventory`) in the alert drawer row and the cell briefing card (`AlertsUIAdapter.openToolInventory(alertId)`), and the Alert Monitor Top-fixes tool card has it in its menu (`am.act_open_tool_inventory`, act `tool-inventory`, not admin-tagged; the primary stays Go to). All three do `App.goto('masterdata')`, `App.gotoMasterSub('tool-inventory')`, then lazy-import and call `ToolInventory.openForTool(plant, tool)` (alert plant, else the selected plant; it switches the top-bar plant when needed and sets the quick filter). It is offered for a zero-copy alert too: raising the copies is the remedy there. `.alert-actions` / `.ac-card-actions` now wrap, because the longest label is 231 px (es) beside Go to / Fix / Dismiss.
- **Excel/review measurements** (node estimate, 7.2 px/char for 12.5 px semibold headers, 7 px/char + 28 px for 12.5 px buttons, 7.8 px/char + 32 px for the 14 px modal footer; NOT browser-verified): the review table in a 720 px body = four ~180 px columns, longest headers "Inventario total" 131 px, "Fuera de servicio" 138 px, "ID de herramienta" 138 px, longest word 110 px ("Inventario"), so headers wrap on word boundaries and never truncate (cells use `overflow-wrap: anywhere`); the summary line is <= 479 px (es), one line; the Apply button is 172 px (en) to 250 px (fr, with a 4-digit count), Cancel <= 102 px. Fallback everywhere: wrap, never truncate; the modal body scrolls (`max-height: 70vh`).

**Tooling rule control (Tool Inventory Wave 5, 2026-10-27; gated).** System Settings > Scheduling Rules > Order Rules gets a `.sched-rule-row sched-rule-row--wide` with `data-rule-key="toolingRule"`: a drop-down `#sys-tooling-rule` (Off / Hard; stored as `setup_policy_config.toolingRule` 'off'|'hard') and an inline hint `#sys-tooling-rule-hint`, rendered ONLY while `TOOLING_RULE_CONTROL_READY` is true (now `export let`, initial `false`; Wave 6 flips the initial value in its last commit; `__setToolingRuleControlReady` is a test hook, tests cover both values). Planners can change it: there is NO `Session.isAdmin()` gate and the route (`POST /master-data/plants/{plant}/tooling-rule`, body `{subnetwork, tooling_rule}`) is planner-level; a 403 or network error reverts the select and toasts `ui.tooling_rule_failed`. The change handler is cloned from `saveUnknownSetupPolicy`: it disables the select while posting, then `commitOrderRule` merges the returned `setup_policy_config` into the LIVE Store row in place (no `Store.setMasterData`, no pane rebuild) and nudges alerts. `RULE_HELP.toolingRule` (now exported) feeds the right-click More info popover (two paragraphs, no `< > &`, "Tool 1 / Tool 2" wording, no SAP field codes). The Tool Inventory status line shows "Tooling rule: Off/Hard" plus a "Change in plant settings" button (`#ti-rule-link`: `App.goto('masterdata')`, `gotoMasterSub('plant')`, `Plant.gotoTab('settings')`) only under the same gate.
