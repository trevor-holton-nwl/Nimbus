# frontend/setup — pure setup resolution and the Setup Matrix admin console

## What lives here

- **`setup-domain.mts`** (595 lines) — pure setup-transition canonicalization/resolution. **No browser, Store, network, persistence, or cache dependency**; holds zero module-level or mutable state. Exports:
  - `normalizedValue(value)` — canonicalizes one setup-attribute value (trimmed/uppercased, except literal `"true"`/`"false"` which stay lowercase) — the single source of truth for setup state-value canonicalization on the client, mirroring `backend/setup/data.py`'s `_normalise_value` **only for real booleans**: the server upper-folds the *string* "true" to "TRUE", so server-sourced strings (machine-state keys, stored rows, observed order values) are re-run through this client rule before any value-default lookup (the server twin for default keys is `canonical_default_value`).
  - `stateSignature(state)` — stable string key for a canonical state: values joined with a NUL (`\u0000`) separator so `('10','220')` and `('102','20')` can never collide (#45); do not key an unvalidated state this way.
  - `buildSetupResolutionIndex(input)` / `SetupResolutionIndex` (interface) — an optional caller-owned O(1) lookup index over matrix rows/overrides **and value defaults**, so a caller resolving the same plant snapshot thousands of times (the optimizer) can skip the three linear scans in `resolveSetup`. The index's `valueDefaults` is a version-filtered `Map<fieldKey, Map<normalizedValue, minutes>>` built once per run, so the default tier costs two Map reads per changed field (the raw arriving value is tried first; normalization is paid only on a miss). Building/owning/caching this index is entirely the caller's responsibility — this module never does it itself.
  - `stateForOrder(order, definition)` — derives one order's canonical state key from its `COLOR`/`PRT_01`/`PRT_02`/`PRODUCTION_VERSION` fields per the plant's active signature definition.
  - `resolveSetup(input)` — the core resolution function: given a from-state/to-state pair (plus optional prebuilt index), returns the resolved setup minutes/source. Precedence: occurrence override, machine row, plant row, implicit zero (identical complete states), **value default** (source `'value-default'`), uncovered. The default tier sums, over every field whose value changed, the default for the *arriving* value (blank arriving values never contribute; changed fields with no default are named in `reason`, so a partial sum is visible); with no contributing field it falls through to uncovered. The override branch's `currentStandard` uses the same tier so the Inspector "Standard" row agrees. `ResolveSetupInput.valueDefaults` is **required** in the type (callers pass `snapshot.value_defaults ?? []`) so `npm run typecheck` catches a missed call site, but the resolver treats `undefined` as `[]` (untyped `.mjs` tests). `computeShadowDiagnostics` counts default minutes in `totalStandardMinutes`.
  - `computeShadowDiagnostics(...)` — Stage-0-style shadow diagnostics for observation without affecting scheduling.
- **`setup-admin.mts`** (2,642 lines) — `SetupAdmin`, the Setup Matrix / definition / machine-state admin console. Extracted verbatim from the former `plant-and-administration.mts` mega-module (Phase P2 of the domain refactor). Deliberately does **not** start the optimizer or alter task placement — this surface is a versioned observation and maintenance console only. Owns: the definition editor, the List/Matrix view toggle, from-state-scoped paged matrix-row fetch/edit/delete, machine-state review, coverage tiles/missing-pairs drill-down, occurrence overrides, and (2026-10-27) the **"Default changeover by value" card**: a third `setup-panel` between the definition and matrix panels with its own mount, `paintValueDefaults()`, Save/Reset bar and module state (`_vdField`, `_vdFilter`, `_vdDirty`, reset on plant / signature version / field change). It offers a field picker over the definition's fields; value rows are the union of the plant priority-list values, the values endpoint's `observed` values and stored defaults (badged listed / observed-only / stored-only); a substring filter, at most 200 rendered rows with an "N more" note, and a "Set all N matching" mass-fill that applies to every matching value. Minutes follow the grid's parse rules (blank removes; typing stages on input so Save works without a blur; no exponent or hex forms), with a hint above one week and a note that sums are not capped. It is admin-only (`permissions.matrixWrite`; a read-only user sees it disabled, not hidden), repaints after every `render()` and on `master-data-changed`, warns before a signature bump or field switch drops staged edits (a plant switch drops them with a toast), keeps half-typed text and focus across a master-data repaint, says defaults are inert while setup-aware optimization is off, and saves only dirty entries in chunks of 2,000 via `Util.fetchTraced` (a later chunk failing still refreshes, clears the saved entries and reports "saved N of M"), then refreshes the snapshot and `invalidatePlant(plant)` (so the coverage tiles refresh). `setupWriteKind` gained a `'value-default'` kind that stales an open optimizer preview. The **grid** has a `'value-default'` cell state (`gridCellState` takes a sixth `defaultMin` argument; class `.setup-grid-value-default`; the cell shows the sum, the hint lists the contributing defaults, typing creates a real row) and the **List view** (the default view) labels default-covered pairs with the source label instead of "Gap", for rows whose effective minutes are null only; the Gap filter and count exclude them. A line override still beats a default at line scope. Coverage tiles read Recorded (`covered_pairs`) / By default (`default_covered_pairs`) / Gaps (`missing_pairs`).
- **`_static-delivery-check.mjs`** — not application code. A fixture asset for `tests/test_static_delivery.py`, pinning the `domain_static_asset_mw` route-collision fix in `brain.py` for `GET /setup/{plant}` (the API path collides syntactically with this folder's static path under the `StaticFiles` mount at `/`). The same pattern exists in `frontend/master-data/_static-delivery-check.mjs`.

## Counterpart

Backend half: `backend/setup/CLAUDE.md` (`backend/setup/routes.py`, `backend/setup/data.py`) — the persistence and route layer this UI reads/writes through.

Note `frontend/optimization/setup-scheduler.mts` (~6,960 lines) is a **separate domain** (optimization, not this one) even though it imports `buildSetupResolutionIndex`/`normalizedValue`/`resolveSetup`/`stateForOrder` from here — don't conflate "setup resolution" (this domain, pure) with "setup-aware scheduling search" (optimization domain, the detached candidate scheduler).

## Key invariants & hazards

- **O(states²) hazard:** the setup matrix is O(states²) per plant. `setup-admin.mts` never renders or fetches a full plant matrix snapshot for a view that needs only one from-state's rows — it uses the from-state-scoped, paged `GET /setup/{plant}/matrix-rows` endpoint (matrix-rows fetch/paging helpers around setup-admin.mts:660-740) precisely to avoid that. Any new matrix UI must follow the same pattern.
- **Observation-only, always:** neither file here ever changes an order's schedule. `setup-domain.mts` is pure computation; `setup-admin.mts` is CRUD on setup truth (definitions/matrix/machine state/overrides) only — the scheduler (`frontend/optimization/`) is what actually reads this data to place orders.
- **`derived < manual < actual` trust ordering** for machine physical state, enforced server-side (`backend/setup/data.py`'s `_SOURCE_TRUST = {"derived": 1, "manual": 2, "actual": 3}`) — `setup-admin.mts`'s machine-state review UI surfaces `source` so an operator can see whether a shown state is a lower-trust inference or a confirmed observation.
- **The "Include setup times in optimizer" activation UX has moved.** As of Workstream D2 (2026-08-20, finalized 2026-08-21), the real activation gate is **`plants.setup_active`**, persisted via `PUT /plant/{plant}/setup-active`. The UI checkbox was removed from `Plant._renderSettingsPane` in `frontend/master-data/admin-ui.mts` in the two-section pass on 2026-08-21 (lines ~1499-1504 and ~87-94 record the deletion); the **only editable surface now is Admin ▸ Manage Data Tables ▸ `plants` grid** (cell `column_metadata` row `('plants','setup_active','Setup-Aware Optimization')`). The older per-signature-version `setup_definition.active` flag and its `PUT /setup/{plant}/active` route are **vestigial but retained** (backend/setup/routes.py's `set_setup_active` docstring says so explicitly: "no UI or optimizer gate reads `setup_definition.active` any more"). `SetupAdmin.setSetupActive` remains exported but has zero callers. `setup-admin.mts` still displays an activation status chip (`activationStatus()`, setup-admin.mts:290; its `matrixVersion` now counts a plant with at least one value default for the current signature version as matrix-backed via `matrixVersionFor`, and `coveragePass` reads gaps that exclude default-covered pairs, so a defaults-only plant can reach activation), but it now takes `plantActive` (sourced from `SetupSnapshot.plant_active`, i.e. `plants.setup_active`) as an explicit parameter rather than owning the write. `frontend/optimization/CLAUDE.md` separately consults `NimbusMasterPlant.setup_active` (the same underlying flag, read via `snapshot.masterData.plants[]` rather than `bounds.setup.plant_active`) to downgrade `validateCandidate`/`computeAlerts` setup-timing severities to warnings when the plant's real flag is off. The per-plant unknown-setup policy control (`unknownSetupPolicy` — `zero`/`plantDefaultMinutes`/`excludeFromSearch` — and its default-minutes value, `POST /master-data/plants/{plant}/unknown-setup-policy`) likewise lives in the master-data Scheduling Rules pane, not in this domain.
- **Plant-default matrix replace needs the read token.** `POST /setup/{plant}/matrix/import` (plant-wide scope) must carry the `plant_matrix_token` from the last `GET /setup/{plant}`; a stale one is a 409 "reload and retry" (see `backend/setup/CLAUDE.md`). Matrix delete (`DELETE /setup/{plant}/matrix`) is chunked 500 rows at a time.
- **Stale stage-doc checkboxes:** `docs/archive/changeover_matrix_stage_{0,1,2}.md` carry stale, never-updated checkboxes even though Stage 0/1/2 all shipped (~50 commits across the git history). **Trust `git log`, not those checkboxes**, if you land here from one of those docs. `docs/changeover_matrix.md` is the design of record; `docs/archive/Setup_matrix_redesign.md` corrects it in places (see the activation note above for one place it is now itself dated).

## Integration points

**Imports in:**
- `setup-domain.mts` imports only `../platform/types.mjs` (types) — genuinely dependency-free at runtime.
- `setup-admin.mts` imports `../platform/foundation.mjs` (`Config`, `Util`, `ErrorLog`, `Toast`, `Modal`, `PerfMonitor`), `../platform/store.mjs` (`Store`), `../security/session.mjs` (`Session`), `../scheduling/persistence.mjs` (`Persistence`), and `../master-data/admin-ui.mjs` (`Plant`) — this last one forms a **two-way ESM cycle**: `Plant.gotoTab` is called from `setup-admin.mts`'s missing-pairs review handoff, while `Plant` itself calls `SetupAdmin.render`. This is carried over unchanged from the pre-split single-file module and resolves safely at runtime (both modules only cross-reference inside method bodies invoked after both finish top-level evaluation, never at load time).
- `setup-admin.mts` also duplicates (not imports) a `_mkCombobox` searchable-combobox helper that also exists verbatim in `frontend/master-data/admin-ui.mjs` — deliberate, to avoid adding a second purely-cosmetic edge onto the `Plant` cycle above. Keep any change to this helper mirrored in both copies.

**Imported by** (grep-verified): `frontend/app-entry.mjs` (`SetupAdmin`, boot bridge), `frontend/master-data/admin-ui.mts` (`SetupAdmin` — the reverse half of the cycle above), `frontend/optimization/engine.mjs` and `frontend/optimization/optimize-ui.mts` (`resolveSetup`/`stateForOrder` from `setup-domain.mjs`), `frontend/optimization/setup-scheduler.mts` (`buildSetupResolutionIndex`, `normalizedValue`, `resolveSetup`, `stateForOrder`, `SetupResolutionIndex` type), `frontend/scheduling/orders.mts` (`resolveSetup`/`stateForOrder` and `SetupAdmin`).

**Endpoints called** (from `setup-admin.mts`): `GET /setup/{plant}`, `GET /setup/{plant}/coverage`, `GET /setup/{plant}/matrix-rows`, `GET /setup/{plant}/missing-pairs.csv`, `PUT /setup/{plant}/definition`, `POST /setup/{plant}/matrix/import`, `DELETE /setup/{plant}/matrix`, `PUT /setup/{plant}/value-defaults`, `GET /setup/{plant}/value-defaults/values`, `PUT /setup/{plant}/lines/{machine}/state`, `PUT|GET /setup/{plant}/lines/{machine}/compatibility`, `POST|PUT|DELETE /setup/{plant}/overrides[/{id}]`. It does **not** call `PUT /setup/{plant}/active` (vestigial) or `PUT /plant/{plant}/setup-active` (owned by the master-data domain's `Plant` module) — see the invariant above.

## Gotchas

- Don't assume `tests/modules/setup/` holds all setup-domain frontend tests — the two `setup-domain.mts` test files sit one level up, directly in `tests/modules/`.
- This folder's `CLAUDE.md` (like every `frontend/<domain>/CLAUDE.md`) is unreachable through the public `StaticFiles` mount — `brain.py`'s `block_markdown_mw` 404s any `.md` path before routing, and `domain_static_asset_mw` only special-cases `setup`/`master-data` two-segment paths ending in a file extension with a dot (e.g. `setup-admin.mjs`), which a `.md` path already fails on both counts.
- If you're asked to wire a new "activate setup for optimizer" control, it belongs in `frontend/master-data/admin-ui.mts`'s `Plant._renderSettingsPane`, calling `PUT /plant/{plant}/setup-active` — not in this domain.
