# Alert Monitor — the profile-driven alert triage tab

Frontend half of the Alert Monitor (spec: `docs/superpowers/specs/2026-10-20-alert-monitor-design.md`; its "UI overhaul — rev 2" section describes the page as it is now, its "Overview band — rev 3" section the retired band (W6b, 2026-10-30: the Inbox | Matrix page replaced it), and its "Shipped vs deferred" section the first build). Backend half: `backend/alert_profiles/` (profiles + acknowledgements). The shared logic lives in `frontend/insights/` (see its CLAUDE.md); this folder is the page, its pure model, the pure Matrix module, the pure day-bucket data helpers and three modals (the profile editor, the acknowledge dialog and the Slot dialog for Needs Planning orders; the Slot design is `docs/superpowers/specs/2026-10-26-needs-planning-slot-design.md`).

## The vocabulary rule

Never user-visible on this page: "points", "pts", "exact", "estimate", "outside the confidence window", "cap". The only numbers shown are counts, dates / relative days and the confidence score (0-100); "Confidence 71 → 78" appears only for a replayed fix whose score changes (a lower after-score is shown too). Ranking is internal (`impactPoints`, `compareAlerts('impact')`, `groupAlerts` order, `LeverageItem.points`). A vocabulary-gate test in `tests/modules/locale-completeness.test.mjs` checks English `am.*` / `leverage.*` values only, against the regex `points?|pts|exact(ly)?|estimates?|estimated`; "outside the confidence window" and "cap" are conventions the gate does not check, and de/es/fr/pt are not gated. Don't add a string that breaks the rule, and don't render `points` anywhere.

## The Top fixes render loop (`_levRun`)

Fixes are computed in two phases so the alert list never waits on them:

1. `_levScheduleFirst()` defers the first run one tick (the list paints first). `_levRun` builds the input (`_levDeps.buildInput`, over `buildPlantSnapshot`), runs **`groupLeverage`** (pure, immediate), sets `_levHave`, and paints — **phase 1**, removal numbers only.
2. Unless `_levSkipAnalysis()` (Sandbox active or `OptimizerPreview.active`), it awaits **`analyzeLeverage`** through the runner (`Compute.leverageBatch`, which runs each batch on its own short-lived worker), re-applies any minutes the user typed (`_levTyped` -> `replayWithMinutes`), and paints again — **phase 2**, replayed numbers.

What keeps it correct: **one in flight** (`_levInFlight`; a request during a run sets `_levRerun` and re-queues afterwards); the **`Store.rev()` stale guard** (`rev0` is read before the work; if the plan moved, the result is dropped and re-queued through `_levDebounced`, at most `_LEV_MAX_STALE_RETRIES = 3` times); a **400 ms debounce** (`_LEV_DEBOUNCE_MS`) on `alerts:change`, `tasks:bulk*`, `setup-snapshot:replace`, `calendar:change`, `blocks:change`, `plantBlocks:change`; a half-typed minutes box survives an unrelated repaint (`_renderLeverage` returns while `.am-fix-min-input` has focus) **except** the repaint that shows that box's own result — `_levMinutesEntered` sets the one-shot `_levForcePaint` around a synchronous `_paint()` (it relies on `_paint` staying synchronous); an Enter and a Replay click on the same row are de-duplicated (`_levReplaying`). **Cancellation:** every run and minutes replay owns an `AbortController` (`_levControllers`, `_levAbortAll`), aborted by `_levReset` (plant change), `setActive(false)` (tab leave) and `_levPlanMoved` (the debounced Store events above abort first, then re-queue), which terminates the dedicated worker; `AbortError` is silent. A 30 s `TimeoutError` stops the worker and keeps the phase-1 removal-only cards (logged with `ErrorLog.warn`, no UI string, no retry, never a main-thread rerun). A `requiresMinutes` row asks for minutes ("Setup minutes" box + Replay), never shows a prediction.

## Action vocabulary

Row actions are `focus | fix | override | slot | diagnose | ack | unack` (`slot` is the `needs_planning` row's action, labelled "◫ Move…" since 2026-10-29: `_runAlertAction` opens `AlertSlotModal` from `alert-slot-modal.mts`, blocked in What-If, and the ⋯ menu path refocuses the row trigger first like `ack` / `override`; an open Diagnose panel of such a row adds a "Suggested move" field from the modal's synchronous, memoised `suggest`, prefixed with the day it was ranked for (`am.slot_suggested_on`, from `suggestedDay`), which is why `DIAG_H` is 166) — **no `dismiss`**: Acknowledge is the only "make it go away" verb on this page (Dismiss stays in the drawer, and `Alerts.dismiss` is untouched). Buttons and ⋯ menu items carry the same `data-alert-action` / `data-alert-id` (+ `data-task-id`) and both end in **one dispatcher**, `_runAlertAction` (button clicks through `_onAlertAction`, menu items by calling it directly); calls match the drawer (`AlertsUIAdapter._handleAction`). Eligibility comes from the shared **`FIXABLE_ALERT_TYPES` / `OVERRIDE_ALERT_TYPES` / `CALENDAR_ALERT_TYPES`** exported by `insights/alert-profiles.mts`, which the drawer, the cell card, the monitor model and the Gantt all import (a parity test over `FIRING_ALERT_TYPES` pins it). Fix and Override are no-ops in What-If and render `aria-disabled` with the `am.whatif_blocked` hint. Fix-row actions (`_onLevAction`) add: `show-alerts` (focus + `AlertProfileMatches.setFocusTaskIds`: the Gantt draws the dashed `alert-focus` outline on those of the row's orders that sit inside the viewed profile, the fills stay profile-based, and the chip reads "M of N outlined" when some are outside; Clear on the Gantt toolbar or Escape also removes it; for the `needs-planning` family it is the primary, labelled "Show these", and `levActions` leaves it out of the ⋯ menu so it is not repeated), `open-table`, `copy-summary`, `goto`/`focus-first`, `diagnose-cell`/`diagnose-worst`, `cal-fix`, `edit-calendar`, `rg-workcenters`, `rg-routing`, `setup-review`/`setup-copy`, `optimize`, `replay-minutes`.

## OverflowMenu usage and focus return

Every ⋯ here is `OverflowMenu.open(anchor, items, {align: 'end', key})` (`frontend/platform/overflow-menu.mts`). The key is the row's alert id, the group key, the fix key or `page`. **The templates must render `data-ovf-key`** on each trigger (`rowHtml`, `fixRowHtml` and the page-menu button do), and `_paint` ends with `OverflowMenu.reconcile()`: a menu whose trigger a repaint replaced closes or follows the same-key trigger. Focus rules: after Fix, Diagnose and Remove acknowledgement the pane repaints and `_restoreRowFocus` focuses the row's trigger (found by `data-ovf-key`), else the next row's, else the previous row's; Acknowledge and Override first `_refocusKey` the live trigger so the modal's own focus return lands on it; "Show 10 more" and the admin disclosure restore focus after their repaint.

## "View as" vs "Set as default"

"View as" calls `AlertProfileMatches.setSessionProfile(id)` — session-only, beats the pref **for this page only** (the pane reads `AlertProfileMatches.view()`; the Gantt, bell, drawer and Orders read `current()`, which ignores the override), until cleared or the plant changes, writes nothing. "Set as default" is the one control that writes the persisted pref (`alertProfileByPlant`: one key holding the whole `{plant: profileId}` map, then clears the session override). The view and lens persist in `alertMonitorView['*']`; the Gantt highlight toggle and "Show acknowledged" (both in the ⋯ page menu) persist as `alertProfileGanttHighlight` / `alertsShowAcknowledged`. (`alertMonitorOverview` is no longer read.)

## The no-Store-event rule

Nothing here emits a Store event: `Store.emit()` bumps the revision and re-renders everything, and the fix list's stale guard reads that revision. Derived UI state (profile matches, profile and ack caches) travels on each module's own `subscribe()` fanout (`AlertProfileMatches`, `AlertProfileClient`, `AlertAcksClient`). The pane only listens to Store events, and only while `_active`.

## Gotchas

- The ack modal's Flatpickr `minDate` is the plant's today (`Util.dayKey(Util.plantToday(plant))`), not the browser's.
- `app.js` assigns `globalThis.NIMBUS = NIMBUS` after building the namespace: `const NIMBUS` is a script-scope binding, not a `window` property, so without that line every `_nim()` read here would be `undefined` (Go To, Override, Confidence, open-in-table all silently do nothing). `tests/modules/legacy-nimbus-global.test.mjs` pins it.
- `DistributionPane.openParent` exists for a distribution deep link, but nothing in this folder calls it yet.
- The editor compares `profileFromDraft(draft)` with the snapshot taken when the draft was loaded (`baseline`); rail switch / New / Duplicate / Copy ask `Modal.confirm` (`ape.discard_*`) when they differ. A non-409 save or delete failure shows the server message or `ape.err_save_failed`, never `ape.err_stale`.
- `am.window_all` is the only `am.*` key kept from the planned deletion list: `windowSummary` returns it for All alerts (the picker's second line and `aria-description`).
- The profile picker's "+ New profile…" row is a pinned footer: the options scroll inside `.am-opt-scroll` and the footer sits outside it, so it stays visible past the 240 px fold.
- Day-group heads and the when column use a short weekday/day/month label (`_fmtDay`), not `Util.fmtDT`; the exact date and time are in the when column's tooltip.
- **Slot: a closed day is never handed to the engine.** The engine refuses a finish on a closed day (`finish_cannot_hold`: the engine moves such a finish earlier, `closed_finish` in `calendar-engine.mts`, and a manual placement refuses a finish that would have to move), so `slotFinishFor` returns the END of the target day's working window and walks back up to `SLOT_LOOKBACK_DAYS` (30) days to the latest open window (`movedBack` counts the days). A walk-back is confirmed (`am.slot_confirm_closed`, names both days); 31 closed days in a row return null and the dialog toasts `am.slot_no_window` and stays open. A short day (need above the free hours, or either unknown, or no free gap that holds the need: `viaGap` false) gets its own confirm (`am.slot_confirm_short`, which names the possible overlap). A day `slotSeams.dayClosed` calls blacked out (`Calendar.effectiveCapacityHours <= 0`) is skipped like a closed one, and the walk-back never goes before the plant's today (the engine would place forward from now anyway); on the plant's today the window and the free hours start at the plant's now. The Go To day and the toast's `{{when}}` are the day the bar ends on (end minus 1 ms, so a 24:00 close does not name the next day). Capacity numbers come from the Utilization matrix cell (`scheduled` already includes derived setup).
- **Slot has no role gate.** `canPlaceSlot()` is "signed in and not What-If", the same as Fix and Override: there is no viewer role in NIMBUS today and `/tasks/update` is `require_authenticated` only. It is the one seam to change if a role check is ever wanted (the pane's `_runAlertAction` also returns early under `Sandbox.active`, and the Place button is disabled with the `am.whatif_blocked` title).
- **Slot's undo closure must unfirm itself.** `UndoStack.restoreTasks` strips `firmed` on purpose (see `frontend/scheduling/CLAUDE.md`), so restoring the snapshot alone would leave the order firmed and the server's firm flag unmarked; the entry pushed by `place()` also calls `Store.setFirmed([id], false, 'undo')` when the order was not firmed before. Place firms through `Engine.applyFirm([id], true, 'alerts')`, which skips an order the frozen horizon (or a running state) already protects (C9: a redundant planner firm would be unremovable), and the undo unfirms only when that firm was actually written. The placement patch alone does not firm. The order diagnostic's "Firming" field shows `Engine.firmStatusText(task)` (the reasons) or "Not firmed"; SAP's flag is not a reason.
- **`slotSeams.routingPlant` duplicates `Table._routingEnabledForTask` by design.** It reads `routing_runtime_enabled` off the order's plant in `Store.masterData.plants` so the dialog needs no `orders.mjs` edge; if the grid's rule for "routing plant" ever changes, change both (it only picks which refusal toast `place()` shows, `toast.pv_machine_ineligible` / `toast.no_routing_at_workcenter` versus the generic one).
- **Slot after a placement.** Go To goes through `Timeline.gotoLineDay` with the placed machine, day and `{taskId}`, not `AlertsUIAdapter.focus`: the alert disappears on the recompute and still names the old line and day. The row leaves the list only after the debounced recompute.
- **Multi-order alerts (Tool Inventory, Wave 2).** A count-aware `tool-conflict` carries `peerIds` (every holder; `peerId` is the earliest). The page reads orders only through `alertOrderIds` (`insights/alert-profiles.mts`; source-gated): `summaryLine` / `groupCounts` count every holder as an affected order, `_runBatchMove` skips an alert when ANY of its orders already moved, `_levShowAlerts` focuses pusher + all holders. The tool leverage card's title `n` is the number of ORDERS and its action reads "Show these orders" (`leverage.action.tool`, still `focus-first`). Alert ids: see `frontend/insights/CLAUDE.md` (legacy `toolc-<prev>|<cur>` for exactly two orders, `toolc-<pusher>|<tool>` otherwise).

## Tool Inventory touches (Wave 5, 2026-10-27)

- **Slot clause.** `slotToolOverage({task, machine, finish, needHours, plant})` (exported from `alert-slot-modal.mts`) runs the compute core's `findToolOverages` over the plant's orders plus the hypothetical interval [finish - need, finish] on the chosen machine; if a cluster involves the slotted order, `place()`'s existing confirm gains the clause `am.slot_confirm_tool` ("Tool {{tool}} would be over its {{available}} copies."), joined to the closed-day / short-gap sentence when both apply, and the confirm now also opens for a tool overage alone. Warn-only (manual placement stays alert-only): Cancel is the only refusal. Silent when the inventory is not loaded. The dialog body also shows a "Raise inventory" button for a tool-queued order (`data-asl-raise`). New import edge: `alert-slot-modal.mts` -> `optimization/tool-queue-confirm.mjs` (imports only foundation).
- **Fix is async.** `Alerts.applyFix` returns `Promise<boolean>`; `_runBatchMove` is async and awaits each fix sequentially (a fix that resolves `false`, e.g. a Fix overload refused for an error finding or cancelled at the tooling confirm, is not counted as moved and the batch continues), the row/menu Fix returns the promise, and the "cal-fix" loop awaits one id at a time. Overload fixes are judged on a detached candidate first and may show the shared tool-queue confirm (see `frontend/optimization/CLAUDE.md`).

**Tool Inventory Wave 5 review fixes (2026-10-27).** `Alerts.applyFix` is guarded per alert id (a second call while the tool confirm is open returns false) and takes `{quiet, onBlocked}`: a refused overload fix is silent under `quiet`, and the batch (`_runBatchMove`, the leverage "Fix movable" `cal-fix` loop) raises ONE `toast.fix_overload_blocked_batch` summary. The overload Undo snapshot is the union of the line-day tasks and the candidate's patch ids (taken after the confirm, before the apply), and the detached apply restores the live tail messages (missing setup, distribution separation, N need planning with the tooling share [shown even when quiet], guarded lines). Async bodies (menu Fix, `cal-fix`, the drawer's Fix) catch and toast instead of leaving unhandled rejections. `slotToolOverage` resolves the plant like order-tooling (selected-plant fallback), accepts `orders` (every order of a multi-order slot; the modal places one today) and uses a split order's segment envelope as its width; still warn-only.
