# frontend/scheduling — Gantt, Orders grid, selection, and backend persistence

## What lives here

- **`gantt.mts`** (~5,550 lines) — the Gantt timeline surface and its supporting UI:
  - `Timeline` — the vis-timeline wrapper (render, item lifecycle, drag/resize hooks).
  - `TimelineNav` — the canvas minimap/navigator strip above the Gantt. It is a **projection of `Timeline._items` + `Timeline._visibleLines()`** (same bars, split-order segments, row order and `.dimmed` filter state the Gantt renders — never re-derive the task/line filter chain here). Repaints are rAF-coalesced and triggered by `Timeline._items.on('*')` (the only signal for GanttFilter's className-only dim/undim updates) plus `lines:selected`/`plant:selected`/alerts/blocks/calendar Store events. Two rules for that `_items` subscriber: **skip events whose changed ids are all `kind:'zone'`** (the 1s ticker pushes zone bands whenever 'now' has moved ≥0.5 px at the current zoom, or an edge input changed) and **never gate on `Timeline._suppressEvents`** (GanttFilter._doApply sets it around exactly the updates the nav needs). Pure geometry helpers `navComputeRange`/`navLayout`/`navBarStyle`/`navClampRect` are exported for tests. Colors are read from CSS tokens at paint time (canvas can't use `var()`); DarkMode's repaint hook in `nimbus-intelligence.js` calls `render()`.
  - `DependencyOverlay` — finish-to-start link line rendering.
  - `Hierarchy` — plant → machine navigation tree.
  - `GanttFilter` — the Gantt's own line/search filter UI.
  - `Interaction` — the unified click/keyboard/drag pipeline (marquee multi-select, hover-preview card, double-click line isolation, multi-order ghost-drag, two-way AG Grid ↔ `Selection` sync).
  - `setupDiagnosticLabel` / `setupSourceLabel` — small label helpers for setup-aware diagnostics badges drawn on the timeline; `SetupPresentationDetail` is their shared type.
- **`orders.mts`** (2,833 lines) — the AG Grid orders table and order-detail chrome:
  - `Table` — the AG Grid wrapper (column defs, cell editors, row model).
  - `Inspector` — the single/multi-selection detail panel.
  - `ContextMenu` — right-click actions on grid rows/Gantt bars.
  - `Printer` — print/export.
  - `notifyResidualFirming` — standalone helper (fires a toast/alert when firming an order leaves a residual gap); `AgGridRowNode` is the row-node type used by both this file and `gantt.mts`.
- **`selection.mts`** (138 lines) — `Selection`, the multi-select store (which task ids are selected, anchor tracking for Shift-range-select, listener fanout). Independent of vis-timeline internals; every UI (Timeline, Table, Inspector, ContextMenu) subscribes to it. Never persisted, never autosaved.
- **`persistence.mts`** (1,769 lines) — `Persistence`: backend fetch (`load`/`loadForPlant`/`reload`), the localStorage cache (`_saveCache`, key `nimbus.state.v3`), dirty-id tracking, and the explicit `saveAll()` backend-save path.
- **`order-field-catalog.mjs`** (124 lines, + `order-field-catalog.d.mts` ambient types) — `ORDER_FIELD_CATALOG`, the single source of truth for which optional Orders fields exist and their default show/hide state in the AG Grid columns and Inspector panel. Deliberately a zero-dependency leaf module (no imports) so both this domain and the admin System Configuration UI can depend on it without adding a cross-domain edge.
- **`gantt-lanes.mts`** — `computeLaneMap(intervals) -> {laneByParent, maxDepth}`, the pure lane assignment behind the Gantt's expandable rows (no imports, no Store, no DOM); test `tests/modules/gantt-lane-map.test.mjs`.
- **`nonworking-spans.mts`** — `buildNonWorkingSpans(fromMs, toMs, windowFor, {closedDaysOnly?, cap?}) -> {spans, truncated}`, the pure merged-span algorithm behind the Gantt's non-working-time shading (no imports, no Store, no DOM). `windowFor` is `Calendar.plantWorkWindow(plant, day)`.

## Counterpart

Backend half: `backend/scheduling/CLAUDE.md` (`backend/scheduling/routes.py`, `backend/scheduling/models.py`) — the `/tasks` family and the xmin concurrency contract this domain's `saveAll()`/`_refreshTasks()` talk to.

This domain's frontend files do not call `db.py`/`master_data.py` directly — they only ever go through the `/tasks*` HTTP endpoints owned by `backend/scheduling/routes.py`. No root-file line ranges to cite here.

## Key invariants & hazards

- **Authoritative runtime inputs and recovery (2026-10-01):** `/tasks/refresh` carries quantity, material, plant and raw SAP start with its runtime/version snapshot. `_prepTask` keeps the raw SAP start as `BASIC_START_DATE`; the client's SAP-start checks (visibility, production-version validity) read that copy. Nothing snaps `original_start_date` any more: the load-time calendar snap was removed in backward scheduling Task 2.5. Explicit `reload()` discards cached task edits only after successful hydration; failed loads and edits made during that request retain the local conflict. Ordinary startup `load()` continues to restore cache edits.

- **Manual firm is server state and an explicit-save edit (2026-10-06).** `GET /tasks` rows carry `firmed` (the planner firm); `Store.setTasks` rebuilds `firmedIds` from it, so a reload or plant switch can never keep a stale local firm. A Firm/Unfirm/undo marks exactly the touched ids dirty (`App._trackDirty`, `firmed:change`; never `_forceIds`, so a firm-only row cannot join an atomic optimizer group) and adds them to `Persistence._firmDirtyIds`; only those rows send `FIRMED` in `POST /tasks/update` (a date-only edit never writes this client's firm copy over another planner's). Firm edits ride the same edit-generation and sent-snapshot checks as dates. `firmed:change` from `'sandbox'` (What-If discard replays the snapshot) or `'refresh'` never dirties; `replaceFirmedIds` reports only ids whose membership changed. `UndoStack.restoreTasks` deliberately strips `firmed` from the snapshot (store.mts:1083): undoing a date/unschedule edit must not flip a firm without a marker, or the save would send no `FIRMED` and the UI would diverge from the server. `/tasks/refresh` rows copy `firmed` back into both `t.firmed` and `firmedIds`. **Start fresh:** the localStorage cache never writes `firmedIds` or per-task `firmed`, and cached `firmedIds`/`fixedIds`/`tasks[].firmed` are ignored on read (offline cache restore shows no firms; cached date edits still restore). The first firm toggle of a session shows `toast.firm_needs_save`; command-palette Firm All asks `confirm.firm_all` first.
- **Locks are frozen horizon, manual firm, and running only (2026-10-06).** SAP's own firm flag is display-only and never locks (`Engine.firmingStatus` reasons `frozen | manual | running`). A running order (`Engine.isInProgress`: start <= now < end) is protected, not "locked", in UI copy; the Gantt's 30s lock-band scan (`Timeline._inLockBand`) tracks frozen-horizon and running membership so an order that starts while the page is open restyles without a reload.
- **Delete / Unschedule = Needs Planning.** `Interaction.unscheduleIds` is the single implementation (Delete key and command palette); it skips locked orders and split orders (2+ segments), applies `Engine.plannerUnscheduleChanges()` (reason code `planner_unscheduled`) and is undoable.
- **Placement exception and the server's width gate (backward-scheduling Task 2.3, 2026-10-14):** the server rejects a single-edge save (`single_edge`) and a continuous bar whose elapsed width is not its run time (`width_mismatch`) unless the bar carries `placement_exception` (`'overtime'` | `'overlong'`); both reasons show through `describeRejections` (`ui.reject_single_edge`, `ui.reject_width_mismatch`). `_taskEditSnapshot` sends `placement_exception` on every save of a task that holds the field (an explicit `null` clears the stored marker; a task that never carried it omits it), and `/tasks/refresh` rows copy it back onto the task. The engine sets it: `Engine.manualSchedulePatchFor` writes `'overtime'` when a planner confirms a firmed order's overtime placement and `'overlong'` when it releases an overlong order as one bar, and the reconcile skips marked rows. The server skips the width gate for a save that does not move the bar (both sent edges equal the stored raw edges and the run time is unchanged). The browser never sends `trust_start`; external callers that do not trust their sent start send it (see `backend/scheduling/CLAUDE.md`).
- **Manual placement holds the finish (backward scheduling Task 2.5, 2026-10-14):** a drop, a typed Planned finish (the grid column and the Inspector field; Planned start and Due date are read-only), the Override dialog's date (now the FINISH, field `ovr-finish`), and the run-time, machine and version edits all reach `Engine.manualSchedulePatchFor(task, line, finish, …)`, which derives the start backward through the working time and always returns both edges. The grid and the Inspector call it through `Engine.manualRoutingSchedulePatchFor`, which delegates to it. A typed End, or a bar drag or resize, on a RUNNING order is refused with `running_finish_locked` (D2): the run-time edit is the only manual resize of a started order. For any other order a bar drag or a right-edge resize sets the finish, and a held finish keeps its exact minute (floored to the minute); only a horizontal Gantt drag snaps (D1), before it reaches the engine. A left-edge-only change is reverted with `toast.left_edge_locked` (`lockLeftEdge` also vetoes it live through vis `onMoving`). A finish that would have to move EARLIER (no working time ends there) is refused with `toast.finish_cannot_hold` and the bar springs back; a backward start that falls before the plant's now is NOT a refusal: the order places forward from now with `derivationIssue {code:'reversal_forward', detail:'due_date_past' | 'run_time_grew'}` and the late alert (O2, OQ3, OQ7 a, OQ19 c); `Engine.lastManualRefusal` says why and whether the engine already toasted. A firmed order whose finish would have to move asks `Engine.confirmOvertimePlacement`, then retries with `confirmedOvertime` and stores `placement_exception = 'overtime'`. A marked order is translated verbatim (width kept) until a planner clears the marker. Run-time, machine and version edits hold the finish, and a running order holds its start (`holdStartIfRunning`, through `Engine.heldStartPatchFor`: the real start survives when it is off the 15-minute grid, and when the remaining run crosses closed time the forward walk returns the calendar's pieces (D3: always walked as `partial_allowed`, because a continuous bar across closed time fails the server width check); a recorded start inside closed time moves to the next open minute and the stored start follows it; `Engine.schedulePatchFor` is therefore on the retained forward-path list). A queued row whose hold is `runtime_unknown`, `overlong_never` or `run_time_over_cap` is anchored at its due instant (`Table._RELEASABLE_HOLDS`); a placement releases only `overlong_never` and `run_time_over_cap` rows to `scheduled`. Gantt lock-band and firming styling read the plant clock (`Timeline._nowFor`). The load-time `_snapToWorkingHours` snap is gone.
- **One plant-zone clock (backward scheduling Task 2.4, 2026-10-14):** `/tasks` carries `meta.server_now`; `Store.setServerNow` turns it into an offset, and `Store.plantNow(plant)` projects the server instant into the plant's IANA zone, or returns null when the plant has no valid zone. A plant with no valid zone is blocked: `Store._blockedPlants` records it, one `toast.plant_no_timezone` is shown per session, and nothing is derived for it. The Gantt's ticker, zone bands and lock band read the plant clock through `Timeline._plantNow` and `Timeline._nowFor`. `/tasks/refresh` and `/tasks/horizons` carry no `server_now`, so they leave the offset as it is.
- **Client placement state (backward scheduling Task 2.6, 2026-10-14):** `Store._markPlaced` sets `user_scheduled` locally on any client write that gives a row both edges. Display-only derivations, refreshes, undo and What-If restores, the `'time-machine'` source (VI8), distribution's own saves and notes do not count. The source `engine-runtime-reconcile-display` is skipped by the dirty tracker (`App._trackDirty`) and by autosave, so a display derivation never dirties a row. `derivationIssue` and `systemMove` are notes the save payload never carries: `Store._clearStaleNotes` clears them on the next schedule, machine or run-time edit and a refresh copy-back clears them. `derivationIssue` IS cached with the task and revived through the persistence overlay (D21), so a reload keeps the reason; `systemMove` stays session-only.
- **Save rejections:** `machine_unknown` (server-side MACHINE validation) gets its own toast and is excluded from `describeRejections`; a second `saveAll()` while one is in flight is skipped, and `toast.save_in_progress` shows only for user-initiated (non-`silent`) saves.
- **Needs Planning (2026-09-09):** `planning_status='needs_planning'` means null committed dates and empty `scheduleSegments`; preserve SAP baseline dates. `_prepTask`, Store normalization, cache overlay, calendar normalization and refresh enforce this. A save that carries dates and no explicit planning status returns the row to `scheduled` (`update_task_dates_bulk`), and a placement that releases an `overlong_never` or `run_time_over_cap` row returns it to `scheduled` in the same patch. Orders exposes status/reason/window and the Needs Planning status filter.
- **Atomic optimizer saves:** `_forceIds` is a historical name for dependent optimizer/undo edits. It now opts `/tasks/update` into `atomic_optimizer=true` with `force=false` for every row. Any rejection preserves all local edits/dirty flags; there is no per-row stale refresh. `schedule-unsaved` remains visible. Offline cache retains `_optimizerDirtyIds` and cannot evict a partial dependent task set; online reload excludes that group's cached positions. Legacy non-optimizer partial-save behavior remains as described below.

- **Timezone-naive save contract (fixed, not open):** `saveAll()` (persistence.mts:1175; payload builder `_taskEditSnapshot`, ~1098-1105) converts every date to local seconds via `Util.toLocalSeconds` before `JSON.stringify` — a raw `Date` would serialize as UTC (`toISOString()`), but the backend read path emits bare naive `strftime` strings that `new Date()` parses as local, so a raw `Date` here would round-trip shifted by the client's UTC offset for non-UTC users. This was a real corruption bug, fixed 2026-07-07; it is not still open.
- **`saveAll()` always POSTs full `blocks`/`calendars`** (persistence.mts:1232 — `JSON.stringify({ tasks: taskPayload, atomic_optimizer: atomicOptimizer, blocks: Store.blocks, calendars: Store.calendars })`) even when the dirty-task list is empty. The backend (`TasksUpdatePayload`) only consumes `tasks` — `blocks`/`calendars` are accepted but ignored (calendars/blackouts persist through the separate `/plant-calendar/*` endpoints). This is legacy ride-along, harmless but worth knowing before assuming an empty save is a no-op network call.
- **Partial-save dirty tracking:** persisted and terminally rejected rows clear dirty state only when the live writable snapshot still matches what was sent. Stale rows remain dirty until a complete authoritative refresh succeeds. Refresh checks the original save snapshot, row version, edit generation and collection generation; a newer edit (including edit-and-revert) is retained with its old token and blocked from ordinary resave until explicit reload/discard. Unrelated ordinary saves remain available; an affected atomic group remains entirely unsaved. Refresh includes writable attributes, nullable runtime, provenance and segments alongside its version.
- **Save-time conflict reporting (N3).** `saveAll()` reads the `conflicts` list off `BulkUpdateResult` (persistence.mts:1358) — advisory only, since the rows it names are already persisted: the server scans the written machines for strict overlaps under a `SAVEPOINT` inside the same save transaction. When present, it toasts `toast.save_conflicts` and emits a `schedule:conflicts` Store event (lines-scoped) instead of importing `insights/services.mjs` directly. Separately, `strict_conflicts` — honored only when the save is also `atomic_optimizer` — makes the server reject the whole batch with HTTP 200, `status:'error'`, `error_code:'schedule.conflicts'`; `saveAll()` detects that via `result.error_code` (persistence.mts:1285) and toasts `toast.optimizer_conflicts` instead, leaving every dependent edit unsaved.
- **Auto-reflow after manual edits:** `Engine.autoReflow()` (owned by the optimization domain) is called only from the overload-alert Fix (`insights/services.mts`), never from this domain's `Interaction`/drag handlers; a drop runs no reflow cascade. When the Fix runs, it re-flows subsequent unfixed orders on one line to clear the overlap. It only shifts dates within one line, triggering an incremental line-scoped alert recompute.
- **Task IDs are MD5 hashes** of `f"{PRODUCTION_ORDER}|{MATERIAL_NUMBER}"` (`make_id()` in root `db.py`, currently line 123). The hash excludes time, so ids are stable across reloads/reschedules — `Selection`, `Table`'s row keying, and drag/edit operations across this whole domain rely on that stability.
- **`gantt.mts` ↔ `orders.mts` form a two-way in-domain module dependency**: `gantt.mts` imports `Table`/`Inspector`/`ContextMenu`/`notifyResidualFirming` from `orders.mjs`, and `orders.mts` imports `Timeline`/`TimelineNav`/`setupDiagnosticLabel`/`setupSourceLabel` back from `gantt.mjs`. This is intentional (both are the same domain) — don't "fix" it by trying to break the cycle across a domain boundary.
- **This `CLAUDE.md` (and every other `frontend/<domain>/CLAUDE.md`) is blocked from public static serving** by `brain.py`'s `block_markdown_mw` (any request path ending `.md` gets a 404), regardless of the `StaticFiles` mount at `/`. Not a scheduling-specific concern, but worth knowing if you're verifying this file isn't web-reachable.
- **Non-working-time shading (2026-10-16; design `docs/CALENDAR_PERIODS_DESIGN.md` section 5).** The Gantt greys the plant's closed days and off-shift hours (plant pattern only, never per line, so the line filter changes nothing). Rules that keep it from fighting the rest of the timeline:
  - Items are **ungrouped** vis background items `{kind:'zone', type:'background', className:'nonworking', editable:false}` with no `group`, ids `nonworking-<dayKey(start)>` (suffix `-t` when the span starts at an off-shift tail instead of local midnight). Ungrouped means they live in the library's BackgroundGroup and `_healBackgroundBands` skips them; `kind:'zone'` makes `TimelineNav` ignore them. Hard cap 600 spans.
  - **Single owner.** `Timeline._nonWorkingDesired(range)` is the one pure builder; `Timeline._nwRange` is the one range, set only by `_syncNonWorking` (and seeded on `init`/rebuild). `_rebuildPass` places the same function's output as the first block of `desired`, so its full diff never removes what the pan path added. There is no separate coarse flag: granularity (closed-days-only when the range is wider than 90 days) is derived from the stored range's span.
  - **Hysteresis.** `_syncNonWorking` runs from the debounced `rangechanged` handler and returns while the window stays inside the covered range's inner band, unless a zoom flips the coarse/fine granularity. No new timer; the ticker is untouched.
  - **Never** set `position`, `top` or `height` on `.vis-item` CSS for these items, **never** remove the DataView `type === 'background'` exemption in `init()`, and never group them or make them per-line.
  - `TimelineNav._wireItemsSubscription` reads `props.oldData` on `remove` and skips the repaint when every removed item is `kind:'zone'`; without that every pan re-diff would repaint the minimap. Absent `oldData` falls back to repainting.
  - Browser check owed (paint order against grouped bands, live `oldData` shape, pan smoothness); see the design doc's section 7.

- **Expandable rows (overlapping orders as lanes).** The Gantt runs `stack:false`, so overlapping bars on a machine draw on top of each other. Each collapsed row whose `maxDepth > 1` shows a red count badge (`.row-stack-toggle`, a real `<button>` in the row label with `aria-expanded`) that expands that ONE row into lanes at the bars' true times. Rules:
  - **Pure lane math** lives in `gantt-lanes.mts` (`computeLaneMap`): greedy per parent order in earliest-start order, strict overlap (back-to-back does NOT stack), all segments of a split order share one lane. `Timeline._computeLaneInfo` runs it for every visible line each rebuild (badge counts); lanes are applied only to `Timeline._expandedLine`.
  - **Subgroups exist only on the expanded line.** Lane = vis subgroup `lane-N` plus numeric `laneIndex`, written by the ONE decorator `Timeline._decorateLane` (rebuild, `_itemPatchFor`, `rebuildSetupForLines`, drop companion updates). It ALWAYS writes `subgroup` explicitly (id or `undefined`) because DataSet `update` merges. A setup bar takes its successor's lane. **Background items never get a subgroup** (`_healBackgroundBands` stretches grouped bands to the full row height; a subgrouped band breaks that).
  - **Lane changes go through `_items.remove` + `add`, never `update`** (`_splitRelocations` / `_writePatches` / the rebuild diff): vis 7.7.3 leaves a dangling subgroup reference when `subgroup` changes through `update`. Writes stay inside `_suppressEvents`. `Timeline._laneIds` is the set of item ids currently stored with a subgroup (`_noteLaneWrites` keeps it current after every write; cleared on plant change and by the heal); the relocation check reads the stored item only for ids in it or on `_expandedLine`, so a straggler (a lane bar vis left in another row) is still found, without a per-item DataSet read for every item. After a relocation `_reapplySelection` puts the Selection back (vis `_removeItem` drops removed ids from its selection).
  - **vis 7.7.3 hazards (found by the fix-wave validation).** The group `className` must never be falsy (`'row-expanded'` / `'row-flat'`): vis turns `''` into `null` and `addClassName(null)` throws on the collapse and on every retry. **Never strip or change `subgroup` mid-drag** (not in `onMoving` either): vis runs `_moveToGroup` before it assigns the new data, so the hovered row registers the old lane and a later `orderSubgroups` throws. **Companion writes are deferred while a row is expanded:** in a multi-drag the per-companion `_writePatches` is skipped when `_expandedLine` is set (`companionWritesDeferred`), because vis's drag-end overwrites it with raw data; the rebuild scheduled by the `'timeline'` Store write (`_onStore`) relocates the companions. A `tasks:bulkUpdate` that moves an order into or out of the expanded line schedules a rebuild (`bulkTouchesExpandedLine`) instead of patching.
  - **Self-heal ladder (`Timeline._heal`)** wraps the rebuild flush, `_refreshViewNow` (returns false on a throw) and the selection re-apply. A throw logs once with `ErrorLog.error`, removes the affected groups first and then their item ids one at a time (each in its own try/catch, inside `_suppressEvents`), and schedules one rebuild. A second consecutive failed pass also clears the sticky `_expandedLine`; a third stops retrying and shows `toast.gantt_reload_needed`. After the item removals the heal purges **ItemSet ghosts** (`Timeline._purgeItemSetGhosts`): vis `_removeItem` deletes the Item from `ItemSet.items` and then `group.remove` throws, by which time DataSet.remove has already dropped the id, so the per-id `items.remove` never reaches the ghost; a later `_onAddGroups` would re-attach it with a stale lane and every pass would throw `orderSubgroups ... setting 'index'`. The purge deliberately touches vis PRIVATE state (`_tl.itemSet.items`, `selection`, `_removeItem`; null-guarded, with a direct delete + DOM detach fallback) for every id not in `Timeline._items`. `_writePatches` is also wrapped: a vis throw during relocate routes to `_heal('write-patches', ...)` instead of being swallowed by `Store.emit` as a console.error. `_healCount` resets on the first clean rebuild pass. Re-initialising the vis Timeline in place was judged unsafe (`init()` starts an un-handled `setInterval` ticker and `Interaction`/`TimelineNav` hold listeners and DataSet subscriptions on the live instance), hence the reload toast.
  - **Row label geometry.** Every label carries a fixed badge slot: `.row-stack-toggle` on a stacked row, an invisible `.row-stack-slot` (NOT the toggle class: the click / double-click guards match that) on the rest, both `min-width: 28px`, so the label column does not shift when a badge appears or 9 becomes 10 (cost: the column is permanently about 30 px wider on the widest-named row). A focused toggle is recorded before the group update (`_focusedToggleLine`) and restored in the post-rebuild rAF (`_restoreToggleFocus`, `preventScroll`), because vis re-appends the label Element on every group update. An expanded row with more than one lane skips the row-count `_fitHeight` (the previous height holds until `_fitHeightMeasured`) to avoid a one-frame jitter.
  - **Sticky state:** `_expandedLine` clears only on an explicit collapse or `plant:selected`; it survives line-filter hide/show and never auto-collapses when the overlap resolves (the row shrinks to one lane, the badge and tint disappear). **Auto-expand on drop:** `Timeline.noteDropLines` (called from `Interaction._onDataSetUpdate` after a planner drag/drop commits; never from optimizer runs or loads) makes a destination row the expanded row when its depth goes from 1 to more than 1.
  - Row label is a DOM Element (`_groupLabel`), not an HTML string, so the button and its aria attributes survive vis's xss filter and the line name is escaped. Toggle click is guarded in `_onClick` (no selection clear) and `_installLabelDblclick` (no isolate); `_installRowToggle` ignores `e.detail > 1`.
  - Timeline height for an expanded row is measured from the real `.vis-group` heights (`_fitHeightMeasured`, in the post-rebuild rAF). Lane heights follow the bars in view, so an expanded row can shrink when you pan away from its stacked bars (known and accepted). Lanes sit 4 px apart; the red `conflict-order` outline keeps bars distinct.
  - Browser checks owed: see the plan (`sometimes-an-order-will-shimmying-cupcake.md`) "Spike first" list; the vis-internal behaviours (group `className` re-apply, subgroup removal) were reasoned from vis 7.7.3, not observed. Also owed: grouped band heights in and below the expanded row; a lane bar dragged over another row (with the strip gone, the hovered row may briefly grow one lane until the drop rebuild); isolate + expand with no height jitter; fixed label width as badges come and go; toggle focus kept after an alert recompute.

- **Profile-match fill on the Gantt (Alert Monitor, 2026-10-20).** `Timeline._itemForTask` appends `Timeline._profileMatchClasses(taskId)` = `profile-match profile-match-<category> profile-match-<err|warn>` for an order in `AlertProfileMatches.current().categoryByTask` (the most severe category among the profile's matched alerts; severity from `sevByTask`). It returns nothing when the `alertProfileGanttHighlight` pref is false, and nothing for an order whose every alert is acknowledged unless `alertsShowAcknowledged` is on. `Timeline._applyProfileMatchClasses()` (subscribed in `Timeline` init through `AlertProfileMatches.subscribe`; never a Store event) re-derives the classes and **diffs only `className`** over the live items: no item rebuild and no re-layout. It runs even while the Gantt is hidden (parity with `GanttFilter`). The Alert Monitor's "Show alerts" focus swaps the set (`setFocusTaskIds`), so the Gantt follows the focused card.
- **Why a fill, not an outline.** Bars are not line-coloured: a standard order is blue (`--bar-standard`) and a firmed order red (`--bar-firmed`), so a red fill would masquerade as firmed and a line colour does not exist to reuse. The five category fills are `--bar-pm-capacity|conflicts|calendar|setup|exceptions` (+ `-fg` text colours), defined once for light and again for dark in `styles.css` with identical values; the set was chosen with the dataviz palette checker after the spec's first candidates failed it (exceptions is a deliberately neutral grey, the weakest pairing against dark `--bar-standard`). Severity is the inner ring, not a colour: `--pm-ring` is `--err` or `--warn-vivid`, switched to the dark ink on the amber capacity fill where the warn ring would be ~1.2:1.
- **Cascade rules (read before touching these rules).** The fill rules set only `background`/`color`, never `border-color` or `box-shadow` (a three-class `!important` there beat `.vis-selected` and `.conflict-order` and hid the selection). The ring is composed from custom properties: `--pm-inner` is the inset ring plus a light keyline (a thinner variant for `.split-order-segment` / `.dist-child`), applied as `box-shadow: var(--pm-inner)`. Selected and conflict compose on top: `.vis-selected.profile-match` adds the accent wash, `.vis-selected.profile-match.conflict-order` the accent. The rules sit after `.dist-sibling` and before `.goto-target`, so the Go To ring still wins (a two-tone ring, white inner keyline plus the ink ring, that stays until the planner moves on; it hides the severity ring). Known: `.dist-sibling`'s `!important` box-shadow hides the severity ring on a profile-matched sibling of the selected order. Browser verification of drag ghosts, split segments, lane rows and dark mode is still owed.
- **Go To centering and spotlight (2026-10-21).** `Timeline.gotoLineDay(line, day, onWindowSet?, anchor?)` centers on the order, not the alert's day: `_gotoWindowFor` makes a window of max(3 days, span x 1.2) (clamped to `ZOOM_MIN_MS`/`ZOOM_MAX_MS`) centered on the span of every segment of the order and its pairwise peer, with an anchor, keeping only the overlap of the alert day with the order's span inside the window (the whole day when there is no overlap or no span); with no anchor the alert's day is centered. `scrollToLine(line, {itemIds?, peerLine?})` centers the row vertically (the target lane inside an expanded row; the midpoint of both rows for a pairwise alert when they fit), clamped at the top and bottom rows (accepted); it returns false until a `.vis-group` is rendered for every visible line. Order: window animation, then (first `rangechanged`, 700 ms fallback) bounded retry, scroll, `_fitHeightMeasured` for an expanded row, scroll again, then the spotlight. The spotlight is a container class `goto-spotlight` (other bars fade) plus DOM-only `goto-row` on the target's group and label, ~2.5 s, one timer, ended by `clearGotoTarget`. It fades in only: bars snap back when it ends, because the transition is scoped to `.goto-spotlight` so GanttFilter's `.dimmed` does not animate. `finish()` spotlights only a target marked by the same Go To (`_gotoMarkSeq`). It is transient and is **never written through a vis group `className` update** (the group/subgroup hazards above). `markGoto*` hold it while `_gotoSettling` is set so it starts after the last scroll; a newer Go To (`_gotoSeq`) aborts the older one's pending steps.
- **`navBarStyle` has a `'profile'` branch** (`gantt.mts`; precedence dimmed, conflict, profile-match, firmed, standard). The minimap draws profile-matched orders in `--accent` with a 1 px `--fg` keyline, not `--warn` (the DESIGN.md semantic-colour rule: warn means a warning).
- **`CALENDAR_ALERT_TYPES` is imported** from `insights/alert-profiles.mjs` (the Gantt day-cell conflict test no longer keeps a local copy); the drawer and the Alert Monitor use the same set.
- **Orders table `'profile'` status filter.** `TableStatusFilter` gains `'profile'`: a row passes when its id is in `AlertProfileMatches.current().taskIds`. The option is **disabled under All alerts** (`Table._profileFilterOff()`: that profile highlights nothing, so the filter would show a silent empty table) and carries a description line; on a profile switch to All alerts a chosen `'profile'` status falls back to the default. ## Gotchas

- `Calendar.workWindow`/`dailyCapacityHours`/`effectiveCapacityHours` are **not** in this domain — they live in `frontend/calendar/calendar-engine.mts`, which delegates the actual union-interval math to `nimbus-compute-core.js` (as of the 2026-09 capacity-math-triplication cleanup, all of it — no independent copy remains anywhere in `calendar-engine.mts`). A change to that capacity math belongs in `nimbus-compute-core.js`, not a mirrored copy, even though `gantt.mts`/`orders.mts` call it.
- `frontend/optimization/setup-scheduler.mts` is **not** part of this domain (it lives under `frontend/optimization/`) even though it consumes `../setup/setup-domain.mjs` — don't confuse it with anything here.
- The `saveAll` comments explicitly warn against ever passing a raw `Date` object into the wire payload — grep `Util.toLocalSeconds` before adding any new date-carrying field to the payload builder.
- **Due-date read rule (backward-scheduling Phase 1, 2026-10-14).** `original_end_date` is the SAP finish as received (`COALESCE(orders.original_finish_received, orders.basic_finish_date)` on the wire). A timed value is used as-is. An exact-midnight value is a date-only SAP finish: `Util.sapDueDate` (`frontend/platform/foundation.mts`) returns the close of that date's working window (a 24:00 close is the close instant, the exclusive next-day 00:00; lateness is `end > due`, so a bar ending exactly there is on time, and the pull/push day math takes the due DAY from `due - 1 ms`, i.e. the previous day), calling `NimbusComputeCore.dueDateInstant` with the day window of the task's line. `Util.setDueCalendarResolver` (wired in `app.js` from Store) supplies the calendar rows. A closed due date moves to the previous open day's close; a line with no calendar reads as raw + 23:59:59. The instant feeds lateness, the derived original start and the bounds text; the grid's and Inspector's original-end fields still show the raw value (a midnight shows as 12 AM).
