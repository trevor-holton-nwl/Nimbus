# frontend/scheduling — Gantt, Orders grid, selection, and backend persistence

## What lives here

- **`gantt.mts`** (~6,380 lines) — the Gantt timeline surface and its supporting UI:
  - `Timeline` — the vis-timeline wrapper (render, item lifecycle, drag/resize hooks).
  - `TimelineNav` — the canvas minimap/navigator strip above the Gantt. It is a **projection of `Timeline._items` + `Timeline._visibleLines()`** (same bars, split-order segments, row order and `.dimmed` filter state the Gantt renders — never re-derive the task/line filter chain here). Repaints are rAF-coalesced and triggered by `Timeline._items.on('*')` (the only signal for GanttFilter's className-only dim/undim updates) plus `lines:selected`/`plant:selected`/alerts/blocks/calendar Store events. Two rules for that `_items` subscriber: **skip events whose changed ids are all `kind:'zone'`** (the 1s ticker pushes zone bands whenever 'now' has moved ≥0.5 px at the current zoom, or an edge input changed) and **never gate on `Timeline._suppressEvents`** (GanttFilter._doApply sets it around exactly the updates the nav needs). Pure geometry helpers `navComputeRange`/`navLayout`/`navBarStyle`/`navClampRect` are exported for tests. Colors are read from CSS tokens at paint time (canvas can't use `var()`); DarkMode's repaint hook in `nimbus-intelligence.js` calls `render()`.
  - `DependencyOverlay` — finish-to-start link line rendering.
  - `Hierarchy` — plant → machine navigation tree.
  - `GanttFilter` — the Gantt's own line/search filter UI.
  - `Interaction` — the unified click/keyboard/drag pipeline (marquee multi-select, hover-preview card, double-click line isolation, multi-order ghost-drag, two-way AG Grid ↔ `Selection` sync).
  - `setupDiagnosticLabel` / `setupSourceLabel` — small label helpers for setup-aware diagnostics badges drawn on the timeline; `SetupPresentationDetail` is their shared type. Since 2026-10-27 `setupSourceLabel` maps the resolver's `'value-default'` source to `ui.setup_source_value_default` ("Default by value"; present in all five locales) next to the `implicit-zero` mapping, so the Inspector's "Setup source" row names a default-derived interval; the Gantt bar and the Inspector agree because `orders.mts`'s two index-less `resolveSetup` calls pass `snapshot.value_defaults ?? []` like every other caller. A default-covered pair is **covered**: it draws a normal setup bar for the summed default minutes, and the `setup-uncovered` "!" marker and alert no longer apply to it (their text now reads "Add a setup rule or a default by value"). On a setup-off plant the bars stay hidden (see the gating bullet below) but the ungated Inspector override editor can still show default-derived minutes. `persistence.mts`'s `SetupWriteKind` gained `'value-default'` so a saved default stales an open optimizer preview.
- **`orders.mts`** (2,833 lines) — the AG Grid orders table and order-detail chrome:
  - `Table` — the AG Grid wrapper (column defs, cell editors, row model).
  - `Inspector` — the single/multi-selection detail panel.
  - `ContextMenu` — right-click actions on grid rows/Gantt bars.
  - `Printer` — print/export.
  - `notifyResidualFirming` — standalone helper (fires a toast/alert when firming an order leaves a residual gap); `AgGridRowNode` is the row-node type used by both this file and `gantt.mts`.
- **`selection.mts`** (138 lines) — `Selection`, the multi-select store (which task ids are selected, anchor tracking for Shift-range-select, listener fanout). Independent of vis-timeline internals; every UI (Timeline, Table, Inspector, ContextMenu) subscribes to it. Never persisted, never autosaved.
- **`persistence.mts`** (1,769 lines) — `Persistence`: backend fetch (`load`/`loadForPlant`/`reload`), the localStorage cache (`_saveCache`, key `nimbus.state.v3`), dirty-id tracking, and the explicit `saveAll()` backend-save path.
- **`order-field-catalog.mjs`** (125 lines, + `order-field-catalog.d.mts` ambient types) — `ORDER_FIELD_CATALOG`, the single source of truth for which optional Orders fields exist and their default show/hide state in the AG Grid columns and Inspector panel. Deliberately a zero-dependency leaf module (no imports) so both this domain and the admin System Configuration UI can depend on it without adding a cross-domain edge. Since 2026-10-28 it also lists `original_start_date` (grid label "SAP Start", `dbColumn` `original_start_received`): the RAW SAP start as received, read-only, shown first in `Table._scheduleDateColumns()` (before Due Date; minWidth 170, date-only via `Table._fmtSapStart`, the time only when the value is non-midnight; hover hint `ui.sap_start_hint`) and as the first row of the Inspector Schedule card. It is NOT the derived Original Start retired by OQ16 (the schedule is anchored on the finish, so SAP Start differs from Planned Start after any edit); it is in `_catalogOnlyColumns`' `handwritten` set, and a saved grid layout that lacks it gets it placed directly before Due Date.
- **`gantt-lanes.mts`** — `computeLaneMap(intervals) -> {laneByParent, maxDepth}`, the pure lane assignment behind the Gantt's expandable rows (no imports, no Store, no DOM); test `tests/modules/gantt-lane-map.test.mjs`.
- **`nonworking-spans.mts`** — `buildNonWorkingSpans(fromMs, toMs, windowFor, {closedDaysOnly?, cap?}) -> {spans, truncated}`, the pure merged-span algorithm behind the Gantt's non-working-time shading (no imports, no Store, no DOM). `windowFor` is `Calendar.plantWorkWindow(plant, day)`.

## Counterpart

Backend half: `backend/scheduling/CLAUDE.md` (`backend/scheduling/routes.py`, `backend/scheduling/models.py`) — the `/tasks` family and the xmin concurrency contract this domain's `saveAll()`/`_refreshTasks()` talk to.

This domain's frontend files do not call `db.py`/`master_data.py` directly — they only ever go through the `/tasks*` HTTP endpoints owned by `backend/scheduling/routes.py`. No root-file line ranges to cite here.

## Key invariants & hazards

- **Authoritative runtime inputs and recovery (2026-10-01):** `/tasks/refresh` carries quantity, material, plant and raw SAP start with its runtime/version snapshot. `_prepTask` keeps the raw SAP start as `BASIC_START_DATE`; the client's SAP-start checks (visibility, production-version validity) read that copy. Nothing snaps `original_start_date` any more: the load-time calendar snap was removed in backward scheduling Task 2.5. Explicit `reload()` discards cached task edits only after successful hydration; failed loads and edits made during that request retain the local conflict. Ordinary startup `load()` continues to restore cache edits.

- **Manual firm is server state and an explicit-save edit (2026-10-06).** `GET /tasks` rows carry `firmed` (the planner firm); `Store.setTasks` rebuilds `firmedIds` from it, so a reload or plant switch can never keep a stale local firm. A Firm/Unfirm/undo marks exactly the touched ids dirty (`App._trackDirty`, `firmed:change`; never `_forceIds`, so a firm-only row cannot join an atomic optimizer group) and adds them to `Persistence._firmDirtyIds`; only those rows send `FIRMED` in `POST /tasks/update` (a date-only edit never writes this client's firm copy over another planner's). Firm edits ride the same edit-generation and sent-snapshot checks as dates. `firmed:change` from `'sandbox'` (What-If discard replays the snapshot) or `'refresh'` never dirties; `replaceFirmedIds` reports only ids whose membership changed. `UndoStack.restoreTasks` deliberately strips `firmed` from the snapshot (store.mts:1083): undoing a date/unschedule edit must not flip a firm without a marker, or the save would send no `FIRMED` and the UI would diverge from the server. `/tasks/refresh` rows copy `firmed` back into both `t.firmed` and `firmedIds`. **Start fresh:** the localStorage cache never writes `firmedIds` or per-task `firmed`, and cached `firmedIds`/`fixedIds`/`tasks[].firmed` are ignored on read (offline cache restore shows no firms; cached date edits still restore). The first firm toggle of a session shows `toast.firm_needs_save`; command-palette Firm All asks `confirm.firm_all` first.
- **Locks are frozen horizon, manual firm, and running only (2026-10-06).** SAP's own firm flag is display-only and never locks (`Engine.firmingStatus` reasons `frozen | manual | running`). A running order (`Engine.isInProgress`: start <= now < end) is firmed (D1/C7, 2026-10-27: the old "protected, not locked" copy rule is superseded and the Inspector reads "Firmed" with the reason "Running"); the Gantt's 30s lock-band scan (`Timeline._inLockBand`) tracks frozen-horizon and running membership so an order that starts while the page is open restyles without a reload.
- **Lock-aware firm actions and the Inspector lock block (2026-10-27, universal firm Workstream C).** Not firmed -> "Firm this order"; planner firm only -> "Unfirm"; frozen or running (with or without a planner firm) -> no firm/unfirm action anywhere (context menu shows the reason in a `.ctx-note`, the override dialog hides its "Also firm" row, the grid toolbar, F key, multi-inspector, command palette and dashboard skip such orders and say how many). Every write goes through `Engine.applyFirm` and every click handler re-checks at click time because the window rolls. The Inspector top block is `[data-insp-lock]` (a Firmed card with the reasons line, only while NIMBUS locks the order, plus a neutral `.sap-pill.neutral.insp-sap-tag` "SAP firmed" outside the card: SAP firm locks nothing) and the Firm/Unfirm button sits in `[data-insp-firm]` (`data-act` listeners, no inline handlers). `Inspector.refreshLock(id)` patches only those two regions and is called by the Gantt's 30 s lock-band scan on EVERY scan (reasons change as the window rolls, with no Store event); it is deliberately not a full `_render` (that would replace the Notes textarea, Flatpickr and the History card). The grid column "SAP Firmed" (key still `FIRMING_INDICATOR`, hidden by default) reads `ecc_firmed` and shows X or blank; `Selection.stats()` no longer carries `firmedCount`.
- **Delete / Unschedule = Needs Planning.** `Interaction.unscheduleIds` is the single implementation (Delete key and command palette); it skips locked orders and split orders (2+ segments), applies `Engine.plannerUnscheduleChanges()` (reason code `planner_unscheduled`) and is undoable.
- **Placement exception and the server's width gate (backward-scheduling Task 2.3, 2026-10-14):** the server rejects a single-edge save (`single_edge`) and a continuous bar whose elapsed width is not its run time (`width_mismatch`) unless the bar carries `placement_exception` (`'overtime'` | `'overlong'`); both reasons show through `describeRejections` (`ui.reject_single_edge`, `ui.reject_width_mismatch`). `_taskEditSnapshot` sends `placement_exception` on every save of a task that holds the field (an explicit `null` clears the stored marker; a task that never carried it omits it), and `/tasks/refresh` rows copy it back onto the task. The engine sets it: `Engine.manualSchedulePatchFor` writes `'overtime'` when a planner confirms a firmed order's overtime placement and `'overlong'` when it releases an overlong order as one bar, and the reconcile skips marked rows. The server skips the width gate for a save that does not move the bar (both sent edges equal the stored raw edges and the run time is unchanged). The browser never sends `trust_start`; external callers that do not trust their sent start send it (see `backend/scheduling/CLAUDE.md`).
- **Manual placement holds the finish (backward scheduling Task 2.5, 2026-10-14):** a drop, a typed Planned finish (the grid column and the Inspector field; Planned start and Due date are read-only), the Override dialog's date (now the FINISH, field `ovr-finish`), and the run-time, machine and version edits all reach `Engine.manualSchedulePatchFor(task, line, finish, …)`, which derives the start backward through the working time and always returns both edges. The grid and the Inspector call it through `Engine.manualRoutingSchedulePatchFor`, which delegates to it. A typed End, or a bar drag or resize, on a RUNNING order is refused with `running_finish_locked` (D2): the run-time edit is the only manual resize of a started order. For any other order a bar drag or a right-edge resize sets the finish, and a held finish keeps its exact minute (floored to the minute); only a horizontal Gantt drag snaps (D1), before it reaches the engine. A left-edge-only change is reverted with `toast.left_edge_locked` (`lockLeftEdge` also vetoes it live through vis `onMoving`). A finish that would have to move EARLIER (no working time ends there) is refused with `toast.finish_cannot_hold` and the bar springs back; a backward start that falls before the plant's now is NOT a refusal: the order places forward from now with `derivationIssue {code:'reversal_forward', detail:'due_date_past' | 'run_time_grew'}` and the late alert (O2, OQ3, OQ7 a, OQ19 c); `Engine.lastManualRefusal` says why and whether the engine already toasted. A firmed order whose finish would have to move asks `Engine.confirmOvertimePlacement`, then retries with `confirmedOvertime` and stores `placement_exception = 'overtime'`. A marked order is translated verbatim (width kept) until a planner clears the marker. Run-time, machine and version edits hold the finish, and a running order holds its start (`holdStartIfRunning`, through `Engine.heldStartPatchFor`: the real start survives when it is off the 15-minute grid, and when the remaining run crosses closed time the forward walk returns the calendar's pieces (D3: always walked as `partial_allowed`, because a continuous bar across closed time fails the server width check); a recorded start inside closed time moves to the next open minute and the stored start follows it; `Engine.schedulePatchFor` is therefore on the retained forward-path list). A queued row whose hold is `runtime_unknown`, `overlong_never` or `run_time_over_cap` is anchored at its due instant (`Table._RELEASABLE_HOLDS`); a placement releases only `overlong_never` and `run_time_over_cap` rows to `scheduled`. Gantt lock-band and firming styling read the plant clock (`Timeline._nowFor`). The load-time `_snapToWorkingHours` snap is gone.
- **Gantt PV drop rule, multi-drag line lock and drag-time row dim (2026-10-21, wave 3; not browser-verified).** Single drop (`Interaction._commitSingleDrop`, values taken at drop time): a same-line drag keeps the plain `Runtime.eligible` block (a time-only drag of an ineligible current pair stays blocked); a line move on a routing plant is `opts.chosenPv ? switch : Runtime.dropDecision(t, newLine)` — keep (current PV covers it; `Runtime.dropDecision` judges pairs with `requireOps`, so a drag never keeps or switches to a PV that `resolve` would reject with `no_operation_at_workcenter`), switch (one other PV; written with the move, `toast.pv_switched`), choose (`Modal.choose` of the covering PVs; the pick re-applies the drop from the CAPTURED `{id,itemId,newLine,requestedFinish,opts}` because any rebuild while the modal is open resets the vis item; a changed task fingerprint aborts with `toast.pv_drop_stale`, cancel springs back; an overtime confirm after the pick re-enters `_commitSingleDrop` from the same capture, not the live vis item), reject (`_rejectRuntimeMove`). The "bar unchanged" short-circuit also compares PV and run time. Multi-drag never changes any order's line on ANY plant (D5/D14): a drop that moves the dragged item to another row is rejected whole with one `toast.multi_drag_line_locked` per gesture (latch on the selection set, cleared by a rebuild or after 2 s); companion ghosts preview on their own line. Row dim: vis `onMoving` (per frame) calls `Timeline.onItemMoving`, which on the first frame of a single, non-sub-order drag on a routing plant dims rows with no eligible pair (`Runtime.eligiblePairs(t,{requireOps:true})`; skipped when `Runtime.hasMapFor(plant)` is false, and the order's own row is never dimmed; right-edge resizes and same-line time drags dim too, because `onMoving` cannot tell them from a row change and the planner may still cross rows mid-gesture) via `_groupClassName` (the only composer of a group className: `row-expanded|row-flat` + `row-drag-ineligible`, never falsy) and one className-only `_groups.update` (never `content`, never `subgroup`). `undimRowsForDrag` runs at the top of `_onDataSetUpdate`, on document `pointerup`/`pointercancel`, and on `plant:selected`; `rebuild()` deliberately does NOT clear it so a mid-drag rebuild keeps the dim. **vis 7.7.3 `timechange`/`timechanged` are custom-time-bar events (browser-verified 2026-11): an item drag emits NO such events, only one DataSet `update` per moved item after the move, so `_onTimeChange` (ghost previews, setup dim, edge auto-scroll) is dead for item drags and stays unwired on purpose (comment at the binding). `Interaction._isDragging` is now driven by hooks that fire: `Interaction._beginItemDrag()` on the first `onMoving` frame, `_endItemDrag()` on document `pointerup`/`pointercancel` and defensively at the top of `_onDataSetUpdate` (state in `drag-state.mts` `createDragGate`). While true it suppresses hover cards and the CENTER_ON_CLICK pan and blocks `Persistence._calendarRefreshBlocked` re-hydrates; a probe that was blocked by the drag is recorded in `Persistence._deferredRefreshPlants` and re-run (`runDeferredRefreshes`, then a Gantt rebuild if horizons moved) on drag end. Drag-time row dimming lives on `onMoving`.
- **PV - Machine on routing plants (2026-10-21; spec `docs/superpowers/specs/2026-10-21-pv-machine-eligibility-design.md`).** `Table._getPairOptions(task)` is the one option list for the grid MACHINE editor (`cellEditorParams`), the Inspector `data-field="PV_MACHINE"` select and `#ovr-line`: `{value: 'pv|machine', label: t('ui.pv_machine_option')}` from `Runtime.eligiblePairs(task, {requireOps: true})` (`computeEligiblePairs` now really drops a pair whose rate-map `ops` has no entry at the PV's work center, so no offered pair fails `resolve` for lack of an operation), the current pair prepended with `ui.pv_machine_current_ineligible` when it is not in the set; a non-routing plant or a `PARENT_ORDER` sub-order gets today's line list as `{value: l, label: l}` (`_getLineOptions` itself is unchanged). `Table._parsePairValue(v)` splits at the first `|` (bare machine gives `pv: null` = keep the PV). `_SearchableLineEditor` takes strings or `{value,label}` options, filters on the label and returns the value; with pair options and nothing chosen it answers the row's own pair, never a bare machine. AG Grid writes the raw editor value (the pair string) onto the Store row before `_onCellChanged`, so the MACHINE branch parses it and puts the pre-edit machine back before anything else (the row is the Store task, so the undo snapshot and line index would otherwise see the new machine). A pair that does not pass `Runtime.eligible` is rejected whole with `toast.pv_machine_ineligible`; re-picking the current pair is a no-op. Writes go through `Engine.pairSchedulePatchFor` (unplaced orders through `_unplacedMachineRuntime(task, machine, pv)`, which writes the PV too), in one `Store.updateTask` wrapped by `UndoStack.snapshotTasks`/`push` (`Table._pushPairUndo`; grid, Inspector and Override each push one entry). D11: the PV grid column is `editable` only off routing plants and the Inspector renders PV as read-only text on them; the old routing PV-edit branches are gone. Setup signatures may include the PV, so a PV switch can change changeover with neighbours (the alerts recompute catches it).
- **PV - Machine fix wave F1 (2026-10-21).** Every PV read in `orders.mts` goes through `Runtime.normPv` (current-pair key in `_getPairOptions`, Inspector/Override selected-option compares, grid/Inspector/Override same-pair no-op checks, `_unplacedMachineRuntime`, the editor's own-pair answer, and `_parsePairValue`'s output), because pilot orders store the unpadded "1" while pair values are "0001|M1". The offered list is exactly the set `Runtime.resolve` accepts (`eligiblePairs` filters through the real gate), so a zero-rate or zero-quantity pair no longer appears and then bounces with `toast.pv_machine_ineligible`; the current-pair "not eligible" label names the failing step via `{{step}}`.
- **One plant-zone clock (backward scheduling Task 2.4, 2026-10-14):** `/tasks` carries `meta.server_now`; `Store.setServerNow` turns it into an offset, and `Store.plantNow(plant)` projects the server instant into the plant's IANA zone, or returns null when the plant has no valid zone. A plant with no valid zone is blocked: `Store._blockedPlants` records it, one `toast.plant_no_timezone` is shown per session, and nothing is derived for it. The Gantt's ticker, zone bands and lock band read the plant clock through `Timeline._plantNow` and `Timeline._nowFor`. `/tasks/refresh` and `/tasks/horizons` carry no `server_now`, so they leave the offset as it is.
- **Client placement state (backward scheduling Task 2.6, 2026-10-14):** `Store._markPlaced` sets `user_scheduled` locally on any client write that gives a row both edges. Display-only derivations, refreshes, undo and What-If restores, the `'time-machine'` source (VI8), distribution's own saves and notes do not count. The source `engine-runtime-reconcile-display` is skipped by the dirty tracker (`App._trackDirty`) and by autosave, so a display derivation never dirties a row. `derivationIssue` and `systemMove` are notes the save payload never carries: `Store._clearStaleNotes` clears them on the next schedule, machine or run-time edit and a refresh copy-back clears them. `derivationIssue` IS cached with the task and revived through the persistence overlay (D21), so a reload keeps the reason; `systemMove` stays session-only.
- **Save rejections:** `machine_unknown` (server-side MACHINE validation) gets its own toast and is excluded from `describeRejections`; a second `saveAll()` while one is in flight is skipped, and `toast.save_in_progress` shows only for user-initiated (non-`silent`) saves.
- **Needs Planning (2026-09-09):** `planning_status='needs_planning'` means null committed dates and empty `scheduleSegments`; preserve SAP baseline dates. `_prepTask`, Store normalization, cache overlay, calendar normalization and refresh enforce this. A save that carries dates and no explicit planning status returns the row to `scheduled` (`update_task_dates_bulk`), and a placement that releases an `overlong_never` or `run_time_over_cap` row returns it to `scheduled` in the same patch. Orders exposes status/reason/window and the Needs Planning status filter.
- **Atomic optimizer saves, split from manual saves (Wave 2, 2026-11-02):** `_forceIds` is a historical name for dependent optimizer/undo edits. `saveAll()` now sends the dirty rows in `_forceIds` as ONE atomic request (`atomic_optimizer=true`, `force=false` for every row) and every other dirty row as a SEPARATE non-atomic request, sequentially (atomic group first), through `_saveGroups` / `_sendSaveGroup` / `_applySaveResult`; each group's result (versions, stale, invalid, toasts) is handled independently, so a stale optimizer row never blocks manual edits and a stale manual row takes the normal stale-refresh path. A single 'Saved to backend' toast shows only when every group saved cleanly. The atomic group keeps its all-or-nothing semantics: any rejection preserves all of its local edits/dirty flags, there is no per-row stale refresh for it, and a conflicted member withholds the whole group (the manual group still goes). `schedule-unsaved` remains visible. A network failure or timeout stops the sequence (the next group would hit the same failure); an HTTP rejection does not. The response handler runs outside the network `try`, so a handler bug toasts `toast.save_handler_error` instead of 'saved locally'. Offline cache retains `_optimizerDirtyIds` and cannot evict a partial dependent task set (`cacheTiers` writes such a snapshot whole); online reload excludes that group's cached positions. Partial-save behavior of the manual group remains as described below.
- **Wave 2 load/save safety (2026-11-02).** `_loadCache(plant)` and the backend-load cache overlay/non-task restore reject a cache whose `selectedPlant` tag differs (`_cacheMatchesPlant`; untagged legacy caches still restore; the single key `nimbus.state.v3` is kept, the tag is the check). The random `_loadDemo` fallback is gone: a failed or timed-out `/tasks` with no usable cache shows an empty board, a 10-minute `toast.backend_unreachable_empty` and the reconnect watcher. Quota tiers (`cacheTiers`) trim clean tasks only, so a dirty task is never evicted. `_overlayUserMoves` restores an unsaved Unschedule (`needs_planning`, null dates, reason) and treats a changed END as a move. `invalid_ids` that still match the sent snapshot are refreshed through `_refreshTasks` (the bar snaps back; the partial-save toast still names the reason). `_sameAsSent` also compares FIRMED (when sent), planning status, reason code and placement exception. A late save response stamps `row_version` on a row whose version is unchanged even if the board was replaced (dirty clearing and toasts stay gated on the collection generation). `/tasks/refresh` has a 15 s timeout; a failed refresh is retried by the next Save for the still-conflicted ids (`_refreshRetry`). `saveAll` prunes dirty ids with no order in the Store and toasts `toast.nothing_to_save` when nothing is left (not for `silent` callers). A `beforeunload` guard asks only while `hasPendingWork()`, and `pagehide` flushes the cache. Both hydration `.finally` fan-outs in `load()` check the load generation. Tests: `tests/modules/scheduling/persistence-wave2.test.mjs`.

- **Timezone-naive save contract (fixed, not open):** `saveAll()` (persistence.mts:1175; payload builder `_taskEditSnapshot`, ~1098-1105) converts every date to local seconds via `Util.toLocalSeconds` before `JSON.stringify` — a raw `Date` would serialize as UTC (`toISOString()`), but the backend read path emits bare naive `strftime` strings that `new Date()` parses as local, so a raw `Date` here would round-trip shifted by the client's UTC offset for non-UTC users. This was a real corruption bug, fixed 2026-07-07; it is not still open.
- **`saveAll()` no longer sends `blocks`/`calendars` (S10-7, 2026-11-02).** The body is `{ tasks, client_id, atomic_optimizer }` per group. The backend (`TasksUpdatePayload`) only ever consumed `tasks`; calendars/blackouts persist through the separate `/plant-calendar/*` endpoints. An empty dirty set no longer POSTs at all (`toast.nothing_to_save`).
- **Partial-save dirty tracking:** persisted and terminally rejected rows clear dirty state only when the live writable snapshot still matches what was sent. Stale rows remain dirty until a complete authoritative refresh succeeds. Refresh checks the original save snapshot, row version, edit generation and collection generation; a newer edit (including edit-and-revert) is retained with its old token and blocked from ordinary resave until explicit reload/discard. Unrelated ordinary saves remain available; an affected atomic group remains entirely unsaved. Refresh includes writable attributes, nullable runtime, provenance and segments alongside its version.
- **Save-time conflict reporting (N3).** `saveAll()` reads the `conflicts` list off `BulkUpdateResult` (persistence.mts:1358) — advisory only, since the rows it names are already persisted: the server scans the written machines for strict overlaps under a `SAVEPOINT` inside the same save transaction. When present, it toasts `toast.save_conflicts` and emits a `schedule:conflicts` Store event (lines-scoped) instead of importing `insights/services.mjs` directly. Separately, `strict_conflicts` — honored only when the save is also `atomic_optimizer` — makes the server reject the whole batch with HTTP 200, `status:'error'`, `error_code:'schedule.conflicts'`; `saveAll()` detects that via `result.error_code` (persistence.mts:1285) and toasts `toast.optimizer_conflicts` instead, leaving every dependent edit unsaved.
- **Auto-reflow after manual edits:** `Engine.autoReflow()` (owned by the optimization domain) is called only from the overload-alert Fix (`insights/services.mts`), never from this domain's `Interaction`/drag handlers; a drop runs no reflow cascade. When the Fix runs, it re-flows subsequent unfixed orders on one line to clear the overlap. It only shifts dates within one line, triggering an incremental line-scoped alert recompute.
- **Task IDs are MD5 hashes** of `f"{PRODUCTION_ORDER}|{MATERIAL_NUMBER}"` (`make_id()` in root `db.py`, currently line 123). The hash excludes time, so ids are stable across reloads/reschedules — `Selection`, `Table`'s row keying, and drag/edit operations across this whole domain rely on that stability.
- **`gantt.mts` ↔ `orders.mts` form a two-way in-domain module dependency**: `gantt.mts` imports `Table`/`Inspector`/`ContextMenu`/`notifyResidualFirming` from `orders.mjs`, and `orders.mts` imports `Timeline`/`TimelineNav`/`setupDiagnosticLabel`/`setupSourceLabel` back from `gantt.mjs`. This is intentional (both are the same domain) — don't "fix" it by trying to break the cycle across a domain boundary.

- **Non-working-time shading (2026-10-16; design `docs/CALENDAR_PERIODS_DESIGN.md` section 5).** The Gantt greys the plant's closed days and off-shift hours (plant pattern only, never per line, so the line filter changes nothing). Rules that keep it from fighting the rest of the timeline:

- `Calendar.workWindow`/`dailyCapacityHours`/`effectiveCapacityHours` are **not** in this domain — they live in `frontend/calendar/calendar-engine.mts`, which delegates the actual union-interval math to `nimbus-compute-core.js` (as of the 2026-09 capacity-math-triplication cleanup, all of it — no independent copy remains anywhere in `calendar-engine.mts`). - The `saveAll` comments explicitly warn against ever passing a raw `Date` object into the wire payload — grep `Util.toLocalSeconds` before adding any new date-carrying field to the payload builder.
- **Due-date read rule (backward-scheduling Phase 1, 2026-10-14).** `original_end_date` is the SAP finish as received (`COALESCE(orders.original_finish_received, orders.basic_finish_date)` on the wire). A timed value is used as-is. An exact-midnight value is a date-only SAP finish: `Util.sapDueDate` (`frontend/platform/foundation.mts`) returns the close of that date's working window (a 24:00 close is the close instant, the exclusive next-day 00:00; lateness is `end > due`, so a bar ending exactly there is on time, and the pull/push day math takes the due DAY from `due - 1 ms`, i.e. the previous day), calling `NimbusComputeCore.dueDateInstant` with the day window of the task's line. `Util.setDueCalendarResolver` (wired in `app.js` from Store) supplies the calendar rows. A closed due date moves to the previous open day's close; a line with no calendar reads as raw + 23:59:59. The instant feeds lateness, the derived original start and the bounds text; the grid's and Inspector's original-end fields still show the raw value (a midnight shows as 12 AM).

- **ErrorLog hooks (2026-10-23).** The `/tasks` `stale` branch logs one `ErrorLog.warn` with `errorCode: 'tasks.conflict'`, the save's `reqId` and ctx `{ids, base_versions}` (from `Store.tasks[id].row_version` at reply time); `_refreshTasks` logs an info `conflict confirmed` `{id, base_version, server_version}` for each row the server answers that is not a silent U25 reconcile. - **Tool inventory load, refresh and freshness (Tool Inventory Wave 3, 2026-10-27).** `Persistence.load` fetches `GET /master-data/tool_inventory?plant=` in each of its three master-data fetch groups (no-plant path: `tool_inventory: undefined`, no fetch) through `_fetchToolInventory` (never rejects; `undefined` on non-ok/timeout/malformed, rows sorted by `tool_id`, so the optimizer's JSON stale diff is deterministic) and `_resolveToolInventory`: a failed fetch is `undefined` (NOT `[]`) plus an `ErrorLog.warn` every time and ONE `toast.tool_inventory_unavailable` per plant per session (`_toolInventoryWarned`); a same-plant reload keeps the rows it holds (keep-on-failure like workcenters); a different plant's rows are never reused. `load()` also clears `masterData.tool_inventory` silently (no emit) the moment a different plant starts loading (`_toolInventoryPlant`), because the first `schedule:hydrated` alert pass runs before master data arrives. `Persistence.refreshToolInventory(plant)` re-fetches into the Store via `setMasterData(..., 'tool-inventory-refresh', 'tool_inventory')` (the shell already turns `master-data-changed` into one alert recompute; do not add another), keeps the held rows on failure, and discards its response on a plant switch or newer `load()` (`selectedPlant` + `_loadRequest`). **Horizons probe:** `GET /tasks/horizons` now also returns `tool_inventory_version` (`"<count>|<max updated_at ISO>"`, null when empty or the table is missing, fail-open) and `tooling_rule` ('off'|'hard', default 'off'). `_noteToolInventoryVersion` (called from `refreshHorizons`) compares the server's version string with `_toolInventoryBaseline`. **The baseline is the server's own version string, read BEFORE the rows** (`_fetchToolInventoryWithVersion`: `_readToolInventoryVersion` = a direct `/tasks/horizons` GET, then `_fetchToolInventory`;
