# frontend/scheduling — Gantt, Orders grid, selection, and backend persistence

## What lives here

- **`gantt.mts`** (4,891 lines) — the Gantt timeline surface and its supporting UI:
  - `Timeline` — the vis-timeline wrapper (render, item lifecycle, drag/resize hooks).
  - `TimelineNav` — the canvas minimap/navigator strip above the Gantt. It is a **projection of `Timeline._items` + `Timeline._visibleLines()`** (same bars, split-order segments, row order and `.dimmed` filter state the Gantt renders — never re-derive the task/line filter chain here). Repaints are rAF-coalesced and triggered by `Timeline._items.on('*')` (the only signal for GanttFilter's className-only dim/undim updates) plus `lines:selected`/`plant:selected`/alerts/blocks/calendar Store events. Two rules for that `_items` subscriber: **skip events whose changed ids are all `kind:'zone'`** (the 1s ticker pushes zone bands whenever 'now' has moved ≥0.5 px at the current zoom, or an edge input changed) and **never gate on `Timeline._suppressEvents`** (GanttFilter._doApply sets it around exactly the updates the nav needs). Pure geometry helpers `navComputeRange`/`navLayout`/`navBarStyle`/`navClampRect` are exported for tests. Colors are read from CSS tokens at paint time (canvas can't use `var()`); DarkMode's repaint hook in `nimbus-intelligence.js` calls `render()`.
  - `DependencyOverlay` — finish-to-start link line rendering.
  - `Hierarchy` — plant → machine navigation tree.
  - `GanttFilter` — the Gantt's own line/search filter UI.
  - `Interaction` — the unified click/keyboard/drag pipeline (marquee multi-select, hover-preview card, double-click line isolation, multi-order ghost-drag, two-way AG Grid ↔ `Selection` sync).
  - `setupDiagnosticLabel` / `setupSourceLabel` — small label helpers for setup-aware diagnostics badges drawn on the timeline; `SetupPresentationDetail` is their shared type.
- **`orders.mts`** (2,822 lines) — the AG Grid orders table and order-detail chrome:
  - `Table` — the AG Grid wrapper (column defs, cell editors, row model).
  - `Inspector` — the single/multi-selection detail panel.
  - `ContextMenu` — right-click actions on grid rows/Gantt bars.
  - `Printer` — print/export.
  - `notifyResidualFirming` — standalone helper (fires a toast/alert when firming an order leaves a residual gap); `AgGridRowNode` is the row-node type used by both this file and `gantt.mts`.
- **`selection.mts`** (138 lines) — `Selection`, the multi-select store (which task ids are selected, anchor tracking for Shift-range-select, listener fanout). Independent of vis-timeline internals; every UI (Timeline, Table, Inspector, ContextMenu) subscribes to it. Never persisted, never autosaved.
- **`persistence.mts`** (1,715 lines) — `Persistence`: backend fetch (`load`/`loadForPlant`/`reload`), the localStorage cache (`_saveCache`, key `nimbus.state.v3`), dirty-id tracking, and the explicit `saveAll()` backend-save path.
- **`order-field-catalog.mjs`** (124 lines, + `order-field-catalog.d.mts` ambient types) — `ORDER_FIELD_CATALOG`, the single source of truth for which optional Orders fields exist and their default show/hide state in the AG Grid columns and Inspector panel. Deliberately a zero-dependency leaf module (no imports) so both this domain and the admin System Configuration UI can depend on it without adding a cross-domain edge.

## Counterpart

Backend half: `backend/scheduling/CLAUDE.md` (`backend/scheduling/routes.py`, `backend/scheduling/models.py`) — the `/tasks` family and the xmin concurrency contract this domain's `saveAll()`/`_refreshTasks()` talk to.

This domain's frontend files do not call `db.py`/`master_data.py` directly — they only ever go through the `/tasks*` HTTP endpoints owned by `backend/scheduling/routes.py`. No root-file line ranges to cite here.

## Key invariants & hazards

- **Authoritative runtime inputs and recovery (2026-10-01):** `/tasks/refresh` carries quantity, material, plant and raw SAP start with its runtime/version snapshot. `_prepTask` keeps the raw SAP start as `BASIC_START_DATE`; the client's SAP-start checks (visibility, production-version validity) read that copy. Nothing snaps `original_start_date` any more: the load-time calendar snap was removed in backward scheduling Task 2.5. Explicit `reload()` discards cached task edits only after successful hydration; failed loads and edits made during that request retain the local conflict. Ordinary startup `load()` continues to restore cache edits.

- **Manual firm is server state and an explicit-save edit (2026-10-06).** `GET /tasks` rows carry `firmed` (the planner firm); `Store.setTasks` rebuilds `firmedIds` from it, so a reload or plant switch can never keep a stale local firm. A Firm/Unfirm/undo marks exactly the touched ids dirty (`App._trackDirty`, `firmed:change`; never `_forceIds`, so a firm-only row cannot join an atomic optimizer group) and adds them to `Persistence._firmDirtyIds`; only those rows send `FIRMED` in `POST /tasks/update` (a date-only edit never writes this client's firm copy over another planner's). Firm edits ride the same edit-generation and sent-snapshot checks as dates. `firmed:change` from `'sandbox'` (What-If discard replays the snapshot) or `'refresh'` never dirties; `replaceFirmedIds` reports only ids whose membership changed. `UndoStack.restoreTasks` deliberately strips `firmed` from the snapshot (store.mts:1083): undoing a date/unschedule edit must not flip a firm without a marker, or the save would send no `FIRMED` and the UI would diverge from the server. `/tasks/refresh` rows copy `firmed` back into both `t.firmed` and `firmedIds`. **Start fresh:** the localStorage cache never writes `firmedIds` or per-task `firmed`, and cached `firmedIds`/`fixedIds`/`tasks[].firmed` are ignored on read (offline cache restore shows no firms; cached date edits still restore). The first firm toggle of a session shows `toast.firm_needs_save`; command-palette Firm All asks `confirm.firm_all` first.
- **Locks are frozen horizon, manual firm, and running only (2026-10-06).** SAP's own firm flag is display-only and never locks (`Engine.firmingStatus` reasons `frozen | manual | running`). A running order (`Engine.isInProgress`: start <= now < end) is protected, not "locked", in UI copy; the Gantt's 30s lock-band scan (`Timeline._inLockBand`) tracks frozen-horizon and running membership so an order that starts while the page is open restyles without a reload.
- **Delete / Unschedule = Needs Planning.** `Interaction.unscheduleIds` is the single implementation (Delete key and command palette); it skips locked orders and split orders (2+ segments), applies `Engine.plannerUnscheduleChanges()` (reason code `planner_unscheduled`) and is undoable.
- **Placement exception and the server's width gate (backward-scheduling Task 2.3, 2026-10-14):** the server rejects a single-edge save (`single_edge`) and a continuous bar whose elapsed width is not its run time (`width_mismatch`) unless the bar carries `placement_exception` (`'overtime'` | `'overlong'`); both reasons show through `describeRejections` (`ui.reject_single_edge`, `ui.reject_width_mismatch`). `_taskEditSnapshot` sends `placement_exception` on every save of a task that holds the field (an explicit `null` clears the stored marker; a task that never carried it omits it), and `/tasks/refresh` rows copy it back onto the task. The engine sets it: `Engine.manualSchedulePatchFor` writes `'overtime'` when a planner confirms a firmed order's overtime placement and `'overlong'` when it releases an overlong order as one bar, and the reconcile skips marked rows. The server skips the width gate for a save that does not move the bar (both sent edges equal the stored raw edges and the run time is unchanged). The browser never sends `trust_start`; external callers that do not trust their sent start send it (see `backend/scheduling/CLAUDE.md`).
- **Manual placement holds the finish (backward scheduling Task 2.5, 2026-10-14):** a drop, a typed Planned finish (the grid column and the Inspector field; Planned start and Due date are read-only), the Override dialog's date (now the FINISH, field `ovr-finish`), and the run-time, machine and version edits all reach `Engine.manualSchedulePatchFor(task, line, finish, …)`, which derives the start backward through the working time and always returns both edges. The grid and the Inspector call it through `Engine.manualRoutingSchedulePatchFor`, which delegates to it. A bar drag or a right-edge resize sets the finish; a left-edge-only change is reverted with `toast.left_edge_locked` (`lockLeftEdge` also vetoes it live through vis `onMoving`). A finish that cannot be held is refused with `toast.finish_cannot_hold` and the bar springs back; `Engine.lastManualRefusal` says why and whether the engine already toasted. A firmed order whose finish would have to move asks `Engine.confirmOvertimePlacement`, then retries with `confirmedOvertime` and stores `placement_exception = 'overtime'`. A marked order is translated verbatim (width kept) until a planner clears the marker. Run-time, machine and version edits hold the finish, and a running order holds its start (`holdStartIfRunning`). A queued row whose hold is `runtime_unknown`, `overlong_never` or `run_time_over_cap` is anchored at its due instant (`Table._RELEASABLE_HOLDS`); a placement releases only `overlong_never` and `run_time_over_cap` rows to `scheduled`. Gantt lock-band and firming styling read the plant clock (`Timeline._nowFor`). The load-time `_snapToWorkingHours` snap is gone.
- **One plant-zone clock (backward scheduling Task 2.4, 2026-10-14):** `/tasks` carries `meta.server_now`; `Store.setServerNow` turns it into an offset, and `Store.plantNow(plant)` projects the server instant into the plant's IANA zone, or returns null when the plant has no valid zone. A plant with no valid zone is blocked: `Store._blockedPlants` records it, one `toast.plant_no_timezone` is shown per session, and nothing is derived for it. The Gantt's ticker, zone bands and lock band read the plant clock through `Timeline._plantNow` and `Timeline._nowFor`. `/tasks/refresh` and `/tasks/horizons` carry no `server_now`, so they leave the offset as it is.
- **Client placement state (backward scheduling Task 2.6, 2026-10-14):** `Store._markPlaced` sets `user_scheduled` locally on any client write that gives a row both edges. Display-only derivations, refreshes, undo and What-If restores, distribution's own saves and notes do not count. The source `engine-runtime-reconcile-display` is skipped by the dirty tracker (`App._trackDirty`) and by autosave, so a display derivation never dirties a row. `derivationIssue` and `systemMove` are session-only notes: `Store._clearStaleNotes` clears them on the next schedule, machine or run-time edit, a refresh copy-back clears them, and the save payload and the local cache never carry them.
- **Save rejections:** `machine_unknown` (server-side MACHINE validation) gets its own toast and is excluded from `describeRejections`; a second `saveAll()` while one is in flight is skipped, and `toast.save_in_progress` shows only for user-initiated (non-`silent`) saves.
- **Needs Planning (2026-09-09):** `planning_status='needs_planning'` means null committed dates and empty `scheduleSegments`; preserve SAP baseline dates. `_prepTask`, Store normalization, cache overlay, calendar normalization and refresh enforce this. A save that carries dates and no explicit planning status returns the row to `scheduled` (`update_task_dates_bulk`), and a placement that releases an `overlong_never` or `run_time_over_cap` row returns it to `scheduled` in the same patch. Orders exposes status/reason/window and the Needs Planning status filter.
- **Atomic optimizer saves:** `_forceIds` is a historical name for dependent optimizer/undo edits. It now opts `/tasks/update` into `atomic_optimizer=true` with `force=false` for every row. Any rejection preserves all local edits/dirty flags; there is no per-row stale refresh. `schedule-unsaved` remains visible. Offline cache retains `_optimizerDirtyIds` and cannot evict a partial dependent task set; online reload excludes that group's cached positions. Legacy non-optimizer partial-save behavior remains as described below.

- **Timezone-naive save contract (fixed, not open):** `saveAll()` (persistence.mts:1119; payload builder `_taskEditSnapshot`, ~1081-1100) converts every date to local seconds via `Util.toLocalSeconds` before `JSON.stringify` — a raw `Date` would serialize as UTC (`toISOString()`), but the backend read path emits bare naive `strftime` strings that `new Date()` parses as local, so a raw `Date` here would round-trip shifted by the client's UTC offset for non-UTC users. This was a real corruption bug, fixed 2026-07-07; it is not still open.
- **`saveAll()` always POSTs full `blocks`/`calendars`** (persistence.mts:1176 — `JSON.stringify({ tasks: taskPayload, atomic_optimizer: atomicOptimizer, blocks: Store.blocks, calendars: Store.calendars })`) even when the dirty-task list is empty. The backend (`TasksUpdatePayload`) only consumes `tasks` — `blocks`/`calendars` are accepted but ignored (calendars/blackouts persist through the separate `/plant-calendar/*` endpoints). This is legacy ride-along, harmless but worth knowing before assuming an empty save is a no-op network call.
- **Partial-save dirty tracking:** persisted and terminally rejected rows clear dirty state only when the live writable snapshot still matches what was sent. Stale rows remain dirty until a complete authoritative refresh succeeds. Refresh checks the original save snapshot, row version, edit generation and collection generation; a newer edit (including edit-and-revert) is retained with its old token and blocked from ordinary resave until explicit reload/discard. Unrelated ordinary saves remain available; an affected atomic group remains entirely unsaved. Refresh includes writable attributes, nullable runtime, provenance and segments alongside its version.
- **Save-time conflict reporting (N3).** `saveAll()` reads the `conflicts` list off `BulkUpdateResult` (persistence.mts:1299) — advisory only, since the rows it names are already persisted: the server scans the written machines for strict overlaps under a `SAVEPOINT` inside the same save transaction. When present, it toasts `toast.save_conflicts` and emits a `schedule:conflicts` Store event (lines-scoped) instead of importing `insights/services.mjs` directly. Separately, `strict_conflicts` — honored only when the save is also `atomic_optimizer` — makes the server reject the whole batch with HTTP 200, `status:'error'`, `error_code:'schedule.conflicts'`; `saveAll()` detects that via `result.error_code` (persistence.mts:1229) and toasts `toast.optimizer_conflicts` instead, leaving every dependent edit unsaved.
- **Auto-reflow after manual edits:** `Engine.autoReflow()` (owned by the optimization domain, called from this domain's `Interaction`/drag handlers) re-flows subsequent unfixed orders on one line to eliminate drag-created overlap. It only shifts dates within one line, triggering an incremental line-scoped alert recompute. Anything in the `Interaction` → `Engine` path must be aware this can fire.
- **Task IDs are MD5 hashes** of `f"{PRODUCTION_ORDER}|{MATERIAL_NUMBER}"` (`make_id()` in root `db.py`, currently line 122). The hash excludes time, so ids are stable across reloads/reschedules — `Selection`, `Table`'s row keying, and drag/edit operations across this whole domain rely on that stability.
- **`gantt.mts` ↔ `orders.mts` form a two-way in-domain module dependency**: `gantt.mts` imports `Table`/`Inspector`/`ContextMenu`/`notifyResidualFirming` from `orders.mjs`, and `orders.mts` imports `Timeline`/`TimelineNav`/`setupDiagnosticLabel`/`setupSourceLabel` back from `gantt.mjs`. This is intentional (both are the same domain) — don't "fix" it by trying to break the cycle across a domain boundary.
- **This `CLAUDE.md` (and every other `frontend/<domain>/CLAUDE.md`) is blocked from public static serving** by `brain.py`'s `block_markdown_mw` (any request path ending `.md` gets a 404), regardless of the `StaticFiles` mount at `/`. Not a scheduling-specific concern, but worth knowing if you're verifying this file isn't web-reachable.

## Gotchas

- `Calendar.workWindow`/`dailyCapacityHours`/`effectiveCapacityHours` are **not** in this domain — they live in `frontend/calendar/calendar-engine.mts`, which delegates the actual union-interval math to `nimbus-compute-core.js` (as of the 2026-09 capacity-math-triplication cleanup, all of it — no independent copy remains anywhere in `calendar-engine.mts`). A change to that capacity math belongs in `nimbus-compute-core.js`, not a mirrored copy, even though `gantt.mts`/`orders.mts` call it.
- `frontend/optimization/setup-scheduler.mts` is **not** part of this domain (it lives under `frontend/optimization/`) even though it consumes `../setup/setup-domain.mjs` — don't confuse it with anything here.
- The `saveAll` comments explicitly warn against ever passing a raw `Date` object into the wire payload — grep `Util.toLocalSeconds` before adding any new date-carrying field to the payload builder.
- **Due-date read rule (backward-scheduling Phase 1, 2026-10-14).** `original_end_date` is the SAP finish as received (`COALESCE(orders.original_finish_received, orders.basic_finish_date)` on the wire). A timed value is used as-is. An exact-midnight value is a date-only SAP finish: `Util.sapDueDate` (`frontend/platform/foundation.mts`) returns the close of that date's working window, calling `NimbusComputeCore.dueDateInstant` with the day window of the task's line. `Util.setDueCalendarResolver` (wired in `app.js` from Store) supplies the calendar rows. A closed due date moves to the previous open day's close; a line with no calendar reads as raw + 23:59:59. The instant feeds lateness, the derived original start and the bounds text; the grid's and Inspector's original-end fields still show the raw value (a midnight shows as 12 AM).
