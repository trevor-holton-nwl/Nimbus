# Calendar — capacity engine, durable persistence, and calendar/blackout admin UI

## What lives here

- **`calendar-engine.mts`** (1,095 lines) — the capacity engine.
  - `candidateDefaultWorkHours()` — fallback work-hours generator, used by `setup-scheduler.mts`'s `freeIntervalsFor`.
  - `Calendar` — `_beginRun`/`_endRun`/`_indexBlocks` (per-run cache lifecycle), `workWindow`, `dailyCapacityHours`, `_indexCapacityBlocks`, `effectiveFromCapacity`, `effectiveCapacityHours`, `nextAvailable`, `fitsContinuous`, `nextOperatingInstant`, `hasNominalWindow` (takes the plant zone and converts both edges through it, VM17), `findContiguousSlot`, `allocateRuntime`, `placeWithSetup`, `_overlapsBlock`, plus private interval-math helpers (`_freeIntervals`, `_blockingIntervals`, `_ceilMinute`/`_floorMinute`, `_nextContiguousMinuteSlot`).
- **`calendar-sync.mts`** (536 lines) — `CalendarSync`, the durable-persistence client for `/plant-calendar*`: `fetchPlantConfig`, `_applyConfig`, `_migrateMissingSlices`, `savePlantHours`, `saveLineHours`/`_flushLineHours` (600ms debounce), `saveLineBlackoutUpsert`/`Delete`, `savePlantBlackoutUpsert`/`Delete`, `flushPlant` (What-If → live promote), `_post` (single write choke point), the pending-delete ledger (`_trackPendingDeletes`/`_replayPendingDeletes`/`_withoutPendingDeletes`/`_trackedDelete`), failure handling (`_notifyUnsynced`/`_freshBody`), plus legacy-migration helpers (`_isDefaultWorkHours`, `_discardLegacyGlobalLineBlocks`/`PlantBlocks`, `_isLegacyFanoutCopy`).
- **`edit-calendar.mts`** (253 lines) — `EditCalendar` (`{ open, openPlant, close, save, onToggle, applyPreset, copyFromPlant }`), the per-line/plant working-hours modal with 14 Flatpickr pickers (verified: `_fp` array sized 14, `_initPickers()` loops 7 days × 2 fields, guarded by `if (_fp.length === 14) return`). An end time of 00:00 is read as 24 (end of day) by `_endHours`, since the picker cannot express 24; the DB and scheduler accept `end <= 24`.
- **`calendar-admin.mts`** (242 lines) — `CalendarUI` (`render`, `_renderBlocks`, `removeBlock`, `openBlockModal`, `saveBlockFromModal`, `_getLines`, `_clearLineFilter`), the blackout-block admin tab. Overlaps in *purpose* with `EditCalendar` (both write `Store.calendars[line].workHours`), but this is a deliberate post-split naming split — `Calendar` (this file's namesake in `calendar-engine.mts`) is capacity math, `CalendarUI` is the blackout-tab remnant UI — not accidental duplication.
- **`calendar-periods.mts`** — pure helpers for plant calendar periods, no DOM and no Store: `periodStatus`, `summarizeWeek`, `validatePeriodDraft`, `periodWarnings`, `buildPeriodStrip`, `buildBlackoutMarks`, `nextPeriodDefaults` and the day-key helpers (`dayIndex`, `keyFromIndex`, `addDaysKey`, `keyToDate`). `buildBlackoutMarks(strip, items, todayKey?)` clips each plant blackout (day keys) to the strip's axis, drops those outside it, merges overlapping or touching ones (gap of one day or less) into one cluster mark and caps the result at `MAX_BLACKOUT_MARKS` (60) clusters, reporting the rest as `truncated`. Over the cap, with `todayKey` it keeps the clusters ending today or later first and then the most recent past ones (oldest past dropped first); output stays time-sorted.
- **`calendar-periods-ui.mts`** — `CalendarPeriodsUI` (`init`, `render`, `openModal`, `save`, `remove`), the Master Data > Plant > Calendar tab: period list, timeline strip and the delegated click handlers. The strip also carries a red blackout marker lane, a `.period-blk-lane` sibling of `.period-track` (never inside it: the track is `overflow:hidden` and its segments, labels and today line would sit over the markers), a legend row and a horizon caption (`#plant-periods-horizon`, "next 12 months" or "through {month}"). The markers are `button[data-action="edit-blackout"]` (`data-id` for one blackout, `data-ids` for a cluster); `CalendarPeriodsUI`'s own click handler ignores them, because the module must not import `master-data/admin-ui.mts`. The click seam is a second delegated listener on `#plant-periods-timeline` in `Plant._wireStaticHandlers` (`admin-ui.mts`): one blackout opens `Plant.openBlockModal(id)`, a cluster calls `Plant._revealBlocks(ids)` (scroll to the list and flash those rows). `Plant.render()` no longer renders the timeline itself; `Plant.gotoTab('calendar')` does, on every switch to the tab and on each `plantBlocks:change`-driven `Plant.render()`. `edit-calendar.mts` also gained a third modal mode, `'period'` (`openPeriod`), alongside `'line'` and `'plant'`.

## Counterpart

`backend/calendars/routes.py` (148 lines) — 6 endpoints: `GET /plant-calendar` (also returns `plant_periods`), `POST /plant-calendar/plant-hours`, `POST /plant-calendar/line-hours`, `POST /plant-calendar/line-blackouts`, `POST /plant-calendar/plant-blackouts`, `POST /plant-calendar/plant-periods` (the last 5 gated by `require_admin`, **except** `plant-blackouts`, which is planner-writable: `require_authenticated` plus `get_allowed_plants_for_request` and `_calendar_plant_guard`, so a non-admin whose `role_plants` scope covers the plant can write; out-of-scope plant is 403, blank plant 400. Line blackouts, hours and periods stay admin-only). `backend/calendars/CLAUDE.md` is a 3-line pointer back to this file — don't duplicate its content there.

This domain's data functions do **not** live in `db.py`/`master_data.py` — calendar/blackout persistence is its own table set behind `backend/calendars/routes.py`, not part of the deferred `db.py`/`master_data.py` split. **Exception, plant periods:** the period data functions (`save_plant_periods`, `load_plant_periods`, `active_work_hours`, `_period_overlaps`, `ensure_plant_calendar_periods`) live in `master_data.py`, called by the new route and the `brain.py` lifespan.

## Key invariants & hazards

- **Capacity-math mirror rule.** `Calendar._dayWindow`, `Calendar._indexCapacityBlocks`, `Calendar.dailyCapacityHours`, and `Calendar.effectiveFromCapacity` all **delegate directly** to their `globalThis.NimbusComputeCore` counterparts rather than duplicating the math — `workWindow`/`effectiveCapacityHours` route through those delegates in turn. This was completed in the 2026-09 capacity-math-triplication cleanup: `dailyCapacityHours` (and the `_indexCapacityBlocks` bucketing it consumes) previously called `Util.mergedOverlapHours` (`platform/foundation.mts`) independently of Core's own copy — a real, live duplicate this file's own Gotchas section previously (incorrectly) claimed didn't exist. `tests/js/compute-core.test.js` pins **Core's own math** (not a Calendar-vs-Core diff), so parity is achieved by delegation, not by an independent pinned comparison. If any *other* `Calendar` method starts duplicating Core math again, it becomes an un-pinned drift risk — watch for that specifically.
- `Calendar.dailyCapacityHours`'s delegate deliberately reads `Store.blocks`/`Store.plantBlocks`/`Store.lineSettings`/`Store.masterData` directly, not the `sourceBlocks()`/`sourcePlantBlocks()`/`sourceGetPlantForLine()` candidate-snapshot-aware accessors most other functions in this file use (see "Two separate import cycles" below) — this preserves its pre-existing behavior exactly. Whether it *should* read through those accessors instead (so it stays correct during a Sandbox what-if/candidate-snapshot session) is a separate, un-investigated question the 2026-09 dedup pass deliberately did not decide.
- **Forward snap primitive.** `Calendar.nextAvailable` (line ~314) returns `null` — never a start — when the line has no working window, the order is longer than the longest single window (it never splits), or nothing fits within 90 days; callers must handle null. A blackout end is rounded up to the next minute so the start is clear of it. The overlong-order diagnostic is deduped per (line, duration) via a bounded module-level set, because the optimizer re-probes the same pair thousands of times. Forward placement is a retained list, not the default. The optimizer's setup-aware evaluators (`optimization/setup-scheduler.mts`, reached from `Engine.runAndApply`) place forward, and `Calendar.nextAvailable`, `Calendar.allocateRuntime`, `Calendar.findContiguousSlot` and `Calendar.placeWithSetup` are still called forward by `optimization/engine.mts` (`schedulePatchFor`, forward under every split policy, which also holds a running order's start; `placeForwardSequence`, shared by Remove Backlog and the reversal queue; the reversal forward leg inside `finishAnchoredPatchFor`, taken only when the backward walk reaches the plant's now; and the `autoReflow` cascade) and by `insights/services.mts` (the `Alerts` Fix, which also triggers `autoReflow`). Every other placement is finish-anchored (backward scheduling Phase 3, 2026-10-14). Gantt drag never calls an allocator directly (`gantt.mts` uses `Calendar.workWindow` only to shade closed days, and wraps a multi-drag batch in `Calendar._beginRun`/`_endRun`): it goes through `Interaction` → `Engine`, and a drop is finish-anchored (`Engine.manualSchedulePatchFor` → `Engine.finishAnchoredPatchFor` → `Calendar.allocateRuntimeBackward`). `scheduling/persistence.mts` does not import the calendar engine (its only calendar import is `CalendarSync`): its load-time `_snapToWorkingHours` re-snap and the `setCalendarService` seam were removed in backward scheduling Task 2.5.
- **Backward walk (backward scheduling Tasks 2.1 and 2.5, 2026-10-14).** `Calendar.allocateRuntimeBackward(line, finish, runtimeMinutes, policy, {floor, minSegmentMinutes, plantTz, setupMinutes?})` lays the run time so it ends at the finish and returns a `BackwardResult`: `placed` (start, end, `scheduleSegments`, `finishMoved`, and `moveReason` = `closed_finish`, `no_slot_at_finish`, `min_piece` or `blackout` when the finish had to move earlier); `reached_now` (the walk reached the floor with minutes still to place, so the caller reverses forward); `overlong` (a contiguous policy and a run time longer than the longest nominal merged window; `partial_allowed` splits instead); or `unavailable` (no operating window in the look-back, or an unusable run time or zone). When the 90-day look-back, not the floor, bounded the walk and nothing fit, the walk retries once with a 400-day look-back and, if that also fails, reports `lookback_exhausted` (VI17), which `finishAnchoredPatchFor` maps to the `no_operating_window` refusal. `setupMinutes` (backward scheduling Task 3.2, OQ2 V1) reserves the changeover immediately before the earliest productive piece inside that piece's own operating fragment: a fragment that cannot hold the piece plus the changeover is skipped (contiguous, `no_slot_at_finish`) and the walk continues backward; under `partial_allowed` the changeover never clips an order that fits one window (D6), only an order that is already split gives up minutes for it; it moves only the start, never the run time or the finish. The reconcile fills it from the setup domain; a manual drop passes 0 (OQ40, alert-only). `Calendar.latestAvailable` is the contiguous-only lookup, with no minimum-piece rule and no snap beyond the minute. `_freeIntervalsBackward` returns chronological free intervals clipped at the minute-floored finish and bounded by the floor, with touching fragments merged across midnight and a 400-day hard cap. Each call walks back about 90 days from the finish (`_backwardFrame` also reads two days past it), so a batch caller wraps its loop in `Calendar._beginRun(plant)` / `Calendar._endRun()`, as the multi-drag, Push +1 h and reconcile paths do. With `plantTz` the elapsed arithmetic runs on plant-zone instants and results are naive wall-clock Dates. Without it the window math still reads the viewer's local getters, so a viewer in a zone with different daylight-saving rules can get a piece boundary in a local hour that does not exist (the OQ46 residual). The wall-clock helpers are on the compute core: `prevCalendarDay`, `plantWallClockFromInstant(tz, instant)` and `plantInstantFromWallClock(tz, wall)` (null for an invalid zone; with no zone they return the date unchanged).
- **`line: null` means per-plant, not global.** Confirmed verbatim in `calendar-admin.mts` (line ~211): "Stamp the block's plant so it persists/scopes per-plant (line:null = all lines in this plant)" — mirrored in `calendar-engine.mts`'s blackout-indexing comment (line ~135).
- **`edit-calendar.mts` still reads a bare global `NIMBUS`** (`/* global NIMBUS */`, used for `NIMBUS!.Plant!._persistPlantHours!` and `NIMBUS!.ProdLines!.render!()`) — a classic-script-era coupling that survived the module split. A lingering global-namespace dependency worth knowing about before assuming this file is fully decoupled from `window.NIMBUS`.
- **Two separate import cycles touch this domain — don't conflate them:**
  1. The 4-file strongly-connected component `optimization/engine.mts → optimization/setup-scheduler.mts → calendar/calendar-engine.mts → optimization/engine.mts`, combined with a direct `engine.mts ↔ insights/services.mts` cycle (all four: `engine.mts`, `setup-scheduler.mts`, `calendar-engine.mts`, `insights/services.mts`). Confirmed in `calendar-engine.mts`'s own header (lines 1-28): it imports `Engine`, `placeWithSetupPure`, `sourceBlocks`, `sourcePlantBlocks`, `sourceGetPlantForLine`, `sourceLineWorkHours`, `sourcePlantWorkHours`, `reportSchedulerDiagnostic` from `optimization/engine.mjs`. All cross-references resolve inside method bodies, never at module-evaluation time (verified safe under every load order), but this means "setup-scheduler is a detached module" is true only at the *runtime-coupling* level (no Store/DOM access), not the *import-graph* level.
  2. A separate two-way cycle between `calendar-sync.mts` and `scheduling/persistence.mts` (documented in `calendar-sync.mts`'s own header, lines 9-20).
- **Failed blackout deletes are durable per plant.** Unconfirmed deletes are recorded in localStorage (`nimbus.calendar.pendingDeletes`) and replayed *before* the backend config is applied on the next `fetchPlantConfig`; still-pending ids are filtered out of the fetched config so the blackout stays deleted locally. Replay treats 404 as done and drops permanent 403/409 with a one-time toast. Re-upserting a blackout clears its pending-delete id. Failed non-delete saves toast honestly with a Retry action that rebuilds the body from current Store state (`_freshBody`) — hours/upserts are not auto-replayed.
- **Hydration state (backward scheduling Task 2.6).** `CalendarSync.calendarState(plant)` is `'pending'` (not fetched / in flight), `'hydrated'` (`_applyConfig` ran: the SERVER's rows are in Store) or `'failed'` (the GET failed and no earlier server copy exists); `hasServerLineCalendar(plant, line)` is true only for lines the server returned an hours row for (the client default is never a server row). The reconcile derives starts only from a hydrated plant; it no longer gates on `hasServerLineCalendar` (D14), so a line with no server row is derived against the default hours and raises no `line_no_calendar` alert. The state is set before the `calendar:change` emit so the synchronous subscriber sees it.
- **Branch-accurate sizes, `Calendar` method list and importer note (kept here so the file merges cleanly with main's adjacent edits).** On this branch `calendar-engine.mts` is 1,095 lines, `calendar-sync.mts` is 546 lines (the "What lives here" bullet above shows main's 536) and `edit-calendar.mts` is 240 lines before main's own edit lands. Beyond the `Calendar` methods listed above, the engine now also carries the backward (finish-anchored) primitives `allocateRuntimeBackward`, `latestAvailable`, `_freeIntervalsBackward`, `_operatingSpansBackward` and `_backwardFrame` (result type `BackwardResult`); `nextAvailable` and `allocateRuntime` are the forward ones. `calendar-engine.mts` is no longer imported by `optimization/scheduler-contract.mts` or `scheduling/persistence.mts` (backward scheduling Task 2.5); the importer list under "Imports out" still names them.
- **Plant blackouts are editable and live on the Calendar tab (2026-10-19).** The Plant Blackouts panel (`#plant-blackouts-panel`, ids unchanged) is a direct child of `#plant-tab-calendar .cal-container`, below the periods list; it opens expanded. Each row's body is a `button.plant-blk-edit` beside the `.plant-blk-remove` ×, bound by one delegated listener on `#plant-blocks-list`. `Plant.openBlockModal(id?)` always sets or clears `_editingBlockId`; `savePlantBlockFromModal` edits through `Store.updatePlantBlock(id, plant, {start,end,reason}, source)` (finds by id and plant, rejects a duplicate range, replaces the object at the same index so What-If change detection by value still works, emits `plantBlocks:change`) and posts the same upsert as an add. If the block vanished while the modal was open it toasts `toast.plant_blackout_gone` and sends nothing, because the upsert would resurrect it. **Last writer wins:** there is no blackout versioning, so an edit saved after another tab deleted the block re-creates it.
- **Store events emitted:** `calendar:change`, `blocks:change`, `plantBlocks:change`. The post-hydration `tasks:bulkUpdate` re-snap in `CalendarSync._applyConfig` was removed in backward scheduling Task 2.5.
- **Plant calendar periods (2026-10-16; design of record `docs/CALENDAR_PERIODS_DESIGN.md`).** A plant has its default weekly pattern plus dated overrides `{id, name, validFrom, validTo|null, workHours}` on `Store.plants[plant].periods` (snake_case on the wire, `plant_periods`). Semantics: a period overrides the default for an inclusive date range; no end date means it never ends; periods for one plant never overlap; an all-closed period is legal (a shutdown); where a period applies its pattern **replaces** the default for that date, never merges with it. Everything that reads plant hours resolves the pattern per date through `NimbusComputeCore.plantWorkHoursOn` (rule: `activeWorkHours`, returns the default by reference when no period matches); machine (line) hours stay one weekly pattern, intersected on the fly with whichever plant pattern is active.
  - **Pessimistic write.** `CalendarSync.savePlantPeriods(plant, next)` posts first and changes the Store only after the server acknowledges (`Store.setPlantPeriods(plant, next, 'plant-periods')`); on a 400 the editor stays open, the Store is untouched and the caller gets `{ok:false, status, code, ids, message}`. In What-If (`Sandbox.active`) it changes the Store only and `flushPlant` promotes the periods (plus `removed.periods` deletes) when What-If is promoted to live. There is no tombstone ledger for periods. The reserved revision key **`'#periods'`** (cannot collide with a machine code) guards hydration like the `''` plant-hours key.
  - **`Store.setPlantPeriods` is the only emitter** outside hydration (`_applyConfig` writes `plants[plant].periods` directly, inside the hydrating try block before the emits). Never assign `periods` anywhere else: `Utilization._cache` and `Dashboard._matrix7Cache` key on `Store.rev()`. Its source must never be `'calendar-sync'`, which the engine reserves for the hydration-triggered reconcile.
  - **D5 clamp-to-union.** `Store.clampLinesToPlant` trims line hours to the union of the default and every period's hours for that weekday (`unionWeeklyHours`), not the default alone. **D6:** a period save raises alerts only; no bar moves, and a period save never calls the clamp.
  - **`Calendar.plantWorkWindow(plant, date)` is plant-only** (not line-intersect-plant); the Gantt non-working shading uses it. `Calendar.nextAvailable` also probes from each `periodBoundaryKeys` start so an order that fits only after a switch date is found.
  - **Stale-core guard.** `resolvePlantHoursOn` (optimization/engine.mts), `setup-scheduler.plantHoursOn` and `nextAvailable` throw `compute-core-stale` when periods exist but the core lacks the helper (the optimizer worker imports Core without a cache-bust); the worker client falls back to the main thread. Never fall back silently to the default pattern.
  - **Import cycle, function-body only:** `edit-calendar.mts` ↔ `calendar-periods-ui.mts` (the editor calls `CalendarPeriodsUI.save/remove`, the UI calls `EditCalendar.openPeriod`). Every cross-reference is inside a function body. `calendar-periods-ui.mts` does not import `admin-ui` (a module-level `Store.subscribe` on `calendar:change` is gated on the DOM instead).

## Gotchas

- The "parity-pinned" framing for the capacity-math mirror rule is slightly imprecise: the pin is on Core's own math, and `Calendar` achieves parity by delegating to Core rather than being independently diffed against it. As of the 2026-09 dedup pass, no `Calendar` method duplicates the math anymore (this really is now true, not just asserted) — but worth restating precisely rather than as a flat "parity-pinned" claim.
- `edit-calendar.mts`'s bare-global `NIMBUS` dependency is a real, surviving classic-script coupling — not fully module-isolated.
- Two distinct import cycles touch this domain (see Key invariants above) — they're independent of each other; don't describe them as one loop.
