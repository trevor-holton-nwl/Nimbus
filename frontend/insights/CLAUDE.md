# Insights — alerts, utilization, and the off-main-thread compute client

## What lives here

- **`services.mts`** (~970 lines)
  - `Compute` — singleton `Worker` client (`new Worker('../nimbus-worker.js?v=' + Config.BUILD_ID)`). `available()`, `alerts(opts, dismissed)`, `utilization(startMs, days)` on the shared worker, and `leverageBatch(base, variants, {signal?})` on its own short-lived worker per call (see Leverage transport).
  - `Alerts` — plain object (patchable property, not a bound function): `recompute`, `_recomputeSync`, `_dismissed`, `dismiss`/`dismissAll`/`clearDismissed`, `applyFix`, `_lastMs`/`_timer`/`_pendingFull`/`_pendingLines`, `_fire`, `_armTimer`, `scheduleRecompute`, `scheduleRecomputeLines`.
  - `scheduleAlertsForPatches(patches, resolveLine)` — schedules an incremental recompute for the lines touched by a patch set.
  - `Utilization` — `_cache`, `computeMatrix`, `sev`, `minutesByDay` (the cell-briefing day-attribution rule, a wrapper over the core's `workingMinutesByDay`), `_prewarm`.
- **`insights-ui.mts`** (~1710 lines; refer to symbols, not line numbers: they drift)
  - `Dashboard` — KPI/heatmap/line-status rendering; keeps its own `_matrix7Cache` field in addition to `Utilization._cache`.
  - `AlertsUIAdapter` — despite this file's own top-of-file comment claiming it "stays in app.js as a thin adapter," it is exported from here. That header line is stale; don't trust it.

## Alert Monitor support modules (profiles, acknowledgements, leverage)

Spec: `docs/superpowers/specs/2026-10-20-alert-monitor-design.md`. The page that consumes these is `frontend/alert-monitor/` (its CLAUDE.md has the render loop and action vocabulary); backend is `backend/alert_profiles/`.

- **`alert-profiles.mts`** — pure profile semantics, no Store/DOM (`ProfileDeps` injects `dueInstant`/`latenessHours`, defaulting to `NIMBUS.Util`; with no deps lateness is 0, so `minLateHours: 0` matches every task-bound alert): `ALL_ALERTS_PROFILE_ID` (`'__all__'`, matches everything, highlights nothing), `ALERT_CATEGORIES` / `categoryOf` (capacity, conflicts, calendar, setup, exceptions), `ruleMatches` / `profileMatches` / `filterByProfile`, `impactPoints`, `compareAlerts`, `groupAlerts` (**`impactPoints` and the group `points` are internal ranking only: they order lists and are never displayed**; the Alert Monitor page shows counts, dates and the confidence score, see its CLAUDE.md "vocabulary rule"), `validateProfile` (returns i18n keys per field path, mirrors the server's limits: name 1-60, at most 20 rules, `minSev`, rule shape; the Alert Monitor editor only renders its result), `resolveActiveProfileId` (session override, then user pref, then role default, then All alerts), `ackLabel`. It also owns the **shared type sets** `FIXABLE_ALERT_TYPES`, `OVERRIDE_ALERT_TYPES`, `CALENDAR_ALERT_TYPES` and `FIRING_ALERT_TYPES`: the drawer row, the cell card, the Alert Monitor model and `scheduling/gantt.mts` all import them, so the two surfaces cannot drift (`alert-leverage.mts` keeps its own deliberately different 3-member `CALENDAR_TYPES`).
- **`dayKeyOf(d)` and `NONE_KEY`** (exported from `alert-profiles.mts`) — the local-date `YYYY-MM-DD` key and the `'none'` sentinel shared by `groupAlerts('day' | 'line' | 'order')` and the Alert Monitor Overview band (`alert-monitor-overview.mts`), so a band bar and a Day group head can never disagree on what a day is.
- **`alert-leverage.mts`** — the leverage engine. Families (`LeverageFamily`): setup-pair, calendar-day, routing-gap, tool, machine-state, optimize-window. `groupLeverage(input)` is pure and immediate (grouping plus removal points; `LeverageItem.points` is the sort key only and is never rendered, the page shows counts and, for a replayed item, the before/after confidence); `analyzeLeverage(input, runner)` replays up to `replayCap` (default `DEFAULT_REPLAY_CAP = 20`) groups through a `LeverageRunner` (the worker, via `Compute.leverageBatch`) to get the score after the fix; `replayWithMinutes` replays one setup-pair card with user-entered minutes (rounded up to an integer, must be positive); `parsePairKey` (tries every `]->`), `hypotheticalSetupSnapshot`. A `requiresMinutes` item carries a removal score, but the UI never presents it as a prediction. Headroom is in hours; `adminOnly` is set for work-center and routing steps (admin-only writes), not for `no_machine`.
- **Clients** — `alert-profile-client.mts` (`AlertProfileClient`) and `alert-acks-client.mts` (`AlertAcksClient`): `cached(plant)` / `list` / `load` / `subscribe`, writes refetch and then fan out (a failed refetch drops the cache and still notifies). `plant-lru.mts` is the shared plumbing: an LRU of `MAX_CACHED_PLANTS = 3` plants, a request token that discards a stale fetch, and `AlertApiError`. A `plant:selected` drops the left plant's cache and keeps the new one. `AlertAcksClient.acknowledgeMany(plant, alertIds, reason, until)` is the bulk write behind a group's "Acknowledge N…": sequential `POST /alert-acks/bulk` chunks of at most 500 ids (`BULK_ACK_CHUNK`, the route's cap), then one forced refetch and one notify; it resolves `{ok, failed}` (`ok` sums the server's `count`; each chunk is transactional, a failed chunk adds its ids to `failed` and the next chunk still runs) and throws the first `AlertApiError` only when every chunk failed.
- **`alert-profile-matches.mts`** — `AlertProfileMatches`, the **always-on producer** (initialised once from `App.init`, independent of the open tab). `current()` returns the saved-default `AlertProfileMatchSet` (session "View as" ignored; the Gantt, bell, drawer and Orders follow it) and `view()` the same set with the session override applied (the Alert Monitor page only); each set has (`plant`, `profileId`, `profile`, `alertIds`, `taskIds`, `sevByTask`, `categoryByTask`, `acked`); it has its **own `subscribe` fanout and never emits a Store event** (`Store.emit()` bumps the revision and re-renders everything). `setSessionProfile(id)` is the session-only "View as" override (cleared on plant change); `setFocusTaskIds(ids)` makes the three task maps describe a focused leverage card instead of the profile (null restores it; no-op when nothing to clear). Acknowledged alerts stay in `alertIds`/`taskIds`; consumers hide them through `acked`. It re-runs on profile, ack, plant and alert changes. A failed profile/ack fetch backs off for 30 s per plant (reset on `plant:selected` or success).

**Leverage transport.** `buildPlantSnapshot(plant, opts)` (`services.mts`) returns the full alert/utilization payload for one plant plus its line set and wall-clock fields; `opts.setupObservation` swaps the derived setup for a what-if replay (the same internal base the worker's `ALERTS` payload uses, pinned by a golden payload test). The worker answers a `LEVERAGE_BATCH` message (`nimbus-worker.ts`; reply `LEVERAGE_BATCH_RESULT` with `results: [{key, alerts, matrix}]`). `Compute.leverageBatch(base, variants, {signal?})` runs each batch on its OWN short-lived worker (`_leverageViaDedicatedWorker`: `new Worker('../nimbus-worker.js?v=' + Config.BUILD_ID)`, its own message id, settles exactly once, then clears handlers and `terminate()`s), so a slow replay never blocks the shared alerts/utilization worker. After `LEVERAGE_BATCH_TIMEOUT_MS` (30 s) or an abort the worker is terminated and the call rejects with a `DOMException` named `TimeoutError` / `AbortError`; the caller keeps its quick (removal-only) ranking and **nothing reruns on the main thread**. Neither outcome touches `_crashCount`, `_dead` or the shared worker. `runLeverageBatchSync` (the same core calls on the main thread) is used only when `Worker` is undefined, the constructor throws, or the leverage worker crashes (`onerror`) or replies `ERROR`, never for timeout/abort. `LeverageRunner`, `analyzeLeverage` and `replayWithMinutes` take an optional trailing `{signal}` that is passed through; the Alert Monitor aborts it on plant change, tab leave and plan move. Per-variant calendars/plants are shallow copies (`{...base.calendars}`, `{...base.plants}`) in both the worker and `runLeverageBatchSync`, because the core's `ensureCalendar`/`ensurePlant` only add missing top-level keys. `Compute._post` no longer makes a measurement-only `structuredClone` of the setup payload. `analyzeLeverage(input, runner, groups?)` accepts the already-computed `groupLeverage` items (copied, not mutated) and `LeverageInput.setupTasks` (`Store.tasksByPlant(plant)`) scopes the replay's setup derivation to the plant. `buildPlantSnapshot` records the `Leverage.buildPlantSnapshot` PerfMonitor key.

**Compute-core additions** (`nimbus-compute-core.js`, exported and mirrored in `.d.ts`): `scoreConfidence({alerts, matrix, overloadedLineDays?, horizonStart, horizonMinutes})` returning `{score, alertPenalty, utilPenalty, rawAlertPoints, overloadedLineDays}`, `alertPoints`, `timeWeight`, `countOverloadedLineDays` and `CONFIDENCE_WEIGHTS` (err 5, warn 2, 3-day weight 1.5, 7-day 1.25, alert cap 50, util cap 20, 1.5 per overloaded line-day). `Confidence._recompute` and `Confidence.showBreakdown` in `nimbus-intelligence.js` now call the core, so the badge, its breakdown and the leverage replay share one formula (parity tests in `tests/js/compute-core.test.js`). The alert penalty caps at 50, which is why leverage ranks by uncapped impact points and shows the capped confidence delta second. Setup alerts also carry `pairKey` and `scope` so a card can name the exact missing pair.

## Counterpart

No `backend/` counterpart — Alerts/Utilization are pure frontend derived-state computation over Store data, not a persisted resource with its own endpoints.

## Key invariants & hazards

- **What follows the alert profile and acknowledgements, and what stays plant-wide (Alert Monitor, D2/D17).** `AlertsUIAdapter._visibleAlerts()` is the one filter: plant lines, then the alert horizon, then acknowledged alerts (hidden unless `Store.pref('alertsShowAcknowledged')`), then — when the active profile is not All alerts and the session-only `AlertsUIAdapter._profileOverride` is off — only `AlertProfileMatches.current().alertIds`. Its consumers are the bell (`renderBell`), the drawer (`renderDrawer`, whose footer shows `alert.profile_hidden` with a "Show all" link, and "Back to profile" while the override is on; reset on `plant:selected`), `Dashboard._renderAlertSummary` and `dismissVisible`; they repaint through `AlertProfileMatches.subscribe` (profile / ack change) and the shell's `alerts:change` hook. These stay **plant-wide, never filtered**: the Gantt `conflict-order` outline (`Timeline._conflictIds()`), the alert day cells, every `Store.alertsByTask()` consumer (the Orders table's conflict / at-risk filters), `NeedsEngine` (command palette) and `Confidence` (acknowledged alerts still count toward the score).

- **Incremental vs. full recompute.** `Alerts.recompute(opts)`: the worker path is used only when a plant is selected (`Store.selectedPlant`); with none selected it routes to the cheap sync path instead of cloning every line's inputs. When `opts.lines` is a non-empty `Set`, results are **merged** into the existing alert list (`retained.concat(alerts)`) rather than replacing it; a bare `recompute()` call (no `lines`) does a full-scan replace. `_recomputeSync` (the sync fallback) mirrors this exactly (`retained.concat(kept)`) — the scoping behavior must survive the worker/sync fork.
- **`tool-conflict` alerts are emitted on the later order's line and can involve a different line than the edited one**; incremental callers therefore escalate to a full recompute whenever a moved order carries a PRT_01/PRT_02 tool id (`taskCarriesTool`, `scheduleAlertsForPatches`, and `Engine.autoReflow`'s two direct `scheduleRecomputeLines` call sites).
- **Adaptive debounce.** `_armTimer`: `delay = clamp(round(_lastMs * 1.5), 90, 500)` ms — delay scales with the last recompute's measured cost, clamped `[_ALERTS_MIN_DEBOUNCE_MS=90, _ALERTS_MAX_DEBOUNCE_MS=500]`.
- **One-click `Alerts.applyFix` refuses any effectively protected order** (`Engine.firmingStatus(task).firmed`: frozen horizon, manual firm, or running; toast `toast.cannot_fix_firmed`). SAP's own firm flag is display-only and does not block a fix. Same union the optimizer and `autoReflow` use.
- **No runtime monkey-patches of `Alerts`.** `nimbus-intelligence.js` (outside this domain, loaded after `app.js`) does not reassign `Alerts.recompute`; `Confidence` and the other intelligence modules react through `Store` events (`alerts:change` etc.) and call `Alerts.scheduleRecompute()`. (An earlier version of this doc described a `Confidence.init` wrapper around `Alerts.recompute`; it no longer exists.)
- **Worker path — verified correct post-move.** `Compute`'s `new Worker(...)` call uses `'../nimbus-worker.js?v=' + Config.BUILD_ID` from `frontend/insights/services.mts`, which correctly resolves to `frontend/nimbus-worker.js` at repo root (one level up from `frontend/insights/`). Phase P4 found and fixed a real bug here (the path needed an extra `../` after this file moved one directory deeper) — the fix is in place and documented in this file's own header. **Gotcha class to watch for elsewhere:** a moved file with a relative asset/worker path silently 404s with no loud error — nothing throws, the fallback below just engages.
- **Permanent worker fallback.** `onerror` handler increments `_crashCount`; at `_crashCount >= 2` it sets `_dead = true` permanently for the session (one retry allowed, no auto-restart after the second crash). Once dead, `Compute.available()` returns false and everything routes through `_recomputeSync`/the synchronous utilization path for the rest of the session.
- **`computeMatrix` memoization — resolved, not the hazard the root doc describes.** The memo key is `` `${start.getTime()}|${days}|${revision}|${scope}` `` where `scope = selectedPlant || 'all'` — **plant is part of the key**. `_prewarm` writes under the identical format/order (`` `${startMs}|7|${rev}|${plant}` ``). The two producers now agree and cannot collide. **The root CLAUDE.md's caveat ("the off-thread prewarm writes... under a cache key the synchronous path expects to be global, so whichever producer runs first wins") is stale — that hazard was fixed here.** Update any doc that still repeats it.
- **Dashboard bypasses the shared memo.** `Dashboard` maintains its own `_matrix7Cache` rather than relying solely on `Utilization._cache` — it always passes a filtered task subset per the root doc's description. Verify the exact call site before assuming a single cache invalidation covers both layers; there may effectively be three caching layers in play (`Utilization._cache`, `Dashboard._matrix7Cache`, the worker prewarm).
- **Day-attribution definitions differ on purpose (OQ12/OQ41/OQ42), and a finish-only row is a real bar (U29).** The Dashboard "Orders today" tile (`Util.overlapsDay`) and the utilization matrix / overload alert / cell briefing (`workingMinutesByDay`, one function in `nimbus-compute-core.js`) count different things: the tile counts any order whose bar touches the day, the matrix puts run-time minutes on each day in proportion to the bar's working-time overlap. A bar with partial working overlap (23:30-00:20) can therefore appear on the tile for both days yet carry all its minutes on one. Both treat a row with an end and no start (a freshly distributed child, `scheduled_start` NULL until the reconcile derives it) as the wall-clock bar `[end - run_time, end]`, so it is visible before the derive; with no run time it stays absent.
- **One clock (I13).** The intelligence panels (`NeedsEngine._readState`, both `Confidence` matrix paths) and `Utilization._prewarm` start the window on `Util.plantToday(Store.selectedPlant)` (the plant clock), exactly like the Dashboard; the prewarm cache key and `computeMatrix`'s key therefore agree. Labor Plan keeps its own start (not changed).
- **`Store.subscribe(..., 'insights-services.hydrated')`**: `scheduling/persistence.mts` emits a `schedule:hydrated` Store event instead of calling `Alerts.scheduleRecompute()` directly, specifically so `persistence.mts` never has to import this domain — a documented reverse-dependency-avoidance seam.
- **`_utilizationSnapshotCloneCache`** (`WeakMap`): caches structured-clones of the six-pack (lineSettings/calendars/plants/blocks/plantBlocks/masterData) per detached preview snapshot so repeated optimizer-preview KPI calls against the same snapshot don't re-clone every time.

- **Imports in:** `platform/foundation.mjs` (Config, Util, ErrorLog, PerfMonitor, Toast, VirtualList), `platform/store.mjs` (Store, UndoStack), `platform/types.mjs`, `calendar/calendar-engine.mjs` (Calendar), `optimization/engine.mjs` (Engine, `deriveSetupObservation` — see cycle note below), `optimization/setup-scheduler.mjs` (type-only `ScheduleSnapshot`), `scheduling/gantt.mjs` (Timeline), `scheduling/orders.mjs` (Table, Inspector, `notifyResidualFirming`).
- **Imports out (who depends on this domain):** `app-entry.mjs` (bridges `Compute, Alerts, scheduleAlertsForPatches, Utilization, Dashboard, AlertsUIAdapter` onto `window.__NIMBUS_*`), `optimization/optimize-ui.mts`, `optimization/engine.mts`, `scheduling/gantt.mts`, `scheduling/orders.mts`, `shell/application-shell.mts`, `labor/labor-planning.mts`, `master-data/admin-ui.mts` (`AlertsUIAdapter` only), `alert-monitor/*` (the whole Alert Monitor page; its lazy-import and `NIMBUS`-global edges are listed in its CLAUDE.md), `shell/application-shell.mts` (`AlertProfileMatches.init`, `AlertProfileClient` for the User Settings rows), `scheduling/gantt.mts` and `scheduling/orders.mts` (`AlertProfileMatches`, the shared type sets).
- **Import cycle:** `insights/services.mts` imports `Engine` from `optimization/engine.mjs` at top level (a real value import, not type-only) — combined with `optimization/scheduler-contract.mts`'s documented 4-file loop (`engine.mts → setup-scheduler.mts → calendar-engine.mts → engine.mts`), this forms one 4-file strongly-connected component: `engine.mts`, `setup-scheduler.mts`, `calendar-engine.mts`, `insights/services.mts`. All cross-references resolve inside function/method bodies, never at module-evaluation time, so there's no TDZ hazard — but reason about the whole loop, not just this file's two neighbors, before adding any new top-level reference here.
- **Store events:** `Dashboard` also re-renders on `firmed:change` and `distribution:summary` (`insights-ui.mts`). `services.mts` listens for `schedule:hydrated` and `schedule:conflicts` (the latter triggers a scoped recompute for the machines the server reported, or a full recompute when no lines are given); alert/utilization consumers subscribe to `Store` publishes triggered after `Alerts.recompute`/`Utilization.computeMatrix` runs.

## Gotchas

- `services.mts`'s own header comment says `AlertsUIAdapter` "stays in app.js" — false as of the live tree; it's exported from `insights-ui.mts`. Leftover prose from an earlier phase's plan.
- The root CLAUDE.md's utilization-cache-collision caveat is resolved in the live code (see above) — don't propagate it as a current risk.
- Three layers of utilization caching may exist simultaneously (`Utilization._cache`, `Dashboard._matrix7Cache`, worker prewarm) — a staleness bug here may need invalidation in more than one place.
