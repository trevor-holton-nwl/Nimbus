# Optimization — the optimizer, auto-reflow, what-if sandbox

## What lives here

- **`sandbox.mts`** (130 lines) — `Sandbox`: What-If mode state + snapshots only. `enter()` deep-clones `tasks`/`blocks`/`calendars`/`plants`/`plantBlocks`/`firmedIds` off the live `Store`; `exit(apply)` either promotes the sandbox state to real state (pushing one `UndoStack` entry) or restores the pre-enter snapshot wholesale via `Store.setTasks` + `Store.replace*()` calls. Emits `sandbox:entered`/`sandbox:exited`/`sandbox:reverted`. DOM banner, toasts, and cross-module side effects (Confidence snapshot/restore, `Persistence.saveAll`, `CalendarSync` flush) are explicitly **not** this module's job — they live in `SandboxAdapter` (`optimize-ui.mts`), which subscribes to the emitted events.
- **`engine.mts`** (about 3,000 lines) — `Engine`: the optimizer dispatcher (`runAndApply(mode)`), auto-reflow (`autoReflow`), the detached candidate-evaluation machinery (`_candidateSnapshot` + `source*` accessors: `sourceBlocks`, `sourcePlantBlocks`, `sourceGetPlantForLine`, `sourceLineWorkHours`, `sourcePlantWorkHours`, `reportSchedulerDiagnostic`), setup-observation derivation (`deriveSetupObservation`), and the `evaluateSchedule` adapter function (module-level, line 3216) that used to live in `setup-scheduler.mts`. Also exports `snapshotSchedule`, `applySchedulePatches`, `effectiveFirmedIdSet`, `SETUP_AWARE_DEADLINE_MS` (`= 5000`), `SETUP_AWARE_NORMAL_BUDGET_MS` (`= 8000`), `SETUP_AWARE_EXHAUSTIVE_BUDGET_MS` (`= 180000`), and the `RuntimeAllocation` type. The finish-anchored placement entry points sit here too: `manualSchedulePatchFor`, `manualRoutingSchedulePatchFor`, `pairSchedulePatchFor`, `finishAnchoredPatchFor`, `pushFinishPatches`, `confirmOvertimePlacement`, `reconcileRuntimeSchedules` and `placeForwardSequence`.
- **`scheduler-contract.mts`** (158 lines) — tiny leaf: `MIN_PRODUCTIVE_SEGMENT_MINUTES` (`= 30`, the default productive-segment floor, plant-overridable via `plants.min_productive_segment_minutes` and resolved by `Engine.minProductiveSegmentMinutesFor`), `capAwareSequence` (helper for due-date push-forward cap ordering during SPT walks), and `RemoveBacklogResult`/`RemoveBacklogDiagnostics`. Exists purely to break one import-cycle edge (see Gotchas) — its own header comment is the canonical explanation and documents the real 4-file transitive loop this domain sits in.
- **`setup-scheduler.mts`** (7,644 lines) — the detached candidate scheduler. Header comment: *"This module receives the complete scheduling read model as a snapshot and returns only patches. It never mutates Store, DOM, persistence, alerts, or Timeline; the workbench owns the one explicit Store commit after Apply."* Verified: the only `Store.`/`document.` occurrences in the file are inside comments, never live code (re-grep rather than trusting line numbers). Exports `placeWithSetup`, the four pure evaluators (`evaluateDueDateFirst`, `evaluateMinChangeover`, `evaluateSptWithSetup`, `evaluateThroughput`), `selectThroughputCandidate`, `applyPatchesToSnapshot`, `buildRunContext`, `activePriorityKeys`, `placeUnknownTail`, `isSearchConclusive`, plus the full type contract (`SchedulePatch`, `ScheduleSnapshot`, `EvaluationRequest`, `CandidateResult`, `PlacementResult`, `SetupPolicyThresholds`, `SearchDiagnostics`, `MissingSetupEdge`, `SETUP_AWARE_CONVERGENCE_WINDOW`/`SETUP_AWARE_TAIL_OVERRUN_MS`, an 8-wide candidate `score` vector (`SCORE_OVER_CAP` at index 7 counts protected orders already past their push-forward limit; it is zero for every unprotected order, because that limit is hard), etc.).
- **`optimizer-worker-contract.mts` / `optimizer-worker-client.mts` / `optimizer-worker.mts`** — clone-safe worker request/response types, cancellable preview adapter and worker entrypoint. The client calls the synchronous detached evaluator when Workers are unavailable or explicitly disabled, so unit tests and non-UI callers keep a deterministic path.
- **`optimize-ui.mts`** (3,091 lines) — the UI layer: `OptimizeDialog` (the Optimize modal), `OptimizerPreview` (`runWithPreview` — before/after KPI preview, verdict scoring, plan comparison + prune tallies, finalist rationale, stale-preview banner), `SandboxAdapter` (the DOM/toast/persistence side effects `sandbox.mts` deliberately excludes).

## Counterpart

No `backend/` counterpart of its own — the optimizer is pure frontend logic. It reads setup/priority/master-data truth that the backend serves (`setup_data.py`, `master_data.py`, root `db.py`) but performs no server calls itself; `optimize-ui.mts`'s persistence path goes through `scheduling/persistence.mts`'s `saveAll` (`POST /tasks/update`), not anything in this domain.

## Key invariants & hazards

- **Optimizer modes are exactly `'spt'` / `'changeover'` / `'duedate'` / `'backlog'`.** `'combined'`/"Smart" and `Engine._dispatchDayIntegrity` were both fully removed — grepping all of `frontend/` finds `'combined'` and `_dispatchDayIntegrity` occurring **only inside historical comments in `engine.mts` itself** (documenting what used to happen), never as live identifiers or string literals anywhere else. Any doc or code found naming either as current behavior is stale.
- **Setup-aware optimizer routing.** `runAndApply('changeover', …)` builds a `SetupSnapshot` — the plant's real active-and-matching `Store.setupSnapshot` when one exists, or `Engine._syntheticZeroCostSetupSnapshot(plant)` (engine.mts) when the plant has no active setup definition — then calls `Engine.evaluateSetupAware('min-changeover', …)`. `'duedate'` calls the same setup-aware seam with the due-date comparator, and `'spt'` calls it with the SPT comparator. Inactive or mismatched setup data uses the synthetic zero-cost snapshot for all three modes, so a plant cannot silently switch algorithms because setup data is absent. This is the only optimizer path: the old per-line forward walk and `_dispatchPolicyAware` were deleted (Task 3.1, OQ22); any unrecognised mode string takes the same setup-aware route.
- **Never-freeze invariant (2026-08-18).** Confirmed live: `_syntheticZeroCostSetupSnapshot`'s doc comment explicitly ties `plant_rows: []`/`machine_rows: []`/`overrides: []` to "the never-freeze invariant already treats [an uncovered transition] as zero setup minutes, never a block" (engine.mts:1000-1001). `placeUnknownTail` (setup-scheduler.mts:4615) is the tail-of-day-bucket placement for unresolvable signatures. Min Changeover, Due Date, and SPT all enforce this guarantee — no order is left frozen by incomplete setup data.
- **Detached-snapshot/patches contract.** `Engine.evaluateSchedule(mode, opts, snapshot)` (engine.mts:930) and `Engine.evaluateSetupAware(mode, bounds, snapshot, thresholds)` (engine.mts:952) both exist with the documented signatures; `evaluateSetupAware` throws unless the plant's `plants.setup_active` flag (`bounds.setup.plant_active`) is on. `snapshotSchedule`/`applySchedulePatches`/`effectiveFirmedIdSet` (engine.mts:210/256/267) round out the detached-evaluation contract. `Engine.lastSetupAwareResult` (line 925, consumed on-demand by preview/diagnostics) and `Engine.lastBacklogResult` (line 917, consumed-and-wiped) both confirmed present. **F1/F2/F4 optimizations (2026-10-06):** exact search runs only for fragments with ≤500 distinct orderings (F1); a per-run free-interval index serves calendar windows (F2); iteration cap = 20,000 × the plant's lines in scope (F4).
- **Reconcile derives starts from the held finish (backward scheduling Task 2.6, 2026-10-14).** `Engine.reconcileRuntimeSchedules(plant, {reason?})` takes the rows that are `runtime_schedule_mismatch` or never placed (`!user_scheduled`). It skips queued rows, rows carrying `placement_exception`, rows with no machine, and rows with unsaved local edits (`Persistence._dirtyIds`). The anchor is a placed row's stored end, else `Util.dueInstant`. A running placed row keeps its start (`heldStartPatchFor`; if the calendar would move the start, the remaining run is walked forward from the held start and returns the calendar's pieces, D3). Every other row is walked backward by `finishAnchoredPatchFor(..., {deferReversal: true})`, and a walk that reaches the plant's now goes forward per line in finish order through `Engine.placeForwardSequence` (`reversal_forward`). A row the server flagged stale gets a DIRTY patch (source `engine-runtime-reconcile`: the next Save persists it, and one `toast.system_moved_n` counts these). An unflagged never-placed row gets a DISPLAY-ONLY patch (source `engine-runtime-reconcile-display`, which the dirty tracker skips, so Save leaves it never-placed). Nothing is derived unless `CalendarSync.calendarState(plant) === 'hydrated'` (otherwise `Engine.derivePausedPlants` and the `ui.derive_paused` banner show); a plant with no zone gets `plant_no_timezone`. A line with no server calendar row is derived like any other line (D14: the reconcile no longer blocks it and there is no `line_no_calendar` alert). Every touched or skipped row carries a session-only `derivationIssue`, and every schedule patch carries `systemMove {from, to, reason}`. Issue codes: `finish_moved_earlier`, `reversal_forward` (detail `due_date_past`, `run_time_grew` or `cutover`), `pull_floor_crossed`, `no_operating_window`, `run_time_zero`, `no_anchor` and `plant_no_timezone`. A row that cannot be one bar under the plant's policy is queued as `overlong_never`. The whole batch runs in one calendar run (`Calendar._beginRun` / `_endRun`). **Setup lookups are indexed (workload relief, 2026-10-22):** the pass resolves changeovers through one `buildSetupResolutionIndex` (`setupResolutionIndexFor`, memoised per setup snapshot object in a `WeakMap` and rebuilt if the rows' arrays or lengths change), builds one active-override orphan map keyed `machine\0successor_order_id`, and groups the line schedule in one pass; the second `setupBefore` site (`orphanedAt`) reuses the first call's orphan verdict when the start is unchanged instead of resolving again. `deriveSetupObservation` resolves through the same memoised index (`deriveSetupObservationUnindexed` is the linear reference the parity tests compare against). Timing keys in `PerfMonitor`: `Setup.deriveObservation`, `Engine.reconcileRuntimeSchedules`.
- **Manual placement and Push +1 h hold the finish (backward scheduling Task 2.5, 2026-10-14).** `Engine.manualSchedulePatchFor(task, line, requestedFinish, policy?, opts?)` takes the FINISH and returns null on a refusal, with the reason in `Engine.lastManualRefusal` (`run_time_zero`, `plant_no_timezone`, `overlong_never`, `no_operating_window`, `finish_cannot_hold`, `needs_overtime_confirm`). `finish_cannot_hold` toasts unless `opts.quiet`. A firmed order whose finish would have to move gets `needs_overtime_confirm`; with `confirmedOvertime` it is placed as one raw bar (start = finish minus run time) marked `placement_exception = 'overtime'`. A row already marked is translated verbatim by its finish delta. A queued `overlong_never` row that is still too long for one bar is released as one continuous bar marked `'overlong'`, and a queued `run_time_over_cap` row that places normally returns to `scheduled`. A running order holds its start (`opts.holdStartIfRunning`). A split order whose productive total is unchanged is translated rigidly; otherwise it is re-derived from the held finish. `Engine.pushFinishPatches(tasks, ms)` moves each order's finish by `ms` (one calendar run per plant), skips orders that `Engine.firmingStatus` reports as firmed (manual, frozen or running), and quietly skips any order whose new finish cannot be held. Manual placement ignores the frozen horizon. `Engine.plannerUnscheduleChanges()` nulls `placement_exception`. **PV - Machine placement (2026-10-21):** `Engine.pairSchedulePatchFor(task, pv, line, requestedFinish, opts)` resolves `Runtime.resolve({...task, PRODUCTION_VERSION: pv}, line)` on every call (a PV-only change keeps the machine, so it cannot take the same-line shortcut), then places through `manualSchedulePatchFor` and returns PRODUCTION_VERSION, MACHINE, RUN_TIME, `run_time_source: 'routing'`, `run_time_basis` and the dates in ONE patch. It returns null when the pair does not resolve (no `lastManualRefusal`; the caller toasts `toast.pv_machine_ineligible`) or when the placement is refused (`lastManualRefusal` set exactly as for `manualSchedulePatchFor`). `ManualPlacementOptions.chosenPv` makes `manualRoutingSchedulePatchFor` delegate to it. D9: inside the routing-enabled branch of `manualRoutingSchedulePatchFor` a line change ALWAYS re-resolves the run time from routing (a manual or SAP run time resets); a same-line call keeps today's behaviour. Non-routing plants and the optimizer never use the pair path.
- **One plant-zone clock (backward scheduling Task 2.4, 2026-10-14).** `Engine.isFrozenHorizon`, `Engine.isInProgress` and `Engine.firmingStatus` default their `now` to `Engine._clockFor(task)`: the task's plant, else its line's, else the selected plant, read through `Store.plantNow`. A null clock means not frozen and not running, never a throw. The Optimize dialog's defaults read the same clock (`Engine._plantWallNow`), `autoReflow` uses the changed order's plant clock, and Remove Backlog's default run-at time is the server clock (`Store.serverNow()`).
- **The optimizer's result is the placed finish (backward scheduling Task 3.1, 2026-10-14; A-lite).** The setup-aware evaluators still place forward, but the placed finish (`end_date`, the last segment end) is what is judged: instability is `|new finish - prior finish|` in minutes (`setup-scheduler.mts`, both the fragment and the final objective), so a task whose finish holds while its start moved is stable. The legacy walk is gone. The retained forward paths are exactly: the optimizer's setup-aware evaluators, the Alerts Fix cascade (`autoReflow`), Remove Backlog (`placeForwardSequence`), the reversal forward leg, and `Engine.schedulePatchFor` reached through `Engine.heldStartPatchFor` (OQ3: a started order keeps its real start and only its finish follows the run time; shared by the reconcile's running branch and the manual run-time/machine/version edit, `holdStartIfRunning`). A row carrying `placement_exception` is fixed in every entry point (`effectiveFirmedIdSet`, Remove Backlog, `autoReflow`, the Alerts Fix cascade) whatever "Respect firmed" says. `Engine.placeForwardSequence` never places a `never`-policy overlong order as one elapsed bar: it is reported in `overlong` and the callers (Remove Backlog, the reversal queue) queue it with `Engine.overlongNeverChanges()` (reason `overlong_never`); Remove Backlog still reports it in `diagnostics.overlongIds`. `UndoStack.restoreTasks` and `TimeMachine.restore` restore the finish, flag the rows `runtime_schedule_mismatch`, and call `Engine.reconcileRestored` (the engine registers `UndoStack.afterRestore` at load), which runs `reconcileRuntimeSchedules(plant, {reason:'undo', ids})`: the ids bypass the unsaved-edit skip and no "N moved" toast is raised. A Store write with source `engine-runtime-reconcile` while an Optimize preview is open stales it (Apply disabled, banner `ui.preview_stale`). The Remove Backlog dialog's hint adds a count of rows tagged `reversal_forward` / `run_time_grew` (`ui.opt_backlog_runtime_grew`).
- **Frozen horizon is finish-based (2026-10-27, universal firm Wave A).** `Engine.isFrozenHorizon` is true when the persisted placement's `end_date` is in `[now, frozenHorizonEnd)` (finish == edge is not frozen; overdue is not frozen; a finish-only placed row freezes on its finish; a straddler is not frozen). The optimizer's frozen floor is a FINISH floor: `Engine.frozenFinishFloor(runNow, snapshot.frozenHorizonEnd)` feeds `DueDateFirstBounds.finishFloor` (serialized as `finishFloor` in `SerializedOptimizerValidation`), and unprotected orders are placed through `placeWithFinishFloor` (every attempt rebuilds the free intervals; `date_window` / `expired_window` / `baselineWithinWindow` enforce it). `earliestAllowedStart` is the pull-forward start floor only; `applyFrozenFloor` was deleted. The reconcile's `frozen_window_crossed` branch is deleted (the alert type id stays accepted for saved profiles and cached notes). Remove Backlog stays exempt (no `finishFloor`).
- **Lock-aware firm actions (2026-10-27, universal firm Workstream C).** `firm-actions.mts` is a pure, import-free leaf: `firmActionForReasons(reasons)` returns `'firm'` (nothing firms the order), `'unfirm'` (planner firm only) or `null` (frozen or running, with or without a planner firm: no firm/unfirm action anywhere; drag stays allowed), `firmReasonLabels` (running, frozen, planner order) and `planFirmActions`. On `Engine` (UI/live path only, never the detached optimizer): `firmActionFor(task, now?)`, `firmPlan(ids, now?) -> {firm, unfirm, locked}` (one clock per plant, one frozenEnd), `firmReasonsText`, `firmStatusText` and `applyFirm(ids, firmed, source) -> {changed, skipped}`, the single choke point for firm writes (C10): every UI surface (context menu, Inspector, Gantt F key, multi-inspector, grid toolbar, command palette incl. Freeze All scoped to the selected plant, override modal, dashboard, Slot modal) calls it, and only Sandbox, undo and Time Machine restores stay on raw `Store.setFirmed`. The Optimize checkbox reads "Respect planner-firmed orders" because it frees only planner firms; frozen and running orders always stay put (`ui.opt_respect_firmed_hint`). `placement_exception` is fixed in the optimizer but is not a firm reason (C11), so the UI may still offer Firm on it.
- **Backlog mode's frozen-horizon carve-out**: `diagnostics.frozenMoved` (now counts finish-in-window orders, including running ones) (scheduler-contract.mts's `RemoveBacklogDiagnostics`, incremented at engine.mts:2065 via `Engine.isFrozenHorizon(item.task, now)`) — the one mode that shifts frozen-window orders instead of treating the frozen horizon like a pinned order.
- **`OptimizeDialog.open(prefill?: { lines?, startDate?, endDate? })`** preselects those machines (unknown ones ignored) and the custom window on top of the usual seed; the Alert Monitor's "Optimize this window" card is the caller, and a plain `open()` is unchanged.
- **The Optimize dialog's plant is read-only.** `_buildPlantSelect` shows the header's `Store.selectedPlant` as a label (the `ui.select_plant_label` placeholder when none is selected), and the dialog closes on `plant:selected`, so a run can never target a plant other than the one the header shows.
- **Sandbox edits the live Store directly.** Confirmed: `enter()` (sandbox.mts:42-55) snapshots via `Util.clone`/`new Set([...])` into `this._snapshot`, then all subsequent Store mutations (drag, optimize, etc. while sandbox is active) hit the real `Store` — there is no isolated Store copy. `exit(false)` restores via `Store.setTasks(..., 'sandbox')` plus five `Store.replace*()` calls (source `'sandbox'`, so firm replacement never dirties). Each `replace*` fires a `'*:replace'` event and then the field's compatibility `'*:change'` event (`replacePlants` emits `plants:replace` then `calendar:change`, never `plants:change`), so existing `'blocks:change'`/`'calendar:change'` subscribers do refresh after a discard (pinned by `tests/modules/optimization/sandbox.test.mjs`). **Applied What-If undo** is different: it restores tasks through `UndoStack.restoreTasks` (source `'undo'`, live `row_version`, so restored ids become dirty and the next save pushes the revert), drops scenario-created tasks, confirms first if calendar/blackout slices changed since Apply, and emits `sandbox:reverted` carrying the `promoted` slices so `SandboxAdapter` can re-sync the backend calendar.
- **The real 4-file import cycle** (documented in full in `scheduler-contract.mts`'s header, confirmed by direct inspection): `engine.mts` → `setup-scheduler.mts` (imports the 4 pure evaluators + `SETUP_AWARE_CONVERGENCE_WINDOW`) → `calendar-engine.mts` (imports `candidateDefaultWorkHours`) → `engine.mts` (imports `Calendar`, and separately exposes `PlaceWithSetupRequest`/`PlacementResult`/`RuntimeAllocation` back to `calendar-engine.mts` through the same edge rather than opening a second cycle). This is genuinely a 4-file strongly-connected component, not two independent 2-file cycles — reason about the whole loop before adding any new **top-level** (module-evaluation-time) cross-reference among `engine.mts`, `setup-scheduler.mts`, `calendar-engine.mts`, or `insights/services.mts`. Every existing cross-reference is safe only because it's inside a function/method body invoked after all four modules finish loading.
- **A separate, direct two-way cycle**: `engine.mts` ↔ `insights/services.mts` (`Alerts`/`scheduleAlertsForPatches` imported by engine.mts; `Engine`/`deriveSetupObservation` imported by services.mts) — distinct from the 4-file loop above, per the same safety rule.
- Dispatching heuristics, not a constraint solver — finish-to-start precedence is not consulted; an order is protected from moving only by a manual firm (`Store.isFirmed`, gated by "Respect firmed"), the frozen horizon, or **running** (`Engine.isInProgress(t, now)`: start <= now < end; not gated by "Respect firmed"). SAP's firm flag (`ecc_firmed`) is display-only (`Engine.isSapFirmed`) and never locks. `Engine.firmingStatus` reasons are `'frozen' | 'manual' | 'running'`; `effectiveFirmedIdSet`, the legacy walk, `autoReflow` and Alerts one-click fixes all use the same union. **Remove Backlog is exempt** and may still move running orders. Preview Apply re-checks `Engine.isInProgress` at apply time and drops patches for orders that started running while the preview was open (toast `toast.opt_apply_running_skipped`; Remove Backlog previews keep theirs). Running orders stay manually draggable — only Optimize, auto-fixes and Delete are blocked. Cross-machine reassignment and labor/material/precedence constraints remain future capability work. See `docs/architecture/optimizer-dispatch.md` for the search/dispatch deep-dive (convergence/deadline controls, shared primary budget, force-place termination guard, rank-cache freshness hazard, constraint registry) — not duplicated here.
- **Optimizer hard date windows (2026-09-09).** Min Changeover, Due Date and SPT all enforce SAP-only local calendar-day bounds through the detached setup-aware evaluator, including synthetic zero-setup plants. `max_pull_forward_days` floors setup/production at the midnight that starts the SAP due date (the due DAY is taken from `due - 1 ms`, because a 24:00 close reads as the exclusive next-day 00:00) minus N calendar days (combined with planning/frozen floors); `max_push_forward_days` caps productive finish at midnight following the SAP due date plus N days. The cap is hard: an order that cannot finish within it is queued as Needs Planning (`push_limit_unmet`), never placed past it. Since backward-scheduling Phase 1 the "SAP due date" is the due instant (`dueInstant` in `setup-scheduler.mts`, `sourceDueInstant` in `engine.mts`): a date-only due (exact midnight) reads as the close of that date's working window, and a closed date reads as the previous open day, so a Sunday due with N = 0 floors at Friday 00:00 and caps at Saturday 00:00. Null limits are unbounded; equality is valid. Missing SAP `original_end_date` / `ORIGINAL_END_DATE` with a configured limit is a planning exception. Never use effective `BASIC_FINISH_DATE` as SAP truth. Remove Backlog, manual moves, auto-fix and autoReflow retain their date policies. Existing queued demand without a committed interval is eligible for repair; malformed scheduled intervals remain immutable until an explicit data-repair flow.
- **Admission and strategy objectives.** Legal candidates compare admitted demand lexicographically by earliest hard deadline, configured priority, SAP due, current schedule order and stable ID, before strategy scores. Min Changeover (single search, admission by order count) then minimizes uncovered edges, setup, priority, lateness and instability, in that order; Due Date remains delivery-first; SPT prefers shorter work within legal admissions. Missing active setup transitions use zero minutes by default, or the plant's `unknownSetupDefaultMinutes` under the `plantDefaultMinutes` policy, with separate visible warnings. Exact/greedy and existing fixed-boundary fragment walks remain the search machinery; failed orders continue to later fragments and capacity failures never force placement. **Tier inversion:** `'due-date'` mode compares late count, total lateness and worst-case lateness *before* `policyKey`; every other mode compares `policyKey` first and lateness after (`compareDueDateCandidate` vs `compareCandidate`, setup-scheduler.mts). This is the per-plant "priority tiers vs. lateness" tradeoff — chosen by mode, not by a setting.

## Gotchas

- Don't trust any doc (including older revisions of root `CLAUDE.md`) that frames `setup-scheduler.mts` as fully "detached" from `engine.mts`/`calendar-engine.mts` in the dependency-graph sense — it's detached from Store/DOM/persistence/alerts/Timeline (verified above), but it's very much *not* detached from the module-graph: it sits in the same 4-file strongly-connected component as `engine.mts` and `calendar-engine.mts`. `scheduler-contract.mts`'s header comment calls this out as "contradicting the 'setup-scheduler is a detached module' framing elsewhere in this codebase's docs" — that's a self-aware flag in the source itself, not something this doc is introducing.
- `RuntimeAllocation` and `PlaceWithSetupRequest`/`PlacementResult` are defined/re-exported from `engine.mts` even though their only real consumers are `Calendar.allocateRuntime`/`Calendar.placeWithSetup` in `calendar-engine.mts` — this is deliberate (routes through the existing cycle edge rather than opening a second one), not a misplaced export.
- `MIN_PRODUCTIVE_SEGMENT_MINUTES` has exactly one source of truth (`scheduler-contract.mts`) — both `Calendar.allocateRuntime` (non-setup-aware) and `setup-scheduler.mts`'s `placeWithSetup` (setup-aware) import it from there rather than declaring their own copy; don't let a future edit reintroduce a second constant.

## Plant calendar periods in the optimizer (2026-10-16)

`snapshotSchedule` carries each plant's dated periods as `plants[].periods` (the whole plant entry is deep-copied), so a period edit while a preview is open shows as `stale_candidate`. Plant hours are resolved per date, never read as `workHours[getDay()]`: `engine.mts` exports `sourcePlantWorkHours(plant, date?)` (live Store, or the detached `_candidateSnapshot`), `sourcePlantPeriods(plant)` (a shared frozen empty array when none) and `resolvePlantHoursOn(entry, date)`; `setup-scheduler.mts` has its own `plantHoursOn` with a fast path that returns `entry.workHours` by reference when there are no periods (Core-less tests keep working). When periods exist but the compute core lacks `plantWorkHoursOn`, both throw `compute-core-stale` instead of using the default pattern silently (the optimizer worker now loads Core through a versioned dynamic `import()` keyed by the `?v=` build id on its own URL, with `onmessage` registered synchronously and each message awaiting that load, so the guard is a second line of defence against a proxy-cached stale core), and `optimizer-worker-client.mts` answers that error from its synchronous main-thread fallback (`syncEvaluator ?? evaluateSchedule`), logging once per session. Design: `docs/CALENDAR_PERIODS_DESIGN.md`; calendar-side rules in `frontend/calendar/CLAUDE.md`.

## Hard-bound candidate and Apply contract

`CandidateResult` exposes `dispositions` (scheduled / needs_planning / protected), `validationFindings` (error / warning), `searchComplete`, and a detached `validationContext`, separately from its eight-wide objective score. `validateCandidate` checks complete scoped accounting, schedule-only patches, due windows, calendar/blackout capacity, runtime, segment/split policy, setup occupancy and protected preservation. `validateCandidateForApply` also compares the baseline read model to the current snapshot; stale or invalid proposals cannot Apply. Existing protected violations are warnings and keep reserving capacity. The engine attaches the raw `baselineSnapshot` separately from effective (planner, frozen-horizon and running) firmed IDs.

`setup_floor`/`setup_calendar`/`setup_overlap` findings downgrade from `'error'` to `'warning'` when the plant's real `NimbusMasterPlant.setup_active` flag (read via `snapshot.masterData.plants[]`, never `bounds.setup.plant_active`) is `false`; a stale/mismatched-but-active cached setup snapshot does not trigger this downgrade and those findings stay `'error'`.

`snapshotSchedule` captures cloned setup truth, calendar/master-data inputs, frozen-horizon metadata and the read-model revision. Candidate validation and Apply use that captured snapshot; a structural diff of the captured and current snapshots (ignoring `readModelVersion`) produces `stale_candidate` before mutation. The engine-supplied `notBefore`/`notAfter` closures are snapshot-bound (they receive `baseSnapshot` as an explicit view) because the worker serializes them after the run ends, when the ambient `_candidateSnapshot` is null and the realm's Store is empty. The worker request/response contract in `optimizer-worker-contract.mts` serializes clone-safe validation bounds, while `optimizer-worker-client.mts` retains a synchronous fallback for tests and non-UI callers.

Queued patches set `planning_status: needs_planning`, a structured reason (`expired_window`, `missing_due_date`, `invalid_runtime`, `no_fit_found`, `search_limit`, `search_incomplete`, `setup_transition_unrecorded`, `segment_floor_unfittable`, `push_limit_unmet`), null dates and empty segments. `segment_floor_unfittable` means the order cannot be cut into productive segments that meet the plant's segment floor. `push_limit_unmet` means every placement finishes past the push-forward limit. `setup_transition_unrecorded` is N8's per-plant `unknownSetupPolicy` (`zero` charges nothing for an unresolved transition, unchanged; `plantDefaultMinutes` charges the plant's configured minutes at every setup-minutes site instead; `excludeFromSearch` refuses to admit an order whose both states are known but the matrix has no row, surfacing this reason only if it is never placed in a later fragment — the unknown-predecessor case is never excluded, so a line is never frozen). Under `excludeFromSearch`, repair also moves an already-scheduled unprotected order behind an unrecorded transition to this reason. `search_incomplete` means a heuristic search found no placement without proving that every alternate legal sequence was exhausted; `no_fit_found` is reserved for a complete search or a complete gap-fill check. Successful retries clear the reason and set `scheduled`. Every scoped order has one disposition, including unchanged valid incumbents and protected orders; unchanged scheduled rows need no redundant patch. Valid incumbents and search winners survive expiration, and objective metrics are recomputed over final scheduled and queued demand. Scheduled rows with one-sided, reversed, invalid or otherwise untrustworthy intervals stay outside the mutable optimizer scope and receive no repair patch. Direct Apply creates one undo entry; preview owns its own single undo entry.

After comparing the independently validated current schedule and search result, retain compatible placements for queued orders from the other proposal. Each addition must pass line validation without displacing the preferred admission; setup-only conflicts can be retried after another addition provides a bridge. This prevents preserving an urgent order on one day from discarding an already-found placement on an empty later day or a different machine. Planner-facing reasons describe the placement/search outcome, never internal incumbent construction.

Exact-search traversal visits each frame's available occurrences in urgency order, not alphabetical setup-group order. This makes the first complete candidate useful for deadline admission before a bounded search explores setup alternatives. The normal strategy comparator still chooses winners; adjacency requirements and iteration/deadline limits remain enforced. The machine-700 regression records the 36-order workload that previously exhausted 20,000 iterations while skipping feasible September demand.

Large covered fragments use bounded heuristic search with deterministic mode-specific seeds: Min Changeover tries setup-nearest, grouped, policy and runtime orders; Due Date tries due, slack, runtime, policy and source orders; SPT starts with productive runtime and then considers due, policy and stable source-order alternatives only when they improve admission. Each seed gets bounded insertion and swap neighbors through the same hard-bound, calendar, coverage and validation path. `SearchDiagnostics.seedCount` and `localMoveCount` report this work; exact fragments remain exhaustive, while greedy and SPT results remain heuristic.

The primary setup-aware deadline and iteration cap are one shared `SearchBudget` for every selected line, fragment, and boundary fallback (Min Changeover is a single pass). The budget comes from `EvaluationRequest.searchBudgetMs` (5 000 ms when absent) and `EvaluationRequest.exhaustive`. The iteration cap is 20 000 × lines in scope × (budget / 5 000), with the scale floored at 1: 32 000 per line at Normal (8 000 ms) and 720 000 per line at Exhaustive (180 000 ms). `exhaustive: true` also sets `exactSearchThreshold` 10 (default 8), `exactSearchLeafCap` 5 000 (default 500) and `convergenceWindow` 10 000 (default 2 000). `respectCalendar` is carried through production, setup reservations, validation and gap fill. `planningStart`, `runNow` and the derived `placementStart` are separate: scope uses the planning window, new work cannot begin before placementStart, and frozen/protected decisions use runNow.

`Engine.evaluateSetupAware` finishes the chosen hard-bound proposal with `fillPlanningGaps`, once per run, including Min Changeover's internally compared candidates. This separate soft gap-fill budget (`gapFillBudgetMs`) is shared across selected lines: 1 000 ms when `searchBudgetMs` is absent, 2 000 ms at 8 000 ms, and 36 000 ms at 180 000 ms. It inserts queued orders in deadline/actual-machine priority order while keeping accepted production fixed. Calendar intervals are cached per line; productive envelopes (including protected overlaps and whole-order splits) reserve capacity. Both setup transitions and active override bindings must remain legal. A successful insertion invalidates earlier failed checks on that line so setup bridges can be reconsidered within the budget. Backlog does not use this pass.

**Background run.** The Optimize dialog's Run in background checkbox (`#opt-chk-background`, with a duration-free hint) chooses between the normal search (unticked, foreground preview) and the exhaustive search (ticked, `exhaustive: true`, 180 000 ms budget, runs in the background). It always reopens unticked, is never persisted in `optimizerDefaults`, and is disabled and unticked for Remove Backlog. User-facing text says "background"; the code identifiers stay `exhaustive`. A background run goes through `runInBackground`, which owns its own `AbortController` (never `_workerAbortController`), so closing the dialog, `discard`, a new foreground run, or switching tabs or plants cannot abort it; only `cancelBackground` does, and only while the run is computing. One background run at a time: `run()` toasts when one already exists, and `#opt-run-btn` is disabled. While computing, the toolbar `#btn-optimize` gets `is-running` and its click asks to cancel, and a `beforeunload` guard is installed. The preview is split into `computePreview(mode, opts, { signal, tick, shouldStop, runSeq, onPrimary? })`, which is DOM-free and touches no preview state when `onPrimary` is omitted, and `present(result, { open })`, which installs the result, sets `active` and starts the task watch; `active` stays false while a background run computes. The foreground path passes `onPrimary` to install Plan A before the alternates, so the single reveal is unchanged. `_commitPatches(kept, { ids, reason }, snap)` is the extracted apply tail. On completion `#modal-opt-background-done` opens with Switch to plant (only when another plant is selected), View preview, Apply without preview and X. Its backdrop carries `data-no-backdrop-close`, which the shell's boot-time backdrop-click handler honours, so only X dismisses (an outside click, for example on the plant selector, no longer discards a finished run); Switch to plant runs `Persistence.confirmPlantSwitch`, then `Store.setSelectedPlant(plant, 'optimize-background')`, and keeps Apply disabled until that plant's `tasks:bulk` arrives. Apply is disabled when the selected plant differs from the run's plant or the candidate has a candidate-wide error finding. `applyPartial` backs both Apply without preview and the preview's "Apply what still fits" (used when the task baseline went stale). It drops patches for orders that are missing, running, or whose live row differs from the baseline, plus their distribution family (PARENT_ORDER + MATERIAL_NUMBER). It validates the kept set against the live board with `validateCandidate(snapshotSchedule(plant), bounds, …)`; a baseline validation with no patches supplies the set of pre-existing `code|taskId|message` defects (the message is in the key so a new overlap naming a different order is not masked by an older one on the same order). A finding on a kept id drops that patch. A finding on a non-kept id counts as a collision only when it is absent from that baseline, in which case the intersecting kept patch (or the nearest preceding one on the line) is dropped; otherwise the apply is refused. Findings without `taskId` refuse, the loop runs up to 3 passes and then refuses, and a missing `validationContext` refuses. Skipped orders are listed in `toast.opt_bg_partial_applied`. Foreground previews keep all-or-nothing Apply. A ticked run is refused with `toast.opt_bg_no_worker` when `Worker` is unavailable (the fallback would freeze the page). `DueDateFirstBounds.exhaustive` makes the capacity-check `search_limit` message omit the "Tick Run in background" advice, and the preview and popup show `ui.opt_pv_diag_limit_reached_note_exhaustive` for an exhaustive run. `_syncToolbarRunning` also restores `#opt-run-btn` when nothing is computing. Deferred: the popup's Apply is looser than the preview's Apply (enabled when every error names an order), What-If interaction during a background run is unguarded, the popup's z-order against the Optimize dialog is unchecked, and the run driver could be extracted to `background-run.mts`.

`CandidateResult.gapFill` separates capacity-check completion, additional placements, unchecked orders and elapsed time from primary `searchComplete`. Completed failures report no slot found without moving scheduled orders; unfinished checks keep a `search_limit` reason with explicit incomplete-capacity wording. Missing dates, invalid runtimes and expired windows retain their specific reasons. Final validation and metrics run after insertion, so the wall-clock budget is soft; successful additions survive expiration. Preview shows the capacity check separately from the primary sequence search. Existing Apply/undo/atomic Save consume the resulting combined patches unchanged.

Historical placement tests use `scheduledPatches` to inspect admitted production independently of new queue patches. The hard-bounds acceptance cases in `tests/modules/setup-scheduler.test.mjs` inspect complete dispositions and queue aggregates, including DST, missing SAP aliases, setup/split overflow, protected reservations, selected/excluded lines, and expiration before and after a search winner.

## Window-end boundary (2026-10-22)

- **A placed order that crosses the window end is held, not re-placed.** `isWindowEndBoundary(snapshot, bounds, task)` in `setup-scheduler.mts` is true for a task with `user_scheduled === true` (same meaning as `engine.mts`; do not import engine, it adds a cycle edge), a valid interval, `start < horizonEnd < end`, not queued, not already firmed/running/frozen (`taskIsFirmed`), and with `bounds.scopeTaskIds` unset (Remove Backlog is exempt). `buildTaskScope` routes it to `boundaries` after the queued branch, and `taskIsEvaluationProtected` also returns true for it; the second step is the critical one: gap fill and the validator overlap/scope checks key on scope membership (the held order is in `boundaries`), while the search, the anchors and the validator setup checks (`setup_floor`, `setup_calendar`, `setup_overlap`) use the `taskIsEvaluationProtected` predicate (otherwise the order is re-placed and Apply fails on an unclearable `scope` finding). An order spanning the whole window (starts before `planningStart` and ends after `horizonEnd`) is also held, since the test is only `start < horizonEnd < end`. Running, frozen and firmed crossers keep the `protected` disposition. `CandidateResult.windowEndHeldIds` carries the ids to the preview (`explanation.windowEndHeld`, locale key `ui.opt_pv_window_end_held`); the held orders drop out of lateness/instability scoring and out of Needs Planning.
- **SAP basis.** SAP fixes activities lying only partly inside the optimization range; NIMBUS adopts that default. Orders that start at or after `horizonEnd` are unchanged (not in scope).
- **Consequence for the Alert Monitor.** "Optimize this window" opens a 1-to-few-day window, so any order crossing that short window end, including the conflicting order itself, stays put; the planner widens the window to move it. The owner chose no exemption (2026-10-22); the preview line makes the hold visible.
- **Known follow-ups.** The validator setup checks evaluate protection on patched copies, so a candidate that wrongly puts an in-window order across the window end is treated as held (low severity, reachable only from a placement that already fails the window check; the fix is to decide protection from the original order). Held orders without a resolvable setup state show the reason 'Firmed order X...' in the preview (cosmetic). Tests do not cover running/frozen straddlers, ends-exactly-at-edge, or the optimize-ui preview line.

## Tool Inventory: the optimizer overflow pass (Wave 6, 2026-10-27; behind the Hard rule)

A tool id is a TYPE; the plant owns several copies (`masterData.tool_inventory`). With the plant's tooling rule **Hard** the optimizer optimizes as before and then runs ONE plant-wide pass that moves or queues orders so that no more distinct machines use a tool than it has copies. **Off, an unloaded inventory and Remove Backlog are byte-identical to a build without the feature** (golden parity: `order-rules-matrix.test.mjs` "Sixth setting", `scheduler-plant-scale.test.mjs`).

- **Activation (`toolRuleContext` in `setup-scheduler.mts`).** Active only when `toolingRuleForSnapshot(snapshot, plant) === 'hard'` AND `snapshot.masterData.tool_inventory` is an ARRAY (`undefined` = not loaded = unconstrained: the pass is a no-op and adds no finding; the Optimize UI already warns) AND `bounds.ignoreToolRule !== true`. The rule and the inventory are read ONLY from `snapshot.masterData` (the worker contract drops unknown bounds fields and `fillPlanningGaps` rebuilds `runContext`). `ignoreToolRule` is set only by Engine's `backlogBounds` and is not serialized (Backlog is foreground-only).
- **Seams.** (1) `finalizeCandidate`: `resolveToolOverflow` runs on BOTH `incumbent` and `result` right after their `repairCandidate` calls and BEFORE `admitted()` / `compareFinalObjectives`, so the comparison is coherent and a pre-existing overlap on the live schedule is judged under the same rule; the pass ends with `repairCandidate` (the old same-line successor's longer or unrecorded setup is the existing repair cascade, exactly as for any queued order) and `reconcileToolOutcomes` keeps `toolBlocked`/`toolMoved` truthful after retain/gap-fill. (2) `retainCompatiblePlacements` and `fillPlanningGaps` take occupancy from the FULL plant `snapshot.tasks` (+ patches), never from the single-line `{...snapshot, tasks: peers}` they validate against: a retained placement's ENVELOPE must be tool-free; gap-fill intersects every gap with the tool-free windows before `placeWithSetup`, and the pass is re-run once on the final candidate when gap-fill placed anything (or the candidate never had the pass). The gap loop was extracted verbatim into `placeTaskInLineGaps(env, task, hooks?)` (hooks absent = the historical walk), shared by gap-fill and the pass. A pass-queued order (`tool_contention`/`tool_unavailable`) is excluded from gap-fill's pending list so its structured reason is never relabelled. (3) `validateCandidate`: new plant-wide `tool_overflow` finding (the per-line trials set `bounds.skipToolOverflowFinding`). It is a WARNING until the candidate carries `toolPass` (the pass has run on it, so `fillPlanningGaps`' `valid` gate never refuses a candidate the pass has not touched) and for any cluster whose holders are all protected / out of scope; an ERROR only for a cluster with a mutable holder, naming exactly ONE order (the least urgent mutable holder, see below) with a FIXED message and the holders in `detail` (`{tool, available, inUse, holders[<=10]}`), so `_pruneAgainstLive`'s `code|taskId|message` key is stable. `repairCandidate` maps a `tool_overflow` error to a structured `tool_contention` queue reason.
- **Occupancy (reads).** Every task of the selected plant after applying the candidate's patches: mutable, protected, `boundaries` (out-of-window protected, window-end held), rows on unselected / `excludeFromOpt` lines, other-scope rows (all RESERVE copies, none is ever patched), and finish-only rows (the U29 bar). Interval = the compute core's `toolOccupancyInterval` (ENVELOPE first segment start to last segment end, run time only: setup may overlap); intervals ending <= runNow are dropped and starts are clipped to runNow; one machine counts once per tool, one order once per tool (same id in PRT_01 and PRT_02); capacity = `availableCopies` (missing row = 1; qty 0 / all out of service = 0). Detection is the core's `findToolOverages` (the alert uses the same function), moves use `toolHeadroom` (tool-free windows, excluding the order's own line) and `toolIndexUpdate`. The base facts (which order carries which tools, in which plant) are memoised per `snapshot.tasks` reference (`ToolStatic`, carried on `bounds.toolIndex`, rebuilt when the reference or `masterData` differs); `_pruneAgainstLive` and `validateCandidateForApply` therefore rebuild from `live0` automatically.
- **Algorithm (writes: `SchedulePatch` on MUTABLE ids only; MACHINE never changes).** Loop: re-sweep -> the first cluster (sorted tool, time) that has a movable holder -> offender = its LEAST URGENT movable holder by `urgencyOrder(snapshot, bounds, '', ...)` (the plant-wide ordering `finalizeCandidate` uses for admission; policy ranks are line-scoped, so mixing lines is the existing convention) -> re-place it on ITS OWN line through the gap loop with every gap intersected with the tool-free windows of EVERY tool it carries (setup + run, conservative; it may move EARLIER than today), then re-check the ENVELOPE (a split order spans the gap) against the whole index; the first gap that passes both wins and the order becomes "settled". No gap -> queue (null dates, structured reason `tool_unavailable` when any carried tool has 0 copies, else `tool_contention`). Movable = in the mutable scope, not `taskIsEvaluationProtected` (firmed, running, frozen, `placement_exception`, window-end held, explicit boundaries), disposition `scheduled`. After the loop a RECOVERY step re-offers every pass-queued order (most urgent first) to the gaps of the FINAL occupancy until nothing changes (found by the oracle: an order queued because of a holder that was itself queued/moved later; seed 730), so a remaining `tool_contention` order really has no legal tool-free slot.
- **Termination.** Each step either queues an order (the number of placed orders strictly decreases) or moves it into a window in which, for every tool it carries, fewer OTHER machines than copies are in use; later steps only remove intervals or add intervals into such windows, so a settled order is never part of a later cluster and a queued order has no interval. Each step consumes one movable tool-carrying order, so steps <= that count (the loop also enforces the bound defensively). Recovery un-queues one order per success from a finite set.
- **Budget.** `resolveToolOverflow(snapshot, bounds, candidate, budgetMs?)`: Normal 1 s, Exhaustive 10 s, soft, on `bounds.clock`, checked per step and inside the gap walk. On expiry the remaining offenders are queued with `incomplete: true` (code stays `tool_contention`, fixed "ran out of time" message) and `toolPass.complete = false`; no error finding is left behind.
- **Reasons.** `planning_reason` = `{code: 'tool_contention' | 'tool_unavailable', message: <FIXED English text>, tool_id, available, holders: [<=10 ids sorted], incomplete?: true}`. `tool_unavailable` also comes from `staticPlanningDefect` (memoised by `masterData` identity + plant), which sits FIRST in every reason chain (`planningDefect`: the search/tail/gap-fill skip such orders, `finalizeCandidate`'s result and baseline chains and `attachDetachedValidationContext` read it before `pushLimitAware`), so a tool wait is never relabelled push-limit / search-incomplete. The UI renders the text from the structured fields (see Wave 5 above).
- **Candidate contract (what Wave 5 consumes).** `toolPass: {complete, elapsedMs}` is present whenever the pass ran (Hard + loaded inventory + not Backlog); `toolBlocked: [{orderId, tool, available, inUse, holderIds}]` (every order queued for tooling, including the static `tool_unavailable` ones: each has a null-date queue patch, which the Wave 5 confirm guard counts) and `toolMoved: [{orderId, tool, fromStart, fromEnd, toStart, toEnd}]` (ISO strings) are present only when non-empty. With the rule Off / inventory undefined / Backlog all three are ABSENT. Plain arrays/objects: they survive the worker `structuredClone` and `rehydrateOptimizerCandidate`'s spread (tested through a real `worker_threads` round trip).
- **Stale-core guard.** `assertToolCoreFor(snapshot, plant)` (called by `Engine.runAndApply` before the evaluators) and `toolRuleContext` throw `compute-core-stale` when a function the pass needs (`TOOL_CORE_FUNCTIONS`) is missing, ONLY for a Hard plant with a loaded inventory; an Off plant never reaches it, so it keeps using the worker with an older cached core (the client's synchronous fallback answers the throw).
- **Determinism.** All inputs are sorted (tool id, start, end, line, id): the same input gives the same patches regardless of `snapshot.tasks` order and of worker vs main thread (`tool-overflow-oracle.test.mjs`, `optimizer-worker.test.mjs`). Only the soft budget (and `toolPass.elapsedMs`) depends on the clock.
- **Apply side.** `_pruneAgainstLive` validates the kept subset against the live board with dispositions only for the kept patches, so a `tool_overflow` error always names a KEPT order and `dropWithFamily` resolves it (a planner edit that lands on a kept order's tool slot drops that order). Dropping a patch reverts the order to its live slot, which can collide with the next kept patch: the 3-pass cap means a chain needing two sequential drops resolves and a chain needing three is refused (`null`), never half-applied (tested). A live inventory or rule change after a background run is caught by the same validation (`validateCandidateForApply` re-derives the rule from the snapshot).
- **Accepted risks / limits.** (a) Setup and run are intersected with tool-free time although the rule is run-time-only (F4, conservative: a few minutes may be lost). (b) A move on the same line is validated by the per-line trial, so a move that would give the old same-line successor a longer setup is rejected there and the order is queued instead (the cascade then handles the successor). (c) A gap-fill-queued order that only failed because of tool windows keeps its capacity reason (`no_fit_found`/`search_limit`), not `tool_contention`. (d) Out-of-window, never-committed SAP baseline bars (`user_scheduled = false`) reserve copies like any other non-mutable row (owner decision F3 says they should only WARN: see the report; one `toolItemFor` filter away). (e) Alternates (Plan B/C) run the same chain at Normal budget but carry only KPIs, so the constraint affects the comparison table, never Apply. (f) `incomplete` is a flag on `tool_contention`; the UI also has a `tool_contention_incomplete` code that the optimizer does not emit.
