# Optimization — the optimizer, auto-reflow, what-if sandbox

## What lives here

- **`sandbox.mts`** (90 lines) — `Sandbox`: What-If mode state + snapshots only. `enter()` deep-clones `tasks`/`blocks`/`calendars`/`plants`/`plantBlocks`/`firmedIds` off the live `Store`; `exit(apply)` either promotes the sandbox state to real state (pushing one `UndoStack` entry) or restores the pre-enter snapshot wholesale via `Store.replace*()` calls. Emits `sandbox:entered`/`sandbox:exited`/`sandbox:reverted`. DOM banner, toasts, and cross-module side effects (Confidence snapshot/restore, `Persistence.saveAll`, `CalendarSync` flush) are explicitly **not** this module's job — they live in `SandboxAdapter` (`optimize-ui.mts`), which subscribes to the emitted events.
- **`engine.mts`** (2,205 lines) — `Engine`: the optimizer dispatcher (`runAndApply(mode)`), auto-reflow (`autoReflow`), the detached candidate-evaluation machinery (`_candidateSnapshot` + `source*` accessors: `sourceBlocks`, `sourcePlantBlocks`, `sourceGetPlantForLine`, `sourceLineWorkHours`, `sourcePlantWorkHours`, `reportSchedulerDiagnostic`), setup-observation derivation (`deriveSetupObservation`), and the `evaluateSchedule` adapter function (module-level, line 2202) that used to live in `setup-scheduler.mts`. Also exports `snapshotSchedule`, `applySchedulePatches`, `effectiveFirmedIdSet`, `SETUP_AWARE_DEADLINE_MS` (`= 5000`), and the `RuntimeAllocation` type.
- **`scheduler-contract.mts`** (64 lines) — tiny leaf: `MIN_PRODUCTIVE_SEGMENT_MINUTES` (`= 30`, the default productive-segment floor, plant-overridable via `plants.min_productive_segment_minutes` and resolved by `Engine.minProductiveSegmentMinutesFor`), `capAwareSequence` (helper for due-date push-forward cap ordering during SPT walks), and `RemoveBacklogResult`/`RemoveBacklogDiagnostics`. Exists purely to break one import-cycle edge (see Gotchas) — its own header comment is the canonical explanation and documents the real 4-file transitive loop this domain sits in.
- **`setup-scheduler.mts`** (4,897 lines) — the detached candidate scheduler. Header comment: *"This module receives the complete scheduling read model as a snapshot and returns only patches. It never mutates Store, DOM, persistence, alerts, or Timeline; the workbench owns the one explicit Store commit after Apply."* Verified: the only `Store.`/`document.` occurrences in the file are inside comments (lines 908, 1560, 1565, 1759), never live code. Exports `placeWithSetup`, the four pure evaluators (`evaluateDueDateFirst`, `evaluateMinChangeover`, `evaluateSptWithSetup`, `evaluateThroughput`), `selectThroughputCandidate`, `applyPatchesToSnapshot`, `buildRunContext`, `activePriorityKeys`, `placeUnknownTail`, `isSearchConclusive`, plus the full type contract (`SchedulePatch`, `ScheduleSnapshot`, `EvaluationRequest`, `CandidateResult`, `PlacementResult`, `SetupPolicyThresholds`, `SearchDiagnostics`, `MissingSetupEdge`, `SETUP_AWARE_CONVERGENCE_WINDOW`/`SETUP_AWARE_TAIL_OVERRUN_MS`, an 8-wide candidate `score` vector (including `SCORE_OVER_CAP` at index 7 for due-date push-forward cap violations), etc.).
- **`optimize-ui.mts`** (2,040 lines) — the UI layer: `OptimizeDialog` (the Optimize modal), `OptimizerPreview` (`runWithPreview` — before/after KPI preview, verdict scoring, plan comparison + prune tallies, finalist rationale, stale-preview banner), `SandboxAdapter` (the DOM/toast/persistence side effects `sandbox.mts` deliberately excludes).

## Counterpart

No `backend/` counterpart of its own — the optimizer is pure frontend logic. It reads setup/priority/master-data truth that the backend serves (`setup_data.py`, `master_data.py`, root `db.py`) but performs no server calls itself; `optimize-ui.mts`'s persistence path goes through `scheduling/persistence.mts`'s `saveAll` (`POST /tasks/update`), not anything in this domain.

## Key invariants & hazards

- **Optimizer modes are exactly `'spt'` / `'changeover'` / `'backlog'`.** `'combined'`/"Smart" and `Engine._dispatchDayIntegrity` were both fully removed — grepping all of `frontend/` finds `'combined'` and `_dispatchDayIntegrity` occurring **only inside historical comments in `engine.mts` itself** (documenting what used to happen), never as live identifiers or string literals anywhere else. Any doc or code found naming either as current behavior is stale.
- **`'changeover'` always routes through the setup-aware evaluator.** `runAndApply('changeover', …)` builds a `SetupSnapshot` — the plant's real active-and-matching `Store.setupSnapshot` when one exists, or `Engine._syntheticZeroCostSetupSnapshot(plant)` (engine.mts:726) when the plant has no active setup definition — then always calls `Engine.evaluateSetupAware('min-changeover', …)`. The synthetic snapshot is confirmed `plant_active: true`, `synthetic: true`, empty `plant_rows`/`machine_rows`/`overrides` (every transition then resolves at zero setup minutes via `resolveSetup`'s `uncovered(...)` branch). `'spt'` is untouched, still the legacy per-line walk via `Engine._sortTerms(mode, { plant })`.
- **Never-freeze invariant (2026-08-18).** Confirmed live: `_syntheticZeroCostSetupSnapshot`'s doc comment explicitly ties `plant_rows: []`/`machine_rows: []`/`overrides: []` to "the never-freeze invariant already treats [an uncovered transition] as zero setup minutes, never a block" (engine.mts:717-719). `placeUnknownTail` (setup-scheduler.mts:3397) is the tail-of-day-bucket placement for unresolvable signatures.
- **Detached-snapshot/patches contract.** `Engine.evaluateSchedule(mode, opts, snapshot)` (engine.mts:653) and `Engine.evaluateSetupAware(mode, bounds, snapshot, thresholds)` (engine.mts:675) both exist with the documented signatures; `evaluateSetupAware` throws unless the plant's setup definition is `active`. `snapshotSchedule`/`applySchedulePatches`/`effectiveFirmedIdSet` (engine.mts:158/188/200) round out the detached-evaluation contract. `Engine.lastSetupAwareResult` (line 648, consumed on-demand by preview/diagnostics) and `Engine.lastBacklogResult` (line 640, consumed-and-wiped) both confirmed present.
- **Backlog mode's frozen-horizon carve-out**: `diagnostics.frozenMoved` (scheduler-contract.mts's `RemoveBacklogDiagnostics`, incremented at engine.mts:1117 via `Engine.isFrozenHorizon(item.task, now)`) — the one mode that shifts frozen-window orders instead of treating the frozen horizon like a pinned order.
- **Sandbox edits the live Store directly.** Confirmed: `enter()` (sandbox.mts:42-55) snapshots via `Util.clone`/`new Set([...])` into `this._snapshot`, then all subsequent Store mutations (drag, optimize, etc. while sandbox is active) hit the real `Store` — there is no isolated Store copy. `exit(false)` restores the snapshot wholesale via six `Store.replace*()` calls, each firing a `'*:replace'` event **distinct from** that field's normal `'*:change'` event — any future `'blocks:change'`/`'calendar:change'`/etc. subscriber must also handle the `'*:replace'` counterpart or it silently misses What-If-discard updates (sandbox.mts:69-76; pinned by `tests/modules/optimization/sandbox.test.mjs`).
- **The real 4-file import cycle** (documented in full in `scheduler-contract.mts`'s header, confirmed by direct inspection): `engine.mts` → `setup-scheduler.mts` (imports the 4 pure evaluators + `SETUP_AWARE_CONVERGENCE_WINDOW`) → `calendar-engine.mts` (imports `candidateDefaultWorkHours`) → `engine.mts` (imports `Calendar`, and separately exposes `PlaceWithSetupRequest`/`PlacementResult`/`RuntimeAllocation` back to `calendar-engine.mts` through the same edge rather than opening a second cycle). This is genuinely a 4-file strongly-connected component, not two independent 2-file cycles — reason about the whole loop before adding any new **top-level** (module-evaluation-time) cross-reference among `engine.mts`, `setup-scheduler.mts`, `calendar-engine.mts`, or `insights/services.mts`. Every existing cross-reference is safe only because it's inside a function/method body invoked after all four modules finish loading.
- **A separate, direct two-way cycle**: `engine.mts` ↔ `insights/services.mts` (`Alerts`/`scheduleAlertsForPatches` imported by engine.mts; `Engine`/`deriveSetupObservation` imported by services.mts) — distinct from the 4-file loop above, per the same safety rule.
- Dispatching heuristics, not a constraint solver — finish-to-start precedence is not consulted; manual pinning (`Store.isFirmed`) is the only protection an order has from being moved. See `docs/architecture/optimizer-dispatch.md` for the search/dispatch deep-dive (convergence/deadline controls, per-line budget share, force-place termination guard, rank-cache freshness hazard, constraint registry) — not duplicated here.
- **Due-date push-forward limit (2026-09-09).** Per-plant `plants.max_push_forward_days` (nullable INTEGER ≥ 0; NULL = no limit, default) bounds lateness. An order is "over cap" when scheduled `end_date` > (original SAP due date local midnight) + (N+1) calendar days. Setup-aware evaluator appends 8th score tier `score[7]` (`SCORE_OVER_CAP`), compared immediately after `policyKey` and before coverage; counted per-sequence via `candidateForSequence`'s simulation cursor. `evaluateMinChangeover`'s due-safe baseline gate: candidate creating newly over-cap orders rejected with `'min-changeover-rejected-lateness-cap'`. Legacy SPT walk uses pure helper `capAwareSequence` (scheduler-contract.mts) to pull capped orders ahead when SPT head would push past latest allowed start. Default-off (NULL) is a no-op: all score[7]=0, ranking unchanged. Violations reported via `toast.optimize_over_lateness_cap` + preview banner. Remove Backlog, manual drag, auto-fix, autoReflow ignore the cap.

## Gotchas

- Don't trust any doc (including older revisions of root `CLAUDE.md`) that frames `setup-scheduler.mts` as fully "detached" from `engine.mts`/`calendar-engine.mts` in the dependency-graph sense — it's detached from Store/DOM/persistence/alerts/Timeline (verified above), but it's very much *not* detached from the module-graph: it sits in the same 4-file strongly-connected component as `engine.mts` and `calendar-engine.mts`. `scheduler-contract.mts`'s header comment calls this out as "contradicting the 'setup-scheduler is a detached module' framing elsewhere in this codebase's docs" — that's a self-aware flag in the source itself, not something this doc is introducing.
- `RuntimeAllocation` and `PlaceWithSetupRequest`/`PlacementResult` are defined/re-exported from `engine.mts` even though their only real consumers are `Calendar.allocateRuntime`/`Calendar.placeWithSetup` in `calendar-engine.mts` — this is deliberate (routes through the existing cycle edge rather than opening a second one), not a misplaced export.
- `MIN_PRODUCTIVE_SEGMENT_MINUTES` has exactly one source of truth (`scheduler-contract.mts`) — both `Calendar.allocateRuntime` (non-setup-aware) and `setup-scheduler.mts`'s `placeWithSetup` (setup-aware) import it from there rather than declaring their own copy; don't let a future edit reintroduce a second constant.
