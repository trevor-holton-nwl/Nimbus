# Optimization — the optimizer, auto-reflow, what-if sandbox

## What lives here

- **`sandbox.mts`** (130 lines) — `Sandbox`: What-If mode state + snapshots only. `enter()` deep-clones `tasks`/`blocks`/`calendars`/`plants`/`plantBlocks`/`firmedIds` off the live `Store`; `exit(apply)` either promotes the sandbox state to real state (pushing one `UndoStack` entry) or restores the pre-enter snapshot wholesale via `Store.setTasks` + `Store.replace*()` calls. Emits `sandbox:entered`/`sandbox:exited`/`sandbox:reverted`. DOM banner, toasts, and cross-module side effects (Confidence snapshot/restore, `Persistence.saveAll`, `CalendarSync` flush) are explicitly **not** this module's job — they live in `SandboxAdapter` (`optimize-ui.mts`), which subscribes to the emitted events.
- **`engine.mts`** (about 3,000 lines) — `Engine`: the optimizer dispatcher (`runAndApply(mode)`), auto-reflow (`autoReflow`), the detached candidate-evaluation machinery (`_candidateSnapshot` + `source*` accessors: `sourceBlocks`, `sourcePlantBlocks`, `sourceGetPlantForLine`, `sourceLineWorkHours`, `sourcePlantWorkHours`, `reportSchedulerDiagnostic`), setup-observation derivation (`deriveSetupObservation`), and the `evaluateSchedule` adapter function (module-level, line 3216) that used to live in `setup-scheduler.mts`. Also exports `snapshotSchedule`, `applySchedulePatches`, `effectiveFirmedIdSet`, `SETUP_AWARE_DEADLINE_MS` (`= 5000`), and the `RuntimeAllocation` type. The finish-anchored placement entry points sit here too: `manualSchedulePatchFor`, `manualRoutingSchedulePatchFor`, `finishAnchoredPatchFor`, `pushFinishPatches`, `confirmOvertimePlacement`, `reconcileRuntimeSchedules` and `placeForwardSequence`.
- **`scheduler-contract.mts`** (158 lines) — tiny leaf: `MIN_PRODUCTIVE_SEGMENT_MINUTES` (`= 30`, the default productive-segment floor, plant-overridable via `plants.min_productive_segment_minutes` and resolved by `Engine.minProductiveSegmentMinutesFor`), `capAwareSequence` (helper for due-date push-forward cap ordering during SPT walks), and `RemoveBacklogResult`/`RemoveBacklogDiagnostics`. Exists purely to break one import-cycle edge (see Gotchas) — its own header comment is the canonical explanation and documents the real 4-file transitive loop this domain sits in.
- **`setup-scheduler.mts`** (7,437 lines) — the detached candidate scheduler. Header comment: *"This module receives the complete scheduling read model as a snapshot and returns only patches. It never mutates Store, DOM, persistence, alerts, or Timeline; the workbench owns the one explicit Store commit after Apply."* Verified: the only `Store.`/`document.` occurrences in the file are inside comments, never live code (re-grep rather than trusting line numbers). Exports `placeWithSetup`, the four pure evaluators (`evaluateDueDateFirst`, `evaluateMinChangeover`, `evaluateSptWithSetup`, `evaluateThroughput`), `selectThroughputCandidate`, `applyPatchesToSnapshot`, `buildRunContext`, `activePriorityKeys`, `placeUnknownTail`, `isSearchConclusive`, plus the full type contract (`SchedulePatch`, `ScheduleSnapshot`, `EvaluationRequest`, `CandidateResult`, `PlacementResult`, `SetupPolicyThresholds`, `SearchDiagnostics`, `MissingSetupEdge`, `SETUP_AWARE_CONVERGENCE_WINDOW`/`SETUP_AWARE_TAIL_OVERRUN_MS`, an 8-wide candidate `score` vector (including `SCORE_OVER_CAP` at index 7 for due-date push-forward cap violations), etc.).
- **`optimizer-worker-contract.mts` / `optimizer-worker-client.mts` / `optimizer-worker.mts`** — clone-safe worker request/response types, cancellable preview adapter and worker entrypoint. The client calls the synchronous detached evaluator when Workers are unavailable or explicitly disabled, so unit tests and non-UI callers keep a deterministic path.
- **`optimize-ui.mts`** (2,554 lines) — the UI layer: `OptimizeDialog` (the Optimize modal), `OptimizerPreview` (`runWithPreview` — before/after KPI preview, verdict scoring, plan comparison + prune tallies, finalist rationale, stale-preview banner), `SandboxAdapter` (the DOM/toast/persistence side effects `sandbox.mts` deliberately excludes).

## Counterpart

No `backend/` counterpart of its own — the optimizer is pure frontend logic. It reads setup/priority/master-data truth that the backend serves (`setup_data.py`, `master_data.py`, root `db.py`) but performs no server calls itself; `optimize-ui.mts`'s persistence path goes through `scheduling/persistence.mts`'s `saveAll` (`POST /tasks/update`), not anything in this domain.

## Key invariants & hazards

- **Optimizer modes are exactly `'spt'` / `'changeover'` / `'duedate'` / `'backlog'`.** `'combined'`/"Smart" and `Engine._dispatchDayIntegrity` were both fully removed — grepping all of `frontend/` finds `'combined'` and `_dispatchDayIntegrity` occurring **only inside historical comments in `engine.mts` itself** (documenting what used to happen), never as live identifiers or string literals anywhere else. Any doc or code found naming either as current behavior is stale.
- **Setup-aware optimizer routing.** `runAndApply('changeover', …)` builds a `SetupSnapshot` — the plant's real active-and-matching `Store.setupSnapshot` when one exists, or `Engine._syntheticZeroCostSetupSnapshot(plant)` (engine.mts) when the plant has no active setup definition — then calls `Engine.evaluateSetupAware('min-changeover', …)`. `'duedate'` calls the same setup-aware seam with the due-date comparator, and `'spt'` calls it with the SPT comparator. Inactive or mismatched setup data uses the synthetic zero-cost snapshot for all three modes, so a plant cannot silently switch algorithms because setup data is absent. This is the only optimizer path: the old per-line forward walk and `_dispatchPolicyAware` were deleted (Task 3.1, OQ22); any unrecognised mode string takes the same setup-aware route.
- **Never-freeze invariant (2026-08-18).** Confirmed live: `_syntheticZeroCostSetupSnapshot`'s doc comment explicitly ties `plant_rows: []`/`machine_rows: []`/`overrides: []` to "the never-freeze invariant already treats [an uncovered transition] as zero setup minutes, never a block" (engine.mts:976-977). `placeUnknownTail` (setup-scheduler.mts:4590) is the tail-of-day-bucket placement for unresolvable signatures. Min Changeover, Due Date, and SPT all enforce this guarantee — no order is left frozen by incomplete setup data.
- **Detached-snapshot/patches contract.** `Engine.evaluateSchedule(mode, opts, snapshot)` (engine.mts:930) and `Engine.evaluateSetupAware(mode, bounds, snapshot, thresholds)` (engine.mts:952) both exist with the documented signatures; `evaluateSetupAware` throws unless the plant's `plants.setup_active` flag (`bounds.setup.plant_active`) is on. `snapshotSchedule`/`applySchedulePatches`/`effectiveFirmedIdSet` (engine.mts:210/256/267) round out the detached-evaluation contract. `Engine.lastSetupAwareResult` (line 925, consumed on-demand by preview/diagnostics) and `Engine.lastBacklogResult` (line 917, consumed-and-wiped) both confirmed present. **F1/F2/F4 optimizations (2026-10-06):** exact search runs only for fragments with ≤500 distinct orderings (F1); a per-run free-interval index serves calendar windows (F2); iteration cap = 20,000 × the plant's lines in scope (F4).
- **Reconcile derives starts from the held finish (backward scheduling Task 2.6, 2026-10-14).** `Engine.reconcileRuntimeSchedules(plant, {reason?})` takes the rows that are `runtime_schedule_mismatch` or never placed (`!user_scheduled`). It skips queued rows, rows carrying `placement_exception`, rows with no machine, and rows with unsaved local edits (`Persistence._dirtyIds`). The anchor is a placed row's stored end, else `Util.dueInstant`. A running placed row keeps its start (`schedulePatchFor`; if the calendar would move the start, the bar becomes start plus run time as one continuous piece). Every other row is walked backward by `finishAnchoredPatchFor(..., {deferReversal: true})`, and a walk that reaches the plant's now goes forward per line in finish order through `Engine.placeForwardSequence` (`reversal_forward`). A row the server flagged stale gets a DIRTY patch (source `engine-runtime-reconcile`: the next Save persists it, and one `toast.system_moved_n` counts these). An unflagged never-placed row gets a DISPLAY-ONLY patch (source `engine-runtime-reconcile-display`, which the dirty tracker skips, so Save leaves it never-placed). Nothing is derived unless `CalendarSync.calendarState(plant) === 'hydrated'` (otherwise `Engine.derivePausedPlants` and the `ui.derive_paused` banner show); a plant with no zone gets `plant_no_timezone`, and a line with no server calendar row gets `line_no_calendar`. Every touched or skipped row carries a session-only `derivationIssue`, and every schedule patch carries `systemMove {from, to, reason}`. Issue codes: `finish_moved_earlier`, `reversal_forward` (detail `due_date_past`, `run_time_grew` or `cutover`), `frozen_window_crossed` (manually firmed rows only), `pull_floor_crossed`, `no_operating_window`, `run_time_zero`, `no_anchor`, `line_no_calendar` and `plant_no_timezone`. A row that cannot be one bar under the plant's policy is queued as `overlong_never`. The whole batch runs in one calendar run (`Calendar._beginRun` / `_endRun`).
- **Manual placement and Push +1 h hold the finish (backward scheduling Task 2.5, 2026-10-14).** `Engine.manualSchedulePatchFor(task, line, requestedFinish, policy?, opts?)` takes the FINISH and returns null on a refusal, with the reason in `Engine.lastManualRefusal` (`run_time_zero`, `plant_no_timezone`, `overlong_never`, `no_operating_window`, `finish_cannot_hold`, `needs_overtime_confirm`). `finish_cannot_hold` toasts unless `opts.quiet`. A firmed order whose finish would have to move gets `needs_overtime_confirm`; with `confirmedOvertime` it is placed as one raw bar (start = finish minus run time) marked `placement_exception = 'overtime'`. A row already marked is translated verbatim by its finish delta. A queued `overlong_never` row that is still too long for one bar is released as one continuous bar marked `'overlong'`, and a queued `run_time_over_cap` row that places normally returns to `scheduled`. A running order holds its start (`opts.holdStartIfRunning`). A split order whose productive total is unchanged is translated rigidly; otherwise it is re-derived from the held finish. `Engine.pushFinishPatches(tasks, ms)` moves each order's finish by `ms` (one calendar run per plant), skips orders that `Engine.firmingStatus` reports as firmed (manual, frozen or running), and quietly skips any order whose new finish cannot be held. Manual placement ignores the frozen horizon. `Engine.plannerUnscheduleChanges()` nulls `placement_exception`.
- **One plant-zone clock (backward scheduling Task 2.4, 2026-10-14).** `Engine.isFrozenHorizon`, `Engine.isInProgress` and `Engine.firmingStatus` default their `now` to `Engine._clockFor(task)`: the task's plant, else its line's, else the selected plant, read through `Store.plantNow`. A null clock means not frozen and not running, never a throw. The Optimize dialog's defaults read the same clock (`Engine._plantWallNow`), `autoReflow` uses the changed order's plant clock, and Remove Backlog's default run-at time is the server clock (`Store.serverNow()`).
- **The optimizer's result is the placed finish (backward scheduling Task 3.1, 2026-10-14; A-lite).** The setup-aware evaluators still place forward, but the placed finish (`end_date`, the last segment end) is what is judged: instability is `|new finish - prior finish|` in minutes (`setup-scheduler.mts`, both the fragment and the final objective), so a task whose finish holds while its start moved is stable. The legacy walk is gone. The retained forward paths are exactly: the optimizer's setup-aware evaluators, the Alerts Fix cascade (`autoReflow`), Remove Backlog (`placeForwardSequence`), the reversal forward leg, and `Engine.schedulePatchFor` reached through `Engine.heldStartPatchFor` (OQ3: a started order keeps its real start and only its finish follows the run time; shared by the reconcile's running branch and the manual run-time/machine/version edit, `holdStartIfRunning`). A row carrying `placement_exception` is fixed in every entry point (`effectiveFirmedIdSet`, Remove Backlog, `autoReflow`, the Alerts Fix cascade) whatever "Respect firmed" says. `Engine.placeForwardSequence` never places a `never`-policy overlong order as one elapsed bar: it is reported in `overlong` and the callers (Remove Backlog, the reversal queue) queue it with `Engine.overlongNeverChanges()` (reason `overlong_never`); Remove Backlog still reports it in `diagnostics.overlongIds`. `UndoStack.restoreTasks` and `TimeMachine.restore` restore the finish, flag the rows `runtime_schedule_mismatch`, and call `Engine.reconcileRestored` (the engine registers `UndoStack.afterRestore` at load), which runs `reconcileRuntimeSchedules(plant, {reason:'undo', ids})`: the ids bypass the unsaved-edit skip and no "N moved" toast is raised. A Store write with source `engine-runtime-reconcile` while an Optimize preview is open stales it (Apply disabled, banner `ui.preview_stale`). The Remove Backlog dialog's hint adds a count of rows tagged `reversal_forward` / `run_time_grew` (`ui.opt_backlog_runtime_grew`).
- **Backlog mode's frozen-horizon carve-out**: `diagnostics.frozenMoved` (scheduler-contract.mts's `RemoveBacklogDiagnostics`, incremented at engine.mts:1840 via `Engine.isFrozenHorizon(item.task, now)`) — the one mode that shifts frozen-window orders instead of treating the frozen horizon like a pinned order.
- **Sandbox edits the live Store directly.** Confirmed: `enter()` (sandbox.mts:42-55) snapshots via `Util.clone`/`new Set([...])` into `this._snapshot`, then all subsequent Store mutations (drag, optimize, etc. while sandbox is active) hit the real `Store` — there is no isolated Store copy. `exit(false)` restores via `Store.setTasks(..., 'sandbox')` plus five `Store.replace*()` calls (source `'sandbox'`, so firm replacement never dirties). Each `replace*` fires a `'*:replace'` event and then the field's compatibility `'*:change'` event (`replacePlants` emits `plants:replace` then `calendar:change`, never `plants:change`), so existing `'blocks:change'`/`'calendar:change'` subscribers do refresh after a discard (pinned by `tests/modules/optimization/sandbox.test.mjs`). **Applied What-If undo** is different: it restores tasks through `UndoStack.restoreTasks` (source `'undo'`, live `row_version`, so restored ids become dirty and the next save pushes the revert), drops scenario-created tasks, confirms first if calendar/blackout slices changed since Apply, and emits `sandbox:reverted` carrying the `promoted` slices so `SandboxAdapter` can re-sync the backend calendar.
- **The real 4-file import cycle** (documented in full in `scheduler-contract.mts`'s header, confirmed by direct inspection): `engine.mts` → `setup-scheduler.mts` (imports the 4 pure evaluators + `SETUP_AWARE_CONVERGENCE_WINDOW`) → `calendar-engine.mts` (imports `candidateDefaultWorkHours`) → `engine.mts` (imports `Calendar`, and separately exposes `PlaceWithSetupRequest`/`PlacementResult`/`RuntimeAllocation` back to `calendar-engine.mts` through the same edge rather than opening a second cycle). This is genuinely a 4-file strongly-connected component, not two independent 2-file cycles — reason about the whole loop before adding any new **top-level** (module-evaluation-time) cross-reference among `engine.mts`, `setup-scheduler.mts`, `calendar-engine.mts`, or `insights/services.mts`. Every existing cross-reference is safe only because it's inside a function/method body invoked after all four modules finish loading.
- **A separate, direct two-way cycle**: `engine.mts` ↔ `insights/services.mts` (`Alerts`/`scheduleAlertsForPatches` imported by engine.mts; `Engine`/`deriveSetupObservation` imported by services.mts) — distinct from the 4-file loop above, per the same safety rule.
- Dispatching heuristics, not a constraint solver — finish-to-start precedence is not consulted; an order is protected from moving only by a manual firm (`Store.isFirmed`, gated by "Respect firmed"), the frozen horizon, or **running** (`Engine.isInProgress(t, now)`: start <= now < end; not gated by "Respect firmed"). SAP's firm flag (`ecc_firmed`) is display-only (`Engine.isSapFirmed`) and never locks. `Engine.firmingStatus` reasons are `'frozen' | 'manual' | 'running'`; `effectiveFirmedIdSet`, the legacy walk, `autoReflow` and Alerts one-click fixes all use the same union. **Remove Backlog is exempt** and may still move running orders. Preview Apply re-checks `Engine.isInProgress` at apply time and drops patches for orders that started running while the preview was open (toast `toast.opt_apply_running_skipped`; Remove Backlog previews keep theirs). Running orders stay manually draggable — only Optimize, auto-fixes and Delete are blocked. Cross-machine reassignment and labor/material/precedence constraints remain future capability work. See `docs/architecture/optimizer-dispatch.md` for the search/dispatch deep-dive (convergence/deadline controls, shared primary budget, force-place termination guard, rank-cache freshness hazard, constraint registry) — not duplicated here.
- **Optimizer hard date windows (2026-09-09).** Min Changeover, Due Date and SPT all enforce SAP-only local calendar-day bounds through the detached setup-aware evaluator, including synthetic zero-setup plants. `max_pull_forward_days` floors setup/production at the midnight that starts the SAP due date (the due DAY is taken from `due - 1 ms`, because a 24:00 close reads as the exclusive next-day 00:00) minus N calendar days (combined with planning/frozen floors); `max_push_forward_days` caps productive finish at midnight following the SAP due date plus N days. Since backward-scheduling Phase 1 the "SAP due date" is the due instant (`dueInstant` in `setup-scheduler.mts`, `sourceDueInstant` in `engine.mts`): a date-only due (exact midnight) reads as the close of that date's working window, and a closed date reads as the previous open day, so a Sunday due with N = 0 floors at Friday 00:00 and caps at Saturday 00:00. Null limits are unbounded; equality is valid. Missing SAP `original_end_date` / `ORIGINAL_END_DATE` with a configured limit is a planning exception. Never use effective `BASIC_FINISH_DATE` as SAP truth. Remove Backlog, manual moves, auto-fix and autoReflow retain their date policies. Existing queued demand without a committed interval is eligible for repair; malformed scheduled intervals remain immutable until an explicit data-repair flow.
- **Admission and strategy objectives.** Legal candidates compare admitted demand lexicographically by earliest hard deadline, configured priority, SAP due, current schedule order and stable ID, before strategy scores. Min Changeover (single search, admission by order count) then minimizes over-cap, uncovered edges, setup, priority, lateness and instability, in that order; Due Date remains delivery-first; SPT prefers shorter work within legal admissions. Missing active setup transitions use zero minutes by default, or the plant's `unknownSetupDefaultMinutes` under the `plantDefaultMinutes` policy, with separate visible warnings. Exact/greedy and existing fixed-boundary fragment walks remain the search machinery; failed orders continue to later fragments and capacity failures never force placement. **Tier inversion:** `'due-date'` mode compares late count, total lateness and worst-case lateness *before* `policyKey`; every other mode compares `policyKey` first and lateness after (`compareDueDateCandidate` vs `compareCandidate`, setup-scheduler.mts). This is the per-plant "priority tiers vs. lateness" tradeoff — chosen by mode, not by a setting.

## Gotchas

- Don't trust any doc (including older revisions of root `CLAUDE.md`) that frames `setup-scheduler.mts` as fully "detached" from `engine.mts`/`calendar-engine.mts` in the dependency-graph sense — it's detached from Store/DOM/persistence/alerts/Timeline (verified above), but it's very much *not* detached from the module-graph: it sits in the same 4-file strongly-connected component as `engine.mts` and `calendar-engine.mts`. `scheduler-contract.mts`'s header comment calls this out as "contradicting the 'setup-scheduler is a detached module' framing elsewhere in this codebase's docs" — that's a self-aware flag in the source itself, not something this doc is introducing.
- `RuntimeAllocation` and `PlaceWithSetupRequest`/`PlacementResult` are defined/re-exported from `engine.mts` even though their only real consumers are `Calendar.allocateRuntime`/`Calendar.placeWithSetup` in `calendar-engine.mts` — this is deliberate (routes through the existing cycle edge rather than opening a second one), not a misplaced export.
- `MIN_PRODUCTIVE_SEGMENT_MINUTES` has exactly one source of truth (`scheduler-contract.mts`) — both `Calendar.allocateRuntime` (non-setup-aware) and `setup-scheduler.mts`'s `placeWithSetup` (setup-aware) import it from there rather than declaring their own copy; don't let a future edit reintroduce a second constant.

## Hard-bound candidate and Apply contract

`CandidateResult` exposes `dispositions` (scheduled / needs_planning / protected), `validationFindings` (error / warning), `searchComplete`, and a detached `validationContext`, separately from its eight-wide objective score. `validateCandidate` checks complete scoped accounting, schedule-only patches, due windows, calendar/blackout capacity, runtime, segment/split policy, setup occupancy and protected preservation. `validateCandidateForApply` also compares the baseline read model to the current snapshot; stale or invalid proposals cannot Apply. Existing protected violations are warnings and keep reserving capacity. The engine attaches the raw `baselineSnapshot` separately from effective ECC/frozen firmed IDs.

`setup_floor`/`setup_calendar`/`setup_overlap` findings downgrade from `'error'` to `'warning'` when the plant's real `NimbusMasterPlant.setup_active` flag (read via `snapshot.masterData.plants[]`, never `bounds.setup.plant_active`) is `false`; a stale/mismatched-but-active cached setup snapshot does not trigger this downgrade and those findings stay `'error'`.

`snapshotSchedule` captures cloned setup truth, calendar/master-data inputs, frozen-horizon metadata and the read-model revision. Candidate validation and Apply use that captured snapshot; a revision mismatch produces `stale_candidate` before mutation. The worker request/response contract in `optimizer-worker-contract.mts` serializes clone-safe validation bounds, while `optimizer-worker-client.mts` retains a synchronous fallback for tests and non-UI callers.

Queued patches set `planning_status: needs_planning`, a structured reason (`expired_window`, `missing_due_date`, `invalid_runtime`, `no_fit_found`, `search_limit`, `search_incomplete`, `setup_transition_unrecorded`), null dates and empty segments. `setup_transition_unrecorded` is N8's per-plant `unknownSetupPolicy` (`zero` charges nothing for an unresolved transition, unchanged; `plantDefaultMinutes` charges the plant's configured minutes at every setup-minutes site instead; `excludeFromSearch` refuses to admit an order whose both states are known but the matrix has no row, surfacing this reason only if it is never placed in a later fragment — the unknown-predecessor case is never excluded, so a line is never frozen). `search_incomplete` means a heuristic search found no placement without proving that every alternate legal sequence was exhausted; `no_fit_found` is reserved for a complete search or a complete gap-fill check. Successful retries clear the reason and set `scheduled`. Every scoped order has one disposition, including unchanged valid incumbents and protected orders; unchanged scheduled rows need no redundant patch. Valid incumbents and search winners survive expiration, and objective metrics are recomputed over final scheduled and queued demand. Scheduled rows with one-sided, reversed, invalid or otherwise untrustworthy intervals stay outside the mutable optimizer scope and receive no repair patch. Direct Apply creates one undo entry; preview owns its own single undo entry.

After comparing the independently validated current schedule and search result, retain compatible placements for queued orders from the other proposal. Each addition must pass line validation without displacing the preferred admission; setup-only conflicts can be retried after another addition provides a bridge. This prevents preserving an urgent order on one day from discarding an already-found placement on an empty later day or a different machine. Planner-facing reasons describe the placement/search outcome, never internal incumbent construction.

Exact-search traversal visits each frame's available occurrences in urgency order, not alphabetical setup-group order. This makes the first complete candidate useful for deadline admission before a bounded search explores setup alternatives. The normal strategy comparator still chooses winners; adjacency requirements and iteration/deadline limits remain enforced. The machine-700 regression records the 36-order workload that previously exhausted 20,000 iterations while skipping feasible September demand.

Large covered fragments use bounded heuristic search with deterministic mode-specific seeds: Min Changeover tries setup-nearest, grouped, policy and runtime orders; Due Date tries due, slack, runtime, policy and source orders; SPT starts with productive runtime and then considers due, policy and stable source-order alternatives only when they improve admission. Each seed gets bounded insertion and swap neighbors through the same hard-bound, calendar, coverage and validation path. `SearchDiagnostics.seedCount` and `localMoveCount` report this work; exact fragments remain exhaustive, while greedy and SPT results remain heuristic.

The primary setup-aware deadline and iteration cap are one shared `SearchBudget` for every selected line, fragment, and boundary fallback (Min Changeover is a single pass). `respectCalendar` is carried through production, setup reservations, validation and gap fill. `planningStart`, `runNow` and the derived `placementStart` are separate: scope uses the planning window, new work cannot begin before placementStart, and frozen/protected decisions use runNow.

`Engine.evaluateSetupAware` finishes the chosen hard-bound proposal with `fillPlanningGaps`, once per run, including Min Changeover's internally compared candidates. This separate soft 1,000 ms budget is shared across selected lines. It inserts queued orders in deadline/actual-machine priority order while keeping accepted production fixed. Calendar intervals are cached per line; productive envelopes (including protected overlaps and whole-order splits) reserve capacity. Both setup transitions and active override bindings must remain legal. A successful insertion invalidates earlier failed checks on that line so setup bridges can be reconsidered within the budget. Backlog does not use this pass.

`CandidateResult.gapFill` separates capacity-check completion, additional placements, unchecked orders and elapsed time from primary `searchComplete`. Completed failures report no slot found without moving scheduled orders; unfinished checks keep a `search_limit` reason with explicit incomplete-capacity wording. Missing dates, invalid runtimes and expired windows retain their specific reasons. Final validation and metrics run after insertion, so the wall-clock budget is soft; successful additions survive expiration. Preview shows the capacity check separately from the primary sequence search. Existing Apply/undo/atomic Save consume the resulting combined patches unchanged.

Historical placement tests use `scheduledPatches` to inspect admitted production independently of new queue patches. The hard-bounds acceptance cases in `tests/modules/setup-scheduler.test.mjs` inspect complete dispositions and queue aggregates, including DST, missing SAP aliases, setup/split overflow, protected reservations, selected/excluded lines, and expiration before and after a search winner.
