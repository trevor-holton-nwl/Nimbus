# Platform — foundation layer (config, generic chrome, reactive state)

## What lives here

Planning exceptions use optional `NimbusTask.planning_status` (missing defaults to scheduled) and structured `planning_reason`. Store normalization clears queue dates/segments, while explicit complete date patches restore scheduled status. `Util.scheduledEnd` never falls back to SAP due for queued orders; overdue queue lateness is measured to now and demand remains visible without scheduled utilization.

Canonical task aggregates carrying `planning_status` retain exact production and segment timestamps during normalization; re-snapping a validated setup interval can invalidate it. Manual date workflows perform their own snapping. Undo restores business/schedule state while preserving the live row version, so an undo after Save can pass the next optimistic concurrency check.

**`foundation.mts`** (1,904 lines) — CQ-1 foundation module; no schedule state, no feature endpoints, no scheduling rules:
- `Config` — frozen-in-spirit (never mutated at runtime) global constants: `STEP_MS` (15-min snap), `DEFAULT_SHIFT`, `COLORS` (10-line palette), `OVERLOAD_THRESHOLD`/`WARN_THRESHOLD`, `LS_KEY` (`'nimbus.state.v3'`), `SCHEMA_VERSION` (6), `BUILD_ID`, `KNOWN_PLANTS`, `CONCURRENCY_CHECK`, `SESSION_MAX_AGE_MS`, etc.
- `Util` — pure helpers plus four DI-seam setters (`setPreferenceResolver`, `setActorResolver`, `setUtilizationResolver`, `setChangeoverFieldsResolver`) that replace old direct references into modules living elsewhere (Store, Session, Utilization, Engine). Also owns `fetchTraced` (traced fetch wrapper), `parseBackendError`, i18n resolver `t()`, `fpDatetime` (Flatpickr factory), date/time formatting, `toLocalSeconds` (the UTC-corruption-bug fix), `scheduleKpis`/`countChangeovers`/`latenessHours` (optimizer-preview KPI math — calls the injected utilization resolver, so not stateless), paste-to-checkbox helpers (`renderLineChecklist`, `matchPasteToCheckboxes`, `wirePasteToCheckboxes` — the last two take an optional `onBatch` so a paste of N lines commits as one change, not N) shared by every line-picker across the app. Also the CSV-export guards `csvGuardText`/`csvProcessCell`/`csvCell` (spreadsheet-formula neutralizing + RFC-4180 quoting — frontend CSV exports go through them) and `errorDetailText` (flattens FastAPI/structured `detail` payloads into a readable, length-capped string for `parseBackendError`).
- `VirtualList<T>` — padding-based windowed list renderer (fixed or variable row height via binary search), with scroll-position preservation across re-renders (`_desiredTop`, `saveTop`/`restoreTop`) and a zero-height-container deferral guard.
- `PerfMonitor` — ring-buffer (100 samples) profiler; `record`/`time`/`stats` (p50/p95/max)/`all()`; read by AdminCockpit's Thread tab.
- `ErrorLog` — structured in-memory + IndexedDB-durable log (max 800 entries; IndexedDB key is per login, `entries:<actor>`, with a one-time read of the legacy `entries` key), four DI-seam setters (`setPlantResolver`, `setRouteResolver`, `setAdminGate`, `setBadgeClickHandler`), breadcrumb ring, error-rate tracking, batched shipping to `POST /logs/frontend` (entries and the ship request carry the user), header badge rendering. Also: `console.error`/`console.warn` are wrapped by `installGlobalHandlers` and recorded as scope `console` (a `_capturing` flag prevents recursion; ErrorLog mirrors through the saved originals); `registerStateProvider(name, fn)` snapshots are attached as `ctx.state` on error-level entries only (2 KB per provider, 20 ms total); `exportJsonPayload()`/`exportJson()` produce the downloadable log. `Util.fetchTraced` tags a real 409 as `http.conflict`.
- `Toast` — top-right notification stack, max 3 visible, dedupes by `(msg, type)`, evicts oldest non-error first. `show(msg, type, ms?, action?)`: default duration is per-type (error 6 s, warn 4 s, else 1.5 s); an optional `{label, run}` action renders a `.toast-action` button (one-shot: fires `run()` once, then dismisses); the stack is a live region. A 5th arg `opts {err?, reqId?, ctx?}` is logged: every `show` call (including deduped repeats and headless callers) writes an ErrorLog entry, scope `toast`, errorCode `toast.<type>` (error to error, warn to warn, info/success to info).
- `Modal` — generic `open`/`close`/`confirm` (promise-based, `confirm({title, message, detail, confirmLabel, tone})`) plus `choose({title, message, options:[{value,label}], confirmLabel?}) -> Promise<string|null>` (the confirm dialog with a `<select>` in the `confirm-detail` slot, labels as text; shares `_confirmBusy`/`_confirmQueue`; Escape/cancel/close/backdrop resolve `null`; the slot and OK styling are restored on close), driven by the `hidden` attribute. `open`/`close` apply dialog semantics centrally (role/aria-modal/aria-labelledby, focus in on open and back to the opener on close, Tab trap on the topmost open dialog, Escape cancels confirm) so call sites need no wiring; focus never returns onto a Flatpickr input, and `[data-autofocus]` marks the intended initial focus.

Brief accuracy: matches — Config, Util, VirtualList, PerfMonitor, ErrorLog, Toast, Modal are exactly what's here, nothing misplaced.

**`overflow-menu.mts`** — the shared overflow (⋯) menu primitive: `OverflowMenu.open(anchor, items, { align?, key? }) → { close }`, `closeAll()`, `isOpen()`, `reconcile()`. One menu at a time, appended to `document.body`, `position: fixed`, no Store imports and no Store events. Pure exports `menuPosition` / `menuKeyNav` carry the positioning (below, flip above, clamp, `align: 'end'`) and keyboard (wrap, skip disabled, Home/End, Escape, Enter/Space) logic. Items take `data` (becomes `data-*`), `checked` (checkbox items stay open and report `onSelect(!checked)`), `danger`, `hint`, `disabled` (`aria-disabled`, focusable, not selectable). `MenuItem` is a discriminated union (plain: `onSelect(item)`; checkbox: `onSelect(next, item)`). Pages that repaint via innerHTML pass `key`; `open()` writes `data-ovf-key` on the trigger and leaves it after close, but the page must ALSO render `data-ovf-key` in its own trigger template, because `reconcile()` (called at the end of the paint) and post-action focus restore find the new trigger by that attribute. If no item is enabled the menu container takes focus so Escape/arrows still work. Tested with the mini-DOM in `tests/modules/helpers/dom-stub.mjs`.

**`store.mts`** (1,113 lines) — reactive schedule state:
- `Store` — single source of truth. Holds `tasks`, `dependencies`, `calendars`, `blocks`, `alerts`, `firmedIds`, `plants`, `plantBlocks`, `lineSettings`, `selectedPlant`, `selectedLines`, `masterData`, `priorityRankMaps`, `setupSnapshot`, `userSettings`, `roleDefaults`, `orderFieldVisibility`, `visibilityHorizonEnd`, `frozenHorizonEnd`, `distributionSummary` (per-plant `{needs_review, changed, problems}`, reset on plant change, emits `distribution:summary`). `siblingsByParent()` is a rev-memoized `PARENT_ORDER` -> sibling-tasks map for O(1) distribution-sibling lookups (treat as read-only). Two DI-seam setters (`setAllowedPlantsResolver`, `setSettingsDefaultsResolver`); `Selection` and `Sandbox` are real cross-file imports forming two-way ESM cycles (see Integration points). Every mutator takes a `source` tag; `emit()` bumps `_rev` (and `_dataRev`, see below) and enriches the event with `{revision, mode}` before fanning out to `_listeners`, timing each listener via `PerfMonitor`.
- **`Store.dataRev()`** — a second revision counter for read-models that depend only on schedule data (utilization). `emit()` bumps it BEFORE listeners run for every event except `DATA_REV_EXCLUDED` (`alerts:change`, `lines:selected`, `distribution:summary`, `undo:pushed`, `settings:change`); `rev()` still bumps on everything and every existing stale guard keeps using it. It is an exclusion list on purpose: a new event type invalidates by default. Add an event to the list only if it cannot change tasks, line settings, calendars, plants, blocks, plant blocks, master data, the setup snapshot or the selected plant. A mutator that changes those inputs WITHOUT emitting (e.g. `ensureCalendar`, `ensurePlant`, `setPriorityRankMaps`) is invisible to both counters.
- `UndoStack` — `MAX: 10`; `push(label, undoFn, ids?)`/`pop` (invokes the stored `undoFn`, shows a toast), `snapshotTasks`/`restoreTasks` helpers used by drag-commit/unschedule flows. `undoFn` may be async; returning `false` means the user aborted (entry kept, no toast), and `pop` is ignored while an async undo is pending (`_busy`). `ids` tags the tasks an entry restores so `invalidate(ids)` can drop entries after a server-side write (e.g. a distribution re-weight) rewrites those tasks. `restoreTasks` deliberately does **not** restore `firmed` (see the firm hazard below).
- `StoreEvent` — exported interface for a subscriber callback's received event shape (revision + mode added to whatever the mutator emitted).

**`types.mts`** (659 lines) — shared ambient-adjacent (but module-scoped, not `declare global`) domain types: `NimbusTask`, `NimbusBlock`, `NimbusPlantBlock`, `NimbusMasterData`/`NimbusMasterPlant`/`NimbusMasterLine`, `WorkHours`, `NimbusLineSetting`, `PriorityRankMaps` and the priority-list wire types, the full setup-transition contract (`SetupDefinition`, `SetupMatrixRow`, `SetupValueDefault`, `SetupSnapshot`, `ResolvedSetup`, `ResolveSetupInput`, etc.; since 2026-10-27 `SetupSnapshot.value_defaults?` is an **optional** list of `{field_key, value, setup_min, signature_version, ...}` that every reader treats as `[]` when absent, `SetupResolutionSource` gains `'value-default'`, and `ResolveSetupInput.valueDefaults` is **required** in the type so a missed call site fails `npm run typecheck`), every string-literal enum (`OptimizerMode`, `AlertType`, `StoreEventType`, `TopLevelTab`, …), and the wire/localStorage encoding types (`NaiveLocalTs`, `IsoUtcTs`, `LiveState`, `StoredState`). Zero runtime code — compiles to an empty `.mjs`. Deliberate naming collision with `nimbus-compute-core.d.ts`'s ambient `NimbusTask`/`NimbusBlock`/etc. (a minimal worker-payload subset) — always import explicitly from `./types.mjs`, never rely on the bare global (see file header, and `docs/archive/typescript_migration.md` trap T-5).

Brief accuracy: matches — this is genuinely the leaf every other domain imports from.

## Counterpart

No `backend/` counterpart — platform is a pure frontend foundation layer with no backend analog. The nearest backend equivalent of "shared truth everything depends on" is `db.py` (whole, unsplit) plus `brain.py`'s root FastAPI app object, but nothing here calls either directly.

## Key invariants & hazards

- **Listener errors go to ErrorLog, not the console.** `Store.emit()` try/catches each subscriber (later ones still run) and logs `ErrorLog.error('store', 'listener error: <msg>', {event, source, listener}, {stack, errorCode: 'store.listener'})`; `listener` is the `_pmLabel` passed to `subscribe`, so label every subscriber. `emit()` records `Store._lastEvent` and a `'platform'` state provider (registered at module tail) snapshots `{plant, selectedLines, lastEvent, rev, mode}` onto error entries as `ctx.state.platform`.
- **`Store.selectedLines` is the global cross-screen line filter** (`store.mts:67`, state field; `store.mts:193`, getter) — an aliased `Set` mutated in place by `setSelectedLines()` (`store.mts:617-627`, `current.clear()` + re-add loop). GanttFilter/Table/Dashboard/Labor Plan/Master Data all hold a direct reference to this exact object; **never replace the reference**, only mutate it.
- **`nimbus.state.v3` cache key + `SCHEMA_VERSION` gate**: `Config.LS_KEY = 'nimbus.state.v3'` and `Config.SCHEMA_VERSION = 6` are both defined here (`foundation.mts:143-144`), with an explicit comment: "do NOT bump [LS_KEY] for shape changes — use SCHEMA_VERSION". The actual cache read/write/discard logic lives in `Persistence` (`frontend/scheduling/persistence.mts`), not here — platform only owns the two constants. `types.mts`'s `StoredState` interface (the on-disk shape) documents the same gate.
- **`UndoStack.MAX = 10`** (`store.mts:958`) — confirmed 10-level cap. It wraps destructive Store mutations generically via `push(label, undoFn)`; callers (Interaction, Engine-adjacent drag/optimize flows) are responsible for calling `push` before a destructive op — UndoStack itself doesn't intercept mutations.
- **`Config.KNOWN_PLANTS` is a fallback-only seed** (`foundation.mts:147`, `['5512', '1006']`). `Store.knownPlants()` (`store.mts:760-779`) prefers `masterData.plants` when present and **only falls back to `KNOWN_PLANTS` merged with dynamically-discovered plants** when `masterData` has no plants at all — confirmed via the `if (masterPlants.length) { … } else { …KNOWN_PLANTS… }` branch.
- **Two real ESM import cycles originate in `store.mts`**: `store.mjs ↔ selection.mjs` (`scheduling/selection.mts`) and `store.mjs ↔ sandbox.mjs` (`optimization/sandbox.mts`). Both are safe only because every cross-reference (`Store.mode()` reads `Sandbox.active`; `Store.removeTask()` calls `Selection.remove()`) happens inside a method body invoked long after both modules finish top-level evaluation — never at module-evaluation time. This mirrors the established `scheduling/gantt.mjs ↔ scheduling/orders.mjs` pattern from Phase P3. Don't add a new top-level (module-evaluation-time) reference across either edge.
- **`setLastOptimize`, `setPriorityRankMaps`, `setVisibilityHorizonEnd`, `setFrozenHorizonEnd` deliberately do NOT call `emit()`** — each has an inline comment explaining why (avoiding a spurious `_rev` bump that would invalidate `Utilization`'s memoized matrix and re-trigger `Persistence.autosave`'s unfiltered subscriber on every optimize run / rank load / tasks load, none of which need a second event beyond `tasks:bulk`/`schedule:hydrated`).
- **`firmedIds` mirrors server state, not a local browser firm.** The manual firm is persisted server-side (`task.firmed`); every wholesale task load clears and rebuilds `firmedIds` from it, old cached firms are dropped (`StoredState.firmedIds` is legacy/ignored), and `replaceFirmedIds` reports only the symmetric difference (so a What-If undo does not mass-dirty the firm set). UI surfaces reach `setFirmed` only through `Engine.applyFirm` (it refuses frozen/running orders; Sandbox, undo and Time Machine restores stay raw). Only `setFirmed`/`replaceFirmedIds` may change a firm, because they mark it firm-dirty for the save; `UndoStack.restoreTasks` strips `firmed` for that reason — restoring it would flip a firm with no marker and the save would send nothing.
- **One clock (backward scheduling Task 2.4, OQ52).** `Store.serverOffsetMs` (server instant minus the browser's `Date.now()`, 0 until the first response) is refreshed by every `/tasks` load from `meta.server_now` (`Store.setServerNow`, called in `Persistence.load`; `/tasks/refresh` carries no meta and leaves it alone). `Store.serverNow()` is the server instant; `Store.plantNow(plant)` is that instant as a naive wall-clock `Date` in the plant's IANA zone (through `NimbusComputeCore.plantWallClockFromInstant`, never an import from calendar/optimization), or `null` when the plant has no valid zone. A plant that exists in master data with no valid zone is added once to `Store._blockedPlants` and toasted once (`toast.plant_no_timezone`); Task 3.3 turns the set into the `plant_no_timezone` alert. A plant master data does not know yet is not recorded. `Engine.isFrozenHorizon`/`isInProgress`/`firmingStatus` default `now` to the task's plant clock (`Engine._clockFor`); `null` means not frozen / not running, never a throw. `Util.plantNowParts` reads the server instant through a resolver `store.mts` wires at load. The alert worker payload carries `now` per plant. Tests that rely on the default clock need a plant with a `timezone` in `Store.masterData` and the compute-core global loaded.
- **`Store.frozenHorizonEnd` is a live getter, not a stored value (2026-10-19).** The frozen horizon rolls like the alert horizon: the window is `[now, now + frozen_horizon_days)` with both edges advancing with the clock. The getter computes plant-local `plantNow` plus the selected plant's `frozen_horizon_days` (wall-clock days) on every read; NULL/0 days, or a plant with no valid clock, gives `null` (never throws). The server instant cached by `setFrozenHorizonEnd` (from `/tasks` `meta` and `/tasks/horizons`) is only a fallback for a plant row that is unknown or lacks the `frozen_horizon_days` key. Never snapshot it for later reuse except as the one concrete `Date` `snapshotSchedule` captures (and `validateCandidate` excludes that field from its staleness diff because it moves every moment).
- **`Store.pref(key, opts)`** resolves `userSettings[key] ?? roleDefaults[key] ?? settingsDefaultsResolver()[key]` — a 3-tier precedence chain; `opts.plant` is an accepted-but-currently-inert extension point (no per-plant regional defaults column exists yet — don't invent one to "complete" this hook).
- **Clearing a pref (2026-10-28).** `Session.setPref(key, null)` now DELETES the key server-side (the PATCH treats null as delete) and `Store.userSettings[key]` is dropped on adoption (`Store.replaceUserSettings(obj, source)` replaces the persisted keys in place and keeps the runtime-only `alertHorizonMinutes`/`confidenceHorizonMinutes`). `Store.pref` therefore falls through to the role default after a null clear. Where a user clear must OVERRIDE a role default, store an explicit empty sentinel the consumer treats as unset: `defaultPlant` uses `''` (boot code tests `!dp`). `0`, `false` and `''` are real values; only `null`/`undefined` fall through.

## Integration points

- **Imports in**: `foundation.mts` imports only `type { NimbusTask }` from `./types.mjs`. `store.mts` imports `{ Config, Util, PerfMonitor, ErrorLog, Toast }` from `./foundation.mjs`, `{ Selection }` from `../scheduling/selection.mjs`, `{ Sandbox }` from `../optimization/sandbox.mjs`, plus types from `./types.mjs`. `types.mts` has zero runtime imports (one type-only import of `SetupResolutionIndex` from `../setup/setup-domain.mjs`).
- **Imports out (who depends on platform)**: essentially every other domain — `admin-ops`, `calendar`, `insights`, `integration`, `labor`, `master-data`, `optimization`, `priority-lists`, `scheduling`, `security`, `setup`, `shell` all import from `platform/foundation.mjs` and/or `platform/store.mjs` and/or `platform/types.mjs`. This is the foundation layer by design — grep `platform/foundation\|platform/store\|platform/types` across `frontend/` to re-verify the current list if it matters for a specific change.
- **Store events emitted here**: `master-data-changed`, `order-field-visibility:changed`, `setup-snapshot:replace`, `tasks:bulk`, `task:update`, `task:remove`, `tasks:bulkUpdate`, `firmed:change`/`firmed:replace`, `distribution:summary`, `calendar:change`/`calendar:replace`, `blocks:change`/`blocks:replace`, `plantBlocks:change`/`plantBlocks:replace`, `lineSettings:change`, `plant:selected`, `lines:selected`, `alerts:change`, `settings:change`, `plants:replace`, `undo:pushed` (from `UndoStack.push`). Full literal union lives in `types.mts`'s `StoreEventType`.
- **No backend endpoints** are called directly from this domain (no `fetch`/`fetchTraced` call sites in these three files beyond `ErrorLog`'s own log-shipping to `POST /logs/frontend` and `Util.fetchTraced` itself, which is infrastructure other domains use).

## Gotchas

- **Capacity-math mirror rule (cross-link):** `Calendar`'s capacity math (`frontend/calendar/calendar-engine.mts`) must stay in parity with `frontend/nimbus-compute-core.js`'s copy, pinned by `tests/js/compute-core.test.js` — see `frontend/calendar/CLAUDE.md` for the substance (delegation vs. independent duplication nuance). Platform itself owns none of that math; this is a pointer only.
- `store.mts`'s header comment is the authoritative explanation for why the two import cycles (with `selection.mjs` and `sandbox.mjs`) are safe — read it before restructuring any top-level reference in either file, not just this doc's summary above.
- `Config.SESSION_MAX_AGE_MS` is a raw literal (`12 * 60 * 60 * 1000`), not `12 * Config.MS_HOUR`, because `Config` can't reference itself mid-object-literal-initializer — a real, commented constraint, not an oversight.
- `Util.changeoverFields()` falls back to a frozen `['COLOR', 'FORM_SIZE']` default when its resolver isn't wired (e.g. Node tests) — this is the exact historical hardcoded pair, kept for behavioral parity, not a stale leftover.
- `ErrorLog`'s IndexedDB durability (`_DB_NAME: 'nimbus-errorlog'`) is a **separate** database from `IntelDB` (owned by `nimbus-intelligence.js`, documented in `frontend/shell/CLAUDE.md`) — don't conflate the two ring stores.
- **`master-data-changed` carries `table` (2026-10-22).** `Store.setMasterData(md, source, table?)` forwards the optional `table` on the emit. Saves from Manage Data pass it (via `refreshStoreMasterData(source, table)`); boot (`persistence`) and Plant Refresh omit it. Subscribers that react to a specific table (`MasterData.runtimeSync` for `plants`/`machine`, `SetupAdmin.cacheReset`, `DistributionPane`) must treat a missing `table` as "any/unknown" and never reload on it, which also prevents double loads.
- **`Store.activeLineHoursOn(line, date?)` (2026-10-23)** is the DISPLAY resolver for a machine's hours: `{ workHours, source: 'period'|'default'|'none', period }`. Inherited line = the plant pattern active that day (dated period via `activePeriodOn`, else the default week); override = its own hours intersected per weekday with that pattern (same math as the compute core's `workWindow`); date defaults to today on the plant clock. `effectiveLineHours` is deliberately unchanged (the editor must open on the default week), and no scheduling reader may use either: they read the raw `calendars` and intersect per date.
- **`Modal.anyOpen()` (2026-10-23)** is true while any dialog tracked by the modal stack (`Modal.open`, confirm, choose) is showing; `Persistence._noteCalendarVersion` uses it so a background calendar re-fetch never lands under an open dialog.
- **`masterData.tool_inventory`: `undefined` means not loaded / failed, NEVER empty (Tool Inventory Wave 3, 2026-10-27).** `NimbusMasterData.tool_inventory` is a REQUIRED key typed `NimbusToolInventoryRow[] | undefined` so `tsc` forces every `Store.setMasterData` writer to say what it carries. It holds the selected plant's rows (a tool id is a type; the plant owns `total_qty` copies; no row = 1 copy), sorted by `tool_id`. `[]` is a plant that loaded fine with no rows; `undefined` is a failed/403/timed-out fetch, a load not finished yet, a plant switch in flight, or no plant: every reader (the compute core, the alert payload) must treat it as "unknown", never as "empty". A writer that rebuilds the object wholesale (`Persistence.load` x3, `refreshStoreMasterData`) must carry it forward (`fresh ?? Store.masterData?.tool_inventory`); the `{...Store.masterData, X}` spreaders already do. Never write `?? []` for it. The worker gets a compact projection inside `masterData` (`projectMasterDataForWorker` in `insights/services.mts`: `{plant, tool_id, available, hasRow: true}`), not a new top-level payload key. `setup_policy_config.toolingRule?: 'off' | 'hard'` rides on the plants rows (absent = 'off').
- **Display-format helpers (settings audit Wave D, 2026-10-28).** `timeFormat` / `dateFormat` reach every user-visible date through the pref-aware `Util` helpers: `_fmtDatePref`, `_fmtTimePref`, `fmtDTPref` (date + time), `fmtDTShortPref` / `fmtDateShortPref` (the dateFormat token with its year dropped), `fmtDayLabelPref` (weekday + short date), `fmtIsoDatePref` and `fmtIsoStampPref` (ISO wire strings rendered from their own parts, no zone shift). The old fixed-format `fmtDT` / `fmtDTShort` / `fmtIsoDate` stay for DATA only: the Orders grid's typed-date cell editor round-trip and the Print CSV export (`orders.mts`), and the Manage Data date columns (`material-grids.mts`, typed `MM/DD/YYYY` parsed by `date-input.mts`, CSV export through the same formatter). Never use `toLocaleDateString` / `toLocaleTimeString` for a display date: `tests/modules/display-format-guard.test.mjs` fails on it (and on a bare `Util.fmtDT(` / `fmtDTShort(` outside its small allowlist). `Util.refreshFlatpickrPrefs()` re-applies altFormat and the week start to every already-built flatpickr instance (found through the `_flatpickr` property on `.flatpickr-input`); the popup clock (`time_24hr`) cannot be patched live and follows the pref on the next picker built. There is no `timezone` setting (removed); plant timezones are master data.
